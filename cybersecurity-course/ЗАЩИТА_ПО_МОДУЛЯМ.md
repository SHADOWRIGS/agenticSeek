# МОДУЛЬ 1 — ЗАЩИТА ФУНДАМЕНТА

## 1.1. Защита сети (уровень OSI / TCP-IP)

### Угроза
Сканирование сети, ARP-спуфинг (MitM), перехват открытого трафика.

### Как действует атакующий
Отправляет поддельные ARP-ответы, выдавая себя за шлюз, и весь трафик жертвы идёт через него. Открытые протоколы (HTTP, FTP, Telnet) читаются как есть.

### Как защититься

**1. Сегментация сети (VLAN).** Разделите сеть: сервера, рабочие станции, гости — в разных VLAN. Компрометация одного сегмента не открывает всю сеть.

**2. Защита от ARP-спуфинга — Dynamic ARP Inspection** на управляемом коммутаторе:
```
# Cisco: привязка IP-MAC и проверка ARP
ip dhcp snooping
ip arp inspection vlan 10
```

**3. Шифрование всего трафика.** Никакого HTTP/FTP/Telnet — только HTTPS, SFTP, SSH.

**4. Обнаружение ARP-спуфинга на Linux:**
```bash
# arpwatch логирует изменения связки IP↔MAC и шлёт алерт
sudo apt install arpwatch
sudo arpwatch -i eth0
# В /var/log/syslog появится "changed ethernet address", если кто-то спуфит
```

### Как проверить/мониторить
- Статическая ARP-запись для шлюза на критичных хостах: `arp -s 192.168.1.1 aa:bb:cc:dd:ee:ff`.
- Мониторинг: всплеск ARP-трафика → алерт в SIEM.

### Практика ученика (blue team)
Запустить arpwatch, провести ARP-спуфинг со второй ВМ (свой стенд) и **поймать** его по логу. Результат: ученик детектирует MitM.

## 1.2. Защита DNS

### Угроза
DNS zone transfer (утечка всех поддоменов), DNS-спуфинг, туннелирование данных через DNS.

### Как защититься

**1. Запретить zone transfer** всем, кроме вторичных серверов (BIND):
```
# named.conf
allow-transfer { 192.168.1.2; };   # только доверенный вторичный DNS
```
Проверка, что закрыто:
```bash
dig axfr example.com @ns1.example.com
# Должно вернуть: Transfer failed.
```

**2. DNSSEC** — подпись записей, защита от подмены.

**3. Мониторинг DNS-туннелирования:** аномально длинные/частые TXT-запросы к одному домену — признак эксфильтрации. Правило в SIEM на длину DNS-запроса > 50 символов.

### Практика ученика
Настроить BIND, закрыть AXFR, убедиться `dig axfr` возвращает отказ.

## 1.3. Защита веб-сервера (HTTP/HTTPS)

### Угроза
Перехват, отсутствие TLS, утечка версий, clickjacking.

### Как защититься — заголовки безопасности

```nginx
# nginx — обязательные заголовки
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
add_header X-Frame-Options "SAMEORIGIN" always;
add_header X-Content-Type-Options "nosniff" always;
add_header Content-Security-Policy "default-src 'self'" always;
server_tokens off;   # скрыть версию nginx
```

Проверка оценки:
```bash
curl -sI https://ваш-сайт | grep -i "strict-transport\|x-frame\|content-security"
```
Онлайн: securityheaders.com, ssllabs.com (цель — рейтинг A/A+).

### Практика ученика
Поднять nginx, получить рейтинг F, добавить заголовки и TLS, довести до A+.

## 1.4. Защита Linux (права, SUID, процессы)

### Угроза
Повышение привилегий через SUID-бинарники, небезопасные cron-задачи, слабые права.

### Как защититься

**1. Аудит SUID — найти и убрать лишнее:**
```bash
# Список всех SUID-файлов
find / -perm -4000 -type f 2>/dev/null
# Снять SUID с того, что не нужно (например, старый бинарник):
chmod u-s /path/to/binary
```

**2. Защита cron:** права на скрипты только root, никаких `rwxrwxrwx`:
```bash
chown root:root /opt/scripts/*.sh
chmod 700 /opt/scripts/*.sh
```

**3. Контроль целостности** — AIDE фиксирует изменения системных файлов:
```bash
sudo apt install aide
sudo aideinit
sudo aide --check   # покажет, что изменилось
```

### Практика ученика
Найти подкинутый SUID-бэкдор на стенде, убрать его, настроить AIDE, поймать повторную подмену.

---

## 1.5. Криптография на стороне защиты

### Угроза
Хранение паролей в MD5, слабое шифрование, самоподписанные сертификаты в проде.

### Как защититься
- Пароли — только **bcrypt / Argon2** с солью, никогда MD5/SHA1.
- Данные в покое — шифрование диска (LUKS), данные в передаче — TLS 1.2+.
- Корректная PKI: валидные сертификаты (Let's Encrypt), ротация ключей.

```bash
# Пример правильного хэширования пароля (Python)
# bcrypt автоматически добавляет соль
import bcrypt
hashed = bcrypt.hashpw(b"password", bcrypt.gensalt())
```

### Практика ученика
Переписать небезопасное хранение (MD5) на bcrypt, показать разницу стойкости к перебору.

# МОДУЛЬ 2 — ЗАЩИТА ОТ РАЗВЕДКИ И МОНИТОРИНГ ТРАФИКА

## 2.1. Обнаружение сканирования (анти-recon)

### Угроза
Nmap-сканирование как первый шаг атаки.

### Как защититься

**1. Детектирование сканов через IDS (Snort/Suricata):**
```
# Правило Suricata: много SYN на разные порты с одного IP
alert tcp any any -> $HOME_NET any (msg:"Port Scan Detected"; \
  flags:S; threshold:type both, track by_src, count 20, seconds 10; sid:1000001;)
```

**2. fail2ban на аномальную активность**, портноки, скрытие версий сервисов (`server_tokens off`, баннеры).

**3. Honeypot** — ложный сервис, обращение к которому = 100% атака:
```bash
# простейший honeypot-порт, логирующий подключения
sudo apt install honeyd   # или endlessh на 22 порт как tarpit
```

### Практика ученика (blue team)
Настроить Suricata, просканировать стенд Nmap-ом со второй ВМ, **увидеть алерт** о скане. Результат: ученик детектирует разведку.

## 2.2. Анализ трафика на стороне защиты (Wireshark/Zeek)

### Угроза
Вредоносный трафик, C2-коммуникации, эксфильтрация.

### Как защититься
- **Zeek (bro)** — сетевой мониторинг, логирует все соединения, DNS, HTTP, файлы.
- Поиск аномалий: соединения на редкие порты, beaconing (регулярные запросы к C2), большие исходящие объёмы.

```bash
# Анализ pcap в Zeek — генерирует conn.log, dns.log, http.log
zeek -r capture.pcap
cat conn.log | zeek-cut id.orig_h id.resp_h id.resp_p duration
```

### Практика ученика
Дать ученику «грязный» pcap, найти C2-beaconing и эксфильтрацию через анализ логов Zeek (разбор как в сложном задании №4, но с позиции защитника).

## 2.3. Защита от OSINT

### Угроза
Сбор данных о компании и сотрудниках из открытых источников → фишинг.

### Как защититься
- Минимизировать публичную информацию (WHOIS privacy, убрать метаданные из документов).
- Обучение сотрудников против фишинга и социальной инженерии.
- Мониторинг утечек (есть ли корпоративные email в утёкших базах — haveibeenpwned).
- Строгая SPF/DKIM/DMARC политика против спуфинга домена в письмах:
```
# DNS TXT запись — жёсткий SPF
v=spf1 ip4:203.0.113.10 -all      # -all, не ~all!
```

### Практика ученика
Провести OSINT по собственному тестовому домену, составить список утечек и закрыть их (настроить DMARC, убрать метаданные).

# МОДУЛЬ 3 — ЗАЩИТА ОТ ЭКСПЛУАТАЦИИ УЯЗВИМОСТЕЙ

## 3.1. Защита веб-приложений (OWASP) — главный блок

### Угроза: SQL-инъекция

**Как защититься — параметризованные запросы (главное правило):**
```python
# ❌ ОПАСНО — конкатенация
cursor.execute("SELECT * FROM users WHERE id = '" + user_id + "'")

# ✅ БЕЗОПАСНО — параметризованный запрос
cursor.execute("SELECT * FROM users WHERE id = %s", (user_id,))
```
Плюс: принцип наименьших привилегий для учётки БД, WAF, валидация ввода.

### Угроза: XSS

**Как защититься:**
```python
# Экранирование вывода (Jinja2 это делает автоматически)
from markupsafe import escape
return f"<p>{escape(user_input)}</p>"
```
Плюс: Content-Security-Policy, флаг HttpOnly на cookie.

### Угроза: CSRF
**Как защититься:** CSRF-токены на все изменяющие формы, `SameSite=Strict` на cookie.

### Защитный инструмент — WAF (ModSecurity)
```bash
# nginx + ModSecurity с набором правил OWASP CRS
# Блокирует типовые SQLi/XSS payloads до приложения
sudo apt install libmodsecurity3
# Включить OWASP Core Rule Set
```

### Практика ученика (blue team)
Взять уязвимое приложение (DVWA), **закрыть** SQLi параметризацией, XSS — экранированием, поставить ModSecurity и убедиться, что прежние payload'ы больше не проходят. Результат: ученик превращает дырявое приложение в защищённое.

## 3.2. Защита систем от повышения привилегий

### Угроза
Атакующий получил доступ как обычный пользователь и ищет путь к root.

### Как защититься
- **Минимум SUID**, аудит `sudo -l`, никаких `NOPASSWD` на `find/vim/nmap` (GTFOBins).
- Обновления (патч-менеджмент) — большинство privesc через непропатченные CVE.
- **auditd** логирует выполнение команд и изменения:
```bash
auditctl -w /etc/passwd -p wa -k passwd_changes
auditctl -a always,exit -F arch=b64 -S execve -F uid=0 -k root_cmds
```
- SELinux/AppArmor — ограничение процессов.

### Практика ученика
Дать уязвимую к privesc машину, закрыть все векторы (SUID, sudo, cron, патчи) и настроить auditd так, чтобы попытка privesc залогировалась.

---

## 3.3. Защита от Metasploit / известных эксплойтов

### Как защититься
- **Патч-менеджмент** — автоматические обновления безопасности:
```bash
sudo apt install unattended-upgrades
sudo dpkg-reconfigure unattended-upgrades
```
- Отключить лишние сервисы (меньше поверхность атаки).
- IDS-сигнатуры детектируют Meterpreter-трафик.
- EDR на хостах.

### Практика ученика
Взять Metasploitable, закрыть эксплуатируемый сервис (обновить/отключить), убедиться, что прежний эксплойт больше не срабатывает.

## 3.4. Защита от brute force

### Как защититься
```ini
# fail2ban — бан после 3 неудач
[sshd]
enabled = true
maxretry = 3
bantime = 7200
```
Плюс: ключи вместо паролей, MFA, политика сложных паролей, блокировка после N попыток на уровне приложения.

### Практика ученика
Настроить fail2ban, провести brute force Hydra со второй ВМ, **увидеть бан** атакующего IP.

## 3.5. Защита Wi-Fi

### Как защититься
- **WPA3**, при невозможности — WPA2 с паролем 16+ символов (случайным).
- Отдельная гостевая сеть, отключённый WPS.
- Мониторинг rogue-точек доступа (fake AP) и deauth-атак:
```bash
# детект deauth-флуда — всплеск deauth-кадров
# инструменты: Kismet (мониторинг эфира и алерты)
```

### Практика ученика
Настроить стойкую WPA2/WPA3 на своей точке, запустить Kismet, поймать собственную deauth-атаку.

# МОДУЛЬ 4 — SOC, МОНИТОРИНГ И РЕАГИРОВАНИЕ (ядро blue team)

> Этого блока у большинства конкурентов нет или он слабый. **Наше ключевое отличие.**

## 4.1. Hardening систем (CIS Benchmarks)

### Как защититься
Чеклист усиления по стандарту CIS:
- SSH hardening (ключи, нестандартный порт, запрет root).
- Файрвол по умолчанию deny.
- Отключение ненужных сервисов.
- Автоматический аудит через **Lynis**:
```bash
sudo apt install lynis
sudo lynis audit system    # даёт hardening index и список рекомендаций
```

### Практика ученика
Прогнать Lynis на свежем сервере (индекс ~55), выполнить рекомендации, довести индекс до 80+.

---

## 4.2. SIEM — централизованный мониторинг

### Что это
Система сбора и корреляции логов со всей инфраструктуры. Сердце SOC.

### Как защититься
- Развернуть **Wazuh** (бесплатный open-source SIEM/XDR) или ELK-стек.
- Собирать логи: auth, веб, сеть, системные события.
- Правила корреляции: 5 неудачных входов + 1 успешный = алерт; создание пользователя с UID=0 = критический алерт.

```bash
# Wazuh детектит типовые атаки из коробки:
# - brute force, privesc, изменение критичных файлов, вредоносные процессы
```

### Практика ученика (ключевая)
Развернуть Wazuh, подключить агент, провести серию атак со стенда (скан, brute force, privesc) и **увидеть все алерты в дашборде SOC**. Результат: ученик работает как SOC-аналитик.

- Интеграция алертов в SIEM.

### Практика ученика

## 4.4. Incident Response — реагирование на инцидент

### Как защититься — процесс (NIST)
1. **Подготовка** — план, контакты, инструменты.
2. **Обнаружение** — алерт SIEM.
3. **Сдерживание** — изоляция хоста, блок IP.
4. **Устранение** — удаление бэкдоров, патч.
5. **Восстановление** — чистый бэкап, проверка.
6. **Выводы** — отчёт, улучшение защиты.

### Практика ученика
Расследовать взломанную учебную машину (как сложное задание №2, но с полным циклом IR): найти точку входа, бэкдоры, составить отчёт об инциденте и план устранения.

## 4.5. Форензика и threat hunting

### Как защититься
- Сбор артефактов: логи, память, timeline файловой системы.
- Проактивный поиск угроз (threat hunting) до срабатывания алерта.

```bash
# Timeline по файловой системе
find / -newermt "2024-01-14 03:00" ! -newermt "2024-01-14 04:00" -type f 2>/dev/null
# Что изменилось в окне атаки
```

### Практика ученика
По дампу памяти/логам восстановить хронологию атаки и действия злоумышленника.
