## Введение в защиту от латерального движения

Латеральное движение (Lateral Movement) — одна из критичнейших фаз атаки. После первоначального проникновения атакующий перемещается между хостами, повышает привилегии и расширяет присутствие в инфраструктуре. Обнаружение на этом этапе — последний шанс остановить атаку до достижения целевых активов.

### Ключевые принципы защиты от латерального движения

1. **Сегментация сети** — микросегментация и VLAN снижают возможности перемещения
2. **Принцип минимальных привилегий** — ни один аккаунт не должен иметь доступ ко всему
3. **Многоуровневая аутентификация** — MFA на все административные интерфейсы
4. **Мониторинг аномальных подключений** — любое новое соединение хост↔хост должно анализироваться
5. **Credential Hygiene** — защита учётных данных в памяти, на диске, в трафике

### Общая конфигурация Sysmon для обнаружения латерального движения

```xml
<!-- Sysmon config: базовый блок для мониторинга lateral movement -->
<Sysmon schemaversion="4.90">
  <EventFiltering>
    <!-- Event ID 1: Создание процессов -->
    <ProcessCreate onmatch="include">
      <Image condition="end with">psexec.exe</Image>
      <Image condition="end with">psexesvc.exe</Image>
      <Image condition="end with">wmic.exe</Image>
      <Image condition="end with">mstsc.exe</Image>
      <Image condition="end with">schtasks.exe</Image>
      <Image condition="end with">sc.exe</Image>
      <Image condition="end with">winrs.exe</Image>
      <ParentImage condition="end with">wmiprvse.exe</ParentImage>
      <ParentImage condition="end with">wsmprovhost.exe</ParentImage>
    </ProcessCreate>

    <!-- Event ID 3: Сетевые подключения -->
    <NetworkConnect onmatch="include">
      <DestinationPort condition="is">445</DestinationPort>
      <DestinationPort condition="is">135</DestinationPort>
      <DestinationPort condition="is">3389</DestinationPort>
      <DestinationPort condition="is">5985</DestinationPort>
      <DestinationPort condition="is">5986</DestinationPort>
      <DestinationPort condition="is">22</DestinationPort>
    </NetworkConnect>

    <!-- Event ID 10: Доступ к процессам (LSASS) -->
    <ProcessAccess onmatch="include">
      <TargetImage condition="end with">lsass.exe</TargetImage>
    </ProcessAccess>

    <!-- Event ID 17/18: Именованные каналы -->
    <PipeEvent onmatch="include">
      <PipeName condition="is">\psexesvc</PipeName>
      <PipeName condition="is">\PSEXESVC</PipeName>
      <PipeName condition="begin with">\msagent_</PipeName>
    </PipeEvent>
  </EventFiltering>
</Sysmon>
```

## Модуль 76: Pass-the-Hash — Обнаружение и защита

### Что это за угроза

Pass-the-Hash (PtH) — техника, при которой атакующий использует перехваченный NTLM-хеш пароля для аутентификации на удалённых системах без знания самого пароля. Это возможно из-за архитектуры NTLM-протокола, где хеш является функциональным эквивалентом пароля.

**Почему это критично:** атакующий, получив хеш одного привилегированного аккаунта, может мгновенно получить доступ ко всем системам, где этот аккаунт имеет права.

### Индикаторы компрометации (IoC)

| Индикатор | Источник | Event ID |
|-----------|---------|----------|
| Аутентификация NTLM вместо Kerberos для привилегированных аккаунтов | Windows Security Log | 4624 (Logon Type 3, NTLM) |
| Аутентификация с нулевым именем рабочей станции | Windows Security Log | 4624 (Workstation Name пусто) |
| Множественные логоны с одного IP на разные хосты за короткий период | Windows Security Log | 4624 |
| Хеш NTLM в памяти lsass.exe с нетипичного процесса | Sysmon Event ID 10 | ProcessAccess |
| Lateral NTLM-аутентификация на контроллер домена | DC Security Log | 4776 |

### Обнаружение

#### Sigma-правило: NTLM-аутентификация привилегированного аккаунта

```yaml
title: Pass-the-Hash — NTLM-аутентификация привилегированного аккаунта
id: e8a4c107-76c3-4e4f-b5a1-def001
status: stable
description: >
  Обнаруживает NTLM-аутентификацию (Logon Type 3) привилегированных аккаунтов,
  что может указывать на Pass-the-Hash.
references:
  - https://attack.mitre.org/techniques/T1550/002/
logsource:
  product: windows
  service: security
detection:
  selection:
    EventID: 4624
    LogonType: 3
    AuthenticationPackageName: 'NTLM'
  filter_machine:
    TargetUserName|endswith: '$'
  filter_normal_services:
    IpAddress:
      - '127.0.0.1'
      - '::1'
  condition: selection and not filter_machine and not filter_normal_services
level: medium
tags:
  - attack.lateral_movement
  - attack.t1550.002
```

#### Sigma-правило: NTLM-логон с пустым именем рабочей станции

```yaml
title: NTLM-аутентификация с пустым Workstation Name (признак PtH)
id: e8a4c107-76c3-4e4f-b5a1-def002
status: experimental
description: >
  Многие инструменты PtH (Mimikatz, Impacket) не передают Workstation Name
  при NTLM-аутентификации.
logsource:
  product: windows
  service: security
detection:
  selection:
    EventID: 4624
    LogonType: 3
    AuthenticationPackageName: 'NTLM'
    WorkstationName: ''
  condition: selection
level: high
tags:
  - attack.lateral_movement
  - attack.t1550.002
```

#### Корреляция: веерный PtH (один источник → много целей)

```yaml
title: Веерный Pass-the-Hash — множественные NTLM-логоны с одного IP
id: e8a4c107-76c3-4e4f-b5a1-def003
status: experimental
description: >
  Один IP-адрес выполняет NTLM-аутентификацию на 5+ разных хостов за 10 минут —
  характерный паттерн автоматизированного PtH.
logsource:
  product: windows
  service: security
detection:
  selection:
    EventID: 4624
    LogonType: 3
    AuthenticationPackageName: 'NTLM'
  timeframe: 10m
  condition: selection | count(TargetServerName) by IpAddress > 5
level: critical
```

#### Запрос Splunk/SIEM

```spl
index=wineventlog EventCode=4624 Logon_Type=3
  Authentication_Package=NTLM
  Workstation_Name=""
| stats count dc(dest) as unique_targets values(dest) as targets
  by src_ip Account_Name
| where unique_targets > 3
| sort -unique_targets
```

#### Запрос Elastic/KQL

```
event.code: "4624" AND winlog.event_data.LogonType: "3"
  AND winlog.event_data.AuthenticationPackageName: "NTLM"
  AND winlog.event_data.WorkstationName: ""
```

### Защита и предотвращение

1. **Отключение NTLM где возможно:**
   ```powershell
   # Групповая политика: Computer Configuration → Windows Settings →
   # Security Settings → Local Policies → Security Options
   # Network security: Restrict NTLM: Incoming NTLM traffic = Deny All
   # Network security: Restrict NTLM: NTLM authentication in this domain = Deny all

   # Аудит NTLM перед полным отключением:
   Set-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Control\Lsa\MSV1_0" `
     -Name "AuditReceivingNTLMTraffic" -Value 2
   ```

2. **Credential Guard (Windows 10+/Server 2016+):**
   ```powershell
   # Включение Credential Guard через реестр
   reg add "HKLM\SYSTEM\CurrentControlSet\Control\DeviceGuard" /v EnableVirtualizationBasedSecurity /t REG_DWORD /d 1 /f
   reg add "HKLM\SYSTEM\CurrentControlSet\Control\Lsa" /v LsaCfgFlags /t REG_DWORD /d 1 /f
   ```

3. **Protected Users Security Group:**
   ```powershell
   # Добавление привилегированных аккаунтов в группу Protected Users
   Add-ADGroupMember -Identity "Protected Users" -Members "admin_account"
   # Запрещает NTLM, DES, RC4 для членов группы
   ```

4. **Сегментация и уровни доступа:**
   - Tier 0 (контроллеры домена) — доступ только с PAW
   - Tier 1 (серверы) — отдельные привилегированные аккаунты
   - Tier 2 (рабочие станции) — локальные admin-аккаунты с LAPS

5. **LAPS (Local Administrator Password Solution):**
   ```powershell
   # Установка и настройка LAPS — уникальный пароль локального админа на каждой машине
   Install-Module -Name LAPS -Force
   # Хеш одной машины бесполезен для других
   ```

### Инструменты защитника

| Инструмент | Назначение | Команда/Применение |
|------------|-----------|-------------------|
| **Windows Event Forwarding** | Централизация логов 4624 | `wecutil qc` |

| **CrowdStrike/SentinelOne** | EDR-обнаружение PtH | Политики NTLM |

| **BloodHound** (защитное использование) | Аудит путей PtH в AD | `SharpHound -c All` |

## Модуль 77: Pass-the-Ticket — Обнаружение и защита

### Что это за угроза

Pass-the-Ticket (PtT) — техника, при которой атакующий крадёт Kerberos-тикеты (TGT или TGS) из памяти и использует их для аутентификации на других системах. В отличие от PtH, здесь используются Kerberos-билеты, которые сложнее обнаружить стандартными средствами.

**Особая опасность:** украденный TGT (Golden Ticket / Silver Ticket) может действовать неделями и даже переживать смену пароля пользователя.

### Индикаторы компрометации (IoC)

| Индикатор | Источник | Event ID |
|-----------|---------|----------|
| TGT-запрос без предшествующего AS-REQ | DC Kerberos Log | 4768 + 4769 (несоответствие) |
| Тикет с аномальным Encryption Type (RC4 вместо AES) | DC Security Log | 4769 (Ticket Encryption Type 0x17) |
| Использование тикета с нетипичного IP | DC Security Log | 4769 (Client Address ≠ обычному) |
| TGS-запрос без предшествующего TGT-запроса | DC Security Log | 4769 без 4768 |
| Аномальный SPN в TGS-запросе | DC Security Log | 4769 |
| Доступ к LSASS из нетипичного процесса | Sysmon Event 10 | TargetImage = lsass.exe |

### Обнаружение

#### Sigma-правило: аномальный Encryption Type в Kerberos-тикете

```yaml
title: Kerberos TGS-запрос с RC4 Encryption (признак Pass-the-Ticket / Golden Ticket)
id: e8a4c107-76c3-4e4f-b5a1-def010
status: stable
description: >
  RC4 (0x17) используется в TGS-запросах, хотя домен настроен на AES.
  Частый признак Mimikatz Golden/Silver Ticket.
logsource:
  product: windows
  service: security
detection:
  selection:
    EventID: 4769
    TicketEncryptionType: '0x17'
  filter_machine_accounts:
    ServiceName|endswith: '$'
  condition: selection and not filter_machine_accounts
level: high
tags:
  - attack.lateral_movement
  - attack.t1550.003
  - attack.credential_access
```

#### Sigma-правило: TGS без предшествующего TGT

```yaml
title: Kerberos TGS-Request без предшествующего AS-Request (Pass-the-Ticket)
id: e8a4c107-76c3-4e4f-b5a1-def011
status: experimental
description: >
  TGS-запрос (4769) без AS-запроса (4768) в пределах сессии указывает
  на импортированный тикет.
logsource:
  product: windows
  service: security
detection:
  tgs_request:
    EventID: 4769
  as_request:
    EventID: 4768
  timeframe: 30m
  condition: tgs_request and not as_request
level: high
tags:
  - attack.lateral_movement
  - attack.t1550.003
```

#### Запрос Splunk для обнаружения аномалий Kerberos

```spl
index=wineventlog source="WinEventLog:Security"
  (EventCode=4769 Ticket_Encryption_Type=0x17)
  OR (EventCode=4769 NOT [search index=wineventlog EventCode=4768
      | rename Account_Name as target_user
      | fields target_user]
     )
| stats count by Account_Name Client_Address Service_Name Ticket_Encryption_Type
| where count > 0
```

### Защита и предотвращение

1. **Принудительное использование AES для Kerberos:**
   ```powershell
   # GPO: Computer Configuration → Policies → Windows Settings →
   # Security Settings → Local Policies → Security Options
   # Network security: Configure encryption types allowed for Kerberos
   # Включить только AES128 и AES256, отключить RC4_HMAC_MD5

   Set-ADUser -Identity "admin_user" -KerberosEncryptionType AES128,AES256
   ```

2. **Регулярная смена пароля krbtgt (против Golden Ticket):**
   ```powershell
   # Смена пароля krbtgt дважды с интервалом минимум 10 часов
   # Это инвалидирует все существующие TGT
   Reset-KrbtgtPassword  # через специальный скрипт Microsoft

   # Проверка времени последней смены
   Get-ADUser krbtgt -Properties PasswordLastSet | Select PasswordLastSet
   ```

3. **Ограничение времени жизни тикетов:**
   ```
   # GPO: Computer Configuration → Windows Settings → Security Settings →
   # Account Policies → Kerberos Policy
   Maximum lifetime for service ticket: 600 минут (по умолчанию)
   Maximum lifetime for user ticket: 10 часов
   Maximum lifetime for user ticket renewal: 7 дней
   ```

4. **Protected Users Group:**
   - Запрещает кеширование credentials
   - Запрещает NTLM-аутентификацию
   - Принудительно AES для Kerberos
   - Тикеты не продлеваются

5. **Мониторинг PAC (Privilege Attribute Certificate):**
   - Включить PAC Validation на всех серверах
   - Аномалии в PAC указывают на подделку тикета

### Инструменты защитника

| Инструмент | Назначение |
|------------|-----------|
| **Microsoft Defender for Identity** | Автодетекция PtT, Golden Ticket, Silver Ticket |
| **Rubeus** (в режиме аудита) | Мониторинг тикетов в домене |
| **Pingcastle** | Аудит AD на уязвимости Kerberos |
| **Purple Knight** | Оценка безопасности Active Directory |
| **Wazuh rule 92660** | Обнаружение аномальных Kerberos-запросов |

## Модуль 78: Overpass-the-Hash — Обнаружение и защита

### Что это за угроза

Overpass-the-Hash (OPtH) — гибридная техника, при которой атакующий берёт NTLM-хеш и использует его для получения Kerberos TGT. Это сочетание PtH и PtT: сначала используется хеш (как в PtH), но результатом является полноценный Kerberos-тикет (как в PtT). Обнаружить сложнее, так как конечный трафик выглядит как легитимная Kerberos-аутентификация.

### Индикаторы компрометации (IoC)

| Индикатор | Источник | Event ID |
|-----------|---------|----------|
| AS-REQ с RC4 Encryption от хоста, поддерживающего AES | DC Security Log | 4768 (Encryption Type 0x17) |
| Kerberos TGT-запрос с нетипичного процесса | Sysmon Event 10 (lsass) + 4768 |
| Logon Type 9 (NewCredentials) перед Kerberos-аутентификацией | Windows Security | 4624 (Type 9) |
| Несоответствие IP: TGT получен с одного IP, TGS используется с другого | DC logs | 4768 vs 4769 IP |

### Обнаружение

#### Sigma-правило: Logon Type 9 (используется runas /netonly и OPtH)

```yaml
title: Logon Type 9 (NewCredentials) — признак Overpass-the-Hash
id: e8a4c107-76c3-4e4f-b5a1-def020
status: experimental
description: >
  Logon Type 9 создаётся при runas /netonly или при инъекции credentials
  в новую сессию (Mimikatz sekurlsa::pth). Редко используется легитимно.
logsource:
  product: windows
  service: security
detection:
  selection:
    EventID: 4624
    LogonType: 9
  filter_known:
    ProcessName|endswith:
      - '\runas.exe'
  condition: selection and not filter_known
level: high
tags:
  - attack.lateral_movement
  - attack.t1550.002
```

#### Sigma-правило: AS-REQ с RC4 от AES-клиента

```yaml
title: Kerberos AS-REQ с RC4 от клиента с поддержкой AES (Overpass-the-Hash)
id: e8a4c107-76c3-4e4f-b5a1-def021
status: experimental
description: >
  Клиент Windows 10+/Server 2016+ запрашивает TGT с RC4 (0x17).
  Легитимные клиенты используют AES. RC4 указывает на OPtH
  через инструменты вроде Mimikatz.
logsource:
  product: windows
  service: security
detection:
  selection:
    EventID: 4768
    TicketEncryptionType: '0x17'
    Status: '0x0'
  filter_service_accounts:
    TargetUserName|endswith: '$'
  condition: selection and not filter_service_accounts
level: high
tags:
  - attack.lateral_movement
  - attack.t1550.002
```

#### Корреляция: OPtH-цепочка (Type 9 → AS-REQ с RC4)

```spl
index=wineventlog
  ((EventCode=4624 Logon_Type=9)
   OR (EventCode=4768 Ticket_Encryption_Type=0x17))
| transaction Account_Name maxspan=5m
| where eventcount >= 2
| table _time Account_Name src_ip dest Logon_Type Ticket_Encryption_Type
```

### Защита и предотвращение

1. **Отключение RC4 в домене:**
   ```powershell
   # Для всех пользователей — принудительно AES
   Get-ADUser -Filter * -Properties msDS-SupportedEncryptionTypes |
     Where-Object { $_.'msDS-SupportedEncryptionTypes' -band 4 } |
     Set-ADUser -KerberosEncryptionType AES128,AES256

   # GPO: Network security: Configure encryption types allowed for Kerberos
   # Оставить только AES128_HMAC_SHA1 и AES256_HMAC_SHA1
   ```

2. **Credential Guard** — не даёт извлечь хеши из LSASS

3. **Мониторинг Logon Type 9:**
   - В большинстве окружений Type 9 — редкость
   - Каждый такой логон должен быть объяснён

4. **Сегментация PAW (Privileged Access Workstations):**
   - Привилегированные аккаунты — только с выделенных PAW
   - Хеши на обычных рабочих станциях бесполезны

### Инструменты защитника

| Инструмент | Назначение |
|------------|-----------|
| **Microsoft Defender for Identity** | Автодетекция OPtH |
| **Elastic Security** | Правило «Kerberos Pre-Authentication with RC4» |
| **Zeek** | Сетевой мониторинг Kerberos AS-REQ шифрования |
| **Wireshark** | Анализ Kerberos-пакетов (фильтр `kerberos.msg_type == 10`) |

### Практическое задание

**Задача:** Обнаружить разницу между легитимной Kerberos-аутентификацией и OPtH.

1. В лаборатории выполнить обычный `runas /user:domain\admin cmd` и зафиксировать Event ID 4624 + 4768
2. Сравнить Encryption Type: нормальный (AES) vs аномальный (RC4)
3. Создать дашборд в Kibana/Grafana с распределением Encryption Types

## Модуль 79: Злоупотребление RDP — Обнаружение и защита

### Что это за угроза

Remote Desktop Protocol (RDP) — легитимный инструмент удалённого администрирования, который активно используется атакующими для латерального движения. RDP-соединения с украденными учётными данными сложно отличить от легитимных, что делает мониторинг аномалий критически важным.

**Типичные сценарии атаки:**
- Перебор паролей RDP (brute force)
- Использование украденных учётных данных
- RDP Hijacking (перехват существующих сессий)
- BlueKeep и DejaBlue (уязвимости протокола)
- Туннелирование через RDP (port forwarding)

### Индикаторы компрометации (IoC)

| Индикатор | Источник | Event ID |
|-----------|---------|----------|
| RDP-логон в нерабочее время | Security Log | 4624 (Type 10) |
| RDP с внешнего/нетипичного IP | Security Log | 4624 (Type 10, Source IP) |
| Множественные неуспешные RDP-логоны | Security Log | 4625 (Type 10) |
| RDP Session Hijacking | Security Log | 4778 (Session Reconnected) |
| RDP Tunneling (нетипичный порт) | Network / Firewall | Port ≠ 3389 |
| Logon с отключённого аккаунта | Security Log | 4625 Status 0xC0000072 |

### Обнаружение

### Защита и предотвращение

1. **Network Level Authentication (NLA):**
   ```powershell
   # Требовать NLA для RDP — блокирует атаки до аутентификации
   Set-ItemProperty -Path 'HKLM:\SYSTEM\CurrentControlSet\Control\Terminal Server\WinStations\RDP-Tcp' `
     -Name UserAuthentication -Value 1
   ```

2. **Ограничение RDP через GPO:**
   ```
   # Computer Configuration → Administrative Templates → Windows Components →
   # Remote Desktop Services → Remote Desktop Session Host → Connections
   # "Restrict Remote Desktop Services users to a single Remote Desktop Services session" = Enabled
   # "Allow users to connect remotely by using Remote Desktop Services" = отключить для серверов без RDP
   ```

3. **RDP Gateway / Jump Server:**
   - Весь RDP-трафик только через централизованный шлюз
   - Логирование и запись сессий на шлюзе
   - MFA на шлюзе

4. **Firewall — ограничить порт 3389:**
   ```powershell
   # Разрешить RDP только из admin-подсети
   New-NetFirewallRule -DisplayName "RDP Admin Only" -Direction Inbound `
     -Protocol TCP -LocalPort 3389 `
     -RemoteAddress "10.0.1.0/24" -Action Allow
   # Заблокировать всё остальное
   New-NetFirewallRule -DisplayName "RDP Block All" -Direction Inbound `
     -Protocol TCP -LocalPort 3389 -Action Block
   ```

5. **Account Lockout Policy:**
   ```
   # GPO: Account lockout threshold: 5 attempts
   # Account lockout duration: 30 minutes
   # Reset lockout counter after: 30 minutes
   ```

## Модуль 80: PsExec/SMB Execution — Обнаружение и защита

### Что это за угроза

PsExec — утилита Sysinternals для удалённого выполнения команд через SMB (порт 445). Атакующие используют как оригинальный PsExec, так и его аналоги (Impacket psexec, smbexec, CrackMapExec) для латерального движения. Характерная цепочка: подключение к ADMIN$ или C$ → создание службы → выполнение команд → удаление следов.

### Индикаторы компрометации (IoC)

| Индикатор | Источник | Event ID |
|-----------|---------|----------|
| Создание службы PSEXESVC | System Log | 7045 |
| Именованный канал `\psexesvc` | Sysmon | Event 17/18 |
| Запись файла в `ADMIN$` | Sysmon | Event 11 (FileCreate) |
| Процесс запущен от `PSEXESVC.exe` | Sysmon | Event 1 (ParentImage) |
| SMB-аутентификация + создание службы | Security + System | 4624 + 7045 |
| Подключение к скрытым шарам (C$, ADMIN$, IPC$) | Security Log | 5140, 5145 |

   ```

3. **Windows Firewall — заблокировать SMB между рабочими станциями:**

   New-NetFirewallRule -DisplayName "Block Workstation-to-Workstation SMB" `

     -RemoteAddress "10.0.2.0/24" -Action Block  # подсеть рабочих станций
   ```

4. **LAPS + уникальные пароли:**
   - PsExec работает через ADMIN$ — нужен локальный admin
   - LAPS делает хеш одной машины бесполезным для остальных

5. **AppLocker / WDAC:**
   ```xml

   <FilePublisherRule Id="..." Name="Block PsExec" Action="Deny">
     <Conditions>
       <FilePublisherCondition PublisherName="O=MICROSOFT*"
         ProductName="*SYSINTERNALS*" BinaryName="PSEXEC*" />
     </Conditions>
   </FilePublisherRule>
   ```

| Инструмент | Назначение |
|------------|-----------|
| **Sysmon** | Мониторинг процессов, pipes, файлов |
| **Wazuh/OSSEC** | SIEM-правила для PsExec/SMB |

## Модуль 81: WinRM/PowerShell Remoting — Обнаружение и защита

### Что это за угроза

Windows Remote Management (WinRM) — легитимный протокол удалённого управления на базе WS-Management. PowerShell Remoting использует WinRM (порты 5985/HTTP, 5986/HTTPS) для выполнения команд на удалённых системах. Атакующие используют его как «легитимный» канал латерального движения, поскольку он встроен в Windows.

**Ключевая опасность:** PowerShell Remoting оставляет меньше следов, чем PsExec, и выглядит как обычное администрирование.

### Индикаторы компрометации (IoC)

| Индикатор | Источник | Event ID |
|-----------|---------|----------|
| WinRM-подключение | WinRM Operational | 91 (Creating WSMan session) |
| PowerShell Remoting-сессия | PowerShell Operational | 4103, 4104 (Script Block) |
| Процесс wsmprovhost.exe | Sysmon Event 1 | ParentImage = svchost.exe |
| Сетевые подключения на 5985/5986 | Sysmon Event 3 | DestinationPort |
| Logon Type 3 с Process wsmprovhost | Security | 4624 (Type 3) |

### Обнаружение

#### Sigma-правило: WinRM-сессия с нетипичного источника

```yaml

  Обнаружение создания WinRM-сессий. Фильтрация по белому списку
  администраторских рабочих станций.
logsource:
  product: windows
  service: winrm
detection:
  selection:
    EventID: 91
  filter_admin_hosts:
    Source|startswith:
      - '10.0.1.'  # Admin subnet
  condition: selection and not filter_admin_hosts

  - attack.lateral_movement
  - attack.t1021.006
```

### Защита и предотвращение

1. **Ограничение WinRM:**
   ```powershell
   # Разрешить WinRM только из admin-подсети
   Set-Item WSMan:\localhost\Service\IPv4Filter -Value "10.0.1.0/24"

   # Или через GPO:
   # Computer Configuration → Administrative Templates → Windows Components →
   # Windows Remote Management (WinRM) → WinRM Service →
   # "Allow remote server management through WinRM" → IPv4 filter: 10.0.1.0/24
   ```

2. **Just Enough Administration (JEA):**
   ```powershell
   # JEA ограничивает, какие команды доступны через PS Remoting
   # Файл конфигурации сессии
   New-PSSessionConfigurationFile -Path "C:\JEA\AdminEndpoint.pssc" `
     -SessionType RestrictedRemoteServer `
     -RunAsVirtualAccount `
     -RoleDefinitions @{
       'DOMAIN\ServerAdmins' = @{ RoleCapabilities = 'ServerMaintenance' }
     }

   # Регистрация JEA-эндпоинта
   Register-PSSessionConfiguration -Name AdminEndpoint `
     -Path "C:\JEA\AdminEndpoint.pssc"
   ```

3. **PowerShell Constrained Language Mode:**
   ```powershell
   # Через GPO → WDAC/AppLocker → автоматический Constrained Language Mode
   # Запрещает .NET, COM, опасные командлеты
   $ExecutionContext.SessionState.LanguageMode  # Проверка текущего режима
   ```

4. **Включить полное логирование PowerShell:**
   ```powershell
   # GPO: Administrative Templates → Windows Components → Windows PowerShell
   # "Turn on Module Logging" → Enabled, Module Names: *
   # "Turn on PowerShell Script Block Logging" → Enabled
   # "Turn on PowerShell Transcription" → Enabled, Output Directory: \\logserver\ps_logs
   ```

5. **Windows Firewall:**
   ```powershell
   # Ограничить 5985/5986 только admin-подсетью
   New-NetFirewallRule -DisplayName "WinRM Admin Only" -Direction Inbound `
     -Protocol TCP -LocalPort 5985,5986 `
     -RemoteAddress "10.0.1.0/24" -Action Allow
   ```

### Инструменты защитника

| Инструмент | Назначение |
|------------|-----------|
| **ScriptBlock Logging** | Полная запись всех PowerShell-команд |
| **Transcription Logging** | Запись ввода-вывода PS-сессий |
| **Sysmon** | Мониторинг wsmprovhost.exe и сетевых подключений |
| **Wazuh** | SIEM-правила для WinRM-аномалий |
| **Just Enough Administration** | Ограничение команд через PS Remoting |

### Практическое задание

1. Включить WinRM между двумя лабораторными машинами
2. Настроить полное PowerShell-логирование (Module, ScriptBlock, Transcription)
3. Выполнить `Invoke-Command -ComputerName target -ScriptBlock {whoami}`
4. Найти все артефакты в логах (Event 91, 4103, 4104, Sysmon 1, Sysmon 3)
5. Настроить JEA-эндпоинт с ограниченным набором команд
6. Попытаться выполнить запрещённую команду через JEA — убедиться в блокировке

## Модуль 82: SSH Lateral Movement — Обнаружение и защита

### Что это за угроза

SSH (Secure Shell) — основной протокол удалённого доступа в Linux/Unix-средах (и всё чаще — в Windows с OpenSSH). Атакующие используют украденные ключи, перехваченные пароли или ssh-agent forwarding для перемещения между серверами. SSH-туннелирование также используется для обхода сегментации.

### Индикаторы компрометации (IoC)

| Индикатор | Источник | Метод |
|-----------|---------|-------|
| SSH-логин в нерабочее время или с нетипичного IP | auth.log / secure | `sshd.*Accepted` |
| Множественные неуспешные попытки | auth.log | `sshd.*Failed` |
| SSH-туннелирование (-L, -R, -D) | Sysmon for Linux / auditd | Аргументы командной строки |
| Использование SSH-агента с нетипичного хоста | auth.log | Agent forwarding |
| SSH-ключ добавлен в `authorized_keys` | auditd | Запись в файл |
| SSH с root-аккаунта | auth.log | `Accepted.*root` |

### Обнаружение

#### Sigma-правило: SSH brute force (Linux)

## Модуль 86: Service Controller Abuse — Обнаружение и защита

### Что это за угроза

Service Controller (sc.exe) позволяет управлять службами Windows, в том числе удалённо: `sc \\remote create`, `sc \\remote start`. Атакующие создают временные службы на удалённых хостах для выполнения произвольного кода — техника, аналогичная PsExec, но без характерных именованных каналов.

| Индикатор | Источник | Event ID |
|-----------|---------|----------|
| Новая служба создана | System Log | 7045 |
| sc.exe с удалённым хостом в командной строке | Sysmon Event 1 | `\\remote` |
| Служба с подозрительным путём (binpath) | System Log | 7045 (ImagePath) |
| Служба запущена и тут же остановлена | System Log | 7036 (started → stopped) |
| Служба удалена после выполнения | Sysmon Event 1 | sc delete |

## Модуль 90: Credential Dumping — Обнаружение и защита

### Что это за угроза

Credential Dumping — извлечение учётных данных (хешей паролей, Kerberos-тикетов, открытых паролей) из памяти процессов (LSASS), реестра (SAM), базы AD (NTDS.dit) и других источников. Это ключевая техника, обеспечивающая все остальные методы латерального движения — без credentials нечего передавать.

**Основные цели:**
- **LSASS** (Local Security Authority Subsystem) — хеши и тикеты в памяти
- **SAM** (Security Accounts Manager) — локальные хеши
- **NTDS.dit** — база AD со всеми хешами домена
- **LSA Secrets** — сервисные аккаунты, кешированные credentials
- **Credential Manager** — сохранённые пароли пользователей

### Индикаторы компрометации (IoC)

| Индикатор | Источник | Event ID |
|-----------|---------|----------|
| Доступ к процессу LSASS | Sysmon Event 10 | TargetImage = lsass.exe |
| Создание дампа LSASS (procdump, comsvcs.dll) | Sysmon Event 1 + 11 | |
| Копирование SAM/SYSTEM/SECURITY | Sysmon Event 1 | reg save, copy |
| Создание теневой копии (для NTDS.dit) | Security Log | 4688 (vssadmin) |
| DCSync — репликация AD | Security Log | 4662 (DS-Replication-Get-Changes) |
| Секреты LSA считаны | Security Log | 4656 (LSA object access) |
| MiniDump от нетипичного процесса | Sysmon Event 10 | GrantedAccess: 0x1010 |

### Обнаружение

### Защита и предотвращение

1. **Credential Guard (защита LSASS):**
   ```powershell
   # Включение Windows Credential Guard
   # Использует VBS (Virtualization-Based Security) для изоляции LSASS
   reg add "HKLM\SYSTEM\CurrentControlSet\Control\DeviceGuard" `
     /v EnableVirtualizationBasedSecurity /t REG_DWORD /d 1 /f
   reg add "HKLM\SYSTEM\CurrentControlSet\Control\Lsa" `
     /v LsaCfgFlags /t REG_DWORD /d 1 /f
   # Требуется перезагрузка
   ```

2. **LSA Protection (RunAsPPL):**
   ```powershell
   # Запуск LSASS как Protected Process Light
   reg add "HKLM\SYSTEM\CurrentControlSet\Control\Lsa" `
     /v RunAsPPL /t REG_DWORD /d 1 /f
   # Блокирует доступ к LSASS из непривилегированных процессов
   ```

3. **Windows Defender Credential Guard + Remote Credential Guard:**
   ```powershell
   # Remote Credential Guard — не оставляет credentials на удалённом хосте
   # На клиенте:
   mstsc /remoteGuard
   # Через GPO: Administrative Templates → System → Credentials Delegation →
   # "Restrict delegation of credentials to remote servers" = Require Remote Credential Guard
   ```

4. **Ограничение DCSync:**
   ```powershell
   # Аудит: кто имеет права репликации?
   (Get-ACL "AD:\DC=domain,DC=local").Access |
     Where-Object {
       $_.ObjectType -eq "1131f6aa-9c07-11d1-f79f-00c04fc2dcd2" -or
       $_.ObjectType -eq "1131f6ad-9c07-11d1-f79f-00c04fc2dcd2"
     } | Select IdentityReference, ActiveDirectoryRights

   # Убрать лишних! Только DC-аккаунты должны иметь Replicating Directory Changes
   ```

5. **Protected Users Group:**
   ```powershell
   # Для привилегированных аккаунтов:
   Add-ADGroupMember -Identity "Protected Users" -Members "admin_user"
   # Запрещает: NTLM, DES/RC4, delegation, кеширование credentials
   ```

6. **LAPS — уникальные локальные пароли:**
   ```powershell
   # Каждая машина имеет уникальный пароль локального admin
   # Дамп SAM одной машины бесполезен для остальных
   ```

7. **Мониторинг через Sysmon Config:**
   ```xml
   <!-- Критически важно для обнаружения credential dumping -->
   <ProcessAccess onmatch="include">
     <TargetImage condition="end with">lsass.exe</TargetImage>
   </ProcessAccess>

   <ProcessCreate onmatch="include">
     <Image condition="end with">procdump.exe</Image>
     <Image condition="end with">mimikatz.exe</Image>
     <CommandLine condition="contains">comsvcs</CommandLine>
     <CommandLine condition="contains">sekurlsa</CommandLine>
     <Image condition="end with">vssadmin.exe</Image>
     <Image condition="end with">ntdsutil.exe</Image>
   </ProcessCreate>
   ```
