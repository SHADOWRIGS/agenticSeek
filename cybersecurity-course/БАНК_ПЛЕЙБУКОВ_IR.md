# БАНК ПЛЕЙБУКОВ РЕАГИРОВАНИЯ НА ИНЦИДЕНТЫ (IR RUNBOOKS)

> 15 готовых плейбуков для SOC-команды. Каждый — пошаговая инструкция от первого алерта до закрытия инцидента.
> Формат: NIST SP 800-61 (Подготовка → Обнаружение → Сдерживание → Устранение → Восстановление → Уроки).

---

## ОБЩИЕ ПРИНЦИПЫ

### Уровни критичности

| Уровень | SLA (реагирование) | SLA (разрешение) | Примеры |
|---------|-------------------|-------------------|---------|
| **P1 — Критический** | 15 мин | 4 часа | Ransomware, активный wiper, массовая эксфильтрация |
| **P2 — Высокий** | 30 мин | 8 часов | C2 beaconing, lateral movement, credential compromise |
| **P3 — Средний** | 2 часа | 24 часа | Фишинг, единичная малварь, cryptominer |
| **P4 — Низкий** | 8 часов | 72 часа | Нарушение политики, suspicious login |

### Эскалация

```
L1 SOC → L2 SOC → L3 / Threat Hunter → IR Lead → CISO → Руководство / Юристы
```

### Золотые правила IR

1. **Не паникуй** — действуй по плейбуку
2. **Не выключай** — сними дамп RAM до отключения
3. **Документируй всё** — тикет, скриншоты, таймлайн
4. **Сохраняй улики** — chain of custody
5. **Изолируй, не удаляй** — сдерживание до устранения
6. **Коммуницируй** — эскалация и уведомления вовремя

## ПЛЕЙБУК 1: RANSOMWARE

### Метаданные
- **Критичность:** P1 — Критический
- **MITRE ATT&CK:** T1486 (Data Encrypted for Impact), T1490 (Inhibit System Recovery)
- **Триггеры:** Алерт на массовое переименование файлов, canary-файл изменён, vssadmin delete shadows, записка о выкупе

### Шаг 1: Триаж (0–15 мин)
1. Подтвердить алерт: проверить хост, пользователя, процесс
2. Определить штамм: проверить расширение зашифрованных файлов, записку о выкупе
3. Оценить масштаб: сколько хостов затронуто?

```bash
# Проверить на SIEM — какие хосты обращались к тому же C2/процессу
# Поиск в Wazuh/ELK:
# rule.description:"vssadmin" OR rule.description:"ransomware"
```

### Шаг 2: Сдерживание (15–60 мин)
1. **Немедленно:** Изолировать заражённые хосты от сети (EDR isolate / отключить сетевой кабель)
2. Заблокировать C2-домены/IP на файрволе и DNS
3. Отключить скомпрометированные учётные записи
4. Остановить распространение: заблокировать SMB (порт 445) между сегментами
5. Снять дамп RAM до перезагрузки:

```bash
# Windows (WinPmem)
winpmem_mini_x64.exe ram_dump.raw

# Linux (LiME)
insmod lime.ko "path=/tmp/ram.lime format=lime"
```

### Шаг 3: Устранение
1. Определить вектор заражения (фишинг? RDP? уязвимость?)
2. Проверить наличие декриптора: https://www.nomoreransom.org
3. Удалить артефакты: persistence (реестр, scheduled tasks, services)
4. Сбросить пароли скомпрометированных аккаунтов
5. Пропатчить уязвимость, если использовалась

### Шаг 4: Восстановление
1. Восстановить данные из бэкапов (проверить целостность бэкапа!)
2. Переустановить ОС на заражённых хостах (если нет уверенности в полной очистке)
3. Постепенно возвращать хосты в сеть с мониторингом
4. Проверить, что persistence удалён

### Шаг 5: Уроки
1. Таймлайн инцидента
2. Root cause analysis
3. Обновить правила детекции
4. Проверить стратегию бэкапов (3-2-1, immutable)
5. Провести учения для сотрудников

### Улики для сбора
- Дамп RAM, образ диска
- Записка о выкупе (текст)
- Зашифрованные файлы (образцы)
- Логи: Security, Sysmon, PowerShell, файрвол
- Сетевой трафик (PCAP)

### Шаблон уведомления
```
ИНЦИДЕНТ: Ransomware [штамм]
Время обнаружения: [ДД.ММ.ГГГГ ЧЧ:ММ]
Затронуто хостов: [N]
Статус: Сдерживание / Устранение / Восстановление
Вектор заражения: [фишинг / RDP / уязвимость / расследуется]
Ответственный: [имя]
Следующий апдейт: через [N] часов
```

## ПЛЕЙБУК 2: ФИШИНГОВОЕ ПИСЬМО

### Метаданные
- **Критичность:** P3 (единичное) / P2 (массовая кампания) / P1 (пользователь перешёл и ввёл данные)
- **MITRE ATT&CK:** T1566.001 (Spearphishing Attachment), T1566.002 (Spearphishing Link)
- **Триггеры:** Сообщение пользователя, алерт email gateway, алерт на подозрительный URL

### Шаг 1: Триаж (0–30 мин)
1. Получить оригинал письма (заголовки, тело, вложения)
2. Извлечь IoC: отправитель, Reply-To, IP, URL, хеши вложений

```bash
# Извлечь заголовки
# Проверить SPF/DKIM/DMARC в заголовках
# Проверить URL на VirusTotal, URLScan.io
# Проверить хеш вложения на VirusTotal
```

3. Определить: кто ещё получил это письмо?

```
# Поиск по почтовому серверу:
# From: attacker@evil.com OR Subject: "тема письма"
```

### Шаг 2: Оценка воздействия
1. Кто-то перешёл по ссылке? (проверить прокси-логи)
2. Кто-то открыл вложение? (проверить EDR/Sysmon)
3. Кто-то ввёл учётные данные? (проверить логи целевого сайта)

### Шаг 3: Сдерживание
1. Удалить письмо из всех почтовых ящиков (purge)
2. Заблокировать домен/URL на прокси и DNS
3. Заблокировать хеш вложения на EDR
4. Если кто-то ввёл пароль: сбросить пароль, отозвать сессии, включить MFA

### Шаг 4: Устранение
1. Просканировать хосты, где открывали вложение
2. Удалить малварь, если обнаружена
3. Проверить persistence на заражённых хостах

### Шаг 5: Восстановление
1. Разблокировать учётные записи после смены паролей
2. Добавить IoC в blocklist и SIEM

### Шаг 6: Уроки
1. Обновить правила email gateway
2. Провести awareness-рассылку для сотрудников
3. Добавить Sigma-правило для нового IoC

## ПЛЕЙБУК 3: КОМПРОМЕТАЦИЯ УЧЁТНЫХ ДАННЫХ

### Метаданные
- **Критичность:** P2 — Высокий
- **MITRE ATT&CK:** T1078 (Valid Accounts), T1110 (Brute Force)
- **Триггеры:** Множественные 4625, вход из аномальной геолокации, impossible travel, password spraying

### Шаг 1: Триаж
1. Какой аккаунт скомпрометирован?
2. Привилегированный ли он? (Domain Admin, root, сервисный)
3. Откуда вход? (IP, геолокация, User-Agent)
4. Что делал после входа? (Event ID 4624 → последующие действия)

### Шаг 2: Сдерживание
1. Заблокировать учётную запись: `usermod -L <user>` / `Disable-ADAccount`
2. Отозвать все активные сессии и токены
3. Заблокировать IP-адрес атакующего на файрволе
4. Если привилегированный аккаунт: сбросить пароль KRBTGT (дважды!)

### Шаг 3: Расследование
1. Проверить все действия аккаунта за последние 30 дней
2. Проверить создание новых аккаунтов (4720)
3. Проверить добавление в группы (4728, 4732)
4. Проверить lateral movement (4624 Type 3 с других хостов)
5. Проверить scheduled tasks, services, WMI subscriptions

### Шаг 4: Устранение
1. Сбросить пароль (сгенерировать сложный)
2. Включить MFA
3. Удалить все persistence-механизмы
4. Закрыть вектор компрометации (утечка, фишинг, brute force)

### Шаг 5: Восстановление
1. Разблокировать аккаунт с новым паролем
2. Мониторить аккаунт 30 дней (повышенное логирование)

### Улики для сбора
- Логи аутентификации (4624, 4625, 4648, 4672)
- Логи VPN / RDP
- Прокси-логи
- Логи MFA

## ПЛЕЙБУК 4: МАЛВАРЬ НА КОНЕЧНОЙ ТОЧКЕ

### Метаданные
- **Критичность:** P3 (единичный хост) / P2 (распространение)
- **MITRE ATT&CK:** T1059 (Command and Scripting Interpreter), T1547 (Boot or Logon Autostart Execution)
- **Триггеры:** Алерт антивируса/EDR, подозрительный процесс в Sysmon, YARA-матч

### Шаг 1: Триаж
1. Какой процесс? PID, путь, хеш, командная строка
2. Кто запустил? (родительский процесс)
3. Что делает? (сетевые соединения, файловые операции, дочерние процессы)
4. Определить семейство малвари (хеш на VirusTotal, sandbox)

```bash
# Sysmon Event ID 1: Process Create
# Sysmon Event ID 3: Network Connection
# Sysmon Event ID 11: File Create
```

### Шаг 2: Сдерживание
1. Изолировать хост (EDR isolate)
2. Завершить вредоносный процесс (если не нужен для анализа)
3. Заблокировать C2 на файрволе/DNS

### Шаг 3: Анализ
1. Снять дамп RAM
2. Собрать артефакты: Prefetch, Amcache, ShimCache, MFT timeline
3. Проверить persistence: реестр, services, scheduled tasks, WMI
4. Проверить lateral movement

### Шаг 4: Устранение
1. Удалить все файлы малвари
2. Удалить persistence
3. Пропатчить уязвимость (если использовалась)
4. Обновить сигнатуры антивируса

### Шаг 5: Восстановление
1. Полная проверка хоста антивирусом
2. Вернуть хост в сеть с мониторингом
3. Добавить IoC в SIEM и EDR blocklist

## ПЛЕЙБУК 5: ПОДОЗРЕНИЕ НА ЭКСФИЛЬТРАЦИЮ ДАННЫХ

### Метаданные
- **Критичность:** P1 — Критический
- **MITRE ATT&CK:** T1041 (Exfiltration Over C2), T1048 (Exfiltration Over Alternative Protocol)
- **Триггеры:** DLP-алерт, аномальный объём исходящего трафика, обращения к облачным хранилищам, DNS tunneling

### Шаг 1: Триаж
1. Какие данные? (ПДн, коммерческая тайна, исходный код)
2. Какой канал? (HTTPS, DNS, email, USB, облако)
3. Кто отправитель? (пользователь, процесс, хост)
4. Куда? (внешний IP/домен)

```bash
# Проверить на прокси: аномальный upload
# Проверить DNS: длинные запросы, TXT-записи
# Проверить DLP-логи
```

### Шаг 2: Сдерживание
1. Заблокировать канал эксфильтрации (IP, домен, порт)
2. Изолировать хост-источник
3. Заблокировать учётную запись (если insider threat)
4. Остановить процесс-источник

### Шаг 3: Расследование
1. Определить объём утечки (сколько данных, какие именно)
2. Построить таймлайн: когда началась эксфильтрация
3. Определить, как атакующий получил доступ к данным
4. Проверить другие хосты на аналогичную активность

### Шаг 4: Устранение
1. Удалить малварь/инструмент эксфильтрации
2. Закрыть уязвимость/вектор доступа
3. Отозвать ключи/токены, которые могли утечь

### Шаг 5: Юридические действия
1. Уведомить руководство и юридический отдел
2. Оценить обязательства по 152-ФЗ (если ПДн)
3. Уведомить Роскомнадзор (если ПДн, в течение 24 часов)
4. Уведомить пострадавших субъектов ПДн
5. Сохранить доказательства для правоохранительных органов

### Улики для сбора
- PCAP сетевого трафика
- DLP-логи
- Прокси-логи с полными URL
- DNS-логи
- Дамп RAM хоста-источника
- Образ диска

## ПЛЕЙБУК 6: ИНСАЙДЕРСКАЯ УГРОЗА

### Метаданные
- **Критичность:** P2 — Высокий
- **MITRE ATT&CK:** T1078 (Valid Accounts), T1530 (Data from Cloud Storage Object)
- **Триггеры:** UEBA-аномалия, массовое копирование файлов, доступ к данным вне рабочих обязанностей, DLP-алерт

### Шаг 1: Триаж
1. **Конфиденциально:** Не предупреждать подозреваемого
2. Подтвердить аномалию: это реально выходит за рамки обычного поведения?
3. Согласовать с HR и юридическим отделом
4. Определить тип: злонамеренный, небрежный или скомпрометированный аккаунт?

### Шаг 2: Мониторинг (скрытый)
1. Усилить логирование для подозреваемого аккаунта
2. Мониторить: файловые операции, email, USB, облако, печать
3. Не изменять доступы до согласования с HR/юристами

### Шаг 3: Сдерживание (после согласования)
1. Ограничить доступ к критичным данным
2. Отключить USB / облачные хранилища
3. Перевести на мониторируемую рабочую станцию

### Шаг 4: Расследование
1. Собрать логи за 90 дней: файловые операции, email, VPN, прокси
2. Проверить личные устройства (с разрешения юристов)
3. Проверить печать конфиденциальных документов
4. Поговорить с непосредственным руководителем (конфиденциально)

### Шаг 5: Действия
1. Принятие решения HR/руководством
2. Сохранение доказательств (chain of custody)
3. При увольнении: немедленная блокировка всех аккаунтов
4. Юридические действия при необходимости

## ПЛЕЙБУК 7: DDoS-АТАКА

### Метаданные
- **Критичность:** P2 (средний сервис) / P1 (критичный сервис)
- **MITRE ATT&CK:** T1498 (Network Denial of Service), T1499 (Endpoint Denial of Service)
- **Триггеры:** Недоступность сервиса, аномальный всплеск трафика, алерт мониторинга, CDN/WAF-алерт

### Шаг 1: Триаж
1. Какой сервис затронут?
2. Тип атаки: volumetric (объёмная), protocol (SYN flood), application (HTTP flood)?
3. Масштаб: Gbps, RPS, количество источников

```bash
# Проверить текущий трафик
iftop -i eth0
netstat -an | awk '/SYN_RECV/ {print}' | wc -l
```

### Шаг 2: Сдерживание
1. Активировать DDoS-защиту провайдера / CDN (Cloudflare, Qrator)
2. Включить rate limiting на WAF/балансировщике
3. Geo-blocking, если атака из конкретных регионов
4. Blackhole routing для наиболее агрессивных IP

```bash
# Временная блокировка через iptables
iptables -A INPUT -s <attacker_ip> -j DROP

# Rate limiting SYN
iptables -A INPUT -p tcp --syn -m limit --limit 1/s --limit-burst 3 -j ACCEPT
```

### Шаг 3: Эскалация
1. Связаться с ISP для фильтрации на upstream
2. Если >10 Gbps: scrubbing-центр провайдера
3. Уведомить бизнес о деградации сервиса

### Шаг 4: Восстановление
1. Плавное снятие фильтров после прекращения атаки
2. Мониторинг на повторную атаку (часто бывает)
3. Проверить, не была ли DDoS отвлечением для другой атаки

### Шаг 5: Уроки
1. Оценить эффективность DDoS-защиты
2. Обновить договор с провайдером/CDN при необходимости
3. Разработать план масштабирования

## ПЛЕЙБУК 8: АТАКА НА ВЕБ-ПРИЛОЖЕНИЕ (SQLi/XSS)

### Метаданные
- **Критичность:** P2 (обнаружено WAF) / P1 (успешная эксплуатация)
- **MITRE ATT&CK:** T1190 (Exploit Public-Facing Application)
- **Триггеры:** WAF-алерт (ModSecurity, Cloudflare), аномальные HTTP-запросы в логах

### Шаг 1: Триаж
1. Какой URL/endpoint атакован?
2. Тип атаки: SQLi, XSS, RCE, LFI, SSRF?
3. WAF заблокировал или пропустил?
4. Есть ли признаки успешной эксплуатации?

```bash
# Проверить логи WAF
# Проверить access.log на аномальные запросы:
grep -E "(union|select|script|\.\.\/|etc\/passwd)" /var/log/nginx/access.log
```

### Шаг 2: Сдерживание
1. Заблокировать IP атакующего на WAF
2. Если успешная SQLi: отключить приложение от БД, проверить данные
3. Если XSS stored: найти и удалить инъекцию
4. Если RCE: изолировать сервер

### Шаг 3: Расследование
1. Проверить, получил ли атакующий доступ к данным
2. Проверить, не установлен ли webshell
3. Проверить целостность БД и файлов

```bash
# Поиск webshell
find /var/www -name "*.php" -newer /var/www/index.php -exec ls -la {} \;
find /var/www -name "*.php" -exec grep -l "eval\|base64_decode\|system\|passthru" {} \;
```

### Шаг 4: Устранение
1. Исправить уязвимость в коде
2. Обновить WAF-правила
3. Если утечка БД: сбросить пароли пользователей

### Шаг 5: Восстановление
1. Деплой исправленной версии
2. Проверить работоспособность
3. Усиленный мониторинг 7 дней

---

## ПЛЕЙБУК 9: ОБНАРУЖЕНО ЛАТЕРАЛЬНОЕ ДВИЖЕНИЕ

### Метаданные
- **Критичность:** P1 — Критический (атакующий уже в сети)
- **MITRE ATT&CK:** T1021 (Remote Services), T1550 (Use Alternate Authentication Material)
- **Триггеры:** Sysmon Event ID 1 (PsExec), Event ID 7045, Event ID 4624 Type 3/10 с аномальных хостов

### Шаг 1: Триаж
1. Откуда и куда движение? (source → destination)
2. Какой метод? (PsExec, WMI, RDP, WinRM, DCOM, SMB)
3. Какой аккаунт используется?
4. Сколько хостов уже затронуто?

### Шаг 2: Сдерживание (НЕМЕДЛЕННО)
1. Изолировать все затронутые хосты
2. Заблокировать скомпрометированный аккаунт
3. Заблокировать связь между сегментами (файрвол)
4. Если Domain Admin: предполагать полную компрометацию AD

```bash
# Поиск lateral movement в логах:
# Event ID 4624 Logon Type 3 + 10 за последние 24 часа
# Event ID 7045 (новые сервисы)
# Event ID 5145 (доступ к шарам ADMIN$, C$, IPC$)
```

### Шаг 3: Расследование
1. Построить карту перемещения (host graph)
2. Найти первоначальную точку входа (patient zero)
3. Проверить credential dumping: Sysmon Event ID 10 → lsass.exe
4. Проверить Golden/Silver Ticket
5. Проверить DCSync (Event ID 4662)

### Шаг 4: Устранение
1. Сбросить пароли ВСЕХ скомпрометированных аккаунтов
2. Сбросить KRBTGT (дважды, с интервалом 12 часов)
3. Удалить persistence на каждом затронутом хосте
4. Пересоздать сервисные аккаунты с новыми паролями

### Шаг 5: Восстановление
1. Постепенное возвращение хостов (начать с чистых)
2. Усиленный мониторинг 30 дней
3. Внедрить Credential Guard, LAPS, сегментацию

## ПЛЕЙБУК 10: C2 BEACONING

### Метаданные
- **Критичность:** P2 — Высокий
- **MITRE ATT&CK:** T1071 (Application Layer Protocol), T1573 (Encrypted Channel)
- **Триггеры:** IDS/Suricata-алерт, JA3-матч, регулярные обращения к одному URL, beacon-анализ

### Шаг 1: Триаж
1. Какой хост? Какой процесс? (Sysmon Event ID 3)
2. Куда подключается? (IP, домен, порт)
3. Паттерн: регулярный интервал? Jitter? Объём данных?
4. Проверить домен/IP на TI-фидах

### Шаг 2: Сдерживание
1. Изолировать хост (EDR isolate — НЕ отключать от сети полностью, если нужен мониторинг)
2. Заблокировать C2-домен/IP на файрволе и DNS sinkhole
3. Проверить, есть ли другие хосты с тем же C2

```bash
# Поиск всех хостов, обращающихся к тому же C2
# В Suricata EVE или прокси-логах:
# dns.query == "c2.evil.com" OR dest_ip == "1.2.3.4"
```

### Шаг 3: Анализ
1. Снять дамп RAM
2. Определить тип C2 (Cobalt Strike, Meterpreter, custom)
3. Проверить, какие команды выполнялись (если возможно)
4. Проверить lateral movement
5. Проверить эксфильтрацию

### Шаг 4: Устранение
1. Удалить имплант (файлы, persistence, in-memory — может потребоваться перезагрузка)
2. Удалить все persistence-механизмы
3. Просканировать весь сегмент на аналогичные импланты

### Шаг 5: Восстановление
1. Переустановить ОС при подозрении на глубокую компрометацию
2. Вернуть хост в сеть с усиленным мониторингом
3. Добавить JA3, домен, IP в blocklist

## ПЛЕЙБУК 11: ПОВЫШЕНИЕ ПРИВИЛЕГИЙ / НЕСАНКЦИОНИРОВАННЫЙ ДОСТУП

### Метаданные
- **Критичность:** P2 — Высокий
- **MITRE ATT&CK:** T1068 (Exploitation for Privilege Escalation), T1078 (Valid Accounts)
- **Триггеры:** Event ID 4672 (special privileges), Event ID 4728/4732 (добавление в группу), аномальный sudo

### Шаг 1: Триаж
1. Кто получил повышенные привилегии?
2. Легитимно ли это? (согласовано с IT/руководством?)
3. Каким методом? (эксплойт, добавление в группу, токен)

### Шаг 2: Сдерживание
1. Отозвать повышенные привилегии
2. Заблокировать аккаунт при подозрении на компрометацию
3. Изолировать хост, если использован эксплойт

### Шаг 3: Расследование
1. Проверить, что было сделано с повышенными правами
2. Проверить создание аккаунтов, бэкдоров
3. Проверить доступ к конфиденциальным данным
4. Для Linux: проверить `sudo` логи, SUID-файлы

```bash
# Linux: последние sudo-команды
grep "sudo" /var/log/auth.log | tail -50

# Windows: Event ID 4672 (special logon)
# Event ID 4728 (member added to security-enabled global group)
```

### Шаг 4: Устранение
1. Пропатчить уязвимость (если эксплойт)
2. Удалить созданные бэкдоры
3. Восстановить правильные ACL

## ПЛЕЙБУК 12: CRYPTOMINER

### Метаданные
- **Критичность:** P3 — Средний
- **MITRE ATT&CK:** T1496 (Resource Hijacking)
- **Триггеры:** Аномальная загрузка CPU/GPU, обращения к mining pool, Stratum-протокол

### Шаг 1: Триаж
1. Какой процесс потребляет CPU? (top, htop, Task Manager)
2. Сетевые соединения процесса (на порты 3333, 4444, 5555, 8333)
3. Один хост или несколько?

```bash
# Linux
top -o %CPU
ss -tulnp | grep -E "(3333|4444|5555|8333)"
```

### Шаг 2: Сдерживание
1. Завершить процесс майнера
2. Заблокировать mining-pool домены/IP
3. Проверить persistence

### Шаг 3: Расследование
1. Как попал? (уязвимость, фишинг, supply chain)
2. Проверить другие хосты в сегменте
3. Оценить ущерб (электричество, производительность, время простоя)

### Шаг 4: Устранение
1. Удалить майнер и persistence
2. Закрыть вектор проникновения
3. Добавить правила IDS для Stratum-протокола

## ПЛЕЙБУК 13: SUPPLY CHAIN COMPROMISE

### Метаданные
- **Критичность:** P1 — Критический
- **MITRE ATT&CK:** T1195 (Supply Chain Compromise)
- **Триггеры:** Алерт на подозрительное обновление ПО, аномальное поведение доверенного приложения, CVE в зависимости

### Шаг 1: Триаж
1. Какой компонент скомпрометирован? (пакет, обновление, плагин)
2. Какие системы его используют?
3. Какая версия затронута?

### Шаг 2: Сдерживание
1. Заблокировать обновления от скомпрометированного поставщика
2. Изолировать хосты с затронутой версией
3. Откатить до безопасной версии

### Шаг 3: Расследование
1. Проверить, активировался ли вредоносный код
2. Проверить SBOM (Software Bill of Materials) для определения всех затронутых систем
3. Проверить хеши и подписи пакетов

### Шаг 4: Устранение
1. Удалить скомпрометированный компонент
2. Установить безопасную версию
3. Проверить отсутствие persistence

### Шаг 5: Уроки
1. Внедрить SCA (Software Composition Analysis)
2. Настроить верификацию подписей пакетов
3. Вести SBOM для критичных систем

## ПЛЕЙБУК 14: DNS TUNNELING

### Метаданные
- **Критичность:** P2 — Высокий
- **MITRE ATT&CK:** T1071.004 (Application Layer Protocol: DNS)
- **Триггеры:** Suricata/Zeek-алерт, аномально длинные DNS-запросы, высокая энтропия поддоменов, TXT-запросы

### Шаг 1: Триаж
1. Какой хост генерирует аномальные DNS-запросы?
2. К какому домену? (проверить на TI)
3. Тип записей: A, TXT, CNAME, NULL?
4. Объём и частота запросов

```bash
# Анализ DNS-логов (Zeek)
# cat dns.log | awk '{print length($10), $10}' | sort -rn | head -20
# Длина поддоменов >50 символов — подозрительно
```

### Шаг 2: Сдерживание
1. Заблокировать домен на DNS-сервере (sinkhole)
2. Изолировать хост
3. Заблокировать IP DNS-сервера атакующего

### Шаг 3: Расследование
1. Определить, что передавалось (данные наружу или команды внутрь)
2. Декодировать содержимое (обычно base32/base64 в поддоменах)
3. Определить инструмент (iodine, dnscat2, custom)
4. Оценить объём утечки

### Шаг 4: Устранение
1. Удалить клиент DNS-туннеля
2. Удалить persistence
3. Настроить DNS-фильтрацию (ограничить длину запросов, типы записей)

### Шаг 5: Превенция
1. Внутренний DNS-резолвер с логированием
2. Блокировка прямых DNS-запросов наружу (только через корпоративный DNS)
3. Мониторинг энтропии DNS-запросов

## ПЛЕЙБУК 15: WIPER / ДЕСТРУКТИВНАЯ МАЛВАРЬ

### Метаданные
- **Критичность:** P1 — Критический (максимальный приоритет)
- **MITRE ATT&CK:** T1485 (Data Destruction), T1561 (Disk Wipe)
- **Триггеры:** FIM-алерт на массовое удаление, перезапись MBR/GPT, синий экран на множестве хостов

### Шаг 1: Триаж (0–5 мин)
1. **НЕМЕДЛЕННО оценить масштаб** — сколько хостов затронуто?
2. Тип: MBR wipe, file wipe, оба?
3. Продолжается ли деструкция прямо сейчас?

### Шаг 2: Сдерживание (5–15 мин)
1. **Отключить всю сеть** (если деструкция продолжается и масштаб растёт) — это единственный случай, когда допускается полное отключение
2. Изолировать незатронутые сегменты
3. Выключить работающие хосты (здесь RAM уже не важна — данные уничтожаются)
4. Защитить бэкапы: отключить бэкап-серверы от сети

### Шаг 3: Оценка ущерба
1. Какие системы уничтожены?
2. Какие данные потеряны?
3. Проверить целостность бэкапов (не заражены ли?)
4. Проверить AD: контроллеры домена живы?

### Шаг 4: Восстановление
1. Восстановить из бэкапов (начать с критичных систем)
2. Если AD уничтожен: восстановить из offline-бэкапа DC
3. Переустановить ОС на всех затронутых хостах
4. Восстанавливать поэтапно, с проверкой каждого хоста

### Шаг 5: Расследование (параллельно восстановлению)
1. Определить вектор распространения
2. Определить время активации (time bomb?)
3. Сохранить образы незатронутых хостов для анализа
4. Привлечь правоохранительные органы

### Шаг 6: Уроки
1. Пересмотреть стратегию бэкапов: WORM/immutable, air-gapped
2. Тестировать восстановление регулярно
3. Улучшить сегментацию
