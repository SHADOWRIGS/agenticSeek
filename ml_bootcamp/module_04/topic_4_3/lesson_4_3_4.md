# Урок 4.3.4: ПРАКТИКА: Сравнение boosting алгоритмов на реальных данных

> **Модуль 4:** Ensemble Mastery & Hyperparameter Optimization · **Тема 4.3:** Gradient Boosting
> **Тип:** практика · **Время:** 6–8 часов

## Задача

Команда начинает новый проект на табличных данных и спрашивает вас: «XGBoost, LightGBM или CatBoost?»
Ответ «CatBoost, он лучше» ничего не стоит: лучше — на каких данных, при каких параметрах, по какой
метрике, с каким временем обучения? За три урока темы вы видели, как легко получить любой желаемый
результат: дать одной библиотеке раннюю остановку, а другой нет; настроить одну и оставить значения
по умолчанию у другой; подобрать число деревьев по тесту.

Работа состоит из двух частей:

1. **Реализация.** Написать стенд для честного сравнения четырёх реализаций бустинга — XGBoost,
   LightGBM, CatBoost и `HistGradientBoosting` из scikit-learn — так, чтобы проходили тесты.
2. **Применение.** Сравнить библиотеки на нескольких наборах данных и написать заключение: какую
   библиотеку выбрать для конкретной задачи и почему.

Честное сравнение — это протокол: одинаковые разбиения, ранняя остановка у всех на одной и той же
валидационной части, тест только для итоговой оценки, одинаковый бюджет настройки, обязательные простые
модели для сравнения, и не одно число «качество», а четыре: качество, время обучения, время
предсказания, размер модели.

## Часть 1. Реализация

Точные требования — в docstring заготовки. Ниже порядок работы и подводные камни.

### Шаг 1. `make_models`

Четыре модели с одинаковыми общими параметрами: верхняя граница числа итераций, шаг обучения, число
потоков, `random_state`. Одни и те же вещи в библиотеках называются по-разному (`n_estimators`,
`iterations`, `max_iter`; `random_state` и `random_seed`; `n_jobs` и `thread_count`) — сводная таблица
есть в уроке 4.3.3. Служебные параметры: CatBoost не должен писать файлы и печатать ход обучения,
LightGBM — печатать предупреждения, XGBoost должен принимать тип `category`.

```bash
uv run pytest -q -k TestMakeModels
```

### Шаг 2. `split_train_valid_test`

Три части вместо двух: валидационная нужна для ранней остановки и выбора параметров, тест — для
итоговой оценки. Два режима: случайный (со стратификацией по классам) и по времени. Подводные камни:
при стратификации она нужна в обоих разбиениях; при разбиении по времени сортировка должна быть
устойчивой, а случайности быть не должно вовсе.

```bash
uv run pytest -q -k TestSplit
```

### Шаг 3. `prepare_categoricals`

Каждая библиотека хочет категории в своём виде: XGBoost, LightGBM и scikit-learn — тип `category`,
CatBoost — строки без пропусков. Список категорий берётся только из обучающей части. Подводный камень
pandas 3: `astype` к типу с заданными категориями для значений, которых в списке нет, выдаёт
предупреждение об устаревании — новые значения нужно заранее заменить пропуском
(`values.where(values.isin(known))`). Тест выполняется с `warnings.simplefilter("error")`.

```bash
uv run pytest -q -k TestPrepareCategoricals
```

### Шаг 4. `fit_with_early_stopping`

Главная функция стенда: одна сигнатура поверх четырёх разных API.

| Библиотека | Как задаётся остановка | Валидационные данные | Число итераций после обучения |
|---|---|---|---|
| XGBoost | `early_stopping_rounds` — параметр модели (`set_params`) | `fit(..., eval_set=[(X, y)])` | `best_iteration + 1` |
| LightGBM | `callbacks=[lightgbm.early_stopping(rounds, verbose=False)]` | `fit(..., eval_X=X, eval_y=y)` | `best_iteration_` |
| CatBoost | `fit(..., early_stopping_rounds=rounds)` | `fit(..., eval_set=(X, y))` | `tree_count_` |
| scikit-learn | `early_stopping=True, n_iter_no_change=rounds` | `fit(..., X_val=X, y_val=y)` | `n_iter_` |

Подводные камни:

- **переданную модель менять нельзя.** Обучайте копию (`sklearn.base.clone` работает со всеми четырьмя
  классами). Иначе повторный вызов с той же моделью даст другой результат, а `early_stopping_rounds`
  останется в модели XGBoost навсегда;
- **scikit-learn по умолчанию сам отрезает валидацию** (`validation_fraction=0.1`) от обучающих данных.
  Тогда его модель учится на меньшей выборке и останавливается по другим данным, чем остальные.
  Передавайте свою валидационную часть через `X_val` и `y_val`;
- **«число деревьев» у scikit-learn значит другое.** XGBoost, LightGBM и CatBoost после остановки
  используют деревья до лучшей итерации. `HistGradientBoosting` отката не делает: `n_iter_` — момент
  остановки, включая итерации ожидания. Сравнивая размеры моделей, помните об этом;
- **LightGBM 4.7.0:** `eval_set` выдаёт предупреждение об устаревании, тест
  `test_no_warnings_and_no_files` его не пропустит;
- **свойство для самопроверки:** модель, обученная без остановки ровно на `n_trees` итераций, должна
  давать те же предсказания. У эталона оно выполняется для всех библиотек в регрессии и для трёх
  в классификации. Исключение — классификация в CatBoost: модель на 15 итераций не совпадает с первыми
  15 деревьями модели на 300 итераций (совпадение восстанавливается при `leaf_estimation_iterations=1`).
  Для этого случая тест сравнивает результат с обрезанной длинной моделью (`ntree_end`).

Тест `test_validation_data_define_the_stop` подменяет ответы валидационной части перемешанными: модель,
которая действительно останавливается по валидации, прекращает обучение почти сразу.

```bash
uv run pytest -q -k TestEarlyStopping
```

### Шаг 5. `evaluate`

RMSE для регрессии и log loss для классификации. В тестовой части может не оказаться какого-то класса,
поэтому в `log_loss` нужно передать список классов модели.

```bash
uv run pytest -q -k TestEvaluate
```

### Шаг 6. `benchmark`

Цикл по моделям: подготовить категории под библиотеку, обучить с остановкой, измерить время обучения
и предсказания (`time.perf_counter`), оценить на валидации и тесте. Тест
`test_test_part_does_not_affect_training` запускает стенд дважды — с настоящими ответами теста
и с перепутанными: число деревьев и качество на валидации обязаны совпасть, а качество на тесте —
резко ухудшиться. Если тестовая часть где-то участвует в обучении, это станет видно.

```bash
uv run pytest -q -k TestBenchmark
```

### Шаг 7. `summarize`

Сводка по нескольким наборам: средний ранг, число побед, среднее отношение к лучшему результату,
суммарное время. Ранг нужен потому, что RMSE в миллионах рублей и log loss нельзя усреднять между собой.

```bash
uv run pytest -q -k TestSummarize
uv run python -W error -m pytest -q
```

## Часть 2. Сравнение

```python
from boosting_bench import benchmark, make_models, split_train_valid_test, summarize
from sklearn.datasets import load_breast_cancer

cancer = load_breast_cancer(as_frame=True)
data = split_train_valid_test(cancer.data, cancer.target, random_state=0, stratify=True)
models = make_models("classification", max_trees=2000, learning_rate=0.1, n_jobs=4)
table = benchmark(models, data, "classification", rounds=50)
```

План:

1. **Данные и разбиение.** 60 % / 20 % / 20 %. Если в данных есть время — разбиение по времени.
   Для наборов меньше нескольких тысяч объектов повторите всё для трёх-пяти значений `random_state`
   и усредните: одно разбиение на 178 объектах ничего не доказывает.
2. **Точки отсчёта.** Линейная модель (масштабирование, one-hot для категорий) и случайный лес.
   Они обучаются на той же обучающей части и оцениваются на том же тесте.
3. **Этап 1: без настройки.** `make_models` с общим шагом 0.1, пределом 2000 итераций и остановкой
   после 50 итераций без улучшения. Остальные параметры — по умолчанию.
4. **Этап 2: одинаковый бюджет настройки.** По четыре конфигурации на библиотеку, лучшая выбирается
   по `valid_score` — не по `score`:

   ```python
   grid = [{"max_depth": depth, "min_child_weight": weight} for depth in (3, 6) for weight in (1, 10)]
   candidates = {
       f"xgboost|{i}": make_models(task, max_trees=2000, n_jobs=4, overrides={"xgboost": params})["xgboost"]
       for i, params in enumerate(grid)
   }
   tuned = benchmark(candidates, data, task, rounds=50)
   best = tuned["valid_score"].idxmin()
   ```

   У эталона: XGBoost — `max_depth` 3, 6 × `min_child_weight` 1, 10; LightGBM — `num_leaves` 7, 31 ×
   `min_child_samples` 5, 50; CatBoost — `depth` 4, 6 × `l2_leaf_reg` 3, 10; scikit-learn —
   `max_leaf_nodes` 7, 31 × `min_samples_leaf` 5, 50. Время настройки — сумма по всем конфигурациям.
5. **Категории.** Передайте `cat_features` в `benchmark`. У `HistGradientBoosting` категориальный признак
   может иметь не больше 255 значений: признаки с большей кардинальностью заранее закодируйте
   `prepare_categoricals(..., kind="ordinal")` и запустите эту модель отдельным вызовом `benchmark`.
6. **Сводка.** `summarize` по всем наборам — отдельно для этапа 1 и этапа 2, с точками отсчёта и без.
7. **Заключение.** Одна страница в `README.md` проекта: какую библиотеку вы выбираете для своего набора
   данных и почему. Аргументы — числа из ваших таблиц: качество с разбросом по разбиениям, время
   обучения с учётом настройки, время предсказания, поведение без настройки. Отдельно: при каких
   условиях вы изменили бы решение.

- **линейная модель лучшая на четырёх наборах из восьми**: на двух маленьких настоящих (`diabetes`,

- **CatBoost первый среди бустингов на шести наборах из восьми** и до настройки, и после. Он же самый
  медленный: примерно в 9 раз дольше LightGBM в сумме;

  на этапе 2 — в сетке этапа 2 нет значения `min_samples_leaf` по умолчанию, а выбор из четырёх
  вариантов по 36 валидационным объектам случаен. На наборах в сотни объектов различия между
  библиотеками меньше разброса между разбиениями: приводите разброс, а не одно число;
- **на больших наборах после настройки различия малы:** мошенничество — от 0.0681 до 0.0690, отток — от
  0.5309 до 0.5326. Выбор библиотеки здесь определяется не качеством;
- **предел итераций нужно проверять.** CatBoost на `digits` дошёл до 2000 итераций: остановка
  не сработала, модель недообучена, и сравнение на этом наборе занижает его результат. Если `n_trees`
  равно `max_trees`, увеличьте предел;
- **числа итераций несравнимы напрямую:** симметричное дерево CatBoost слабее дерева LightGBM, поэтому
  их нужно больше; у scikit-learn в число входят итерации ожидания.

## Критерии приёмки

- [ ] `uv run pytest -q` — все 85 тестов проходят, полный прогон занимает меньше 60 секунд
      (эталон — 6 секунд);
- [ ] `uv run python -W error -m pytest -q` проходит: код не вызывает предупреждений библиотек;
- [ ] `uv run ruff check .` проходит без ошибок;
- [ ] в репозитории нет папки `catboost_info`, сохранённых моделей и скачанных данных;
- [ ] сравнение выполнено минимум на четырёх наборах: два встроенных, один из данных курса и настоящий
      набор по вашему выбору (не меньше 10 тысяч объектов, с категориальными признаками);
- [ ] у всех библиотек одинаковые разбиения, общая валидационная часть для остановки и одинаковый
      бюджет настройки; параметры выбраны по `valid_score`;
- [ ] в таблицах есть линейная модель и случайный лес;
- [ ] для каждого набора приведены качество, время обучения, время предсказания и число итераций;
      для маленьких наборов — разброс по разбиениям;
- [ ] заключение называет библиотеку для вашей задачи, опирается на числа из таблиц и указывает
      условия, при которых решение изменится.

## Как оценить свою работу

| Уровень | Признаки |
|---|---|
| Базовый | все тесты проходят; есть таблицы этапов 1 и 2 и сводка |
| Уверенный | вы можете по памяти написать раннюю остановку для каждой из четырёх библиотек и объяснить, чем различается «число деревьев» после неё; в заключении есть разброс по разбиениям и сравнение с точками отсчёта |
| Продвинутый | выполнено хотя бы два задания из раздела ниже |

## Идеи для усложнения

1. **Доверительные интервалы.** Повторите сравнение для десяти разбиений и для каждой пары библиотек
   посчитайте долю разбиений, в которых первая лучше второй. Какие различия из таблицы ориентиров
   значимы?
2. **Кривая «качество — время».** Для каждой библиотеки постройте качество на валидации как функцию
   времени обучения (по итерациям). Какая библиотека лучше при бюджете 1 секунда? 10 секунд?
3. **Размер выборки.** Обучите модели на 1, 3, 10, 30 и 100 % обучающей части настоящего набора.
   Меняется ли порядок библиотек с ростом данных? Сравните с таблицей из урока 4.3.3.
4. **Кодирование категорий как параметр.** Добавьте в стенд способ кодирования: для LightGBM и XGBoost
   сравните встроенную обработку, порядковое кодирование и упорядоченные статистики из урока 4.3.3.
5. **Время предсказания одного объекта.** Измерьте время предсказания для одной строки и для пакета
   в 100 тысяч строк. Сохраните модели и сравните размеры файлов.
6. **Другая метрика.** Добавьте в `evaluate` ROC-AUC и PR-AUC. Меняется ли вывод, если библиотеки
   сравнивать по ранжированию, а не по вероятностям?
7. **Калибровка.** Для задач классификации постройте диаграммы надёжности четырёх моделей (урок 3.2.2).
   Какая библиотека лучше откалибрована без дополнительных усилий?
