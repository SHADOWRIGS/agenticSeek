## 3. Hyperopt

Hyperopt — библиотека, в которой появился TPE. Интерфейс — одна функция `fmin`:

```python
from hyperopt import STATUS_OK, Trials, fmin, hp, space_eval, tpe
from hyperopt.pyll import scope

space = {
    "num_leaves": scope.int(hp.qloguniform("num_leaves", np.log(4), np.log(64), 1)),
    "colsample_bytree": hp.uniform("colsample_bytree", 0.4, 1.0),
    "reg_lambda": hp.loguniform("reg_lambda", np.log(1e-3), np.log(100.0)),
}


def objective(params):
    return {"loss": evaluate(params), "status": STATUS_OK}


trials = Trials()
best = fmin(
    objective, space, algo=tpe.suggest, max_evals=40, trials=trials,
    rstate=np.random.default_rng(0), show_progressbar=False,
)
```

| Понятие | Смысл |
|---|---|
| `space` | пространство поиска: словарь (или вложенная структура) из выражений `hp.*`; описывается заранее |
| `hp.uniform`, `hp.loguniform` | вещественный параметр; у `loguniform` границы задаются **логарифмами** |
| `hp.quniform`, `hp.qloguniform` | то же с округлением до шага; результат — `float` |
| `hp.choice(label, options)` | выбор из списка; элементы списка могут быть вложенными пространствами |
| `scope.int(...)` | приводит значение к целому до вызова целевой функции |
| `algo` | `tpe.suggest`, `rand.suggest` (случайный поиск), `anneal.suggest` (отжиг) |
| `Trials` | история: `trials.losses()`, `trials.best_trial`, `trials.trials` |
| `fmin` | минимизирует всегда; для максимизации возвращают метрику со знаком минус |

Результат за 12 с:

```python
best                       # {'colsample_bytree': 0.981, 'num_leaves': 13.0, 'reg_lambda': 0.0032}
space_eval(space, best)    # {'colsample_bytree': 0.981, 'num_leaves': 13, 'reg_lambda': 0.0032}
min(trials.losses())       # 0.6277
trials.best_trial["tid"]   # 26
```

Подводные камни, на которые наступают все:

- **`fmin` возвращает сырые значения, а не параметры.** `num_leaves` равно `13.0`: `scope.int` применяется
  только при вызове целевой функции. Для `hp.choice` возвращается **номер** варианта. Настоящие параметры даёт
  `space_eval(space, best)`;
- **границы `loguniform` — логарифмы.** `hp.loguniform("reg_lambda", 1e-3, 100)` означает диапазон от
  $e^{0.001}$ до $e^{100}$;
- **метка параметра** (первый аргумент `hp.*`) должна быть уникальной во всём пространстве;
- **первые 20 попыток `tpe.suggest` случайны** (в Optuna — 10). В едином эксперименте запуски Hyperopt с TPE и
  со случайным поиском при `seed=0` вернули одну и ту же лучшую точку: она нашлась в первых двадцати попытках,
  и оставшиеся тридцать попыток TPE её не улучшили.

### Условные пространства

Условность описывается вложенностью внутри `hp.choice`:

```python
cond_space = hp.choice("model", [
    {"model": "ridge", "alpha": hp.loguniform("ridge_alpha", np.log(1e-3), np.log(1e3))},
    {"model": "lightgbm", "num_leaves": scope.int(hp.qloguniform("lgbm_num_leaves", np.log(4), np.log(128), 1))},
])
best = fmin(cond_objective, cond_space, algo=tpe.suggest, max_evals=30, trials=Trials(),
            rstate=np.random.default_rng(0), show_progressbar=False)
best                            # {'lgbm_num_leaves': 13.0, 'model': 1}
space_eval(cond_space, best)    # {'model': 'lightgbm', 'num_leaves': 13}
```

За 30 попыток линейная модель проверена 11 раз, LightGBM — 19 (в похожем примере урока 4.4.2 Optuna проверила
её 6 раз из 30).

### Что ещё есть и чего нет

- остановка всего подбора при отсутствии улучшений: `early_stop_fn=no_progress_loss(15)` из
  `hyperopt.early_stop`. При `max_evals=200` подбор остановился после 25 попыток с результатом 0.6323 — хуже,
  чем 0.6277 за 40 попыток: правило «15 попыток без улучшения» для шумной функции слишком строгое;
- отсечения отдельных попыток (pruning) нет; параллельный запуск — через `SparkTrials` (кластер Spark) и
  `MongoTrials` (общая база MongoDB). В уроке они не запускались;
- хранилища с возобновлением «из коробки» нет: объект `Trials` сохраняют сами (`pickle`).

## 4. SMAC

SMAC (Sequential Model-based Algorithm Configuration) — байесовская оптимизация, в которой суррогатная модель
— **случайный лес**. Лес предсказывает значение целевой функции по конфигурации, а разброс предсказаний
деревьев служит оценкой неопределённости; следующая точка выбирается по ожидаемому улучшению.

Чем это отличается от TPE:

- лес естественно работает с категориальными и условными параметрами и с их взаимодействиями (TPE по умолчанию
  рассматривает параметры независимо);
- SMAC создавался для настройки алгоритмов на наборах задач: он умеет сравнивать конфигурации на нескольких
  seed или экземплярах задачи и не тратить повторы на заведомо худшие (intensification). При
  `deterministic=True` каждая конфигурация вычисляется один раз;
- пространство описывается отдельным объектом `ConfigurationSpace` с явными условиями.

```python
from ConfigSpace import Categorical, ConfigurationSpace, EqualsCondition, Float, Integer
from smac import HyperparameterOptimizationFacade, Scenario

cs = ConfigurationSpace(seed=0)
model = Categorical("model", ["ridge", "lightgbm"])
alpha = Float("ridge_alpha", (1e-3, 1e3), log=True)
leaves = Integer("num_leaves", (4, 128), log=True)
cs.add([model, alpha, leaves])
cs.add([EqualsCondition(alpha, model, "ridge"), EqualsCondition(leaves, model, "lightgbm")])


def target(config, seed: int = 0) -> float:
    if config["model"] == "ridge":
        return cv_score(make_pipeline(ridge_prep, Ridge(alpha=config["ridge_alpha"])))
    return cv_score(lgb.LGBMRegressor(**(FIXED | {"num_leaves": int(config["num_leaves"])})))


scenario = Scenario(cs, n_trials=30, deterministic=True, seed=0, output_directory="smac_out/cond")
facade = HyperparameterOptimizationFacade(scenario, target, overwrite=True, logging_level=30)
incumbent = facade.optimize()
dict(incumbent)                                # {'model': 'lightgbm', 'num_leaves': 17}
facade.runhistory.get_cost(incumbent)          # 0.6333
```

За 30 попыток (11 с): линейная модель — 12 раз, LightGBM — 18. Конфигурация ветви `ridge` содержит только
`model` и `ridge_alpha`: неактивных параметров в ней нет.

Что нужно знать:

- **facade** — готовая сборка компонентов. `HyperparameterOptimizationFacade` — случайный лес;
  `BlackBoxFacade` — гауссовский процесс для небольших непрерывных пространств; `MultiFidelityFacade` —
  Hyperband поверх суррогатной модели (раздел 6);
- SMAC пишет журнал и историю в `output_directory` — добавьте папку в `.gitignore`;
- накладные расходы выше, чем у TPE: в едином эксперименте 50 попыток заняли 29 с против 16 с у Optuna. При
  попытке длиной в минуты это несущественно, при попытке в доли секунды — заметно.

## 5. Встроенные средства scikit-learn

### RandomizedSearchCV

```python
from scipy.stats import loguniform, uniform
from sklearn.model_selection import RandomizedSearchCV

distributions = {
    "num_leaves": sorted({int(v) for v in np.geomspace(4, 64, 40).round()}),
    "min_child_samples": sorted({int(v) for v in np.geomspace(5, 100, 40).round()}),
    "subsample": uniform(0.5, 0.5),              # uniform(loc, scale): от 0.5 до 1.0
    "colsample_bytree": uniform(0.4, 0.6),
    "reg_lambda": loguniform(1e-3, 100.0),
    "reg_alpha": loguniform(1e-3, 10.0),
}
search = RandomizedSearchCV(
    lgb.LGBMRegressor(**FIXED), distributions, n_iter=50, cv=FOLDS,
    scoring="neg_root_mean_squared_error", random_state=0, refit=False,
).fit(X_train, y_train)
```

Распределение — объект с методом `rvs` (подходят распределения `scipy.stats`) или список значений.
`loguniform` возвращает вещественные числа, поэтому целый параметр в логарифмической шкале проще задать
списком: значения `np.geomspace`, округлённые до целых. Условных пространств и использования истории нет; зато
не нужны зависимости и работает всё, что работает с `Pipeline`.

### Successive halving

Идея: не тратить полный бюджет на каждого кандидата. Все кандидаты оцениваются на малом **ресурсе** (часть
данных, малое число деревьев), лучшая доля $1/\eta$ переходит на следующую ступень с ресурсом в $\eta$ раз
больше, и так до полного ресурса.

```python
from sklearn.experimental import enable_halving_search_cv  # noqa: F401
from sklearn.model_selection import HalvingRandomSearchCV

search = HalvingRandomSearchCV(
    lgb.LGBMRegressor(**FIXED), distributions, n_candidates=150, factor=3,
    resource="n_estimators", max_resources=100, min_resources=11,
    cv=FOLDS, scoring="neg_root_mean_squared_error", random_state=0, refit=False,
).fit(X_train, y_train)
search.n_candidates_, search.n_resources_       # [150, 50, 17], [11, 33, 99]
```

В scikit-learn 1.9.1 эти классы всё ещё экспериментальные: без строки
`from sklearn.experimental import enable_halving_search_cv` импорт завершается ошибкой `ImportError`.

150 кандидатов на 11 деревьях, 50 лучших — на 33, 17 лучших — на 99. В пересчёте на деревья это
$(150 \cdot 11 + 50 \cdot 33 + 17 \cdot 99) / 100 = 49.8$ полных обучений: втрое больше кандидатов за цену 50
попыток. Две оговорки, обе подтверждены измерением:

- **ресурс — не время.** Тот же «бюджет» занял 38 с против 16–17 с у обычного случайного поиска: обучение на
  11 деревьях не в девять раз быстрее, чем на 99, — подготовка данных одинакова при любом числе деревьев;
- **ранний результат должен предсказывать итоговый.** Конфигурация, лучшая на 11 деревьях, не обязана быть
  лучшей на 99, — та же проблема, что с отсечением по кривой обучения в уроке 4.4.2. В едином эксперименте
  halving не лучше обычного случайного поиска.

Ресурсом может быть объём данных. `HalvingGridSearchCV` на сетке из 45 конфигураций с `resource="n_samples"`,
`min_resources=300`:

| Ступень | Кандидатов | Объектов |
|---|---|---|
| 1 | 45 | 300 |
| 2 | 15 | 900 |
| 3 | 5 | 2 700 |

Стоимость — около 12 обучений на полной выборке вместо 45, время — 8 с. `best_score_` (0.6914) посчитан на
последней ступени, то есть на 2 700 объектах, и не сравним с оценками на всей выборке: у выбранной
конфигурации обычная кросс-валидация даёт 0.6407.

## 6. Идеи алгоритмов

**Successive halving** требует выбрать число кандидатов $n$ при фиксированном бюджете: много кандидатов на
малом ресурсе (агрессивно, риск отсечь «медленно стартующих») или мало на большом (надёжно, но мало охвата).
Правильный выбор зависит от задачи и заранее неизвестен.

**Hyperband** снимает этот выбор перебором: запускает несколько successive halving с разными $n$ — от самого
агрессивного до обычного случайного поиска на полном ресурсе — и делит бюджет между ними. Потери — не больше
небольшого множителя по сравнению с лучшим из вариантов. В Optuna это `HyperbandPruner`, в SMAC —
`MultiFidelityFacade`, в Ray Tune — планировщик ASHA (асинхронный вариант).

**BOHB** (Bayesian Optimization + Hyperband) заменяет случайный выбор кандидатов в Hyperband выбором по модели
в духе TPE: на ранних ступенях работает Hyperband, по мере накопления результатов кандидаты всё чаще
предлагает модель. Комбинация «TPE + `HyperbandPruner`» в Optuna — то же по смыслу.

**Эволюционные стратегии** поддерживают не одну точку, а распределение. **CMA-ES**: на каждом поколении из
многомерного нормального распределения выбирается популяция точек, лучшие определяют новое среднее и новую
ковариационную матрицу — распределение сдвигается и вытягивается вдоль «долины» функции. Сильная сторона —
непрерывные параметры с зависимостями между ними и бюджет в сотни и тысячи вычислений; слабая — категориальные
и условные параметры (`CmaEsSampler` в Optuna для них использует другой алгоритм) и малые бюджеты: популяции
нужно несколько поколений.

**Population-based training (PBT)** подбирает не значения, а **расписание** гиперпараметров во время одного
обучения. Популяция моделей обучается параллельно; периодически худшие копируют веса и параметры лучших
(exploit) и случайно меняют параметры (explore). Нужна возможность продолжить обучение с контрольной точки,
поэтому PBT — инструмент для нейросетей и обучения с подкреплением (модули 5 и 8), а не для бустинга.
Реализация — в Ray Tune.

| Идея | Когда полезна | Когда нет |
|---|---|---|
| случайный поиск | точка отсчёта; малый бюджет; много параллельных исполнителей | — |
| TPE, SMAC | бюджет от 30–50 попыток, смешанные и условные пространства | попытка стоит миллисекунды |
| гауссовский процесс | очень дорогие попытки, до ~20 непрерывных параметров | категории, тысячи попыток |
| halving, Hyperband, BOHB | есть дешёвый ресурс, и ранний результат предсказывает итоговый | шаг обучения в пространстве поиска |
| CMA-ES | непрерывные параметры, большой бюджет | категории, 20–50 попыток |
| PBT | долгое обучение нейросетей, нужны расписания | модели без контрольных точек |

## 7. Другие инструменты

**Ray Tune** — в первую очередь исполнитель: распределяет попытки по ядрам, GPU и машинам кластера,
останавливает бесперспективные (ASHA, PBT), переживает сбои. Сами алгоритмы выбора точек он берёт из других
библиотек, включая Optuna и Hyperopt. Ниша — подбор для нейросетей на кластере. Не запускался.

**Nevergrad** — библиотека оптимизации без производных: эволюционные стратегии, дифференциальная эволюция, рой
частиц и «мета-оптимизатор» `NGOpt`, выбирающий алгоритм по размерности и бюджету. Ниша — непрерывные и
смешанные задачи с большим бюджетом, не только машинное обучение. Проверено на тестовой функции двух
переменных: за 60 вычислений получено значение 0.0005 при минимуме 0.

**scikit-optimize** — байесовская оптимизация на гауссовских процессах с интерфейсом в стиле scikit-learn
(`gp_minimize`, `BayesSearchCV`). Версия 0.10.2 установилась и за 25 вычислений дошла до значения 0.0002 на
той же тестовой функции. Библиотека развивается медленно; для новых проектов похожие возможности есть в Optuna
(`GPSampler`, которому нужен `torch`).

**Ax и BoTorch** — байесовская оптимизация на гауссовских процессах поверх PyTorch: ограничения, несколько
критериев, параллельные пакеты попыток, шумные наблюдения. Ниша — действительно дорогие эксперименты (часы на
попытку, бюджет в десятки попыток), в том числе не модельные: A/B-тесты, настройка систем. Тяжёлые
зависимости; для подбора параметров бустинга избыточны. Не запускались.

## 8. Единый эксперимент

Одна задача (раздел 2), одно пространство из шести параметров, один бюджет — 50 вычислений целевой функции,
пять запусков с разными seed. Для halving бюджет — 49.8 в пересчёте на деревья. Оценка на кросс-валидации у
всех инструментов пересчитана одной и той же функцией `evaluate`; тест — модель с лучшими параметрами,
обученная на всей обучающей части. Четыре запуска шли параллельно на четырёх ядрах.

Как читать таблицу.

**Мерило шума — три случайных поиска.** Optuna, Hyperopt и scikit-learn реализуют один и тот же алгоритм, а
средние различаются на 0.003 (0.6258, 0.6277, 0.6289) при разбросе между запусками 0.003–0.009. Различия
такого размера между инструментами ничего не значат.

**Алгоритмы с моделью лучше случайного поиска на кросс-валидации** на 0.005–0.010: 0.618–0.623 против
0.626–0.629. Это около одного стандартного отклонения — эффект есть, но небольшой. При этом у Optuna TPE один
запуск из пяти (0.6294) хуже среднего случайного поиска.

**Между алгоритмами с моделью различий нет.** Optuna TPE, Hyperopt TPE, SMAC и CMA-ES укладываются в 0.005 —
столько же, сколько три реализации случайного поиска. Вывода «TPE из Optuna лучше TPE из Hyperopt» эта таблица
не поддерживает.

**На тесте порядок другой.** SMAC — в тройке лучших на кросс-валидации и предпоследний на тесте;
`RandomizedSearchCV` — последний на кросс-валидации и второй на тесте. Стандартное отклонение тестовых
значений — до 0.015, поэтому различия между инструментами на тесте (0.677–0.694) статистически не
подтверждены. На кросс-валидации любой подбор заметно лучше параметров по умолчанию (0.6485); на тесте все
средние тоже лучше (0.6958), но у худшего варианта — всего на 0.002.

**Время определяется целевой функцией**, а не оптимизатором: 15–18 с у шести вариантов. Исключения — SMAC
(обучение суррогатного леса на каждой попытке) и halving (много мелких обучений).

Вывод тот же, что в уроке 4.4.2, но теперь для инструментов: **при равном бюджете различия между разумными
оптимизаторами меньше шума оценки.** Выбирать инструмент по качеству на одной задаче бессмысленно; выбирать
нужно по возможностям.

## 10. Рекомендации

1. **По умолчанию — Optuna:** TPE, фиксированные фолды, отсечение по фолдам, SQLite. Причина — не качество
   поиска (оно как у остальных), а удобство: условные пространства обычным кодом, возобновление, параллельный
   запуск, анализ истории.
2. **Модель целиком в `Pipeline` scikit-learn, параметров два-три, бюджет до 30 попыток —**
   `RandomizedSearchCV`. Лишняя зависимость ничего не даст.
3. **Halving и Hyperband — когда есть дешёвый ресурс и ранний результат надёжен:** объём данных, число эпох
   при фиксированном шаге. Не число деревьев при подбираемом шаге.
4. **Hyperopt — когда он уже есть:** в существующем коде или в инфраструктуре на Spark. Переписывать
   работающий подбор на Optuna ради качества незачем.
5. **SMAC — для больших пространств с категориями и условиями** (выбор модели вместе с её параметрами, десятки
   параметров) и для настройки на наборе задач.
6. **Ray Tune — когда узкое место в исполнении:** кластер, GPU, длинные обучения нейросетей, PBT.
7. **Ax/BoTorch — когда попытка стоит часы** и их будет несколько десятков.

Когда менять инструмент: когда не хватает возможности (условий, отсечения, кластера), а не когда на одном
запуске другой инструмент дал на 0.003 лучше. Гораздо больше, чем смена оптимизатора, дают: правильное
пространство поиска (диапазоны, логарифмические шкалы), ранняя остановка, надёжная оценка (больше фолдов,
повторы) и признаки.

## 11. AutoML

AutoML-системы (auto-sklearn, AutoGluon, FLAML, H2O AutoML, LightAutoML) автоматизируют всю цепочку темы:
подготовку признаков, выбор семейства моделей, подбор гиперпараметров и построение ансамбля. Внутри — те же
идеи: условное пространство «модель → её параметры», байесовская оптимизация (auto-sklearn построен на SMAC),
successive halving, стекинг на out-of-fold предсказаниях (на нём основан AutoGluon). Тяжёлые библиотеки в
уроке не запускались.

Когда уместен:

- сильная точка отсчёта за час машинного времени вместо дня ручной работы;
- много однотипных задач, на каждую из которых нет времени;
- проверка себя: если AutoML с бюджетом в час обгоняет вашу модель, вы что-то упустили.

Почему не заменяет понимания:

- AutoML оптимизирует ту метрику и на той валидации, которые вы ему дали. Утечка, неверное разбиение (без
  учёта времени и групп), метрика, не связанная с целью бизнеса, — всё это он добросовестно оптимизирует.
  Ошибки постановки дороже ошибок подбора;
- результат — обычно ансамбль из десятков моделей: вопросы урока 4.4.1 о цене предсказания, поддержке и
  объяснимости встают в полный рост;
- признаки, знание предметной области и качество данных автоматизации почти не поддаются, а именно они дают
  основной прирост (модуль 2);
- чтобы понять, почему AutoML ошибся, нужно знать всё, что он делает внутри.

## Типичные ошибки

| Симптом | Причина | Решение |
|---|---|---|
| Hyperopt вернул `num_leaves=13.0` или номер вместо названия | `fmin` возвращает сырые значения | `space_eval(space, best)` |
| Hyperopt перебирает абсурдно большие значения | в `hp.loguniform` переданы границы, а не их логарифмы | `np.log(low)`, `np.log(high)` |
| Подбор на Hyperopt падает под `-W error` | `DeprecationWarning` от `numpy 2.5` в `tpe.py` | точечный `warnings.filterwarnings` |
| `ImportError` при импорте `HalvingRandomSearchCV` | класс экспериментальный | `from sklearn.experimental import enable_halving_search_cv` |
| `best_score_` у halving хуже, чем у обычного поиска | оценка посчитана на последней ступени ресурса | пересчитать лучшую конфигурацию обычной кросс-валидацией |
| Halving «с тем же бюджетом» работает дольше | ресурс считается в деревьях или объектах, а не в секундах | сравнивать по времени |
| `LGBMRegressor` падает на `num_leaves=12.7` | `loguniform` даёт вещественные числа | список целых из `np.geomspace` |
| «Инструмент А лучше Б» по одному запуску | разница меньше разброса между seed | несколько запусков; сравнение с тремя реализациями случайного поиска |
