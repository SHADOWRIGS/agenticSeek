## 1. Подбор гиперпараметров как оптимизация

Целевая функция подбора — «качество на кросс-валидации как функция гиперпараметров». У неё три свойства,
которые определяют всё остальное:

- **дорогая:** одно вычисление — это несколько обучений модели;
- **шумная:** значение зависит от разбиения на фолды и от seed модели;
- **чёрный ящик:** производных нет, вид зависимости неизвестен, параметры разнотипны (целые, вещественные,
  категориальные, условные).

Задача урока: цены квартир из темы 4.2 (3 500 в обучении, 1 500 в тесте), LightGBM. Шаг обучения зафиксирован
на 0.1, число деревьев определяет ранняя остановка, фолды одни и те же для всех попыток.

```python
FOLDS = list(KFold(5, shuffle=True, random_state=0).split(X_train))
FIXED = {"n_estimators": 2000, "learning_rate": 0.1, "subsample_freq": 1, "random_state": 0, "n_jobs": 1, "verbose": -1}


def cv_rmse(params, trial=None):
    scores, trees = [], []
    for step, (train_idx, valid_idx) in enumerate(FOLDS):
        model = lgb.LGBMRegressor(**(FIXED | params))
        model.fit(
            X_train.iloc[train_idx],
            y_train[train_idx],
            eval_X=X_train.iloc[valid_idx],
            eval_y=y_train[valid_idx],
            callbacks=[lgb.early_stopping(30, verbose=False)],
        )
        scores.append(root_mean_squared_error(y_train[valid_idx], model.predict(X_train.iloc[valid_idx])))
        trees.append(model.best_iteration_)
        if trial is not None:                      # pruning, раздел 6
            trial.report(float(np.mean(scores)), step)
            if trial.should_prune():
                raise optuna.TrialPruned()
    return float(np.mean(scores)), int(np.mean(trees))
```

Параметры по умолчанию: RMSE 0.6439 на кросс-валидации (123 дерева), 0.6978 на тесте. Одно вычисление функции
занимает 0.4–1 с.

## 2. Сетка и случайный поиск

Сетка перебирает все комбинации заранее выбранных значений. Случайный поиск берёт столько же точек, но каждую
— случайно из диапазонов. Три параметра, 27 вычислений: сетка 3 × 3 × 3 (`num_leaves` 4, 23, 128; `reg_alpha`
0.001, 0.1, 10; `subsample` 0.5, 0.75, 1.0) против 27 случайных точек из тех же диапазонов (`num_leaves` и
`reg_alpha` — в логарифмической шкале).

| | Лучший RMSE на кросс-валидации |
|---|---|
| Сетка | 0.6191 |
| Случайный поиск, 20 запусков с разными seed | медиана 0.6125, от 0.6090 до 0.6166 |

Случайный поиск лучше сетки **во всех 20 запусках**. Причина — в устройстве функции. По всем 540 случайным
точкам корреляция RMSE с логарифмом `num_leaves` равна 0.82, с логарифмом `reg_alpha` — −0.14, с `subsample` —
−0.10: важен в основном один параметр.

| `num_leaves` | 4–5 | 6–7 | 8–10 | 11–14 | 15–20 | 21–32 | 33–64 | 65–128 |
|---|---|---|---|---|---|---|---|---|
| Лучший RMSE | 0.6131 | 0.6091 | 0.6090 | 0.6148 | 0.6195 | 0.6206 | 0.6268 | 0.6283 |
| Медиана | 0.6230 | 0.6181 | 0.6180 | 0.6215 | 0.6258 | 0.6323 | 0.6428 | 0.6494 |

Оптимум — 6–10 листьев. Сетка проверила три значения важного параметра (4, 23, 128) по девять раз каждое и
оптимум не накрыла. Случайный поиск за те же 27 вычислений проверил около 22 разных значений `num_leaves`.
Сетка тратит попытки на перебор неважных параметров при одних и тех же значениях важного; случайный поиск
каждой попыткой получает новое значение каждого параметра. **Вывод:** когда важных параметров мало и заранее
неизвестно, какие именно, случайный поиск при том же бюджете лучше сетки. Сетка уместна для одного-двух
параметров, которые нужно просмотреть полностью.

## 3. Байесовская оптимизация

Случайный поиск не использует результаты прошлых попыток. Байесовская оптимизация использует:

1. по уже вычисленным точкам строится **суррогатная модель** — дешёвое приближение целевой функции, которое
   даёт не только прогноз, но и неопределённость;
2. **функция выбора** (acquisition function) оценивает для каждой точки-кандидата, насколько выгодно вычислить
   функцию именно там; выбирается лучшая;
3. целевая функция вычисляется, точка добавляется в историю, цикл повторяется.

Функция выбора балансирует **использование** (проверять рядом с лучшими найденными точками) и **исследование**
(проверять там, где суррогатная модель не уверена). Чистое использование застревает в первом удачном месте,
чистое исследование — это случайный поиск.

### TPE

Классический суррогат — гауссовский процесс; он плохо работает с категориальными и условными параметрами. TPE
(Tree-structured Parzen Estimator), алгоритм Optuna и Hyperopt по умолчанию, устроен иначе:

1. первые `n_startup_trials` попыток (по умолчанию 10) — случайные;
2. история делится на «хорошие» точки (лучшая доля $\gamma$) и «плохие» (остальные). В Optuna число хороших —
   $\min(\lceil 0.1 n \rceil, 25)$;
3. по хорошим точкам строится плотность $l(x)$, по плохим — $g(x)$: сглаженные гистограммы (ядерные оценки)
   значений каждого параметра;
4. из $l(x)$ выбирается `n_ei_candidates` кандидатов (по умолчанию 24), и берётся тот, у которого отношение
   $l(x) / g(x)$ наибольшее: «похож на хорошие, не похож на плохие».

Что из этого следует на практике:

- TPE моделирует не значение функции, а распределение параметров у хороших попыток. Шум ему не страшен,
  категориальные и условные параметры — естественны;
- по умолчанию плотности строятся для каждого параметра отдельно: взаимодействия параметров TPE не видит.
  `TPESampler(multivariate=True)` строит совместную плотность;
- первые 10 попыток `TPESampler(seed=s)` и `RandomSampler(seed=s)` совпадают; преимущество появляется позже.
  При бюджете в 20 попыток байесовская оптимизация — почти случайный поиск.

## 4. Optuna: study, trial, objective

```python
def suggest(trial):
    return {
        "num_leaves": trial.suggest_int("num_leaves", 4, 128, log=True),
        "min_child_samples": trial.suggest_int("min_child_samples", 5, 100, log=True),
        "subsample": trial.suggest_float("subsample", 0.5, 1.0),
        "colsample_bytree": trial.suggest_float("colsample_bytree", 0.4, 1.0),
        "reg_lambda": trial.suggest_float("reg_lambda", 1e-3, 100.0, log=True),
        "reg_alpha": trial.suggest_float("reg_alpha", 1e-3, 10.0, log=True),
    }


def objective(trial):
    score, n_trees = cv_rmse(suggest(trial))
    trial.set_user_attr("n_trees", n_trees)
    return score


optuna.logging.set_verbosity(optuna.logging.WARNING)
study = optuna.create_study(direction="minimize", sampler=optuna.samplers.TPESampler(seed=0))
study.optimize(objective, n_trials=100)
study.best_value, study.best_params, study.best_trial.user_attrs
```

- **study** — один процесс подбора: история попыток, направление (`direction="minimize"` или `"maximize"`),
  алгоритм выбора точек (`sampler`), алгоритм отсечения (`pruner`);
- **trial** — одна попытка. Через него целевая функция запрашивает значения параметров;
- **objective** — ваша функция: получает `trial`, возвращает число.

| Метод | Что возвращает |
|---|---|
| `suggest_float(name, low, high)` | вещественное из отрезка |
| `suggest_float(..., log=True)` | то же в логарифмической шкале — для параметров, меняющихся на порядки |
| `suggest_int(name, low, high, log=False, step=1)` | целое |
| `suggest_categorical(name, choices)` | одно из значений списка |

Логарифмическая шкала нужна там, где важно отношение, а не разность: между `reg_lambda` 0.001 и 0.01 разница
такая же, как между 10 и 100. Без `log=True` 90 % попыток пришлись бы на значения от 10 до 100.

Результат: 100 попыток за 70 с, лучшая — № 93.

| Попытка | RMSE | `num_leaves` | `min_child_samples` | `colsample_bytree` | `subsample` | `reg_lambda` | `reg_alpha` | Деревьев |
|---|---|---|---|---|---|---|---|---|
| 93 | 0.6040 | 9 | 10 | 0.861 | 0.785 | 1.38 | 0.024 | 228 |
| 95 | 0.6069 | 8 | 10 | 0.882 | 0.780 | 1.91 | 0.031 | 245 |

Лучшее значение за первые 10 попыток — 0.6328, за 25 — 0.6241, за 50 — 0.6102, за 100 — 0.6040. Итоговая
модель обучается на всей обучающей части с числом деревьев из `user_attrs` — на тесте 0.6732 против 0.6978 у
параметров по умолчанию. Таблица получена из `study.trials_dataframe()`: по строке на попытку, столбцы
`number`, `value`, `datetime_start`, `datetime_complete`, `duration`, `params_*`, `user_attrs_*`, `state`.

## 5. Условные пространства, алгоритмы выбора точек, воспроизводимость

Пространство поиска в Optuna не описывается заранее — оно возникает по ходу выполнения целевой функции.
Обычный `if` делает параметр условным:

```python
def objective_cond(trial):
    kind = trial.suggest_categorical("model", ["ridge", "lightgbm"])
    if kind == "ridge":
        model = make_pipeline(ridge_prep, Ridge(alpha=trial.suggest_float("ridge_alpha", 1e-3, 1e3, log=True)))
    else:
        params = {"num_leaves": trial.suggest_int("num_leaves", 4, 128, log=True)}
        if trial.suggest_categorical("use_subsample", [True, False]):
            params["subsample"] = trial.suggest_float("subsample", 0.5, 0.95)
        model = lgb.LGBMRegressor(**(FIXED | {"n_estimators": 200} | params))
    return -cross_val_score(model, X_train, y_train, cv=FOLDS, scoring="neg_root_mean_squared_error").mean()
```

За 30 попыток линейная модель была выбрана 6 раз (лучший результат 1.014), LightGBM — 24 раза (0.6162): TPE
сам перестал тратить попытки на заведомо худшую ветвь. В `trials_dataframe()` параметр, которого в попытке не
было, равен `NaN`. Имя параметра должно всегда означать одно и то же: один диапазон и одна шкала.

Алгоритм задаётся параметром `sampler`: `TPESampler` (по умолчанию), `RandomSampler` (случайный поиск — точка
отсчёта для любого сравнения), `GridSampler` и `BruteForceSampler` (сетка и полный перебор), `CmaEsSampler`
(эволюционная стратегия CMA-ES, урок 4.4.3; нужен пакет `cmaes`), `GPSampler` (гауссовский процесс; нужен
`torch`), `QMCSampler` (квазислучайные последовательности; помечен экспериментальным), `NSGAIISampler`
(генетический алгоритм для нескольких критериев). Воспроизводимость требует трёх условий: `seed` у sampler,
фиксированные фолды и seed модели, последовательное выполнение. При параллельном запуске порядок завершения
попыток зависит от времени, и история перестаёт быть воспроизводимой.

## 6. Pruning: ранняя остановка бесперспективных попыток

Попытка сообщает промежуточные результаты (`trial.report(value, step)`), а pruner решает, стоит ли продолжать
(`trial.should_prune()`). Если нет — целевая функция бросает `optuna.TrialPruned`.

| `pruner` | Правило |
|---|---|
| `MedianPruner(n_startup_trials, n_warmup_steps)` | остановить, если промежуточное значение хуже медианы прошлых попыток на том же шаге |
| `SuccessiveHalvingPruner(min_resource, reduction_factor)` | на каждой ступени ресурса продолжает лучшая доля $1/\eta$ попыток |
| `HyperbandPruner(min_resource, max_resource, reduction_factor)` | несколько successive halving с разной агрессивностью (урок 4.4.3) |

### По фолдам

Шаг — номер фолда: в `cv_rmse` выше после каждого фолда сообщается среднее по пройденным. Попытка, которая
после первого фолда хуже медианы остальных, остальные четыре не считает. Pruner задаётся при создании study:
`pruner=optuna.pruners.MedianPruner(n_startup_trials=10, n_warmup_steps=0)`; целевая функция передаёт свой
`trial` в `cv_rmse`. Среднее по пяти запускам с разными seed, 200 попыток:

| | Отсечено попыток | Время, с | Лучший RMSE на кросс-валидации | RMSE на тесте |
|---|---|---|---|---|
| TPE | 0 | 147 | 0.6007 | 0.6705 |
| TPE + `MedianPruner` | 80 | 91 | 0.6003 | 0.6645 |

Время сократилось на 38 % без потери качества. Отсечение по фолдам безопасно: все попытки сравниваются на
одних и тех же данных, а фолды равноправны.

### По итерациям бустинга

Интеграции с библиотеками вынесены в пакет `optuna-integration`. Импорт из `optuna.integration` в версии 5.0.0
выдаёт `FutureWarning` — он объявлен устаревшим с 4.9 и будет удалён в 6.0. В установленных версиях проверены
три интеграции: `LightGBMPruningCallback(trial, "rmse")` — в `fit(..., eval_metric="rmse", callbacks=[...])`;
`XGBoostPruningCallback(trial, "validation_0-rmse")` — в `XGBRegressor(callbacks=[...])`;
`CatBoostPruningCallback(trial, "RMSE")` — в `fit(callbacks=[...])`, после обучения нужно вызвать
`callback.check_pruned()`; этот класс помечен экспериментальным и выдаёт `ExperimentalWarning`. Эксперимент:
одна отложенная часть, 1 000 деревьев без ранней остановки, шаг обучения входит в пространство поиска (от 0.01
до 0.3).

| Pruner | 100 попыток: завершено | итераций бустинга | время, с | лучший RMSE | 64 секунды: попыток | лучший RMSE |
|---|---|---|---|---|---|---|
| нет | 100 | 100 000 | 64 | **0.6050** | 100 | **0.6050** |
| `MedianPruner(5, 50)` | 20 | 25 692 | 20 | 0.6222 | 419 | 0.6222 |
| `SuccessiveHalvingPruner(50, 3)` | 11 | 22 839 | 11 | 0.6236 | 704 | 0.6159 |
| `HyperbandPruner(50, 1000, 3)` | 30 | 42 470 | 25 | 0.6129 | 215 | 0.6131 |

Отсечение сэкономило от 58 до 77 % итераций, но результат хуже — и при равном числе попыток, и при равном
времени, когда отсекающие варианты успевают в 2–7 раз больше попыток. Причина: кривые обучения при разном шаге
несравнимы. Модель с шагом 0.01 первые сотни итераций отстаёт от модели с шагом 0.3 и отсекается, хотя к
тысячной итерации была бы лучше. У `MedianPruner` лучшей так и осталась попытка № 4 с шагом 0.011, завершённая
до начала отсечения. **Вывод:** отсечение по кривой обучения работает, когда ранний результат предсказывает
итоговый. Параметры, меняющие скорость обучения (шаг, число деревьев), это условие нарушают. Для бустинга
надёжнее фиксированный шаг, ранняя остановка внутри попытки и отсечение по фолдам.

## 7. Сохранение, возобновление, параллельный запуск

```python
storage = "sqlite:///optuna_housing.db"
study = optuna.create_study(study_name="lgbm_housing", storage=storage, direction="minimize",
                            sampler=optuna.samplers.TPESampler(seed=0), load_if_exists=True)
study.optimize(objective, n_trials=100)

study = optuna.load_study(study_name="lgbm_housing", storage=storage, sampler=optuna.samplers.TPESampler(seed=1))
len(study.trials)                        # 100
study.optimize(objective, n_trials=20)   # всего 120, лучший результат 0.6024
```

История хранится в файле SQLite (266 КБ на 120 попыток). Прерванный подбор продолжается с того же места;
sampler в базе не хранится — при загрузке его нужно передать заново. Файл базы в репозиторий не кладут.

Параллельный запуск — два способа:

| Способ | 40 попыток | Замечания |
|---|---|---|
| последовательно | 29 с | воспроизводимо |
| `study.optimize(objective, n_trials=40, n_jobs=4)` | 11 с | потоки одного процесса; помогает, когда обучение освобождает GIL, как у LightGBM |
| два процесса с общим `storage`, по 20 попыток | 18 с | масштабируется на несколько машин |

Для второго способа каждый процесс выполняет один и тот же скрипт с `load_if_exists=True`. **Study нужно
создать до запуска процессов.** Когда два процесса одновременно создавали базу SQLite, один из них завершился
с ошибкой `sqlite3.IntegrityError` при инициализации схемы. Для многих процессов и машин документация Optuna
рекомендует PostgreSQL или MySQL. Параметр `constant_liar=True` у `TPESampler` (в версии 5.0.0 включён по
умолчанию) заставляет считать ещё не завершённые попытки плохими и не выбирать те же точки повторно.

| `reg_lambda` | 0.07 | 0.04 | 0.04 | 0.01 |
| `reg_alpha` | 0.12 | 0.05 | 0.06 | 0.01 |

Четыре оценки дают четыре разных порядка. Главное расхождение — `num_leaves`: по случайному поиску это самый
важный параметр (как и в разделе 2), а по истории TPE — почти неважный. TPE быстро понял, что нужны маленькие
деревья, и 94 попытки из 100 провёл при `num_leaves` не больше 16. Внутри этой узкой области параметр
действительно мало что меняет. **Важность по истории адаптивного поиска описывает исследованную область, а не
всё пространство.** Вывод «параметр неважен, его можно не подбирать» по такой таблице делать нельзя.

Графики (`optuna.visualization`, нужен `plotly`; каждая функция возвращает `plotly.graph_objects.Figure`,
дальше `fig.show()` или `fig.write_html(...)`):

- `plot_optimization_history` — значение по попыткам и лучшее на данный момент: вышла ли кривая на плато;
- `plot_slice` — значение против каждого параметра: упирается ли оптимум в границу диапазона;
- `plot_parallel_coordinate` и `plot_contour` — сочетания и взаимодействия параметров;
- `plot_param_importances` — важности (с оговоркой выше); `plot_intermediate_values` — что и когда отсекается.

Самая полезная проверка — границы. В нашей истории лучшие попытки имеют `colsample_bytree` 0.8–0.9 (медиана
RMSE 0.616 против 0.635 при значениях ниже 0.6) и `num_leaves` 8–10 — оптимум внутри диапазонов. Если бы
лучшие значения лежали на границе, диапазон следовало бы расширить.

## 9. Несколько критериев

Качество и скорость предсказания конфликтуют. Optuna умеет искать не одну точку, а **фронт Парето** — попытки,
которые нельзя улучшить по одному критерию, не ухудшив другой.

```python
study = optuna.create_study(directions=["minimize", "minimize"], sampler=optuna.samplers.TPESampler(seed=0))
study.optimize(objective_mo, n_trials=60)       # возвращает (RMSE, микросекунд на объект)
study.best_trials                               # фронт Парето; best_trial и best_value не определены
```

На фронте 4 попытки из 60: от RMSE 0.6068 при 10.7 мкс на объект (10 листьев, 185 деревьев) до 0.6737 при 8.9
мкс (4 листа, 280 деревьев); по всем попыткам время — от 8.9 до 35.8 мкс. На этой задаче конфликта почти нет:
лучшие по качеству модели состоят из маленьких деревьев и потому быстры. Выбор точки на фронте — решение
человека. Измеренное время шумит: берите минимум из нескольких замеров.

## 10. Практические правила

### Что подбирать у бустинга

| Что | XGBoost | LightGBM | CatBoost | Диапазон | Шкала |
|---|---|---|---|---|---|
| сложность дерева | `max_depth` | `num_leaves` | `depth` | 3–10; листьев 4–256 | целая; для листьев — лог. |
| минимальный лист | `min_child_weight` | `min_child_samples` | — | 1–100 | лог. |
| доля строк | `subsample` | `subsample` и `subsample_freq=1` | `subsample` | 0.5–1.0 | линейная |
| доля признаков | `colsample_bytree` | `colsample_bytree` | `rsm` | 0.3–1.0 | линейная |
| L2-регуляризация | `reg_lambda` | `reg_lambda` | `l2_leaf_reg` | 0.001–100 | лог. |
| L1-регуляризация | `reg_alpha` | `reg_alpha` | — | 0.001–10 | лог. |
| шаг | `learning_rate` | `learning_rate` | `learning_rate` | фиксировать: 0.05–0.1 | — |
| число деревьев | `n_estimators` | `n_estimators` | `iterations` | не подбирать | — |

**Число деревьев не подбирают — его определяет ранняя остановка** (урок 4.3.1). Шаг и число деревьев связаны:
меньше шаг — больше деревьев и почти всегда чуть лучше качество. Включить оба в пространство поиска — значит
тратить попытки на изучение этой известной связи. Порядок: зафиксировать шаг, при котором одна попытка
быстрая; подобрать остальное; в конце уменьшить шаг в 3–5 раз и переобучить с ранней остановкой. В нашей схеме
фолд используется и для остановки, и для оценки — оценка слегка оптимистична, но одинаково для всех попыток.

**Фолды одни для всех попыток.** Иначе разница между попытками — это отчасти разница между разбиениями.

### Шум оценки

Лучшие параметры одного из запусков TPE (200 попыток): RMSE 0.6027 на фолдах подбора. Десять лучших попыток
этого запуска — от 0.6027 до 0.6047. Пересчитаем те же параметры по-другому:

| Что меняется | Значения RMSE | Среднее | Ст. отклонение |
|---|---|---|---|
| seed разбиения на фолды, 10 значений | от 0.6027 до 0.6340 | 0.6192 | 0.0092 |
| seed модели на фолдах подбора, 10 значений | от 0.6027 до 0.6210 | 0.6151 | 0.0051 |

- Разброс от смены разбиения (0.009) в четыре раза больше разницы между первой и десятой попытками (0.002).
  Попытка № 10 на десяти разбиениях в среднем даёт 0.6202 и выигрывает у «лучшей» на четырёх из десяти.
  **Порядок попыток в верхней части списка — шум.**
- Значение на фолдах и seed подбора — **наименьшее** в обоих рядах. Поиск нашёл не просто хорошие параметры, а
  параметры, которым повезло именно на этих фолдах и с этим seed.
- Настоящий эффект при этом есть: параметры по умолчанию на тех же десяти разбиениях дают 0.6562 ± 0.0083, и
  подобранные лучше на всех десяти.

### Подгонка под валидацию

Чем больше попыток, тем вероятнее, что лучшая из них лучшая отчасти по везению. Лучшая из первых $N$ попыток
по кросс-валидации и качество тех же параметров на отложенном тесте (среднее по пяти запускам):

| $N$ | TPE: кросс-валидация | тест | разрыв | Случайный поиск: кросс-валидация | тест | разрыв |
|---|---|---|---|---|---|---|
| 10 | 0.6264 | 0.6750 | 0.049 | 0.6264 | 0.6750 | 0.049 |
| 25 | 0.6129 | 0.6631 | 0.050 | 0.6149 | 0.6763 | 0.061 |
| 50 | 0.6061 | 0.6711 | 0.065 | 0.6115 | 0.6648 | 0.053 |
| 100 | 0.6039 | 0.6669 | 0.063 | 0.6098 | 0.6648 | 0.055 |
| 200 | 0.6007 | 0.6705 | 0.070 | 0.6073 | 0.6639 | 0.057 |

Оценка на кросс-валидации улучшается с каждым удвоением бюджета. Качество на тесте у TPE после 25 попыток не
улучшается вовсе, у случайного поиска — после 50. Разрыв у TPE вырос с 0.049 до 0.070: последние 0.012
«улучшения» на кросс-валидации — подгонка под пять конкретных фолдов. Адаптивный поиск подгоняется сильнее
случайного, потому что целенаправленно уточняет то, что хорошо выглядит на этих фолдах. (Стандартное
отклонение тестовых значений между запусками — 0.005–0.013, поэтому колебания в третьем знаке внутри столбца
«тест» — шум.)

Следствия:

- **лучшее значение подбора — не оценка качества.** Честная оценка — отложенный тест, не участвовавший в
  подборе, или вложенная кросс-валидация (урок 3.2.3), где весь подбор повторяется внутри каждого внешнего
  фолда;
- **бюджет в сотни попыток на небольших данных не окупается.** После первых десятков попыток растёт оценка, а
  не качество;

## 11. Сравнение при равном бюджете

Бюджет — 64 вычисления целевой функции. Сетка: `num_leaves` 7, 15, 31, 63 × `min_child_samples` 5, 10, 20, 50
× `colsample_bytree` 0.4, 0.6, 0.8, 1.0. Случайный поиск и TPE — шесть параметров из раздела 4, пять запусков
с разными seed (среднее ± стандартное отклонение). Время — сумма длительностей попыток.

| Способ | RMSE на кросс-валидации | RMSE на тесте | Время, с |
|---|---|---|---|
| параметры по умолчанию | 0.6439 | 0.6978 | 1 |
| сетка 4 × 4 × 4 | 0.6194 | 0.6859 | 48 |
| случайный поиск | 0.6114 ± 0.0049 | 0.6700 ± 0.0126 | 69 |
| TPE | 0.6061 ± 0.0034 | 0.6711 ± 0.0044 | 53 |
| TPE + pruning по фолдам | 0.6056 ± 0.0028 | 0.6684 ± 0.0053 | 42 |

- **Любой подбор намного лучше параметров по умолчанию:** 0.698 → 0.67–0.69 на тесте.
- **Сетка хуже случайного поиска** и на кросс-валидации, и на тесте, хотя сетка составлена «разумно».
- **TPE лучше случайного поиска на кросс-валидации** (0.6061 против 0.6114, разница — одно стандартное
  отклонение) и стабильнее от запуска к запуску. **На тесте преимущества нет:** 0.6711 против 0.6700. При 200
  попытках картина та же: 0.6007 против 0.6073 на кросс-валидации, 0.6705 против 0.6639 на тесте. На этой
  задаче TPE эффективнее оптимизирует оценку, но выигрыш оценки — уже за пределами её точности.
- **TPE быстрее случайного поиска при том же числе попыток:** он сосредоточен в области маленьких деревьев,
  которые обучаются быстрее. Pruning добавляет ещё 20 % экономии.

На больших данных, где шум оценки мал, а попытка стоит минуты, преимущество в оценке может превратиться в
преимущество в качестве — но проверять это нужно на отложенных данных.

## Типичные ошибки

| Симптом | Причина | Решение |
|---|---|---|
| Лучшие параметры меняются от запуска к запуску | разница между лучшими попытками меньше шума оценки | фиксированные фолды; сравнивать с разбросом по seed; не уточнять третий знак |
| На новых данных качество ниже лучшего значения подбора | лучшее из сотен значений — оптимистичная оценка | отложенный тест или вложенная кросс-валидация |
| 90 % попыток — при больших значениях регуляризации | диапазон на порядки без `log=True` | логарифмическая шкала |
| Лучшие значения параметра лежат на границе | диапазон узок | расширить диапазон, проверить `plot_slice` |
| Pruning отсекает попытки, которые были бы лучшими | ранний результат не предсказывает итоговый | отсечение по фолдам; `n_warmup_steps`; не подбирать шаг |
| «Параметр неважен» по `get_param_importances` | важность посчитана по узкой области, исследованной TPE | оценивать важность по случайному поиску |
