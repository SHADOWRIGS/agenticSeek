## Зачем это нужно

В практике 2.1.4 вы получили планку: прогноз «среднее за 28 дней» ошибается на 34 % оборота (WAPE 0.341).
Градиентный бустинг — основной инструмент для табличных данных — про время ничего не знает: для него строка
таблицы не связана с соседними. Всё, что модель узнает о прошлом ряда, она узнает из столбцов, которые
построите вы. Поэтому в прогнозировании спроса, загрузки, оттока качество определяется признаками и схемой
проверки, а не выбором библиотеки.

Вторая половина урока — проверка: ошибка в схеме валидации не ухудшает модель, а прячет её недостатки
до запуска в продакшен.

Инструменты из уроков 2.1.1 и 2.1.3 (`groupby`, `shift`, `rolling`, правило «сначала `shift`, потом
`rolling`», календарные признаки) считаем известными и идём дальше.

## 1. Прогноз как табличная задача

Одна строка обучающей таблицы — один прогноз: «сколько единиц товара продаст магазин в день `date`».
Целевая переменная — `units`, признаки — всё, что известно **в момент, когда прогноз делается**.

Этот момент задаёт **горизонт прогноза** `h`: прогноз на день `t` делается в конце дня `t − h`. Если заказ
поставщику уходит за неделю, то `h = 7`, и вчерашних продаж в момент прогноза ещё не существует.

| Признак для строки с датой `t` | `h = 1` | `h = 7` |
|---|---|---|
| продажи в день `t − 1` | доступен | **недоступен** |
| продажи в день `t − 7` | доступен | доступен |
| среднее за дни `t − 7 … t − 1` | доступно | **недоступно** |
| день недели, праздник в день `t` | доступен | доступен |
| промо в день `t` | если акции планируются заранее | если планируются минимум за неделю |
| погода в день `t` | только прогноз погоды | только прогноз на неделю |

Правило: **лаг не может быть короче горизонта, а окно должно заканчиваться не позже чем за `h` дней до
даты строки**. Признаки делятся на три группы: история целевой переменной (сдвигается на горизонт),
известное заранее (календарь, плановые акции, цены) и неизвестное заранее (погода, действия конкурентов) —
последнее можно использовать только в виде прогноза или лага.

Подготовим данные и вспомогательные функции. Файл [`sales_data.py`](../topic_2_1/sales_data.py) скопируйте
в проект рядом с ноутбуком.

```python
import numpy as np
import pandas as pd
from sklearn.ensemble import HistGradientBoostingRegressor
from sklearn.inspection import permutation_importance
from sklearn.metrics import make_scorer
from sklearn.model_selection import KFold, TimeSeriesSplit

from sales_data import make_sales

KEYS = ["store_id", "product"]
TEST_START = "2024-11-01"


def wape(y_true, y_pred):
    return np.abs(y_true - y_pred).sum() / np.abs(y_true).sum()


def past_rolling(df, column, by, window, func, horizon):
    """Статистика за window дней, заканчивающихся за horizon дней до даты строки."""
    shifted = df.groupby(by)[column].shift(horizon)
    rolled = shifted.groupby([df[key] for key in by]).rolling(window, min_periods=window // 2).agg(func)
    return rolled.droplevel(by)
```

`past_rolling` — то же «сначала `shift`, потом `rolling`», но без `lambda`: сдвиг и окно выполняются
встроенными средствами внутри групп. `min_periods=window // 2` разрешает считать статистику, если известна
хотя бы половина окна: в данных есть пропуски, и строгое окно теряло бы каждую восьмую строку.

## 2. Семейства признаков

Все признаки собирает одна функция с параметром `horizon`. Разберём её по частям.

```python
def build_features(sales, horizon=1):
    df = sales.sort_values([*KEYS, "date"], ignore_index=True)
    units = df.groupby(KEYS)["units"]

    # 1. Лаги: только те, что известны за horizon дней до даты прогноза
    for lag in (1, 2, 3, 7, 14, 21, 28):
        if lag >= horizon:
            df[f"lag_{lag}"] = units.shift(lag)

    # 2. Скользящие статистики разных окон
    for window in (7, 28, 56):
        df[f"mean_{window}"] = past_rolling(df, "units", KEYS, window, "mean", horizon)
    df["std_28"] = past_rolling(df, "units", KEYS, 28, "std", horizon)
    df["max_28"] = past_rolling(df, "units", KEYS, 28, "max", horizon)

    # 3. Тренд: отношение и разность короткого и длинного окна
    df["trend_7_28"] = df["mean_7"] / (df["mean_28"] + 1)
    df["diff_7_28"] = df["mean_7"] - df["mean_28"]

    # 4. Тот же день недели: среднее за четыре ближайшие доступные недели
    first = -(-horizon // 7) * 7  # ближайшее кратное 7, не меньшее горизонта
    same_day = pd.concat([units.shift(lag) for lag in range(first, first + 28, 7)], axis=1)
    df["dow_mean_4"] = same_day.mean(axis=1)

    # 5. Календарь
    df["day_of_week"] = df["date"].dt.day_of_week
    df["is_weekend"] = df["day_of_week"] >= 5
    df["month"] = df["date"].dt.month
    df["day_of_year"] = df["date"].dt.day_of_year

    # 6. События: доля дней с промо в окне и число дней с прошлого промо
    promo_flag = df.assign(promo=df["promo"].astype(float))
    df["promo_share_28"] = past_rolling(promo_flag, "promo", KEYS, 28, "mean", horizon)
    keys = [df[key] for key in KEYS]
    last_promo = df["date"].where(df["promo"]).groupby(keys).shift(1).groupby(keys).ffill()
    df["days_since_promo"] = (df["date"] - last_promo).dt.days

    # 7. Иерархия: средние продажи на уровнях выше пары «магазин — товар»
    levels = {"cat_store": ["store_id", "category"], "product_all": ["product"], "store_all": ["store_id"]}
    for name, by in levels.items():
        level = df.groupby([*by, "date"], as_index=False)["units"].sum()
        level[f"{name}_mean_28"] = past_rolling(level, "units", by, 28, "mean", horizon)
        df = df.merge(level.drop(columns="units"), on=[*by, "date"], how="left")

    return df.astype({"store_id": "category", "product": "category"})
```

| Семейство | Что сообщает модели | На что обратить внимание |
|---|---|---|
| Лаги | последние известные значения | шумные: одно значение — одна реализация случайной величины |
| Скользящие статистики | уровень (среднее), разброс (`std`), пики (`max`) | короткое окно быстрее реагирует, длинное меньше шумит — дают оба |
| Отношения и разности окон | направление: растёт ряд или падает | `+ 1` в знаменателе защищает от деления на ноль у редких товаров |
| Тот же день недели | недельную сезонность в уровне именно этого ряда | сдвиги кратны 7 и не короче горизонта |
| Календарь | регулярные эффекты: день недели, сезон | деревьям достаточно номера, циклическое кодирование не нужно |
| События | эффект акции и «загрязнение» окон акциями | известно ли будущее значение? |
| Время с последнего события | затухание и накопление эффекта | событие дня `t` считать нельзя, только прошлые |
| Иерархия | более устойчивую оценку уровня и общие сдвиги | агрегат тоже сдвигается на горизонт |

**События.** Столбец `promo` относится к дню прогноза, и мы используем его без сдвига. Это законно только
потому, что акции планирует сама сеть и знает их заранее. Для каждого такого признака задавайте вопрос:
«откуда это значение возьмётся в продакшене за `h` дней до даты?» Если ответа нет — признак сдвигается на
горизонт, как и продажи. `promo_share_28` нужен по другой причине: среднее за 28 дней завышено, если
в окно попало много акций, и модель может сделать на это поправку.

**Праздники.** В учебных данных их нет, в настоящих — это один из сильнейших признаков. Календарь по странам
даёт библиотека `holidays`: `holidays.country_holidays("RU", years=[2024, 2025])` возвращает словарь
«дата — название». Кроме флага праздника полезны «дней до ближайшего праздника» и «дней после»: спрос
меняется заранее. Праздники известны на годы вперёд, сдвигать их на горизонт не нужно.

## 3. Модель против простых прогнозов

```python
sales = make_sales()
data = build_features(sales, horizon=1).dropna(subset="units").reset_index(drop=True)
is_test = data["date"] >= TEST_START
train, test = data[~is_test], data[is_test]          # 64 019 и 5 822 строки

for column in ("lag_1", "lag_7", "mean_28", "dow_mean_4"):
    known = test[column].notna()
    print(column, round(wape(test.loc[known, "units"], test.loc[known, column]), 3))
```

lag_1 0.468
lag_7 0.447
mean_28 0.343

Строки без целевой переменной удаляем **после** построения признаков: иначе сдвиги считались бы по
строкам, а не по дням. Планка — 0.343 (в практике 2.1.4 было 0.341: там окно строгое и строк с пропусками
в окне в расчёте нет).

Модель — `HistGradientBoostingRegressor` из scikit-learn: он не требует заполнять пропуски и сам
обрабатывает столбцы типа `category`.

```python
IDS = ["store_id", "product"]
LAGS = [column for column in data.columns if column.startswith("lag_")]
ROLLING = ["mean_7", "mean_28", "mean_56", "std_28", "max_28", "trend_7_28", "diff_7_28", "dow_mean_4"]
CALENDAR = ["day_of_week", "is_weekend", "month", "day_of_year"]
PROMO = ["promo", "promo_share_28", "days_since_promo"]
HIERARCHY = ["cat_store_mean_28", "product_all_mean_28", "store_all_mean_28"]
FEATURES = IDS + LAGS + ROLLING + CALENDAR + PROMO + HIERARCHY


def make_model(**params):
    return HistGradientBoostingRegressor(categorical_features="from_dtype", random_state=42, **params)


def holdout_wape(features, train, test):
    model = make_model().fit(train[features], train["units"])
    return wape(test["units"], model.predict(test[features]))


holdout_wape(FEATURES, train, test)     # 0.296
```

Добавляя семейства по одному, видим вклад каждого:

| Набор признаков | Признаков | WAPE |
|---|---|---|
| простой прогноз `mean_28` | — | 0.343 |
| лаги | 7 | 0.348 |
| + скользящие статистики | 15 | 0.339 |
| + календарь | 19 | 0.328 |
| + промо в день прогноза | 20 | 0.296 |
| + история промо | 22 | 0.297 |
| + иерархия | 25 | 0.297 |
| + магазин и товар | 27 | 0.296 |

Что здесь важно:

- бустинг на одних лагах **хуже** простого среднего: семь шумных чисел уступают одному усреднённому;
- самый большой шаг дал не признак из прошлого, а знание о будущем — флаг акции в день прогноза. Без него
  полный набор даёт 0.329;
- последние три строки меняют третий знак — это шум, а не улучшение. К отбору вернёмся в разделе 7.

**Сколько вообще можно выиграть.** Продажи в генераторе — пуассоновская случайная величина вокруг
известного среднего. Если подставить это среднее как прогноз, получится WAPE 0.288: ниже не опустится
никакая модель. Модель прошла путь от 0.343 до 0.296 из возможных 0.343 → 0.288. В настоящих задачах
предел неизвестен, но он есть всегда: если метрика перестала улучшаться, дело может быть не в признаках.

**Горизонт.** Та же модель при `horizon=7` даёт 0.297 (24 признака, `mean_28` — 0.341), при
`horizon=28` — 0.298 (21 признак, `mean_28` — 0.347). Короткие лаги исчезают, окна отодвигаются в прошлое,
но качество почти не падает: уровень ряда меняется медленно, а главные признаки — календарь и акции —
известны заранее. На рядах с быстрыми изменениями падение будет заметным. Для нескольких горизонтов
обычно обучают отдельную модель на каждый.

## 4. Преобразование целевой переменной

Продажи неотрицательны и скошены вправо: медиана 3, максимум 45, коэффициент асимметрии 1.97. Частый
приём — обучать модель на `log1p(units)` и возвращать прогноз через `expm1`. Логарифм сжимает правый
хвост (асимметрия становится −0.12), редкие всплески перестают доминировать в квадратичной ошибке,
а мультипликативные эффекты («в выходные на 35 % больше») превращаются в аддитивные. `log1p`, а не `log`, —
потому что в данных есть нули.

```python
predictions = {
    "units": make_model().fit(train[FEATURES], train["units"]).predict(test[FEATURES]),
    "log1p": np.expm1(make_model().fit(train[FEATURES], np.log1p(train["units"])).predict(test[FEATURES])),
    "poisson": make_model(loss="poisson").fit(train[FEATURES], train["units"]).predict(test[FEATURES]),
}
for name, prediction in predictions.items():
    print(name, round(wape(test["units"], prediction), 3), round(prediction.sum() / test["units"].sum(), 3))
```

| Целевая переменная и функция потерь | WAPE | Сумма прогнозов / сумма фактов |
|---|---|---|
| `units`, квадратичная ошибка | 0.296 | 0.995 |
| `log1p(units)`, квадратичная ошибка | 0.301 | 0.915 |
| `units`, пуассоновская функция потерь | 0.296 | 0.982 |

На этих данных логарифм **ухудшил** результат, и второй столбец объясняет почему: модель в логарифмической
шкале оценивает среднее логарифма, а после `expm1` это уже не среднее продаж, а величина меньше него.
Прогноз систематически занижен на 8.5 %. Для закупок это значит постоянную нехватку товара.

Преобразование оправдано, когда метрика сама считается в логарифмах (RMSLE), когда целевая переменная
меняется на порядки (выручка, цены недвижимости) или когда важнее не ошибиться в разы на малых значениях,
чем в штуках на больших. Для счётных данных чаще лучше оставить шкалу и сменить функцию потерь
(`loss="poisson"`). В любом случае проверяйте смещение: отношение суммы прогнозов к сумме фактов должно
быть близко к единице.

## 5. Валидация по времени

Отложенный период (holdout) — последние два месяца — мы уже использовали. Одно число ненадёжно: неясно,
повезло ли с периодом. Кросс-валидация по времени повторяет ту же схему несколько раз: обучение — всегда
прошлое, проверка — следующий за ним отрезок.

`TimeSeriesSplit` из scikit-learn делит **строки** по порядку. В наших данных на одну дату приходится 96
строк, поэтому делить нужно даты, а не строки — иначе один день окажется и в обучении, и в проверке:

```python
def date_folds(dates, n_splits=4, test_size=28, gap=0, max_train_size=None):
    """Разбиение по датам: все строки одного дня попадают в одну часть."""
    days = np.sort(dates.unique())
    splitter = TimeSeriesSplit(n_splits=n_splits, test_size=test_size, gap=gap, max_train_size=max_train_size)
    for train_days, valid_days in splitter.split(days):
        yield dates.isin(days[train_days]).to_numpy(), dates.isin(days[valid_days]).to_numpy()


for fit_mask, valid_mask in date_folds(train["date"]):
    fit, valid = train[fit_mask], train[valid_mask]
    print(
        fit["date"].max().date(),
        valid["date"].min().date(),
        round(holdout_wape(FEATURES, fit, valid), 3),
        round(wape(valid["units"], valid["mean_28"]), 3),
    )
```

Кросс-валидацию проводим на данных до 1 ноября: тестовый период остаётся нетронутым до самого конца.

| Фолд | Обучение до | Проверка | WAPE модели | WAPE `mean_28` | Скользящее окно 365 дней |
|---|---|---|---|---|---|
| 1 | 2024-07-11 | 12.07 – 08.08 | 0.392 | 0.436 | 0.392 |
| 2 | 2024-08-08 | 09.08 – 05.09 | 0.366 | 0.408 | 0.369 |
| 3 | 2024-09-05 | 06.09 – 03.10 | 0.346 | 0.392 | 0.347 |
| 4 | 2024-10-03 | 04.10 – 31.10 | 0.324 | 0.372 | 0.327 |
| Среднее | | | 0.357 | 0.402 | 0.359 |

Наблюдения:

- WAPE сильно зависит от периода: летом продажи ниже, относительный шум выше. Поэтому модель сравнивают
  с простым прогнозом **на том же фолде**, а не с числом из другого периода. Выигрыш стабилен: 0.042–0.048;
- **расширяющееся окно** (по умолчанию) обучается на всей истории, **скользящее** (`max_train_size=365`) —
  только на последнем годе. Здесь старые данные немного помогают; при резких изменениях поведения
  покупателей выиграло бы скользящее окно.

**Зазор.** При горизонте 7 прогноз на 6 сентября делается 30 августа, и обучающие данные заканчиваются
30 августа: продажи 31 августа – 5 сентября в момент прогноза неизвестны, их нельзя использовать даже как
целевую переменную. Между обучением и проверкой остаётся зазор в `h − 1` дней: `date_folds(dates, gap=6)`.
Зазор нужен и тогда, когда целевая переменная сама растянута во времени («купит ли клиент в ближайшие
30 дней»): без него метки последних строк обучения пересекаются с периодом проверки.

## 6. Почему случайный KFold завышает оценку

Случайное разбиение перемешивает дни: чтобы предсказать 10 декабря, модель обучается на 9 и 11 декабря.
В продакшене будущих дней нет. Сравним две схемы **на одних и тех же строках** — ноябрь и декабрь 2024 года:
случайный `KFold` по всем данным (берём прогнозы вне фолда только для этих строк) и честный отложенный
период. И две модели: без единого признака из истории продаж и с полным набором.

```python
data["day_number"] = (data["date"] - data["date"].min()).dt.days
train, test = data[~is_test], data[is_test]
variants = {"календарь + номер дня": IDS + CALENDAR + ["promo", "day_number"], "все признаки урока": FEATURES}

for name, features in variants.items():
    out_of_fold = np.zeros(len(data))
    for fit_idx, valid_idx in KFold(n_splits=5, shuffle=True, random_state=42).split(data):
        model = make_model().fit(data.iloc[fit_idx][features], data.iloc[fit_idx]["units"])
        out_of_fold[valid_idx] = model.predict(data.iloc[valid_idx][features])
    shuffled = wape(test["units"], out_of_fold[is_test])
    print(name, round(shuffled, 3), round(holdout_wape(features, train, test), 3))
```

| Уровень данных | Модель | Случайный KFold | По времени |
|---|---|---|---|
| магазин — товар — день | календарь + номер дня | 0.289 | 0.301 |
| магазин — товар — день | все признаки урока | 0.293 | 0.296 |
| магазин — день (сумма по товарам) | календарь + номер дня | 0.109 | 0.139 |
| магазин — день (сумма по товарам) | календарь + лаги | 0.112 | 0.130 |

Нижние две строки — тот же эксперимент на продажах, просуммированных по товарам: шум там меньше, и эффект
виден лучше.

Выводы:

1. **Оценка завышена.** Случайный KFold сообщает, что модель без истории продаж достигла 0.289 — то есть
   почти теоретического предела 0.288. На деле она даёт 0.301. На уровне магазинов разрыв ещё больше:
   0.109 против 0.139, ошибка занижена более чем на 20 %.
2. **Выбор модели переворачивается.** По случайному KFold календарная модель лучше модели с лагами на
   обоих уровнях. По времени — наоборот. Вы выбрали бы худшую модель и узнали бы об этом в продакшене.
3. **Причина — интерполяция.** Деревья не умеют продолжать тренд за пределы виденного. В случайном
   разбиении этого и не требуется: соседние дни есть в обучении, и уровень ряда модель берёт у них через
   `day_number`. Лаги и окна переносят уровень ряда честно, поэтому у моделей с ними разрыв меньше.

В учебных данных шум каждой строки независим. В настоящих у соседних дней есть общие причины — погода,
новости, сбои, — и утечка через соседей заметно сильнее.

## 7. Важность признаков и отбор

Permutation importance отвечает на вопрос: насколько ухудшится метрика, если значения одного признака
перемешать, разорвав его связь с целевой переменной? Считают её на данных, которых модель не видела,
и не на тестовом периоде: по нему мы отчитываемся, а не принимаем решения.

```python
VALID_START = "2024-09-01"
fit, valid = train[train["date"] < VALID_START], train[train["date"] >= VALID_START]
model = make_model().fit(fit[FEATURES], fit["units"])

scorer = make_scorer(wape, greater_is_better=False)
result = permutation_importance(
    model, valid[FEATURES], valid["units"], scoring=scorer, n_repeats=10, random_state=42
)
importance = pd.DataFrame({"mean": result.importances_mean, "std": result.importances_std}, index=FEATURES)
importance.sort_values("mean", ascending=False).head(6).round(4)
```

```
               mean     std
mean_28      0.1440  0.0033
promo        0.0553  0.0015
day_of_week  0.0314  0.0017
mean_7       0.0234  0.0015
product      0.0169  0.0009
mean_56      0.0141  0.0008
```

Число в столбце `mean` — на сколько вырастает WAPE при перемешивании признака. У 14 признаков из 27 прирост
не превышает двух стандартных отклонений — он неотличим от нуля. Среди них все короткие лаги, `month`,
`is_weekend`, `days_since_promo`. Уберём их:

```python
selected = [name for name in FEATURES if importance.loc[name, "mean"] > 2 * importance.loc[name, "std"]]
len(selected), round(holdout_wape(selected, train, test), 3), round(holdout_wape(FEATURES, train, test), 3)
# (13, 0.295, 0.296)
```

Тринадцать признаков дают то же качество, что двадцать семь. Модель стала проще и дешевле в поддержке:
каждый признак в продакшене — это код, который нужно считать и проверять каждый день.

Как читать важность:

- **низкая важность не значит «бесполезен сам по себе»**. `is_weekend` дублирует `day_of_week`, `lag_1`
  содержится в `mean_7`: сильно коррелирующие признаки делят важность между собой;
- **важность зависит от данных.** `days_since_promo` бесполезен здесь, потому что акции в генераторе
  случайны и не влияют на последующие дни. В настоящих данных после акции часто бывает спад.

## Типичные ошибки

| Симптом | Причина | Решение |
|---|---|---|
| Метрика на валидации намного лучше, чем в продакшене | лаг или окно короче горизонта прогноза | параметр `horizon` в функции признаков; тест «изменили день — признаки дня не изменились» |
| Случайная кросс-валидация показывает качество лучше отложенного периода | модель обучалась на днях, соседних с проверочными | разбиение по времени, причём по датам, а не по строкам |
| Признак события резко улучшил метрику, но в продакшене его нет | значение на день прогноза неизвестно заранее | сдвинуть на горизонт или заменить прогнозом |
| Лаги «съехали» после удаления строк | строки с пропусками удалены до построения признаков | сначала признаки на полном календаре, потом удаление |
| Прогноз систематически ниже факта | обучение на `log1p` без поправки | проверить отношение суммы прогнозов к сумме фактов; сменить функцию потерь |
| Важность признака около нуля, а без него метрика хуже | признак дублируется другим, важность делится | удалять по одному и перепроверять метрику |
