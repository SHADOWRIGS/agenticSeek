# Урок 2.3.4: ПРАКТИКА: Feature engineering для Kaggle конкурса

> **Модуль 2:** Data-Centric Machine Learning · **Тема 2.3:** Feature Engineering мастерство
> **Тип:** практика · **Время:** 6–8 часов

## Задача

Возьмите табличный конкурс Kaggle и улучшите результат **только признаками**. Модель зафиксирована:
градиентный бустинг с параметрами по умолчанию. Менять можно одно — таблицу, которую он получает на вход.

Ограничение сделано намеренно. Когда одновременно меняются признаки, модель и её параметры, невозможно
понять, что именно помогло. Здесь каждый прирост метрики — это подтверждённая гипотеза о данных, а каждое
отсутствие прироста — опровергнутая. Обе записываются.

Работа состоит из двух частей: стенд экспериментов (модуль, проверяется автотестами) и исследование
на данных конкурса (ноутбук и отправка решения, проверяются по критериям).

## Как устроен конкурс

| Файл | Что в нём |
|---|---|
| `train.csv` | признаки и целевая переменная |
| `test.csv` | те же признаки без целевой переменной |
| `sample_submission.csv` | образец ответа: идентификаторы строк `test.csv` и столбец с прогнозом |

Вы обучаете модель на `train.csv`, делаете прогноз для `test.csv`, сохраняете его в формате образца
и отправляете. Kaggle сравнивает прогноз со скрытыми ответами и показывает метрику.

Ответы тестовой выборки разделены на две части. По **публичной** (обычно 20–50 % строк) результат
виден сразу после отправки — это публичный лидерборд. По **приватной** результат открывается после
окончания конкурса, и итоговые места определяет только он. Число отправок в день ограничено.

### Почему нельзя подгоняться под лидерборд

Каждая отправка — это взгляд на тестовые данные. Если отправить много вариантов и оставить лучший по
публичной таблице, вы выберете не лучшую модель, а ту, которой повезло на публичной части.

Эксперимент на демо-данных этой практики (публичная часть — 1 150 строк, приватная — 2 850). К прогнозу
одной и той же модели 200 раз добавили слабый случайный шум — получили 200 «вариантов решения», каждый
из которых по построению не лучше исходного.

| | Публичная часть | Приватная часть |
|---|---|---|
| исходная модель | 0.8080 | 0.7991 |
| лучший из 200 вариантов по публичной части | 0.8131 | 0.7932 |

Четверть вариантов обошла исходную модель на публичной части. Лучший «улучшил» результат на 0.005 —
и потерял 0.006 там, где подводятся итоги. Корреляция между публичным и приватным результатом вариантов —
около нуля. На настоящих конкурсах это называется shake-up: после открытия приватной таблицы участники,
подгонявшие решение под публичную, теряют сотни мест.

Правила работы:

1. Решения принимаются по локальной кросс-валидации. На ней тысячи строк и несколько фолдов —
   это надёжнее публичной части теста.
2. Лидерборд — проверка валидации, а не инструмент выбора. После отправки сравните: если метрика
   кросс-валидации выросла, а публичная упала, сначала разберитесь, почему они расходятся.
3. Отправок мало, и каждая записывается в журнал вместе с локальной метрикой.

## Демо-данные

```bash
uv run python make_demo_data.py
```

Задача: уйдёт ли клиент оператора связи (`churn`), метрика — ROC AUC. В `train.csv` 8 000 строк,
в `test.csv` — 4 000; уходит 16 % клиентов. Столбцы: возраст, город, тариф, тип договора, дата
подключения, стаж в месяцах, ежемесячный платёж, число обращений в поддержку, трафик, модель устройства,
идентификатор пригласившего.

В данные заложены эффекты, которые модель не увидит в исходных столбцах или увидит плохо:

- категория с сотнями значений, в которой есть сигнал, и столбец-идентификатор, в котором сигнала нет;
- информация, спрятанная внутри строкового значения;
- величина, которая важна не сама по себе, а относительно типичного значения своей группы;
- интенсивность: одно число, делённое на другое;
- пропуск, который сам является признаком;
- сочетание категории и числового порога.

Ориентиры эталонного решения курса (кросс-валидация, 5 фолдов): пять числовых столбцов как есть — 0.605;
с простым кодированием категорий — 0.769; после построения признаков — 0.788 при 13 признаках.

Локальный «лидерборд»:

```bash
uv run python make_demo_data.py --score submission.csv
```

Команда печатает результат на публичной и приватной частях. На приватную смотрите один раз — в конце.

## Часть 1. Стенд экспериментов

Реализуйте функции в `fe_lab.py`. Точное поведение описано в docstring каждой функции.

| Функция | Что делает | Материал |
|---|---|---|
| `count_encode` | частотное кодирование категории | урок 2.3.2 |
| `out_of_fold_target_encode` | target encoding без утечки: обучающая часть — по фолдам, тестовая — по всей обучающей | урок 2.3.2 |
| `evaluate_features` | метрика набора признаков на каждом фолде кросс-валидации | уроки 2.3.1, 2.3.2 |
| `compare_feature_sets` | таблица сравнения наборов: прирост к базовому и число выигранных фолдов | — |
| `log_experiment`, `load_experiments` | журнал экспериментов в формате JSON Lines | — |

```bash
cd projects/p_2_3_kaggle/practice
uv run pytest -q                                   # сначала падают все тесты
uv run pytest -q -k TestOutOfFoldTargetEncode      # работайте над одной функцией за раз
```

Советы:

- тест `test_own_target_does_not_leak` меняет целевую переменную одной строки и проверяет, что её
  собственная кодировка не изменилась. Если он падает — строка участвует в расчёте своего признака;
- тест `test_noise_feature_stays_noise` кодирует случайный идентификатор: честная схема не должна найти
  связь с целевой переменной, которой нет;
- `evaluate_features` отказывается принимать нечисловые столбцы. Это сделано намеренно: каждое
  кодирование — решение, которое вы принимаете явно и записываете в журнал;
- столбец `wins` в `compare_feature_sets` считает фолды, где набор лучше базового. Прирост 0.002 при
  счёте 3 из 5 — шум; прирост 0.002 при счёте 5 из 5 заслуживает внимания.

## Часть 2. Исследование

Ноутбук `kaggle_fe.ipynb` использует функции стенда. Порядок работы:

1. **Паспорт данных.** Для каждого столбца: тип, доля пропусков, число уникальных значений, примеры.
   Распределение целевой переменной. Сравнение распределений признаков в `train` и `test`: отличаются ли
   доли пропусков, есть ли в тесте категории, которых нет в обучении.
2. **Схема валидации.** Выберите разбиение и объясните выбор. Если в данных есть группы (одна семья,
   один клиент), строки группы не должны попадать в разные фолды; если есть время — разбиение по времени.
3. **Базовый набор.** Числовые столбцы как есть и простейшее кодирование категорий. Запишите результат
   в журнал и сделайте первую отправку. Запишите рядом метрику кросс-валидации и публичный результат.
4. **Гипотезы.** Не меньше десяти. Для каждой: формулировка («клиенты с помесячным договором уходят
   в первые месяцы, потому что…»), признак, сравнение с текущим лучшим набором через
   `compare_feature_sets`, запись в журнал. Неподтвердившиеся гипотезы тоже записываются.
5. **Отбор.** Соберите подтвердившиеся признаки вместе, посчитайте permutation importance, уберите
   лишнее. Проверьте, что итоговый набор не хуже полного.
6. **Итог.** Вторая отправка — с итоговым набором. Таблица: набор признаков, метрика кросс-валидации,
   публичный результат. Согласованы ли они?

Откуда брать гипотезы:

| Семейство | Примеры |
|---|---|
| Кодирование категорий | частота; target encoding по схеме out-of-fold; объединение редких значений |
| Части строк | титул из имени, палуба из номера каюты, бренд из модели, домен из адреса |
| Отношения и разности | цена за квадратный метр, расходы на человека, платёж относительно тарифа |
| Статистики по группам | отклонение от среднего по группе, размер группы, ранг внутри группы |
| Пропуски | флаг пропуска, число пропусков в строке |
| Даты | год, месяц, день недели, время от события до события |
| Взаимодействия | произведение или сочетание двух признаков, порог по числу внутри категории |

Признаки, которые не используют целевую переменную (частоты, статистики по группам), на Kaggle допустимо
считать по объединению `train` и `test`. В рабочих проектах так делать нельзя: тестовых данных в момент
обучения не существует. В отчёте укажите, какой вариант вы выбрали.

## Критерии приёмки

- [ ] `uv run pytest -q` — все 40 тестов проходят;
- [ ] `uv run ruff check .` и `uv run ruff format --check .` проходят без ошибок;
- [ ] ноутбук выполняется целиком сверху вниз и использует функции из `fe_lab.py`, а не их копии;
- [ ] модель во всех экспериментах одна и та же; меняются только признаки;
- [ ] в журнале не меньше десяти экспериментов, у каждого заполнен комментарий с гипотезой;
- [ ] все кодирования, использующие целевую переменную, выполнены по схеме out-of-fold;
- [ ] итоговый набор лучше базового на кросс-валидации, и прирост получен не меньше чем в 4 фолдах из 5;
- [ ] сделано не больше пяти отправок, для каждой записаны локальная и публичная метрики;
- [ ] на демо-данных: метрика кросс-валидации не ниже 0.78, приватный результат посчитан один раз;
- [ ] данные, журнал и токен Kaggle не закоммичены; в `README.md` проекта написано, как получить данные;
- [ ] в конце ноутбука есть раздел «Выводы»: три признака, давшие наибольший прирост, и три гипотезы,
      которые не подтвердились, с объяснением.

## Как оценить свою работу

| Уровень | Признаки |
|---|---|
| Базовый | тесты проходят; есть базовый набор, десять гипотез и итоговая отправка |
| Уверенный | гипотезы следуют из паспорта данных, а не из перебора; метрика кросс-валидации и публичный результат согласованы, расхождения объяснены |
| Продвинутый | на демо-данных найдено не меньше пяти заложенных эффектов из шести; выполнено задание из раздела ниже |

## Идеи для усложнения

1. **Shake-up своими руками.** Повторите эксперимент из раздела о лидерборде на своём решении: добавьте
   к прогнозам слабый шум 200 раз, выберите лучший вариант по публичной части и сравните его с исходным
   на приватной.
2. **Вложенная проверка кодирования.** В стенде target encoding считается один раз до кросс-валидации.
   Перенесите его внутрь `Pipeline` (`sklearn.preprocessing.TargetEncoder`) и сравните оценки: насколько
   оптимистична схема стенда?
3. **Автоматические признаки.** Разложите данные конкурса на несколько таблиц (например, пассажиры
   и группы) и получите признаки через featuretools из урока 2.3.3. Сравните с ручными по метрике и по
   числу признаков.
4. **Состязательная валидация.** Обучите модель отличать строки `train` от строк `test`. Если ROC AUC
   заметно выше 0.5, найдите признаки, по которым выборки различаются, и решите, что с ними делать.
5. **Другая модель.** Проверьте лучший набор признаков на логистической регрессии. Какие признаки
   нужны линейной модели, но бесполезны бустингу, и наоборот?
