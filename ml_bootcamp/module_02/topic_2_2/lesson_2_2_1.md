## Зачем это нужно

## 1. Откуда берётся ускорение

```python
import numpy as np

values = list(range(1_000_000))
arr = np.arange(1_000_000)
```

Ниже `py_sum(xs)` — обычный цикл: `total = 0`, затем `for x in xs: total += x`.

| Вариант | Время | Относительно `arr.sum()` |
|---|---|---|
| `py_sum(values)` — цикл по списку | 18.6 мс | в 59 раз медленнее |
| `sum(values)` — встроенная функция | 3.4 мс | в 11 раз медленнее |
| `arr.sum()` | 0.31 мс | — |
| `py_sum(arr)` — цикл по массиву NumPy | 48.8 мс | в 155 раз медленнее |
| `np.sum(values)` — NumPy от списка | 23.9 мс | в 76 раз медленнее |

Причин ускорения пять, и все они следуют из того, как устроен массив:

1. **Типизированный непрерывный буфер.** Список хранит указатели на объекты, разбросанные по памяти.
   Массив хранит сами числа подряд: миллион `int64` — это ровно 8 МБ. Тот же список занимает 36 МБ
   (8 МБ указателей и по 28 байт на каждый объект `int`).
2. **Нет упаковки объектов.** В цикле Python каждое `total += x` — это проверка типов обоих операндов,
   поиск метода сложения, создание нового объекта `int`, обновление счётчиков ссылок. В NumPy тип известен
   заранее и один на весь массив.
3. **Цикл выполняется в C.** Интерпретатор не участвует: миллион итераций — это миллион машинных сложений.
4. **SIMD.** Числа одного типа лежат подряд, поэтому процессор складывает их по 4–8 штук одной инструкцией.
5. **Кэш процессора.** Последовательное чтение непрерывного блока памяти процессор предугадывает и
   подгружает данные заранее. Переходы по указателям списка так предсказать нельзя.

Две последние строки таблицы — главные ловушки. Цикл `for` по массиву NumPy медленнее, чем по списку:
на каждой итерации число приходится упаковывать в объект `np.int64`. А `np.sum(values)` сначала
превращает список в массив, и это дороже самого суммирования. Вывод: **NumPy быстр, только когда данные
уже лежат в массиве, а операция применяется к массиву целиком.**

## 2. Как массив устроен в памяти

`ndarray` — это буфер байтов и небольшое описание того, как его читать:

```python
a = np.arange(12, dtype=np.int32).reshape(3, 4)
a.dtype, a.shape, a.strides, a.nbytes        # (dtype('int32'), (3, 4), (16, 4), 48)
```

`strides` — на сколько байт сдвинуться в буфере, чтобы перейти к следующему элементу по каждой оси:
следующая строка — через 16 байт (4 элемента по 4 байта), следующий столбец — через 4. Многие операции
не трогают буфер, а только меняют это описание. Результат такой операции называется **view**:

```python
t = a.T                # те же данные, оси переставлены
t.strides              # (4, 16)
s = a[:, ::2]          # каждый второй столбец
s.strides              # (16, 8)
np.shares_memory(a, t), np.shares_memory(a, s)       # (True, True)

row = a[1]             # тоже view
row[:] = 0
a[1]                   # array([0, 0, 0, 0], dtype=int32) — исходный массив изменён
```

View создаётся мгновенно и не занимает памяти, но изменение view меняет исходный массив.

| Операция | Результат |
|---|---|
| срез `a[1:3]`, `a[:, ::2]`, `a.T`, `a[np.newaxis]` | всегда view |
| `a.reshape(...)`, `a.ravel()` | view, если возможно; иначе копия |
| `a.flatten()`, `a.copy()`, `a.astype(...)` | всегда копия |
| индексация маской или массивом индексов | всегда копия (урок 2.2.2) |
| арифметика `a + 1`, `a * b` | новый массив |

«Если возможно» проверяется так: `np.shares_memory(a, a.reshape(2, 6))` — `True`, а
`np.shares_memory(a, a.T.reshape(2, 6))` — `False`: после транспонирования элементы идут в буфере не в том
порядке, и NumPy молча делает копию. Сомневаетесь — вызывайте `np.shares_memory`.

**Порядок C и F.** По умолчанию массив хранится по строкам (порядок C): элементы одной строки лежат рядом.
Порядок F (Fortran) — по столбцам. От порядка зависит, какой обход дружит с кэшем. На матрице 4000×4000
сумма по строкам в цикле (`m[i, :].sum()`) заняла 13 мс, по столбцам (`m[:, j].sum()`) — 56 мс: столбец
в C-порядке — это элементы, отстоящие друг от друга на 32 КБ. Отсюда соглашение ML-библиотек: объекты —
строки, признаки — столбцы, батч — первые оси.

**Типы.** Тип результата определяется типами операндов, и это источник тихих ошибок:

```python
np.array([200, 100], dtype=np.uint8) * 2      # array([144, 200], dtype=uint8) — переполнение без ошибки
x = np.array([1, 2, 3])
x[0] = 1.7                                    # x -> array([1, 2, 3]): дробная часть отброшена молча
f32 = np.ones(3, dtype=np.float32)
(f32 * 2.0).dtype, (f32 + np.ones(3)).dtype   # (dtype('float32'), dtype('float64'))
```

Число Python тип массива не меняет, а массив `float64` — меняет: так модель на `float32` незаметно
переходит на `float64` и начинает занимать вдвое больше памяти.

## 3. Векторизация

Векторизация — запись вычисления в виде операций над массивами целиком. Стандартизация признаков
(вычесть среднее столбца, поделить на стандартное отклонение):

```python
rng = np.random.default_rng(42)
X = rng.normal(size=(100_000, 20)) * rng.uniform(0.1, 50, size=20) + rng.uniform(-10, 10, size=20)


def standardize(X):
    return (X - X.mean(axis=0)) / X.std(axis=0)


Z = standardize(X)             # Z.mean(axis=0) — нули, Z.std(axis=0) — единицы
```

Та же функция с циклами по столбцам и строкам выполняется 1.36 с, векторная — 25 мс: в 54 раза быстрее.

`np.vectorize` векторизацией не является: это цикл Python в удобной обёртке.
`np.vectorize(lambda v: v * 2 + 1)` на миллионе элементов работает 158 мс против 0.9 мс у `x * 2 + 1`.

## 4. Broadcasting

В `X - X.mean(axis=0)` складываются массивы форм `(100000, 20)` и `(20,)`. Правила, по которым NumPy
согласует формы:

1. Формы выравниваются **по правому краю**; недостающие оси слева считаются равными 1.
2. В каждой позиции размеры должны совпадать, либо один из них должен быть равен 1.
3. Ось размера 1 «растягивается» до размера партнёра — без копирования данных.

```
X            (100000, 20)        A[:, None, :]   (2000,    1, 64)        X           (5, 3)
X.mean(0)    (       20)         B[None, :, :]   (   1, 1000, 64)        X.sum(1)    (   5)
результат    (100000, 20)        результат       (2000, 1000, 64)        ошибка: 3 и 5 несовместимы
```

Проверить формы, не создавая массивов: `np.broadcast_shapes((8, 1, 3), (7, 1))` вернёт `(8, 7, 3)`.
Третий столбец схемы — самая частая ошибка: поделить каждую строку на её сумму.

```python
X5 = np.arange(15.0).reshape(5, 3)
row_sum = X5.sum(axis=1)                        # форма (5,)
# X5 / row_sum  -> ValueError: operands could not be broadcast together with shapes (5,3) (5,)

X5 / row_sum[:, np.newaxis]                     # (5, 3) / (5, 1): np.newaxis (синоним None) вставляет ось
X5 / row_sum.reshape(-1, 1)                     # то же через reshape
X5 / X5.sum(axis=1, keepdims=True)              # ось не исчезает при агрегации — предпочтительный способ
```

Ошибка формы — хороший исход. Плохой — когда формы случайно совместимы и код молча считает не то:

```python
S = np.arange(1.0, 10.0).reshape(3, 3)
(S / S.sum(axis=1)).sum(axis=1)                 # array([0.425, 1.25 , 2.075]) — строки НЕ нормированы
(S / S.sum(axis=1, keepdims=True)).sum(axis=1)  # array([1., 1., 1.])

y = np.array([1.0, 2.0, 3.0])                   # форма (3,)
pred = np.array([[1.1], [1.9], [3.2]])          # форма (3, 1) — так возвращают многие модели
((y - pred) ** 2).mean()                        # 1.42: разность имеет форму (3, 3)!
((y - pred.ravel()) ** 2).mean()                # 0.02 — правильный MSE
```

На квадратной матрице деление на `(3,)` прошло без ошибки, но поделило столбцы, а не строки. Во втором
примере вместо трёх разностей посчитаны девять — функция потерь выглядит правдоподобно, модель не учится.
Правило: **перед вычитанием целей и предсказаний проверяйте `shape` обоих массивов**, а при агрегации
по оси, результат которой участвует в арифметике с исходным массивом, пишите `keepdims=True`.

## 5. Универсальные функции (ufuncs)

`np.add`, `np.exp`, `np.maximum` и ещё около сотни функций — объекты типа `np.ufunc`: поэлементные
операции с поддержкой broadcasting. Операторы `+`, `*`, `>` — это вызовы ufunc. У бинарных ufunc есть
методы:

```python
x = np.array([1, 2, 3, 4])
np.add.reduce(x)                                    # 10 — то же, что x.sum()
np.add.accumulate(x)                                # array([ 1,  3,  6, 10]) — то же, что x.cumsum()
np.maximum.accumulate(np.array([3, 1, 4, 1, 5]))    # array([3, 3, 4, 4, 5]) — бегущий максимум
np.multiply.outer(np.arange(1, 4), np.arange(1, 5)) # таблица умножения 3×4: все пары элементов

counts = np.zeros(4, dtype=int)
np.add.at(counts, np.array([0, 1, 1, 3, 1]), 1)     # counts -> array([1, 3, 0, 1])
```

`at` выполняет операцию на месте по индексам и, в отличие от `counts[idx] += 1`, учитывает повторяющиеся
индексы. Почему `+=` их теряет и где это ломает обучение — в уроке 2.2.2.

Параметр `out=` записывает результат в готовый массив, `where=` применяет функцию только там, где
условие истинно, остальные элементы `out` не трогаются:

```python
p = np.array([0.5, 0.0, 0.25, 1.0])
np.log(p, out=np.zeros_like(p), where=p > 0)        # array([-0.693,  0.   , -1.386,  0.   ])

num, den = np.array([1.0, 2.0, 3.0]), np.array([2.0, 0.0, 4.0])
np.divide(num, den, out=np.zeros_like(num), where=den != 0)    # array([0.5 , 0.  , 0.75])
```

Без `where=` обе строки выдали бы `RuntimeWarning` и `-inf`/`inf` в результате. Используйте `where=`
всегда вместе с `out=`: без него «пропущенные» элементы содержат мусор из неинициализированной памяти.

## 6. Агрегации по осям

`axis` — ось, которая **исчезает** из результата:

```python
M = np.arange(6).reshape(2, 3)       # [[0, 1, 2], [3, 4, 5]]
M.sum()                              # 15 — по всем элементам
M.sum(axis=0)                        # array([3, 5, 7]) — исчезла ось строк: сумма по каждому столбцу
M.sum(axis=1)                        # array([ 3, 12]) — сумма по каждой строке
M.argmax(axis=1)                     # array([2, 2]) — номер максимума в каждой строке

batch = rng.random((32, 28, 28, 3))  # 32 картинки 28×28 с тремя каналами
batch.mean(axis=(0, 1, 2)).shape     # (3,) — среднее по каждому каналу
batch.mean(axis=(1, 2)).shape        # (32, 3) — средний цвет каждой картинки
```

Пропуски «заражают» результат: `np.array([1.0, np.nan, 3.0]).mean()` — `nan`; игнорируют их `np.nanmean`,
`np.nansum`, `np.nanstd`. Длинные накопленные суммы считайте во `float64`: для десяти миллионов значений
`0.1` типа `float32` последний элемент `np.cumsum(x)` равен `1087937` — ошибка 9 %.

## 7. `np.einsum`

`einsum` описывает операцию над осями строкой: буквы — оси, повторяющаяся буква — умножение вдоль общей
оси, буква, которой нет после `->`, суммируется.

```python
A, B, v = rng.random((4, 3)), rng.random((3, 5)), rng.random(3)

np.einsum("ij,jk->ik", A, B)         # матричное произведение A @ B
np.einsum("ij,j->i", A, v)           # матрица на вектор A @ v
np.einsum("ij,ij->i", A, A)          # сумма квадратов каждой строки: (A * A).sum(axis=1)

Q, K = rng.random((8, 4, 3)), rng.random((8, 5, 3))
np.einsum("bqd,bkd->bqk", Q, K).shape    # (8, 4, 5): то же, что Q @ K.transpose(0, 2, 1), — ядро attention
```

Когда `einsum` выигрывает: `"ij,ij->i"` на массиве 200 000×64 выполняется 13 мс против 41 мс у
`(X * X).sum(axis=1)` — временный массив `X * X` не создаётся. Когда проигрывает: произведение матриц
1000×1000 через `einsum("ij,jk->ik", ...)` — 395 мс, через `@` — 47 мс, потому что `@` вызывает
оптимизированную библиотеку BLAS. С параметром `optimize=True` `einsum` тоже обращается к BLAS (39 мс).
Правило: для обычного матричного произведения — `@`, для нестандартных свёрток по осям — `einsum`.

## 8. Временные массивы и операции на месте

Каждая операция создаёт новый массив размером с результат. В выражении `a * b + c * 2.0 - 1.0` для
массивов по 40 МБ пиковое потребление — 80 МБ сверх исходных данных: `a * b` и `c * 2.0` существуют
одновременно. Избавиться от выделений памяти можно, считая в заранее созданные буферы:

```python
n = 5_000_000
a, b, c = rng.random(n), rng.random(n), rng.random(n)
out, tmp = np.empty(n), np.empty(n)

np.multiply(a, b, out=out)
np.multiply(c, 2.0, out=tmp)
out += tmp                # операции на месте: новый массив не создаётся
out -= 1.0
```

Исходное выражение выполняется 25.4 мс и выделяет 80 МБ, вариант с буферами — 19.2 мс и не выделяет
ничего. Выигрыш по времени — 25 %, и ради него одного усложнять код не стоит. Буферы оправданы в двух
случаях: операция повторяется в цикле тысячи раз (шаг обучения) или массивы настолько велики, что лишняя
копия не помещается в память.

Ловушка операций на месте — функция, которая меняет свой аргумент: `x -= x.mean()` внутри функции
изменит массив вызывающего кода, и данные «испортятся» далеко от места ошибки. Операции на месте
применяйте только к массивам, которые создали сами.

## 9. Приёмы в задачах ML

### Попарные расстояния

Нужны квадраты евклидовых расстояний между всеми парами строк `A` (2000×64) и `B` (1000×64) — основа kNN,
k-means, поиска похожих объектов. Через broadcasting — дословная запись определения:

```python
A, B = rng.random((2000, 64)), rng.random((1000, 64))


def pairwise_broadcast(A, B):
    diff = A[:, np.newaxis, :] - B[np.newaxis, :, :]        # (2000, 1000, 64)
    return (diff**2).sum(axis=-1)
```

Через разложение ‖a − b‖² = ‖a‖² + ‖b‖² − 2·a·b трёхмерный массив не нужен:

```python
def pairwise_gram(A, B):
    a2 = np.einsum("ij,ij->i", A, A)[:, np.newaxis]         # (2000, 1)
    b2 = np.einsum("ij,ij->i", B, B)[np.newaxis, :]         # (1, 1000)
    d2 = a2 + b2 - 2.0 * (A @ B.T)                          # (2000, 1000)
    return np.maximum(d2, 0.0, out=d2)
```

| Вариант | Время | Пиковая память |
|---|---|---|
| двойной цикл Python по парам строк | 2.8 с | 16 МБ |
| `pairwise_broadcast` | 718 мс | 2064 МБ |
| `pairwise_gram` | 23.6 мс | 32 МБ |

Вариант с broadcasting создаёт `diff` и `diff**2` по 2000·1000·64·8 байт = 1 ГБ каждый, хотя результат
занимает 16 МБ. На выборке в десять раз больше он потребует 200 ГБ. Разложение быстрее в 30 раз (основная
работа — одно матричное произведение в BLAS) и почти не требует памяти.

Цена разложения — точность: из больших близких чисел вычитаются большие близкие числа. Расстояние
от точки до самой себя получается не нулём, а величиной порядка 10⁻⁸ со случайным знаком, во `float32`
на данных масштаба 1000 — до ±16. Поэтому результат обрезается снизу нулём: иначе `np.sqrt` вернёт `nan`.

### Softmax

```python
def softmax(z):
    shifted = z - z.max(axis=1, keepdims=True)
    e = np.exp(shifted)
    return e / e.sum(axis=1, keepdims=True)


logits = np.array([[1.0, 2.0, 3.0], [1000.0, 1001.0, 1002.0]])
softmax(logits)
# array([[0.09003057, 0.24472847, 0.66524096],
#        [0.09003057, 0.24472847, 0.66524096]])
```

Вычитание максимума строки не меняет результат (числитель и знаменатель делятся на одно и то же число),
но делает наибольший показатель экспоненты нулём. Без него `np.exp(1000.0)` переполняется, и вторая
строка превращается в `[nan, nan, nan]` с предупреждением `overflow encountered in exp`. Если нужен
логарифм вероятностей, считайте его напрямую — `shifted - np.log(np.exp(shifted).sum(axis=1, keepdims=True))`:
`np.log(softmax(z))` для логитов `[0, 800]` даёт `-inf`, прямая формула — `-800`.

### Косинусное сходство и one-hot

```python
E, Qv = rng.normal(size=(5, 4)), rng.normal(size=(2, 4))     # 5 документов и 2 запроса
En = E / np.linalg.norm(E, axis=1, keepdims=True)
Qn = Qv / np.linalg.norm(Qv, axis=1, keepdims=True)
sim = Qn @ En.T                      # (2, 5): сходство каждого запроса с каждым документом
sim.argmax(axis=1)                   # номер самого похожего документа для каждого запроса

labels = np.array([2, 0, 1, 2])
np.eye(3, dtype=np.float32)[labels]  # one-hot: строка единичной матрицы для каждой метки
```

One-hot через индексацию единичной матрицы — пример fancy indexing, темы следующего урока.

## Типичные ошибки

| Симптом | Причина | Решение |
|---|---|---|
| NumPy-код не быстрее чистого Python | цикл `for` по элементам массива или `np.vectorize` | операции над массивом целиком |
| `operands could not be broadcast together with shapes (5,3) (5,)` | агрегат по строкам потерял ось | `keepdims=True` или `[:, np.newaxis]` |
| Функция потерь считается, модель не учится | `y` формы `(n,)` вычтен из предсказаний формы `(n, 1)` — получилась матрица `(n, n)` | проверять `shape`, привести обе формы к `(n,)` |
| Изменился массив, который не трогали | работали с view (срез, `reshape`, `.T`) | `.copy()`; проверка через `np.shares_memory` |
| `MemoryError` или своп на попарных операциях | broadcasting создал массив `(n, m, d)` | разложение через матричное произведение или обработка частями |
| `nan` после `np.exp`, предупреждение `overflow` | экспонента от больших значений | вычесть максимум до `exp` |
| Значения «зацикливаются» (200 + 100 = 44) | переполнение целого типа малой разрядности | привести к более широкому типу до арифметики |
| Память выросла вдвое после одной операции | `float32` смешан с массивом `float64` | следить за `dtype`, приводить входы к одному типу |
