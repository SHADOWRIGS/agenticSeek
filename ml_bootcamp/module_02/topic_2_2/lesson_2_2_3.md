## Цели урока

После урока вы сможете:

- распознать вычисление, которое не векторизуется в NumPy или векторизуется слишком дорого;

- применять `cache=True`, `parallel=True` с `prange` и `fastmath=True` и объяснять их цену;
- находить причины, по которым код с Numba остаётся медленным;

- выбрать между NumPy, Numba и Cython для конкретной задачи.

## Зачем это нужно

Векторизация из двух прошлых уроков покрывает большинство задач, но не все. Экспоненциальное сглаживание,
в котором каждое значение зависит от предыдущего. Обход ряда с условиями и состоянием. Попарные
расстояния, для которых векторная запись требует гигабайты временных массивов. В таких местах код либо
остаётся циклом Python и работает в сто раз медленнее остального пайплайна, либо превращается
в нечитаемую конструкцию из `cumsum` и `where`.

Numba и Cython решают эту задачу одинаково: превращают цикл в машинный код. Numba — компилятором «на лету»
прямо из Python-функции, Cython — заранее, через C. Этот урок — рабочее знакомство с обоими. Устройство
JIT-компиляции подробно разбирается в уроке 6.3.3, расширения на C++ — в теме 6.1.

Проверено на Python 3.12.13, NumPy 2.5.4, Numba 0.68.1 (llvmlite 0.50.0), Cython 3.3.1, setuptools 84.2.1,
компилятор gcc 13.3. Замеры — на машине с четырьмя ядрами; ваши цифры будут другими, важен порядок величин.

## 1. Когда NumPy недостаточно

**Шаги зависят друг от друга.** Экспоненциальное сглаживание: `out[i] = α·x[i] + (1 − α)·out[i − 1]`.

```python
import numpy as np


def ewma_python(x, alpha):
    out = np.empty(len(x))
    out[0] = x[0]
    for i in range(1, len(x)):
        out[i] = alpha * x[i] + (1.0 - alpha) * out[i - 1]
    return out
```

Чтобы посчитать `out[i]`, нужен уже готовый `out[i - 1]` — операцией над массивом целиком это не выразить.
Для самых частых рекуррентных формул есть готовые функции (`np.cumsum`, `scipy.signal.lfilter`,
`ewm` в pandas), но стоит добавить в формулу условие — и готовой функции нет.

**Ветвления и состояние.** Самая длинная серия подряд идущих значений выше порога:

```python
def longest_streak(x, threshold):
    best = current = 0
    for value in x:
        if value > threshold:
            current += 1
            best = max(best, current)
        else:
            current = 0
    return best
```

Векторная версия существует (найти границы серий через сравнение соседних элементов маски и вычесть их),
на миллионе элементов она работает 1.5 мс против 37 мс у цикла по списку. Но она занимает пять неочевидных
строк и ломается при любом изменении условия — например, «серия прерывается только двумя значениями подряд».

**Временные массивы.** Попарные расстояния через broadcasting из урока 2.2.1 создают массив `(n, m, d)`.
Цикл считает то же самое, не выделяя ничего, кроме результата, — если бы он не был циклом Python.

## 2. Numba: `@njit`

Установка: `uv add numba`. Numba поддерживает ограниченный диапазон версий NumPy: версия 0.68.1 требует
`numpy < 2.6`. `uv` учитывает это сам и при необходимости оставит более старый NumPy — не обходите это
ограничение вручную.

```python
from numba import njit

ewma_numba = njit(ewma_python)          # то же, что поставить @njit над определением функции
```

`@njit` (сокращение от `@jit(nopython=True)`) при первом вызове определяет типы аргументов, компилирует
функцию в машинный код под эти типы и дальше вызывает его в обход интерпретатора. Код функции не меняется.

```python
import time

x = np.random.default_rng(42).normal(size=1_000_000).cumsum()

start = time.perf_counter()
ewma_numba(x, 0.1)
print(f"первый вызов: {(time.perf_counter() - start) * 1e3:.0f} мс")     # первый вызов: 683 мс

start = time.perf_counter()
ewma_numba(x, 0.1)
print(f"второй вызов: {(time.perf_counter() - start) * 1e3:.1f} мс")     # второй вызов: 2.8 мс
```

Первый вызов в 240 раз медленнее второго: в него входит компиляция. Отсюда два правила.

1. **Замеряйте второй вызов.** `%timeit` сразу после определения функции покажет завышенное время, если
   компиляция попадёт в замер. Вызовите функцию один раз на маленьком входе, затем измеряйте.
2. **Компиляция окупается не всегда.** Функция, которая вызывается один раз и работает 100 мс, с Numba
   станет медленнее.

Скомпилированные варианты хранятся отдельно для каждого набора типов: вызов с массивом `float32` после
`float64` запустит компиляцию заново (`ewma_numba.signatures` покажет оба варианта).

**`cache=True`** сохраняет машинный код на диск (в `__pycache__`), и следующий запуск программы его
загружает, а не компилирует:

| Функция | Первый вызов без кэша | Первый вызов из кэша |
|---|---|---|
| `ewma` с `@njit(cache=True)` | 450 мс | 320 мс |
| попарные расстояния с `@njit(parallel=True, cache=True)` | 900 мс | 330 мс |

Около 300 мс остаётся в любом случае — это инициализация самой Numba при первом обращении к ней. При
изменении исходного кода функции кэш сбрасывается, и она компилируется заново.

## 3. `parallel=True` и `fastmath=True`

Попарные квадраты расстояний — три вложенных цикла:

```python
from numba import prange


@njit(parallel=True)
def pairwise_numba_parallel(a, b):
    n, m, d = a.shape[0], b.shape[0], a.shape[1]
    out = np.empty((n, m))
    for i in prange(n):                 # итерации внешнего цикла раздаются потокам
        for j in range(m):
            acc = 0.0
            for k in range(d):
                diff = a[i, k] - b[j, k]
                acc += diff * diff
            out[i, j] = acc
    return out
```

`prange` объявляет, что итерации цикла независимы и могут выполняться в разных потоках. Проверить это
Numba не может: если итерации пишут в одну и ту же ячейку (кроме простых накоплений вида `total += ...`
в скалярную переменную), результат будет неверным без каких-либо ошибок. Здесь каждая итерация `i` пишет
только в свою строку `out[i]` — это безопасно.

`fastmath=True` разрешает компилятору нарушать стандарт IEEE 754: переставлять слагаемые, считать, что
`nan` и бесконечностей не бывает. Перестановка слагаемых позволяет складывать по несколько чисел одной
SIMD-инструкцией.

| Вариант (A: 2000×64, B: 1000×64) | Время |
|---|---|
| `@njit` | 50.7 мс |
| `@njit(fastmath=True)` | 22.0 мс |
| `@njit(parallel=True)`, 4 потока | 37.1 мс |

Цена `fastmath`: результат может отличаться в последних знаках от обычной версии, а проверки вида
`np.isnan(x)` компилятор вправе выбросить. Не включайте его в коде, где возможны пропуски. Цена
`parallel`: потоки делят память и кэш процессора, поэтому на четырёх ядрах получилось ускорение в 1.4 раза,
а не в четыре; на маленьких входах запуск потоков дороже самой работы.

## 4. Что Numba не умеет и почему код остаётся медленным

Numba компилирует подмножество Python: числа, кортежи, циклы, условия, массивы NumPy и большую часть
функций NumPy. Не поддерживаются pandas, scikit-learn, SciPy (кроме отдельных функций), произвольные
классы, словари и списки со значениями разных типов, обработка строк в привычном объёме. Попытка передать
`DataFrame` заканчивается ошибкой при первом вызове:

```
numba.core.errors.TypingError: Failed in nopython mode pipeline (step: nopython frontend)
non-precise type pyobject
```

Рабочая схема: pandas и логика — снаружи, внутрь `@njit`-функции передаются массивы
(`df["units"].to_numpy()`), наружу возвращаются массивы.

| Причина медленного кода | Что происходит | Наш замер |
|---|---|---|
| Компиляция попала в замер | первый вызов включает сотни миллисекунд компиляции | 683 мс против 2.8 мс |
| На вход передан список | список копируется и проверяется поэлементно при каждом вызове | сумма миллиона чисел: 449 мс против 0.6 мс для массива |
| Временные массивы внутри цикла | `a[i] ** 2` выделяет память на каждой итерации | нормы 200 000 строк: 8.0 мс против 1.5 мс у скалярного цикла |
| Код уже векторизован | NumPy и BLAS оптимизированы лучше, чем простой цикл | расстояния через `A @ B.T`: 19 мс против 51 мс у `@njit` |
| Маленький вход, один вызов | компиляция не окупается | — |

Третья строка — непривычное следствие: внутри `@njit` выгоден стиль, обратный векторизации. Явные циклы
со скалярными переменными быстрее операций над срезами, потому что не создают массивов.

## 5. Cython

Cython — язык-надмножество Python с объявлениями типов C. Файл `.pyx` транслируется в C и компилируется
в модуль расширения, который импортируется как обычный модуль. Нужен компилятор C — вы установили его
в уроке 1.1.1 (`build-essential` или Xcode Command Line Tools).

Файл `fast_ops.pyx`:

```cython
# cython: language_level=3, boundscheck=False, wraparound=False
import numpy as np


def ewma(const double[::1] x, double alpha):
    cdef Py_ssize_t i, n = x.shape[0]
    cdef double[::1] out = np.empty(n)
    out[0] = x[0]
    for i in range(1, n):
        out[i] = alpha * x[i] + (1.0 - alpha) * out[i - 1]
    return np.asarray(out)


def pairwise_sq_distances(const double[:, ::1] a, const double[:, ::1] b):
    cdef Py_ssize_t i, j, k
    cdef Py_ssize_t n = a.shape[0], m = b.shape[0], d = a.shape[1]
    cdef double acc, diff
    cdef double[:, ::1] out = np.empty((n, m))
    for i in range(n):
        for j in range(m):
            acc = 0.0
            for k in range(d):
                diff = a[i, k] - b[j, k]
                acc += diff * diff
            out[i, j] = acc
    return np.asarray(out)
```

Что здесь отличается от Python:

- **`cdef`** объявляет переменную C. Цикл по `cdef Py_ssize_t i` и арифметика над `cdef double` выполняются
  без объектов Python;
- **`double[::1]`** — типизированный memoryview: одномерный непрерывный буфер `float64`. `double[:, ::1]` —
  двумерный массив в C-порядке. Обращение `x[i]` превращается в чтение из памяти по адресу. `const`
  разрешает принимать массивы, доступные только для чтения;
- **`np.asarray(out)`** превращает memoryview обратно в массив NumPy без копирования;
- **директивы в первой строке**: `boundscheck=False` отключает проверку выхода за границы,
  `wraparound=False` — поддержку отрицательных индексов.

**Сборка.** Минимальный способ — утилита `cythonize`, которая ставится вместе с Cython:

```bash
uv add cython setuptools
uv run cythonize -i fast_ops.pyx
```

Флаг `-i` (in-place) кладёт собранный модуль рядом с исходником: появляются `fast_ops.c`,
`fast_ops.cpython-312-x86_64-linux-gnu.so` (имя зависит от платформы) и папка `build/`. Все три — продукты
сборки, добавьте `*.c`, `*.so` и `build/` в `.gitignore`. После этого модуль импортируется из той же папки:

```python
import fast_ops

smoothed = fast_ops.ewma(x, 0.1)
```

Когда расширение становится частью пакета, сборку описывают в `setup.py`:

```python
from Cython.Build import cythonize
from setuptools import Extension, setup

extensions = [Extension("fast_ops", ["fast_ops.pyx"], extra_compile_args=["-O3"])]
setup(name="fast_ops", ext_modules=cythonize(extensions, annotate=True))
```

и собирают командой `uv run python setup.py build_ext --inplace`. Параметр `annotate=True` создаёт
`fast_ops.html`: строки, в которых остались обращения к интерпретатору Python, подсвечены жёлтым.
Это главный инструмент оптимизации в Cython — жёлтых строк внутри циклов быть не должно.

**Типы решают всё.** Тот же `ewma`, собранный Cython в трёх вариантах:

| Вариант | Время (миллион элементов) |
|---|---|
| код Python без единого `cdef`, просто скомпилированный | 190 мс |
| типизированный, с проверкой границ | 1.82 мс |
| типизированный, `boundscheck=False`, `wraparound=False` | 1.78 мс |

Компиляция без типов почти ничего не даёт (цикл Python по массиву — 241 мс): операции по-прежнему идут через
объекты. Ускорение в сто раз приносят объявления типов. Отключение проверок на этом цикле — в пределах
погрешности, на попарных расстояниях — 66 мс против 71 мс. При этом с `boundscheck=False` выход за границы
массива — это не `IndexError`, а чтение чужой памяти: мусор в результате или аварийное завершение процесса.
Отключайте проверки в последнюю очередь, на отлаженном коде.

**Строгость к входам.** Типизированный memoryview принимает только то, что объявлено:

```python
fast_ops.ewma(x[::2], 0.1)                  # ValueError: ndarray is not C-contiguous
fast_ops.ewma(x.astype(np.float32), 0.1)    # ValueError: Buffer dtype mismatch, expected 'const double' ...
```

Numba в этих случаях молча скомпилирует ещё один вариант функции; Cython требует привести вход явно:
`np.ascontiguousarray(values, dtype=np.float64)`.

## 6. Сравнение

**Экспоненциальное сглаживание**, миллион элементов `float64`:

| Реализация | Время | Ускорение |
|---|---|---|
| цикл Python по массиву NumPy | 241 мс | 1 |
| цикл Python по списку | 67.9 мс | 3.5 |
| готовая функция `scipy.signal.lfilter` | 4.46 мс | 54 |
| Numba `@njit` | 1.90 мс | 127 |
| Cython | 1.78 мс | 135 |

**Попарные квадраты расстояний**, A: 2000×64, B: 1000×64:

| Реализация | Время | Ускорение | Пиковая память |
|---|---|---|---|
| три вложенных цикла Python | 29.9 с | 1 | 16 МБ |
| NumPy, broadcasting | 813 мс | 37 | 2064 МБ |
| NumPy, разложение через `A @ B.T` | 19.2 мс | 1560 | 32 МБ |
| Numba `@njit` | 50.7 мс | 590 | 16 МБ |
| Numba `@njit(fastmath=True)` | 22.0 мс | 1360 | 16 МБ |
| Numba `@njit(parallel=True)` | 37.1 мс | 810 | 16 МБ |
| Cython | 48.0 мс | 620 | 16 МБ |

Выводы из таблиц:

1. Numba и Cython дают один порядок скорости: оба порождают машинный код одного и того же цикла.
   Выбор между ними — вопрос удобства, а не производительности.
2. Там, где задача сводится к матричному произведению, NumPy с BLAS не уступает компилируемому циклу:
   удачная формула важнее инструмента.
3. Неудачная векторизация (broadcasting с массивом на 2 ГБ) в 16 раз медленнее скомпилированного цикла
   и требует в 130 раз больше памяти.
4. Цикл Python по массиву NumPy — худший из вариантов; если цикл неизбежен и компилировать его нельзя,
   переведите данные в список (`x.tolist()`).

## 7. Что выбирать

| Ситуация | Инструмент |
|---|---|
| Операция выражается через массивы целиком без гигантских временных массивов | NumPy |
| Есть готовая функция в NumPy, SciPy или pandas | готовая функция |
| Цикл с зависимостью шагов, ветвлениями, состоянием; данные — числовые массивы | Numba |
| Нужно быстро проверить, даст ли компиляция выигрыш | Numba: один декоратор |
| Код поставляется как библиотека, зависимость от Numba и компиляция при запуске нежелательны | Cython |
| Нужно вызвать существующую библиотеку на C или работать с её структурами | Cython |
| Большой объём кода на C++ с собственными классами | pybind11 (тема 6.1) |

Порядок действий всегда один: сначала профилирование (урок 1.2.3), чтобы найти функцию, на которую
действительно уходит время; затем попытка векторизации; затем Numba; Cython — когда есть причина
из таблицы. Ускорять код, который занимает 2 % времени пайплайна, бессмысленно любым инструментом.

## Типичные ошибки

| Симптом | Причина | Решение |
|---|---|---|
| «Numba не ускорила код» в замере | измерен первый вызов вместе с компиляцией | вызвать функцию один раз до замера |
| `TypingError: ... non-precise type pyobject` | в функцию передан объект, который Numba не понимает (`DataFrame`, произвольный класс) | передавать массивы NumPy и числа |
| `NumbaPendingDeprecationWarning: ... reflected list` и медленная работа | на вход передан список Python | `np.asarray(values)` до вызова |
| Результат с `parallel=True` меняется от запуска к запуску | итерации `prange` пишут в общие ячейки | каждая итерация пишет только в «свои» элементы |
| `ModuleNotFoundError` после `cythonize` | модуль собран в другой папке или под другую версию Python | собирать с `-i` через `uv run` из папки с `.pyx` |
| `ValueError: ndarray is not C-contiguous` | в memoryview `double[::1]` передан срез с шагом | `np.ascontiguousarray(...)` |
| `Buffer dtype mismatch` | тип массива не совпал с объявленным | `astype(np.float64)` или привести тип при загрузке |
| Cython-код не быстрее Python | в цикле остались нетипизированные переменные | `cdef` для индексов и накопителей; проверить отчёт `annotate` |
| Процесс падает с `Segmentation fault` | выход за границы при `boundscheck=False` | вернуть проверки, найти ошибку, отключить снова |
