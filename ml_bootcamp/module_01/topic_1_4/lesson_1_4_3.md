# Урок 1.4.3: Автоматизация задач: cron, systemd timers

> **Модуль 1:** Foundations & Mindset Engineer · **Тема 1.4:** Linux и командная строка
> **Тип:** теория · **Время:** 90 минут + 90 минут на домашнее задание

## Цели урока

После урока вы сможете:

- читать и писать расписания cron и настраивать задачи через `crontab`;
- объяснить, почему команда работает в терминале, но не работает в cron, и исправить это;
- защитить периодическую задачу от наложения запусков и сохранить её вывод в лог;
- оформить задачу парой юнитов systemd `.service` + `.timer` и проверить расписание до установки;
- выбрать между cron, таймерами systemd и оркестратором для конкретной задачи.

## Зачем это нужно

Вокруг модели всегда есть работа, которую никто не хочет делать руками: переобучить модель на свежих данных
ночью, раз в час забрать выгрузку из хранилища, раз в неделю удалить старые чекпоинты, раз в сутки сделать
бэкап. Сделать «по расписанию» легко. Сложнее сделать так, чтобы задача:

- запускалась в том же окружении, в котором её отлаживали;
- не запускалась второй раз, пока не закончился первый запуск;
- оставляла после себя лог, по которому утром видно, что произошло ночью;
- не терялась, если сервер в назначенное время был выключен.

Типичный инцидент: ежечасная выгрузка данных однажды работает 70 минут, cron запускает вторую копию поверх
первой, обе пишут в один файл, и ночное переобучение стартует на испорченных данных.

## 1. cron: устройство и команды

Демон `cron` раз в минуту просматривает таблицы заданий (crontab) и запускает те строки, расписание которых
совпало с текущим временем. У каждого пользователя своя таблица; задачи выполняются от его имени.

```bash
crontab -l                      # показать свою таблицу
crontab -e                      # открыть её в редакторе; после сохранения cron подхватит изменения сам
crontab crontab.txt             # заменить таблицу содержимым файла
crontab -l > crontab.backup     # сохранить копию
```

`crontab -r` удаляет всю таблицу без подтверждения, а на клавиатуре `r` соседствует с `e`. Поэтому таблицу
держат в файле под Git и устанавливают командой `crontab crontab.txt`.

Системные задачи лежат в `/etc/crontab` и `/etc/cron.d/`. Формат там отличается одним полем: после расписания
указывается имя пользователя.

## 2. Синтаксис расписания

Строка crontab — пять полей расписания и команда:

```text
┌───────── минута        (0–59)
│ ┌─────── час           (0–23)
│ │ ┌───── день месяца   (1–31)
│ │ │ ┌─── месяц         (1–12)
│ │ │ │ ┌─ день недели   (0–7; 0 и 7 — воскресенье)
│ │ │ │ │
30 2 * * *  команда
```

| Запись в поле | Значение |
|---|---|
| `*` | любое значение |
| `5` | ровно это значение |
| `1,15` | список значений |
| `9-18` | диапазон |
| `*/15` | каждое 15-е значение, начиная с нуля |

| Расписание | Когда выполняется |
|---|---|
| `30 2 * * *` | каждый день в 02:30 |
| `5 * * * *` | каждый час на 5-й минуте |
| `*/15 * * * *` | каждые 15 минут |
| `0 */6 * * *` | в 00:00, 06:00, 12:00 и 18:00 |
| `0 9-18 * * 1-5` | каждый час с 09:00 до 18:00 по будням |
| `0 4 * * 0` | по воскресеньям в 04:00 |
| `0 1 1 * *` | первого числа каждого месяца в 01:00 |
| `@hourly`, `@daily` | сокращения для `0 * * * *` и `0 0 * * *` |
| `@reboot` | один раз при старте системы |

Три ловушки синтаксиса:

1. **Забытая минута.** `* 2 * * *` — не «в два часа ночи», а каждую минуту с 02:00 до 02:59: 60 запусков.
2. **День месяца и день недели объединяются по «или».** `0 0 13 * 5` сработает и 13-го числа, и в каждую
   пятницу, а не только в пятницу 13-го.
3. **Символ `%` в команде cron заменяет на перевод строки.** В `date +%F` его нужно экранировать: `date +\%F`.

Время в расписании — местное время сервера, а серверы обычно живут в UTC. Проверьте командой `date`:
02:30 UTC — это 05:30 по Москве.

## 3. Окружение cron: почему «в терминале работает, а в cron нет»

Задача cron запускается не из вашей оболочки. Отличия от терминала:

| Что | В терминале | В cron |
|---|---|---|
| Оболочка | bash | `/bin/sh` |
| `PATH` | длинный, с `~/.local/bin` и другими папками | `/usr/bin:/bin` |
| `~/.bashrc`, `~/.profile` | прочитаны | не читаются |
| Активированное окружение Python | есть | нет |
| Текущая папка | папка проекта | домашняя папка |
| Переменные вроде `CUDA_VISIBLE_DEVICES`, ключи доступа | заданы | не заданы |

Отсюда типичные поломки: `uv: command not found`, `python` оказывается системным без нужных пакетов,
`FileNotFoundError` на относительном пути `data/train.csv`.

Воспроизвести окружение cron в терминале можно, запустив команду с «пустым» окружением:

```bash
env -i HOME="$HOME" SHELL=/bin/sh PATH=/usr/bin:/bin /bin/sh -c 'command -v uv || echo "uv: not found"'
```

Если команда не работает здесь, она не будет работать и в cron. Правила, которые закрывают проблему:

- в начале crontab задайте `SHELL` и `PATH`;
- в каждой задаче переходите в папку проекта: `cd /opt/ml-project && ...`;
- вызывайте интерпретатор окружения напрямую: `.venv/bin/python train.py`;
- сложную логику выносите в скрипт, а в crontab оставляйте одну короткую строку.

## 4. Логи и защита от наложения

cron записывает в системный журнал только факт запуска (`journalctl -u cron` или `grep CRON /var/log/syslog`).
Вывод самой команды он пытается отправить владельцу по почте, а на сервере без почтовой службы — выбрасывает.
Поэтому вывод перенаправляют в файл явно: `>> logs/task.log 2>&1`.

Наложение запусков предотвращает `flock`: он захватывает файл-блокировку, запускает команду и освобождает
блокировку при её завершении. С флагом `-n` второй экземпляр не ждёт, а сразу завершается с кодом 1:

```bash
flock -n /tmp/export.lock ./scripts/export_data.sh
```

Итоговый crontab ML-проекта:

```bash
SHELL=/bin/bash
PATH=/home/mlops/.local/bin:/usr/local/bin:/usr/bin:/bin
MAILTO=""

# Ежечасная выгрузка данных, на 5-й минуте часа
5 * * * *     cd /opt/ml-project && flock -n /tmp/export.lock ./scripts/export_data.sh >> logs/export.log 2>&1

# Ночное переобучение по будням в 02:30
30 2 * * 1-5  cd /opt/ml-project && flock -n /tmp/retrain.lock ./scripts/retrain.sh >> logs/retrain.log 2>&1

# Удаление чекпоинтов старше 14 дней, по воскресеньям в 04:00
0 4 * * 0     find /data/checkpoints -name '*.pt' -mtime +14 -delete >> /opt/ml-project/logs/cleanup.log 2>&1

# Бэкап моделей первого числа каждого месяца в 01:00
0 1 1 * *     cd /opt/ml-project && tar -czf /backup/models_$(date +\%F).tar.gz models >> logs/backup.log 2>&1
```

Внутри `retrain.sh` обучение запускается как `timeout 6h .venv/bin/python train.py ...`: зависший процесс
будет завершён через 6 часов, а `timeout` вернёт код 124. Перед тем как доверить `find ... -delete`
расписанию, выполните ту же команду с `-print` вместо `-delete` и посмотрите на список.

## 5. Таймеры systemd

В systemd периодическая задача — это два юнита с одинаковым именем: `.service` описывает, **что** запускать,
`.timer` — **когда**. Сервис — обычный юнит из прошлого урока, только с `Type=oneshot`: процесс должен
отработать и завершиться.

`/etc/systemd/system/cleanup-checkpoints.service`:

```ini
[Unit]
Description=Remove model checkpoints older than 14 days

[Service]
Type=oneshot
User=mlops
ExecStart=/usr/bin/find /data/checkpoints -name "*.pt" -mtime +14 -delete
```

`/etc/systemd/system/cleanup-checkpoints.timer`:

```ini
[Unit]
Description=Weekly checkpoint cleanup

[Timer]
OnCalendar=Sun 04:00
Persistent=true
RandomizedDelaySec=10min

[Install]
WantedBy=timers.target
```

| Директива таймера | Смысл |
|---|---|
| `OnCalendar` | расписание по календарю |
| `Persistent=true` | если в назначенное время сервер был выключен, задача выполнится сразу после включения |
| `RandomizedDelaySec` | случайная задержка, чтобы задачи разных таймеров не стартовали в одну секунду |
| `OnBootSec`, `OnUnitActiveSec` | альтернатива календарю: «через 10 минут после загрузки», «через час после прошлого запуска» |
| `Unit` | какой сервис запускать, если его имя отличается от имени таймера |

Формат `OnCalendar` — `ДеньНедели Год-Месяц-День Час:Минута:Секунда`, любую часть можно опустить:

| `OnCalendar` | Нормализованная форма | Когда |
|---|---|---|
| `hourly` | `*-*-* *:00:00` | каждый час |
| `daily` | `*-*-* 00:00:00` | каждый день в полночь |
| `weekly` | `Mon *-*-* 00:00:00` | по понедельникам в полночь |
| `*-*-* 02:30:00` | `*-*-* 02:30:00` | каждый день в 02:30 |
| `Mon..Fri 02:30` | `Mon..Fri *-*-* 02:30:00` | по будням в 02:30 |
| `Sun 04:00` | `Sun *-*-* 04:00:00` | по воскресеньям в 04:00 |
| `*:0/15` | `*-*-* *:00/15:00` | каждые 15 минут |
| `*-*-01 01:00:00` | `*-*-01 01:00:00` | первого числа каждого месяца в 01:00 |
| `*-*-* 02:30:00 Europe/Moscow` | `*-*-* 02:30:00 Europe/Moscow` | каждый день в 02:30 по московскому времени |

Расписание проверяется до установки. Команда показывает, как systemd понял выражение и когда наступят
ближайшие срабатывания:

```bash
systemd-analyze calendar --iterations=3 'Mon..Fri 02:30'
```

```text
  Original form: Mon..Fri 02:30
Normalized form: Mon..Fri *-*-* 02:30:00
    Next elapse: Wed 2026-11-11 02:30:00 UTC
       From now: 1h 11min left
   Iteration #2: Thu 2026-11-12 02:30:00 UTC
       From now: 1 day 1h left
   Iteration #3: Fri 2026-11-13 02:30:00 UTC
       From now: 2 days left
```

(Даты зависят от момента запуска команды.) На ошибочное выражение, например `25:00`, команда ответит
`Failed to parse calendar specification`.

Установка и управление:

```bash
systemd-analyze verify ./cleanup-checkpoints.service ./cleanup-checkpoints.timer
sudo cp cleanup-checkpoints.service cleanup-checkpoints.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now cleanup-checkpoints.timer    # включают таймер, а не сервис

systemctl list-timers                                    # все таймеры: когда сработают и когда срабатывали
sudo systemctl start cleanup-checkpoints.service         # выполнить задачу сейчас, не дожидаясь расписания
systemctl status cleanup-checkpoints.service             # результат последнего запуска
journalctl -u cleanup-checkpoints.service --since today  # вывод задачи
```

Пример вывода `systemctl list-timers` (иллюстративный, сокращён: без столбца `ACTIVATES` с именем сервиса):

```text
NEXT                        LEFT   LAST                        PASSED     UNIT
Sun 2026-03-08 04:03:41 UTC 4 days Sun 2026-03-01 04:07:12 UTC 2 days ago cleanup-checkpoints.timer
```

Что таймеры дают «бесплатно»: stdout и stderr задачи попадают в журнал без перенаправлений; пока сервис
ещё работает, таймер не запустит второй экземпляр — `flock` не нужен; к задаче применимы `User`,
`WorkingDirectory`, `Environment`, `MemoryMax`, `CPUQuota` и `TimeoutStartSec` из прошлого урока.

Без прав root таймер можно установить на уровне пользователя: файлы кладут в `~/.config/systemd/user/`,
директиву `User=` убирают, ко всем командам добавляют флаг `--user` (`systemctl --user enable --now ...`,
`journalctl --user -u ...`). Чтобы такие таймеры работали, когда вы не вошли в систему, один раз выполните
`sudo loginctl enable-linger "$USER"`.

## 6. cron или таймеры systemd

| Критерий | cron | Таймеры systemd |
|---|---|---|
| Настройка | одна строка в crontab | два файла и несколько команд |
| Логи задачи | перенаправлять самому | автоматически в журнале, `journalctl -u` |
| Сервер был выключен в момент запуска | запуск потерян | с `Persistent=true` выполнится после включения |
| Наложение запусков | возможно, нужен `flock` | исключено: сервис не стартует, пока активен |
| Окружение | минимальное, задаётся в crontab | явное: `User`, `WorkingDirectory`, `Environment` |
| Ограничение ресурсов и времени | только вручную (`timeout`) | `MemoryMax`, `CPUQuota`, `TimeoutStartSec` |
| Состояние и история | нет | `systemctl status`, `systemctl list-timers` |
| Запуск вне расписания | копировать команду из crontab | `systemctl start имя.service` |
| Проверка расписания | нет встроенной | `systemd-analyze calendar` |
| Где доступен | практически везде | только в системах с systemd |

Практическое правило: личная мелочь на одной машине — cron; задача, от которой зависит работа команды
и о сбое которой нужно узнать, — таймер systemd.

## 7. Когда пора переходить к оркестратору

И cron, и таймеры запускают **отдельные задачи по времени**. Они перестают подходить, когда:

- задачи зависят друг от друга: обучение должно начаться после успешной выгрузки, а не «в 02:30, выгрузка
  к этому времени обычно заканчивается»;
- упавший шаг нужно автоматически повторить, а о неудаче — оповестить;
- нужно перезапустить расчёт за прошлые даты (backfill);
- задач десятки, и нужен единый экран с историей запусков, длительностью и логами;
- задачи выполняются на нескольких машинах.

Для этого существуют оркестраторы. Apache Airflow разбирается в уроке 7.1.2. До тех пор достаточно cron
и таймеров, а скрипты, написанные по правилам этой темы, позже без изменений станут шагами пайплайна.

## Типичные ошибки

| Симптом | Причина | Решение |
|---|---|---|
| В терминале команда работает, в cron — `command not found` | `PATH` в cron равен `/usr/bin:/bin` | задать `PATH` в crontab или писать абсолютные пути |
| Скрипт в cron не находит `data/train.csv` | текущая папка — домашняя, а не папка проекта | `cd /opt/ml-project && ...` |
| Задача cron «ничего не делает», и непонятно почему | вывод не сохранён | `>> logs/task.log 2>&1`; проверить факт запуска в `journalctl -u cron` |
| Задача запускается 60 раз за час | `*` в поле минут: `* 2 * * *` | `0 2 * * *` |
| Команда с `date +%F` обрывается | `%` в crontab означает перевод строки | `date +\%F` |
| Два экземпляра задачи пишут в один файл | предыдущий запуск не успел закончиться | `flock -n` в cron или таймер systemd |
| Задача выполняется на три часа раньше ожидаемого | расписание в UTC, ожидание — в местном времени | `date`; в таймере — часовой пояс в `OnCalendar` |
| Таймер установлен, но в `list-timers` его нет | включён сервис, а не таймер, или нет `daemon-reload` | `sudo systemctl enable --now имя.timer` |
| После выключения сервера ночная задача не выполнилась | cron не догоняет пропущенные запуски | таймер с `Persistent=true` |

## Домашнее задание

Настройте одну и ту же периодическую задачу двумя способами и подготовьте расписание для ML-проекта.

1. Напишите скрипт `heartbeat.sh`, который дописывает в `~/heartbeat.log` строку с текущим временем,
   load average и объёмом доступной памяти. Требования к скрипту — как в уроке 1.4.1.
2. Добавьте в crontab запуск `heartbeat.sh` каждую минуту и вторую задачу, которая один раз в минуту
   сохраняет вывод `env` в файл. Через три минуты убедитесь, что в логе три строки. Сравните сохранённое
   окружение с выводом `env` в терминале и запишите в `report.md` три найденных отличия. Удалите обе задачи.
3. Оформите ту же задачу парой `heartbeat.service` + `heartbeat.timer` с расписанием «каждые 5 минут».
   Проверьте юниты через `systemd-analyze verify`, расписание — через `systemd-analyze calendar`.
   Установите таймер (на уровне системы или пользователя), дождитесь двух срабатываний, сохраните в отчёт
   вывод `systemctl list-timers` и `journalctl` для сервиса. Отключите таймер.
4. Составьте файл `crontab.txt` для ML-проекта: выгрузка данных каждый час на 10-й минуте; переобучение
   по будням в 03:00 с ограничением по времени; удаление чекпоинтов старше 30 дней по субботам; ежедневный
   бэкап папки `models` с датой в имени архива. В файле должны быть `SHELL`, `PATH`, логи и `flock`.

**Критерии приёмки:**

- [ ] `heartbeat.sh` проходит `shellcheck` и работает в «пустом» окружении из раздела 3;
- [ ] в `report.md` перечислены три отличия окружения cron от окружения терминала;
- [ ] `systemd-analyze verify` не выдаёт предупреждений, `systemd-analyze calendar` показывает срабатывание
      каждые 5 минут;
- [ ] в отчёте есть вывод `systemctl list-timers` с вашим таймером и две записи в журнале сервиса;
- [ ] в `crontab.txt` четыре задачи, у каждой — переход в папку проекта или абсолютные пути и лог-файл;
- [ ] символ `%` в `crontab.txt` экранирован, ни в одном расписании нет `*` в поле минут;
- [ ] после проверки в `crontab -l` и `systemctl list-timers` не осталось учебных задач.

Если systemd в вашей системе недоступен (WSL2 без `systemd=true` в `/etc/wsl.conf`), в пункте 3 достаточно
