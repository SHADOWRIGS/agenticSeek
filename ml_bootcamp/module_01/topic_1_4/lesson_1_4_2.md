# Урок 1.4.2: Мониторинг ресурсов: htop, nvidia-smi, systemd

> **Модуль 1:** Foundations & Mindset Engineer · **Тема 1.4:** Linux и командная строка
> **Тип:** теория · **Время:** 120 минут + 90 минут на домашнее задание

## Цели урока

После урока вы сможете:

- за минуту оценить, готов ли сервер к запуску обучения: CPU, память, диск, GPU;
- читать вывод `top`/`htop`, `free`, `df`, `vmstat` и `nvidia-smi` и находить узкое место обучения;
- найти процесс, который удерживает память GPU, и корректно его остановить;
- оформить ML-сервис как юнит systemd: автозапуск, перезапуск при сбое, логи, ограничения ресурсов.

## Зачем это нужно

Обучение, которое «почему-то идёт медленно» или «почему-то упало», почти всегда упирается в один из четырёх
ресурсов. Примеры из практики:

- GPU за несколько тысяч долларов загружена на 15 %, потому что данные читает и аугментирует один процесс
  на одном ядре CPU;
- запуск на 20 часов падает на 19-м часу с `No space left on device` при сохранении чекпоинта;
- процесс обучения исчезает без трейсбека: память кончилась, и ядро убило его (OOM killer);
- новый запуск получает `CUDA out of memory`, хотя «ничего не запущено»: память GPU держит процесс,
  оставшийся от вчерашнего эксперимента.

Каждый из этих случаев диагностируется одной-двумя командами, если знать, куда смотреть.

## 1. Чек-лист перед запуском

```bash
uptime            # давно ли работает сервер и насколько он загружен
nproc             # сколько ядер CPU доступно
free -h           # сколько оперативной памяти доступно
df -h /data ~     # сколько места там, где лежат данные и куда пишутся чекпоинты
nvidia-smi        # свободна ли GPU
who               # кто ещё сейчас работает на сервере
```

На общем сервере это ещё и вопрос вежливости: запуск поверх чужого обучения замедлит оба.

## 2. CPU и load average

Пример вывода `uptime`:

```text
 14:02:11 up 37 days,  3:12,  2 users,  load average: 7.85, 8.10, 6.40
```

Три числа load average — среднее количество процессов, которые выполняются или
ждут своей очереди на CPU либо диск, за последние 1, 5 и 15 минут. Число имеет смысл только в сравнении
с количеством ядер из `nproc`:

| Load average при 16 ядрах | Что означает |
|---|---|
| 2 | сервер почти свободен |
| 14–16 | CPU загружен полностью, очереди нет |
| 40 | процессы стоят в очереди: всё работает медленнее, чем могло бы |

Сравнение трёх чисел показывает динамику: `7.85, 8.10, 6.40` — нагрузка держится около 15 минут.

**htop** — основной интерактивный монитор (`sudo apt install -y htop`). В верхней части — загрузка каждого
ядра, память и swap; ниже — список процессов.

| Столбец | Значение |
|---|---|
| `PID`, `USER` | идентификатор процесса и его владелец |
| `CPU%` | доля одного ядра: 400 % — процесс занимает четыре ядра |
| `MEM%`, `RES` | доля и объём реально занятой оперативной памяти |
| `VIRT` | зарезервированное адресное пространство; у процессов с CUDA это десятки гигабайт, и это нормально |
| `S` | состояние: `R` — выполняется, `S` — спит, `D` — ждёт диск, `Z` — зомби |
| `TIME+` | суммарное процессорное время |

| Клавиша в htop | Действие |
|---|---|
| `F6` (или `P`, `M`) | выбрать сортировку (по CPU, по памяти) |
| `F5` или `t` | дерево процессов: видно, какие процессы порождены вашим `train.py` |
| `F4` | фильтр по подстроке, например `python` |
| `u` | показать процессы одного пользователя |
| `F9` | отправить сигнал выбранному процессу |
| `F10` или `q` | выход |

`top` есть на любом сервере без установки. В нём `1` показывает ядра по отдельности, `M` и `P` сортируют
по памяти и CPU. Для скриптов и логов оба монитора неудобны — используйте `ps`:

```bash
ps aux --sort=-%mem | head -n 6                                      # топ-5 процессов по памяти
ps -eo pid,user,%cpu,%mem,rss,etime,cmd --sort=-%cpu | head -n 6     # топ-5 по CPU, с временем работы
pgrep -af train.py                                                   # PID и командные строки по шаблону
```

**Диагноз по CPU.** Обучение с `DataLoader(num_workers=8)` в дереве процессов выглядит как один главный
процесс и восемь дочерних. Если все дочерние стоят на 100 %, а GPU простаивает, — узкое место в подготовке
данных. Если загружено одно ядро из шестнадцати — вероятно, `num_workers=0` и данные готовит главный процесс.

## 3. Оперативная память

Пример вывода `free -h`:

```text
               total        used        free      shared  buff/cache   available
Mem:            62Gi        22Gi       1.2Gi       1.0Gi        40Gi        40Gi
Swap:          8.0Gi          0B       8.0Gi
```

Главная ошибка — смотреть на столбец `free` и пугаться. Linux использует свободную
память под файловый кеш (`buff/cache`): прочитанный датасет остаётся в памяти, и вторая эпоха читает его
быстрее. Этот кеш отдаётся программам по первому требованию. **Смотреть нужно на `available`** — столько
памяти реально может получить новый процесс.

Когда память кончается, ядро убивает самый «тяжёлый» процесс. Признаки: в терминале одно слово `Killed`,
код возврата 137 (128 + номер сигнала SIGKILL), трейсбека Python нет. Подтверждение — в журнале ядра:

```bash
sudo dmesg -T | grep -i -E 'out of memory|killed process'
```

Частые причины в ML: весь датасет загружен в память целиком, слишком много воркеров `DataLoader` (каждый
держит свою копию данных), утечка в цикле обучения — например, в список складывают тензоры с графом
вычислений вместо чисел. Наблюдать за ростом памяти процесса удобно так:

```bash
watch -n 5 'ps -o pid,rss,etime,cmd -p 41237'     # RSS в килобайтах каждые 5 секунд
```

## 4. Диск

```bash
df -h                                        # заполненность всех файловых систем
df -h /data                                  # файловая система, на которой лежит /data
df -i /data                                  # свободные inode: кончаются на миллионах мелких файлов
du -sh data/ checkpoints/                    # размер конкретных папок
du -h --max-depth=1 . | sort -rh | head      # самые большие подпапки текущей папки
```

Диск заполняют чекпоинты (модель на 1 ГБ, сохранённая после каждой из 100 эпох), кеши (`~/.cache/huggingface`,
`~/.cache/pip`), логи и забытые копии датасетов. Для интерактивного разбора удобна утилита `ncdu`.

Вторая проблема диска — скорость. Если обучение читает с медленного или сетевого хранилища, GPU ждёт данные:

```bash
vmstat 1          # раз в секунду; интересны столбцы r, b, si, so, wa
iostat -xz 1      # пакет sysstat; загрузка каждого диска, столбец %util
```

| Столбец `vmstat` | На что указывает |
|---|---|
| `r` | процессы в очереди на CPU; устойчиво больше числа ядер — CPU не хватает |
| `b` | процессы, заблокированные на вводе-выводе |
| `si`, `so` | обмен со swap; ненулевые значения во время обучения — памяти не хватает |
| `wa` | доля времени, когда CPU простаивает в ожидании диска; десятки процентов — узкое место в хранилище |

Сеть на ML-сервере нужна реже. Достаточно двух команд: `ss -tlnp` показывает, какие процессы слушают какие
порты (кто занял 8888 под Jupyter), `ip -s link` — счётчики переданных байт и ошибок по интерфейсам.

## 5. GPU: как читать nvidia-smi

Пример вывода (иллюстративный, сокращён; оформление таблицы зависит от версии драйвера):

```text
+---------------------------------------------------------------------------------------+
| NVIDIA-SMI 535.154.05             Driver Version: 535.154.05   CUDA Version: 12.2     |
|-----------------------------------------+----------------------+----------------------+
| GPU  Name                 Persistence-M | Bus-Id        Disp.A | Volatile Uncorr. ECC |
| Fan  Temp   Perf          Pwr:Usage/Cap |         Memory-Usage | GPU-Util  Compute M. |
|=========================================+======================+======================|
|   0  NVIDIA GeForce RTX 3090        Off | 00000000:01:00.0 Off |                  N/A |
| 45%   67C    P2             310W / 350W |  21504MiB / 24576MiB |     97%      Default |
|   1  NVIDIA GeForce RTX 3090        Off | 00000000:02:00.0 Off |                  N/A |
| 30%   34C    P8              22W / 350W |  18210MiB / 24576MiB |      0%      Default |
+-----------------------------------------+----------------------+----------------------+
| Processes:                                                                            |
|  GPU   GI   CI        PID   Type   Process name                            GPU Memory |
|=======================================================================================|
|    0   N/A  N/A     41237      C   python                                    21490MiB |
|    1   N/A  N/A     30112      C   python                                    18196MiB |
+---------------------------------------------------------------------------------------+
```

| Поле | Что показывает | На что смотреть |
|---|---|---|
| `Memory-Usage` | занятая и общая видеопамять | хватит ли места вашей модели и батчу |
| `GPU-Util` | доля времени, когда GPU выполняла вычисления | при обучении должна быть близка к 100 % |
| `Temp`, `Pwr` | температура и потребление | устойчивая температура у верхней границы — проверить охлаждение |
| `Processes` | PID процессов и их видеопамять | кто именно занимает GPU |
| `CUDA Version` | максимальная версия CUDA, поддерживаемая драйвером | это не версия CUDA в вашем окружении Python |

`Memory-Usage` и `GPU-Util` независимы. В примере GPU 0 занята работой, а GPU 1 держит 18 ГБ памяти при
нулевой загрузке — кандидат на «забытый» процесс.

Для наблюдения и логирования:

```bash
watch -n 1 nvidia-smi                 # обновлять экран раз в секунду
nvidia-smi -l 5                       # печатать сводку каждые 5 секунд
nvidia-smi -L                         # список GPU

nvidia-smi --query-gpu=index,name,utilization.gpu,memory.used,memory.total,temperature.gpu --format=csv
nvidia-smi --query-compute-apps=pid,process_name,used_memory --format=csv
nvidia-smi --help-query-gpu           # все поля, доступные для --query-gpu

# журнал загрузки GPU на время эксперимента: CSV раз в 5 секунд
nvidia-smi --query-gpu=timestamp,index,utilization.gpu,memory.used --format=csv,noheader,nounits -l 5 \
    > logs/gpu_usage.csv
```

Формат `csv,noheader,nounits` даёт строки вида `0, NVIDIA GeForce RTX 3090, 97, 21504, 24576, 67` —
их удобно разбирать в скриптах через `awk -F', '`.

Удобные альтернативы: **nvtop** (`sudo apt install -y nvtop`) — интерактивный монитор в духе htop
с графиками; **gpustat** (`uv tool install gpustat`) — компактная сводка, одна строка на GPU;
`gpustat -cpu` добавляет команду, PID и пользователя, `gpustat -i 1` обновляет вывод раз в секунду.

### Типичные диагнозы

**Низкая загрузка GPU.** `GPU-Util` скачет между 0 и 40 %, память занята. GPU ждёт данные. Проверьте
в `htop` воркеры загрузки и столбец `wa` в `vmstat`. Лечение: увеличить `num_workers`, включить `pin_memory`,
вынести тяжёлую предобработку в отдельный этап, переложить данные на локальный SSD. Если данные в порядке,
возможно, слишком мал размер батча.

**CUDA out of memory.** Сначала посмотрите таблицу процессов: память может занимать чужой или ваш
предыдущий запуск. Если GPU свободна, а памяти всё равно не хватает — уменьшайте батч, включайте смешанную
точность (mixed precision), используйте накопление градиентов. Учтите, что PyTorch не возвращает освобождённую
память драйверу сразу: `nvidia-smi` показывает зарезервированный объём, а не реально занятый тензорами.

**Процесс удерживает память.** Память занята, `GPU-Util` 0 %. Типичные источники: ядро Jupyter, оставленное
после эксперимента; воркеры, пережившие `Ctrl+C`; обучение, приостановленное через `Ctrl+Z`.

```bash
nvidia-smi --query-compute-apps=pid,used_memory --format=csv     # кто держит память
ps -o pid,user,etime,stat,cmd -p 30112                           # что это за процесс и давно ли запущен
kill 30112                                                       # сначала SIGTERM
kill -9 30112                                                    # только если не помогло
```

Чужой процесс на общем сервере не убивайте — напишите владельцу (столбец `user`). Внутри Docker-контейнера
таблица процессов `nvidia-smi` может быть пустой: смотрите её на хосте.

Выбрать GPU для запуска можно переменной окружения: `CUDA_VISIBLE_DEVICES=1 python train.py`.

## 6. systemd: сервисы, которые не нужно запускать руками

`tmux` подходит для экспериментов. Сервис инференса должен сам стартовать после перезагрузки, перезапускаться
при падении и писать логи в одно место. В Ubuntu и Debian этим занимается systemd. Описание того, чем он
управляет, называется юнитом: `.service` — сервис, `.timer` — расписание (следующий урок).

| Команда | Действие |
|---|---|
| `systemctl status ml-inference` | состояние, PID, потребление памяти, последние строки лога |
| `sudo systemctl start` / `stop` / `restart ml-inference` | запустить, остановить, перезапустить сейчас |
| `sudo systemctl enable ml-inference` | запускать при загрузке системы (`enable --now` — ещё и сразу) |
| `sudo systemctl disable ml-inference` | убрать из автозагрузки |
| `systemctl list-units --type=service --state=running` | работающие сервисы |
| `systemctl --failed` | юниты в состоянии ошибки |
| `sudo systemctl daemon-reload` | перечитать unit-файлы после правки |
| `journalctl -u ml-inference -f` | логи сервиса в реальном времени |
| `journalctl -u ml-inference -n 100 --since "1 hour ago"` | последние 100 строк за час |

`start` и `enable` независимы: первое — про «сейчас», второе — про «после перезагрузки».

Unit-файл сервиса инференса, `/etc/systemd/system/ml-inference.service`:

```ini
[Unit]
Description=ML inference API (sentiment model)
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=mlops
Group=mlops
WorkingDirectory=/opt/ml-inference
Environment=MODEL_PATH=/opt/ml-inference/models/sentiment-v3.onnx
Environment=PYTHONUNBUFFERED=1
EnvironmentFile=-/etc/ml-inference/env
ExecStart=/opt/ml-inference/.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000
Restart=on-failure
RestartSec=5
MemoryMax=4G
CPUQuota=200%

[Install]
WantedBy=multi-user.target
```

| Директива | Смысл |
|---|---|
| `User`, `Group` | от чьего имени работает процесс; сервис инференса не должен работать от root |
| `WorkingDirectory` | текущая папка процесса — от неё считаются относительные пути |
| `Environment`, `EnvironmentFile` | переменные окружения; файл удобен для секретов (права `600`), минус перед путём — «файла может не быть» |
| `ExecStart` | команда запуска; путь к исполняемому файлу обязательно абсолютный |
| `Restart=on-failure`, `RestartSec` | перезапуск через 5 секунд при ненулевом коде возврата или гибели от сигнала |
| `MemoryMax` | жёсткий предел памяти: при превышении процесс сервиса будет убит, остальная система не пострадает |
| `CPUQuota` | предел CPU: `200%` — не больше двух ядер |
| `WantedBy=multi-user.target` | куда «подключить» юнит при `enable`: обычная загрузка сервера |

Сервис не читает `~/.bashrc`: у него нет вашего `PATH`, активированного окружения и переменных. Поэтому
в `ExecStart` стоит путь к интерпретатору из `.venv`, а всё нужное задано через `Environment`.

Установка и проверка:

```bash
systemd-analyze verify ./ml-inference.service      # проверка файла до установки
sudo cp ml-inference.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now ml-inference
systemctl status ml-inference
journalctl -u ml-inference -f
```

`systemd-analyze verify` сообщает об опечатках в директивах (`Unknown key name 'MemoryMaxx' in section
'Service', ignoring`) и об отсутствующем исполняемом файле из `ExecStart`. На опечатке код возврата остаётся
нулевым, поэтому читайте сам вывод.

Пример вывода `systemctl status` (иллюстративный, сокращён):

```text
● ml-inference.service - ML inference API (sentiment model)
     Loaded: loaded (/etc/systemd/system/ml-inference.service; enabled; preset: enabled)
     Active: active (running) since Tue 2026-03-03 10:15:02 UTC; 2h 5min ago
   Main PID: 1423 (uvicorn)
     Memory: 1.2G (max: 4.0G)
        CPU: 3min 12.402s
```

Смотреть на строку `Active`: `active (running)` — работает; `failed` — упал и не перезапущен;
`activating (auto-restart)` — падает и перезапускается по кругу, причину ищите в `journalctl`.

**WSL2.** systemd включается в файле `/etc/wsl.conf` (секция `[boot]`, строка `systemd=true`), после чего
нужно выполнить `wsl --shutdown` в PowerShell и заново открыть Ubuntu.

## Типичные ошибки

| Симптом | Причина | Решение |
|---|---|---|
| «Памяти почти нет»: `free` показывает 1 ГБ в столбце `free` | остальное занято файловым кешем | смотрите столбец `available` |
| Процесс завершился словом `Killed`, код возврата 137 | OOM killer: кончилась оперативная память | `dmesg -T`; уменьшить число воркеров и объём данных в памяти |
| `No space left on device`, хотя `df -h` показывает свободное место | кончились inode или заполнен другой раздел | `df -i`, `df -h` для конкретного пути |
| `GPU-Util` 10–30 % при обучении | узкое место в загрузке данных | `htop`, `vmstat`; `num_workers`, быстрый диск, предобработка заранее |
| `CUDA out of memory` на «свободной» GPU | память держит старый процесс или ядро Jupyter | найти PID в `nvidia-smi`, `kill`; остановить ядро ноутбука |
| Load average 60 на 16 ядрах, обучение ползёт | воркеров и потоков больше, чем ядер, либо несколько запусков сразу | сократить `num_workers`, договориться с соседями по серверу |
| Сервис в systemd не находит `python` или модуль | у сервиса нет вашего `PATH` и окружения | абсолютные пути в `ExecStart`, `Environment=` |
| Правка unit-файла не действует | systemd не перечитал файл | `sudo systemctl daemon-reload`, затем `restart` |
| Сервис работает, но после перезагрузки не поднялся | выполнен `start`, но не `enable` | `sudo systemctl enable ml-inference` |

## Контрольные вопросы

1. Load average равен 12. Это много или мало? Чего не хватает для ответа?
2. Чем `available` отличается от `free` в выводе `free -h` и почему важен именно `available`?

## Домашнее задание

Снимите «паспорт» своей машины и оформите сервис под управлением systemd.

1. Создайте файл `server_report.md`. Запишите в него вывод и своё толкование для: `nproc` и `uptime`
   (загружена ли машина), `free -h` (сколько памяти доступно новому процессу), `df -h` для домашней папки,
   трёх самых больших подпапок домашней папки.
2. Эксперимент с CPU: запустите в фоне четыре процесса `python3 -c "while True: pass"`, найдите их в `htop`,
   дождитесь роста load average, завершите их одной командой. Запишите в отчёт значения load average до,
   во время и после.

   `nvidia-smi --query-gpu=name,memory.used,memory.total,utilization.gpu --format=csv`. Если нет — ответьте
