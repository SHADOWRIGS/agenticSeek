## Цели урока

После урока вы сможете:

## Зачем это нужно

`uv.lock` фиксирует версии Python-пакетов, но ML-проект зависит не только от них: версия самого Python,
системные библиотеки, драйверы и библиотеки CUDA. Модель, обученная на вашем ноутбуке, должна запуститься
на сервере с GPU, в облаке и на машине коллеги. Docker упаковывает проект вместе со всем окружением в образ,
который везде запускается одинаково.

Docker — это ещё и стандартный формат поставки: Kubernetes, облачные ML-платформы и CI-системы принимают
на вход именно образы. Дальше в курсе контейнеры встретятся в MLOps (модуль 7) и в финальном проекте.

## 1. Основные понятия

| Понятие | Что это | Аналогия |
|---|---|---|
| Образ (image) | неизменяемый шаблон: файловая система с ОС, Python, пакетами и кодом | класс |
| Контейнер | запущенный экземпляр образа: изолированный процесс со своей файловой системой | объект класса |
| Dockerfile | текстовый рецепт сборки образа | исходный код |
| Слой (layer) | результат одной инструкции Dockerfile; слои кэшируются | шаг сборки |
| Реестр (registry) | хранилище образов: Docker Hub, GitHub Container Registry | PyPI для образов |
| Том (volume) | папка, которая живёт вне контейнера и подключается к нему | внешний диск |

Контейнер — не виртуальная машина. Он использует ядро хост-системы и запускается за доли секунды; изолируются
только процессы, файловая система и сеть. Главное следствие для практики: **всё, что записано внутри
контейнера, исчезает вместе с ним**. Данные, модели и результаты экспериментов должны лежать в томах.

## 2. Установка

- **Linux:** установите Docker Engine по инструкции для вашего дистрибутива из официальной документации,
  затем разрешите запуск без `sudo`:

  ```bash
  sudo usermod -aG docker $USER    # после этого нужно выйти из системы и войти снова
  ```

- **macOS и Windows:** установите Docker Desktop. На Windows включите в его настройках интеграцию с вашим
  дистрибутивом WSL (Settings → Resources → WSL Integration) и работайте из терминала Ubuntu.

Проверка:

```bash
docker --version
docker run --rm hello-world
```

## 3. Первые команды

```bash
docker run --rm python:3.12-slim python -c "import sys; print(sys.version.split()[0])"
```

Docker скачал из Docker Hub образ `python:3.12-slim`, создал контейнер, выполнил в нём команду и удалил
контейнер (`--rm`). На вашей машине при этом может не быть Python вообще.

Интерактивный запуск — «зайти внутрь» и осмотреться:

```bash
docker run --rm -it python:3.12-slim bash
```

| Команда | Что делает |
|---|---|
| `docker run [флаги] образ [команда]` | создать и запустить контейнер |
| `docker ps` / `docker ps -a` | работающие контейнеры / все контейнеры |
| `docker logs -f <контейнер>` | вывод контейнера, `-f` — следить в реальном времени |
| `docker exec -it <контейнер> bash` | открыть оболочку в работающем контейнере |
| `docker stop <контейнер>` | остановить контейнер |
| `docker images` | список локальных образов и их размеры |
| `docker build -t имя:тег .` | собрать образ из Dockerfile в текущей папке |
| `docker system df` | сколько места занимают образы, контейнеры и кэш |
| `docker system prune` | удалить остановленные контейнеры и неиспользуемые слои |

Основные флаги `docker run`:

| Флаг | Назначение |
|---|---|
| `--rm` | удалить контейнер после завершения |
| `-it` | интерактивный режим с терминалом |
| `-d` | запуск в фоне |
| `-v хост:контейнер` | подключить папку хоста внутрь контейнера |
| `-p хост:контейнер` | пробросить порт |
| `-e ИМЯ=значение` | задать переменную окружения |
| `--name имя` | дать контейнеру имя |
| `--gpus all` | дать доступ к GPU (раздел 8) |

## 4. Проект для примера

Возьмём минимальный проект: `pyproject.toml` и `uv.lock` (зависимость `scikit-learn`, в dev-группе —
`jupyterlab`) и скрипт обучения `train.py`:

```python
from pathlib import Path

import joblib
from sklearn.datasets import load_wine
from sklearn.ensemble import RandomForestClassifier
from sklearn.model_selection import train_test_split

X, y = load_wine(return_X_y=True)
X_train, X_test, y_train, y_test = train_test_split(X, y, test_size=0.25, random_state=42, stratify=y)

model = RandomForestClassifier(n_estimators=200, random_state=42).fit(X_train, y_train)
print(f"accuracy: {model.score(X_test, y_test):.3f}")

models_dir = Path("models")
models_dir.mkdir(exist_ok=True)
joblib.dump(model, models_dir / "wine_rf.joblib")
print(f"model saved to {models_dir / 'wine_rf.joblib'}")
```

## 5. Dockerfile

```dockerfile
FROM python:3.12-slim AS base

COPY --from=ghcr.io/astral-sh/uv:0.11.32 /uv /uvx /bin/

ENV UV_COMPILE_BYTECODE=1 \
    UV_LINK_MODE=copy \
    PYTHONUNBUFFERED=1

WORKDIR /app

COPY pyproject.toml uv.lock ./
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --frozen --no-install-project --no-dev

ENV PATH="/app/.venv/bin:$PATH"


FROM base AS dev

RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --frozen --no-install-project
EXPOSE 8888
CMD ["jupyter", "lab", "--ip=0.0.0.0", "--port=8888", "--no-browser", "--allow-root"]


FROM base AS runtime

COPY train.py ./
RUN useradd --create-home appuser && mkdir models && chown appuser models
USER appuser
CMD ["python", "train.py"]
```

Разбор по строкам:

| Инструкция | Зачем |
|---|---|
| `FROM python:3.12-slim AS base` | базовый образ: Debian с Python 3.12 без лишних пакетов; `AS base` даёт этапу имя |
| `COPY --from=ghcr.io/astral-sh/uv:0.11.32 ...` | берём готовые бинарные файлы `uv` из официального образа; версия зафиксирована |
| `UV_COMPILE_BYTECODE=1` | компилировать `.pyc` при сборке — контейнер стартует быстрее |
| `UV_LINK_MODE=copy` | копировать пакеты из кэша, а не создавать ссылки (кэш лежит на отдельном томе сборки) |
| `PYTHONUNBUFFERED=1` | `print` сразу попадает в `docker logs`, а не копится в буфере |
| `WORKDIR /app` | рабочая папка для всех следующих инструкций |
| `COPY pyproject.toml uv.lock ./` + `uv sync` | сначала только файлы зависимостей — см. раздел 6 |
| `--mount=type=cache,...` | кэш скачанных пакетов хранится вне образа и переиспользуется между сборками |
| `--frozen` | ставить ровно то, что записано в `uv.lock`, и не пытаться его обновить |
| `--no-dev` | без инструментов разработки: в образе для обучения JupyterLab не нужен |
| `ENV PATH=...` | `python` в контейнере — это Python из окружения проекта |
| `USER appuser` | процесс работает не от root — базовая мера безопасности |
| `CMD [...]` | команда по умолчанию при запуске контейнера |

В этом Dockerfile три этапа (multi-stage build): общий `base` с зависимостями и два образа на его основе —
`runtime` для обучения и `dev` с JupyterLab. Какой из них собирать, выбирает флаг `--target`.

## 6. Слои и кэш сборки

Каждая инструкция создаёт слой. При пересборке Docker идёт сверху вниз и переиспользует слои из кэша, пока
не встретит инструкцию, входные данные которой изменились; **начиная с этого места всё пересобирается**.

Поэтому порядок инструкций — от редко меняющегося к часто меняющемуся:

1. базовый образ и системные пакеты;
2. зависимости (`pyproject.toml`, `uv.lock`) — меняются раз в несколько дней;
3. код — меняется постоянно.

Если бы мы написали `COPY . .` до установки зависимостей, любое изменение в `train.py` заставляло бы заново
ставить все пакеты. При правильном порядке пересборка после правки кода занимает около секунды.

**`.dockerignore`** — файл в корне проекта с тем, что не должно попадать в контекст сборки:

```
.venv
.git
__pycache__
.ipynb_checkpoints
data
models
notebooks
*.ipynb
.env
```

Без него в сборку уедут гигабайты данных и локальное окружение, а файл `.env` с секретами может оказаться
внутри образа.

## 7. Сборка и запуск

```bash
docker build --target runtime -t ml-bootcamp:0.1 .
docker run --rm ml-bootcamp:0.1
```

```
accuracy: 1.000
model saved to models/wine_rf.joblib
```

Модель сохранилась — и исчезла вместе с контейнером. Подключим папку хоста как том:

```bash
mkdir -p models
docker run --rm --user "$(id -u):$(id -g)" -v "$(pwd)/models:/app/models" ml-bootcamp:0.1
ls models
```

Флаг `-v "$(pwd)/models:/app/models"` подключает папку `models` текущего каталога в `/app/models` контейнера.
Флаг `--user "$(id -u):$(id -g)"` запускает процесс с идентификатором вашего пользователя — так у контейнера
есть право писать в вашу папку, а созданные файлы принадлежат вам, а не root. Тем же способом подключают
данные; чтобы контейнер не мог их испортить, добавляют `:ro` (только чтение):

```bash
docker run --rm -v "$(pwd)/data:/app/data:ro" ml-bootcamp:0.1
```

**Размер образа.** Проверьте `docker images`. В нашем примере образ `runtime` занимает 632 МБ, из которых
179 МБ — базовый `python:3.12-slim`, остальное — scikit-learn с NumPy и SciPy. Если убрать из Dockerfile
`--mount=type=cache`, кэш `uv` останется в слое и образ вырастет до 907 МБ. Образ `dev` с JupyterLab — 914 МБ.
Что делать, чтобы образ не разрастался:

- брать `slim`-вариант базового образа;
- не ставить dev-зависимости в образ для обучения и инференса;
- не оставлять в слоях кэши пакетных менеджеров;
- не копировать в образ данные и модели — подключать их томами.

Образы с PyTorch и CUDA занимают несколько гигабайт, и это нормально; тем важнее не добавлять лишнего.

## 8. JupyterLab в контейнере

```bash
docker build --target dev -t ml-bootcamp:dev .
docker run --rm -p 8888:8888 -v "$(pwd):/app/work" -w /app/work ml-bootcamp:dev
```

В выводе появится ссылка вида `http://127.0.0.1:8888/lab?token=...` — откройте её в браузере.

- `-p 8888:8888` пробрасывает порт контейнера на вашу машину. Внутри контейнера Jupyter должен слушать
  `0.0.0.0`, иначе снаружи он недоступен, — это задано в `CMD`.
- Проект подключён в `/app/work`, а не в `/app`: иначе том закрыл бы собой папку `/app/.venv` с установленными
  пакетами.
- Ноутбуки сохраняются в папке проекта на хосте и переживают удаление контейнера.

Альтернатива — расширение Dev Containers для VS Code (установлено в уроке 1.1.1): редактор целиком
подключается к контейнеру, и вы работаете в нём как в локальном проекте.

## 9. Docker Compose

Длинные команды `docker run` неудобно запоминать и передавать коллегам. Compose описывает их в файле
`compose.yaml`:

```yaml
services:
  train:
    build:
      context: .
      target: runtime
    image: ml-bootcamp:0.1
    volumes:
      - ./models:/app/models

  jupyter:
    build:
      context: .
      target: dev
    image: ml-bootcamp:dev
    ports:
      - "8888:8888"
    volumes:
      - .:/app/work
    working_dir: /app/work
```

```bash
docker compose build                                       # собрать оба образа
docker compose run --rm --user "$(id -u):$(id -g)" train   # запустить обучение
docker compose up -d jupyter                               # поднять JupyterLab в фоне
docker compose logs jupyter                                # найти ссылку с токеном
docker compose exec jupyter python -c "import sklearn; print(sklearn.__version__)"
docker compose down                                        # остановить и удалить контейнеры
```

Файл `compose.yaml` коммитят в репозиторий: он документирует, как запускать проект.

## 10. GPU в контейнере

Контейнеру не нужны собственные драйверы видеокарты: драйвер ставится на хост, а библиотеки CUDA лежат
в образе. Для этого на хосте должны быть установлены драйвер NVIDIA и NVIDIA Container Toolkit, после чего
контейнеру можно передать GPU:

```bash
docker run --rm --gpus all <образ с CUDA> nvidia-smi
```

Если команда печатает таблицу с вашей видеокартой, GPU внутри контейнера доступен. В качестве базовых берут
готовые образы с CUDA — например, официальные образы PyTorch, — а не собирают CUDA вручную. На машине без
видеокарты NVIDIA этот раздел выполнить нельзя; к работе с GPU вернёмся в теме 6.2.

## Типичные ошибки

| Симптом | Причина | Решение |
|---|---|---|
| `permission denied ... docker.sock` | пользователь не в группе `docker` | `sudo usermod -aG docker $USER`, затем выйти и войти в систему |
| `PermissionError` при записи в подключённую папку | пользователь в контейнере не владеет папкой хоста | запуск с `--user "$(id -u):$(id -g)"` |
| Файлы, созданные контейнером, принадлежат root | контейнер работал от root | тот же флаг `--user`; исправить владельца: `sudo chown -R $USER .` |
| Каждая сборка заново ставит все пакеты | `COPY . .` стоит до установки зависимостей | сначала копировать `pyproject.toml` и `uv.lock`, код — в конце |
| Сборка отправляет гигабайты контекста | нет `.dockerignore` | добавить `.dockerignore` с `data`, `models`, `.venv`, `.git` |
| Jupyter запущен, но страница не открывается | сервер слушает `127.0.0.1` внутри контейнера или порт не проброшен | `--ip=0.0.0.0` и `-p 8888:8888` |
| Вывод обучения появляется в логах с задержкой | буферизация stdout | `PYTHONUNBUFFERED=1` |
| Результаты пропали после остановки контейнера | они записаны в файловую систему контейнера | писать в подключённый том |
| Закончилось место на диске | накопились старые образы и кэш сборки | `docker system df`, затем `docker system prune` |
| Процесс убит без сообщения об ошибке при работе с большими данными | контейнеру не хватило памяти | увеличить лимит памяти в Docker Desktop или читать данные частями (тема 1.2) |
