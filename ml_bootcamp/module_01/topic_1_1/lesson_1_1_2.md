# Урок 1.1.2: Настройка Git, GitHub, создание репозитория курса

> **Модуль 1:** Foundations & Mindset Engineer · **Тема 1.1:** Установка профессионального окружения
> **Тип:** теория · **Время:** 90 минут + 60 минут на домашнее задание

## Цели урока

После урока вы сможете:

- настроить Git и подключиться к GitHub по SSH-ключу;
- вести историю проекта осмысленными коммитами и работать через ветки и pull request;
- составить `.gitignore` для ML-проекта и не допустить попадания в репозиторий данных, моделей и секретов;
- хранить ноутбуки в Git так, чтобы их можно было ревьюить;
- автоматически проверять код перед каждым коммитом с помощью pre-commit.

## Зачем это нужно

В ML-проекте меняется всё сразу: код, данные, гиперпараметры. Через две недели экспериментов возникает
вопрос «на каком коде получена метрика 0.87?» — и без истории изменений на него нет ответа. Git отвечает
за код и конфигурации; данные и модели версионируют отдельными инструментами (DVC — урок 7.2.1), но
привязывают к тем же коммитам.

Вторая причина практическая: репозиторий курса станет вашим портфолио. Работодатель смотрит не только на
результат, но и на историю коммитов — по ней видно, как человек работает.

## 1. Установка и первичная настройка

```bash
sudo apt install -y git        # Linux и WSL; на macOS Git ставится вместе с xcode-select --install
git --version
```

Настройки, которые делаются один раз на машине:

```bash
git config --global user.name "Имя Фамилия"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main
git config --global pull.rebase true
git config --global core.editor "code --wait"
git config --global core.autocrlf input
```

| Настройка | Что делает |
|---|---|
| `user.name`, `user.email` | подпись ваших коммитов; email должен совпадать с указанным в GitHub |
| `init.defaultBranch main` | основная ветка новых репозиториев называется `main` |
| `pull.rebase true` | при `git pull` ваши коммиты переносятся поверх чужих, без лишних merge-коммитов |
| `core.editor` | редактор для сообщений коммитов |
| `core.autocrlf input` | в репозиторий попадают только Unix-переводы строк (важно при работе с Windows) |

Проверить результат: `git config --global --list`.

## 2. Модель Git за пять минут

У каждого файла три возможных «места жительства»:

```
рабочая папка  --git add-->  индекс (staging)  --git commit-->  история (коммиты)
```

- **Рабочая папка** — файлы, как они лежат на диске.
- **Индекс** — черновик следующего коммита. Он позволяет закоммитить часть изменений, а не всё подряд.
- **Коммит** — снимок проекта с автором, датой, сообщением и ссылкой на предыдущий коммит.
- **Ветка** — подвижный указатель на коммит. Создать ветку — значит создать ещё один указатель, это мгновенно.
- **Удалённый репозиторий (remote)** — копия истории на сервере, обычно под именем `origin`.

Базовый цикл работы:

```bash
git status                      # что изменилось
git diff                        # что именно изменилось в файлах
git add src/features.py         # добавить файл в индекс
git add -p                      # добавить изменения по частям, просматривая каждую
git commit -m "Add lag features for sales data"
git log --oneline --graph -10   # последние 10 коммитов
```

Привычка, которая отличает инженера: перед `git commit` всегда смотреть `git status` и `git diff --staged`.

## 3. `.gitignore` для ML-проекта

Правило: в Git хранится то, что написано человеком. Всё, что можно скачать или пересчитать, — не хранится.

```gitignore
# Окружение и кэши
.venv/
__pycache__/
.ipynb_checkpoints/
.ruff_cache/
.pytest_cache/

# Данные и модели — версионируются отдельно (DVC, урок 7.2.1)
data/
models/
*.csv
*.parquet
*.pkl
*.pt
*.onnx

# Результаты экспериментов
mlruns/
wandb/
outputs/

# Секреты
.env
*.pem

# Редактор и ОС
.DS_Store
.idea/
```

Пустые папки Git не хранит. Чтобы сама папка `data/` осталась в репозитории, правило `data/` заменяют
парой правил и кладут в папку пустой файл `.gitkeep`:

```gitignore
data/*
!data/.gitkeep
```

**Почему нельзя коммитить данные и модели.** Git хранит каждую версию каждого файла вечно. Один закоммиченный
файл весов на 500 МБ останется в истории, даже если удалить его следующим коммитом, и каждый `git clone` будет
его скачивать. GitHub к тому же отклоняет файлы больше 100 МБ.

## 4. Секреты

Ключи API, пароли и токены не должны попадать в репозиторий никогда — ни в код, ни в ноутбуки, ни в конфиги.
Их кладут в файл `.env`, который указан в `.gitignore`, и читают из переменных окружения:

```python
import os

api_key = os.environ["KAGGLE_KEY"]   # упадёт с понятной ошибкой, если переменная не задана
```

В репозиторий коммитят файл-образец `.env.example` с именами переменных без значений.

Если секрет всё же попал в коммит и коммит отправлен на GitHub — **секрет скомпрометирован**. Удалить коммит
недостаточно: публичные репозитории сканируются ботами в течение минут. Единственное правильное действие —
немедленно отозвать ключ и выпустить новый.

## 5. Подключение к GitHub по SSH

```bash
ssh-keygen -t ed25519 -C "you@example.com"    # создаёт пару ключей в ~/.ssh
cat ~/.ssh/id_ed25519.pub                     # публичный ключ — его и только его показываем GitHub
```

Скопируйте вывод второй команды в GitHub: Settings → SSH and GPG keys → New SSH key. Проверка:

```bash
ssh -T git@github.com
```

В ответ должно прийти приветствие с вашим логином. Файл `id_ed25519` без расширения — приватный ключ,
он не покидает вашу машину.

## 6. Репозиторий курса

Создайте на GitHub пустой репозиторий `ml-bootcamp` (без README и `.gitignore` — они уже есть локально).
Проект из урока 1.1.1 уже является Git-репозиторием: `uv init` выполнил `git init` за вас.

```bash
cd ~/projects/ml-bootcamp
git add .
git status                                   # убедитесь, что .venv и данные не попали в индекс
git commit -m "Initial project setup"
git branch -M main                           # репозиторий создан до настройки defaultBranch и мог получить ветку master
git remote add origin git@github.com:<ваш-логин>/ml-bootcamp.git
git push -u origin main
```

Флаг `-u` связывает локальную ветку `main` с веткой на сервере; дальше достаточно `git push` и `git pull`.

Рекомендуемая структура репозитория курса:

```
ml-bootcamp/
├── README.md            # кто вы, что это за репозиторий, оглавление проектов
├── pyproject.toml
├── uv.lock
├── homework/            # домашние задания: homework/m01/hw_1_1_1/ ...
├── projects/            # практические проекты тем: projects/p_1_1_workspace/ ...
├── notebooks/           # черновики и эксперименты
└── src/                 # переиспользуемый код
```

## 7. Ветки и pull request

Даже работая в одиночку, не коммитьте напрямую в `main`. Рабочий процесс (GitHub Flow):

```bash
git switch -c hw-1-1-2                 # новая ветка от текущего состояния
# ... работа, коммиты ...
git push -u origin hw-1-1-2            # отправить ветку на GitHub
```

Затем на GitHub откройте pull request (PR): опишите, что сделано и как проверить, просмотрите собственный
diff — на этом шаге находится половина ошибок — и слейте PR в `main`. После слияния:

```bash
git switch main
git pull
git branch -d hw-1-1-2
```

**Сообщения коммитов.** Первая строка — до 72 символов, отвечает на вопрос «что делает этот коммит»:

| Плохо | Хорошо |
|---|---|
| `fix` | `Fix data leakage in target encoding` |
| `update notebook` | `Add learning curves to baseline notebook` |
| `изменения` | `Remove duplicated rows before train/test split` |

Один коммит — одно логическое изменение. Коммит «поправил баг, добавил фичу и переформатировал весь файл»
невозможно ни проверить, ни откатить.

## 8. Ноутбуки в Git

Файл `.ipynb` — это JSON, в котором вместе с кодом лежат результаты ячеек: картинки, таблицы, счётчики
выполнения. Из-за этого diff ноутбука нечитаем, репозиторий раздувается, а в выводах могут оказаться
персональные данные. Решение — очищать выводы автоматически при коммите:

```bash
uv add --dev nbstripout
uv run nbstripout --install      # подключает фильтр к текущему репозиторию
```

После этого в Git попадает только код ячеек, а в вашем локальном файле выводы остаются.

## 9. Автоматические проверки: pre-commit

pre-commit запускает проверки перед каждым коммитом и не даёт закоммитить код, который их не прошёл.

```bash
uv add --dev pre-commit
```

Файл `.pre-commit-config.yaml` в корне проекта:

```yaml
repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v6.0.0
    hooks:
      - id: check-added-large-files
        args: ["--maxkb=1000"]
      - id: check-yaml
      - id: check-toml
      - id: end-of-file-fixer
      - id: trailing-whitespace
      - id: detect-private-key
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.17.4
    hooks:
      - id: ruff-check
        args: ["--fix"]
      - id: ruff-format
  - repo: https://github.com/kynan/nbstripout
    rev: 0.9.1
    hooks:
      - id: nbstripout
```

```bash
uv run pre-commit autoupdate         # обновить версии проверок (rev) до актуальных
uv run pre-commit install            # включить запуск при каждом коммите
uv run pre-commit run --all-files    # прогнать проверки по всему проекту
```

Что здесь важно для ML: `check-added-large-files` не пропустит случайно добавленный датасет или файл весов,
`detect-private-key` — приватный ключ, `nbstripout` очистит выводы ноутбуков. Если проверка изменила файлы
(например, отформатировала код), коммит отменяется: посмотрите изменения, выполните `git add` и повторите коммит.

## 10. Как отменять изменения

| Ситуация | Команда | Опасность |
|---|---|---|
| Отменить правки в файле, которые ещё не добавлены в индекс | `git restore file.py` | правки теряются безвозвратно |
| Убрать файл из индекса, сохранив правки | `git restore --staged file.py` | безопасно |
| Исправить сообщение или дополнить последний коммит | `git commit --amend` | только если коммит ещё не отправлен |
| Отменить коммит, который уже отправлен на сервер | `git revert <хеш>` | безопасно: создаёт новый коммит-отмену |
| Вернуть ветку к более раннему коммиту | `git reset --hard <хеш>` | стирает незакоммиченные правки |
| Временно отложить правки | `git stash`, потом `git stash pop` | безопасно |
| Найти «потерянный» коммит | `git reflog` | безопасно |

Главное правило: **историю, которая уже отправлена в общую ветку, не переписывают** (`--amend`, `rebase`,
`reset` + `push --force`). Отправленное отменяют через `git revert`.

## Типичные ошибки

| Симптом | Причина | Решение |
|---|---|---|
| `Permission denied (publickey)` при `git push` | ключ не добавлен в GitHub или remote настроен на другой аккаунт | проверьте `ssh -T git@github.com` и `git remote -v` |
| `rejected ... fetch first` при `git push` | на сервере есть коммиты, которых нет локально | `git pull`, затем `git push` |
| Файл из `.gitignore` всё равно отслеживается | он был закоммичен до добавления правила | `git rm --cached <файл>` и коммит |
| `git push` отклонён: файл больше 100 МБ | в коммит попали данные или модель | уберите файл из коммита (`git reset --soft HEAD~1`, поправьте `.gitignore`, закоммитьте заново) |
| Конфликт при слиянии ноутбуков | выводы ячеек изменились с обеих сторон | подключите `nbstripout`; ноутбук с конфликтом проще пересоздать из одной из версий |
| Коммиты подписаны неизвестным автором | не заданы `user.name` и `user.email` | настройте их, как в разделе 1 |
