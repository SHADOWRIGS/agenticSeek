# Урок 1.3.1: Структура ML проектов (CookieCutter, templates)

> **Модуль 1:** Foundations & Mindset Engineer · **Тема 1.3:** Инструменты репроизводимости
> **Тип:** теория · **Время:** 90 минут + 60 минут на домашнее задание

## Цели урока

После урока вы сможете:

- разложить ML-проект по стандартным папкам и объяснить назначение каждой;
- оформить код проекта как устанавливаемый пакет (src-layout) и импортировать его из ноутбуков и тестов;
- решить, какие файлы проекта попадают в Git, а какие нет;
- сгенерировать проект из шаблона Cookiecutter и объяснить, чем от него отличается Copier;
- собрать команды проекта в Makefile, чтобы установка, обучение и проверки запускались одинаково у всех.

## Зачем это нужно

ML-проект разрастается быстрее обычного: кроме кода в нём появляются данные нескольких стадий обработки,
ноутбуки, обученные модели, графики, конфигурации экспериментов. Без договорённости о том, где что лежит,
через месяц в корне оказываются `final_v2.ipynb`, `data_new.csv`, `model_best_REAL.pkl`, и никто, включая
автора, не может сказать, из каких данных и каким кодом получена модель.

Стандартная структура решает три практические задачи:

1. **Вход в проект за минуты.** Новый человек открывает репозиторий и сразу знает: сырые данные в `data/raw`,
   код в `src`, запуск через `make train`. Не нужно читать весь код, чтобы найти точку входа.
2. **Воспроизводимость.** Когда исходные данные отделены от производных, а код — от артефактов, любой
   результат можно удалить и получить заново.
3. **Автоматизация.** CI, Docker и планировщики задач опираются на предсказуемые пути и команды.

## 1. Эталонная раскладка

Самый известный стандарт — Cookiecutter Data Science (CCDS). В курсе используем раскладку в его духе,
адаптированную под `uv` и src-layout:

```text
churn-model/
├── configs/              конфигурации экспериментов (урок 1.3.3)
├── data/
│   ├── raw/              исходные данные: только чтение
│   ├── interim/          промежуточные результаты обработки
│   └── processed/        готовые наборы данных для обучения
├── models/               обученные модели и результаты запусков
├── notebooks/            исследовательские ноутбуки
├── reports/
│   └── figures/          графики и таблицы для отчётов
├── src/
│   └── churn_model/      весь переиспользуемый код проекта
├── tests/                тесты
├── .gitignore
├── .python-version
├── Makefile              команды проекта
├── pyproject.toml        зависимости и настройки инструментов
├── README.md
└── uv.lock
```

Правила, которые делают эту структуру полезной:

| Правило | Что это значит на практике |
|---|---|
| Сырые данные неизменяемы | файлы в `data/raw` не правят руками и не перезаписывают; любая очистка — это код, который читает `raw` и пишет в `interim` или `processed` |
| Всё производное можно удалить | `data/interim`, `data/processed`, `models`, `reports/figures` восстанавливаются запуском кода |
| Ноутбуки — для исследования | код, который нужен второй раз, переезжает в `src`; ноутбук его импортирует |
| Ноутбуки пронумерованы | `01_eda.ipynb`, `02_baseline.ipynb`: порядок и назначение видны из имени |
| Один вход для каждой задачи | обучение, тесты, проверки запускаются командами из `Makefile`, а не «откройте ноутбук и выполните ячейки 3–17» |

Раскладка — не догма: в маленьком проекте не нужна папка `reports`, в большом добавятся `docs` и `scripts`.
Важно, чтобы назначение папок было зафиксировано в README и соблюдалось.

## 2. src-layout: код проекта как пакет

Представьте проект, где модуль `features.py` лежит в корне, а в `notebooks/explore.py` написано
`from features import clean`. Запуск скрипта заканчивается ошибкой:

```text
ModuleNotFoundError: No module named 'features'
```

Python ищет модули в папке запущенного скрипта (здесь это `notebooks/`) и в `site-packages` окружения. Корня
проекта в этом списке нет. Ноутбуки и тесты страдают от того же. Обычная «заплатка» —
`sys.path.append("..")` в первой ячейке — ломается при запуске из другой папки и расходится по всем
ноутбукам.

Инженерное решение: оформить код как пакет и установить его в окружение проекта. Тогда
`import churn_model` работает одинаково из ноутбука, теста, скрипта и Docker-контейнера. `uv` умеет создавать
такие проекты сразу:

```bash
cd ~/projects
uv init churn-model --package --python 3.12
cd churn-model
uv add scikit-learn pandas
uv add --dev pytest ruff
```

От обычного `uv init` результат отличается папкой `src/churn_model/` с файлом `__init__.py` и двумя секциями
в `pyproject.toml`:

```toml
[project.scripts]
churn-model = "churn_model:main"

[build-system]
requires = ["uv_build>=0.11.32,<0.12.0"]
build-backend = "uv_build"
```

Секция `[build-system]` сообщает, что проект — пакет и чем его собирать (номер версии `uv_build` зависит
от вашей версии `uv`). Увидев её, `uv sync` и `uv run` устанавливают проект в `.venv` в режиме editable:
в `site-packages` попадает не копия кода, а файл `churn_model.pth` с путём к папке `src`. Поэтому правки
в коде видны сразу, без переустановки, а импорт работает из любой папки:

```bash
mkdir notebooks && cd notebooks
uv run python -c "import churn_model; print(churn_model.__file__)"
```

```text
/home/user/projects/churn-model/src/churn_model/__init__.py
```

Секция `[project.scripts]` создаёт консольную команду: `uv run churn-model` вызовет функцию `main` из
`churn_model/__init__.py`. Так оформляют точки входа, которыми пользуются часто.

Зачем отдельная папка `src`, если можно положить `churn_model/` в корень? Когда пакет лежит в корне, запуск
из корня импортирует его напрямую из текущей папки, даже если пакет не установлен или установлен неправильно.
Ошибка всплывёт позже: в CI или в контейнере. С `src` импорт работает только через установленный пакет,
и проблема видна сразу.

**Как превратить существующий проект в пакет:** перенесите модули в `src/<имя_пакета>/`, добавьте туда
`__init__.py`, допишите в `pyproject.toml` секцию `[build-system]` из примера выше и выполните `uv sync`.
Имя пакета — имя проекта, в котором дефисы заменены подчёркиваниями.

## 3. Что коммитить, а что нет

Git хранит то, что написано человеком и нужно для воспроизведения. Всё, что получается запуском кода или
скачивается, в Git не попадает.

| Коммитим | Не коммитим | Почему |
|---|---|---|
| код в `src`, `tests`, ноутбуки | `.venv`, `__pycache__`, кеши линтера и тестов | восстанавливается командой `uv sync` и запуском инструментов |
| `pyproject.toml`, `uv.lock`, `.python-version` | — | без них окружение не воспроизвести |
| `configs/`, `Makefile`, `README.md` | — | это описание того, как получить результат |
| `.gitkeep` в пустых папках | содержимое `data/` | данные большие и часто закрытые; Git не рассчитан на большие бинарные файлы |
| — | содержимое `models/`, `reports/figures/` | производные артефакты, восстанавливаются запуском |
| `.env.example` с именами переменных | `.env` с паролями и токенами | секрет, попавший в историю Git, считается скомпрометированным |

Git не отслеживает пустые папки, поэтому в `data/raw`, `models` и подобные кладут пустой файл `.gitkeep` —
это соглашение, а не возможность Git. Фрагмент `.gitignore`, который игнорирует содержимое папок, но сохраняет
их структуру:

```gitignore
.venv/
__pycache__/
.pytest_cache/
.ruff_cache/
.ipynb_checkpoints/
.env

/data/*/*
!/data/*/.gitkeep
/models/*
!/models/.gitkeep
```

Почему файл игнорируется, покажет команда `git check-ignore -v data/raw/big.csv`: она печатает строку
`.gitignore` с правилом, под которое файл попал.

Данные и модели тоже нужно версионировать — для этого есть отдельные инструменты (DVC, реестры моделей),
до них дойдём в модуле 7. Пока достаточно правила: в README написано, откуда взять данные и какой командой
получить из них всё остальное.

## 4. Cookiecutter: проект из шаблона

Создавать структуру руками для каждого проекта долго, и каждый раз что-то забывается. Cookiecutter — утилита,
которая генерирует проект из шаблона. Шаблон — это папка или Git-репозиторий, где лежат файл
`cookiecutter.json` с переменными и папка `{{cookiecutter.project_slug}}/` с содержимым будущего проекта.
`cookiecutter.json` из стартового шаблона курса (папка [practice](practice/)):

```json
{
  "project_name": "ML Project",
  "project_slug": "{{ cookiecutter.project_name.lower().replace(' ', '-').replace('_', '-') }}",
  "package_name": "{{ cookiecutter.project_slug.replace('-', '_') }}",
  "author": "Your Name",
  "python_version": "3.12",
  "description": "ML-проект, созданный из шаблона курса"
}
```

Имена папок и файлов и их содержимое проходят через шаблонизатор Jinja: `{{ cookiecutter.package_name }}`
заменяется значением переменной. Значение по умолчанию может вычисляться из других переменных — так
из названия «Churn Prediction» получаются имя папки `churn-prediction` и имя пакета `churn_prediction`.

Ставить Cookiecutter в проект не нужно: `uvx` запускает утилиту во временном окружении.

```bash
uvx cookiecutter ml_bootcamp/module_01/topic_1_3/practice -o ~/projects
```

```text
  [1/6] project_name (ML Project): Churn Prediction
  [2/6] project_slug (churn-prediction):
  [3/6] package_name (churn_prediction):
  [4/6] author (Your Name): Anna Ivanova
  [5/6] python_version (3.12):
  [6/6] description (ML-проект, созданный из шаблона курса):
```

Enter принимает значение в скобках. В результате в `~/projects/churn-prediction` лежит готовый проект.

| Вариант запуска | Что делает |
|---|---|
| `uvx cookiecutter <шаблон> -o <папка>` | задаёт вопросы и создаёт проект в указанной папке |
| `uvx cookiecutter --no-input <шаблон> project_name="Churn Prediction"` | без вопросов: значения по умолчанию и переопределения из командной строки |
| `uvx cookiecutter <адрес репозитория> --checkout v0.1.0` | берёт шаблон из Git-репозитория на указанном теге, ветке или коммите |
| `uvx cookiecutter --replay <шаблон>` | повторяет генерацию с ответами прошлого запуска |

Сам Cookiecutter Data Science — тоже шаблон, со своей утилитой-обёрткой:
`uvx --from cookiecutter-data-science ccds`. Его раскладка отличается от нашей в деталях: пакет с кодом лежит
в корне проекта, а не в `src`, есть папки `data/external` для данных из сторонних источников, `docs`
и `references`. Изучите её — с проектами на основе CCDS вы встретитесь в работе.

Шаблон может содержать скрипты-хуки, то есть запускает на вашей машине чужой код. Используйте шаблоны только
из источников, которым доверяете.

## 5. Copier: шаблон, который можно обновлять

У Cookiecutter есть ограничение: проект создаётся один раз и теряет связь с шаблоном. Если через полгода
в шаблоне исправили Makefile или обновили настройки линтера, в двадцать созданных проектов правки придётся
переносить руками.

Copier решает эту задачу. Он записывает в проект файл `.copier-answers.yml` с ответами на вопросы, адресом
и версией шаблона. Когда у шаблона появляется новая версия (Git-тег), команда `copier update` внутри проекта
подтягивает изменения и сливает их с вашими правками; при пересечении оставляет в файле конфликт, как Git
при слиянии.

| | Cookiecutter | Copier |
|---|---|---|
| Описание переменных | `cookiecutter.json` | `copier.yml` |
| Создание проекта | `uvx cookiecutter <шаблон>` | `uvx copier copy <шаблон> <папка проекта>` |
| Обновление проекта после изменения шаблона | нет | `uvx copier update` в папке проекта |
| Требования для обновления | — | шаблон — Git-репозиторий с тегами; проект — Git-репозиторий без незакоммиченных правок |
| Когда выбирать | разовая генерация, чужие шаблоны (их очень много, включая CCDS) | свой шаблон на команду, который будет развиваться |

В практике 1.3.4 делаем шаблон на Cookiecutter: он проще и распространён шире. Перенос на Copier —
одно из заданий на усложнение.

## 6. Makefile: единая точка входа

Команды проекта быстро становятся длинными: `uv run python -m churn_model.train --config configs/base.yaml`.
Их забывают, записывают в README, README устаревает. Makefile хранит команды под короткими именами — и для
людей, и для CI:

```makefile
.DEFAULT_GOAL := help
.PHONY: help install train test lint format

CONFIG ?= configs/base.yaml

help:  ## Показать список команд
	@grep -E '^[a-z_-]+:.*## ' $(MAKEFILE_LIST) | awk -F ':.*## ' '{printf "%-10s %s\n", $$1, $$2}'

install:  ## Создать окружение и установить зависимости
	uv sync

train:  ## Обучить модель: make train CONFIG=configs/base.yaml
	uv run python -m churn_model.train --config $(CONFIG)

test:  ## Запустить тесты
	uv run pytest

lint:  ## Проверить код линтером и форматтером
	uv run ruff check .
	uv run ruff format --check .

format:  ## Исправить замечания линтера и отформатировать код
	uv run ruff check --fix .
	uv run ruff format .
```

Что здесь важно:

- команды под именем цели начинаются с **табуляции**, не с пробелов;
- `.PHONY` перечисляет цели, которые не являются файлами: без этого `make test` ничего не сделает, если
  в проекте появится файл или папка с именем `test`;
- `CONFIG ?= ...` задаёт значение по умолчанию, которое переопределяется при вызове:
  `make train CONFIG=configs/deep.yaml`;
- цель `help` собирает список команд из комментариев `##`, а `.DEFAULT_GOAL` делает её целью по умолчанию:
  `make` без аргументов печатает имена целей с описаниями.

`make` у вас уже установлен после урока 1.1.1: в Ubuntu он входит в `build-essential`, в macOS —
в инструменты командной строки Xcode. Современная альтернатива — `just` с файлом `justfile`: отступы
пробелами, у команд есть параметры, но утилиту нужно ставить отдельно:

```just
# Обучить модель: just train configs/deep.yaml
train config="configs/base.yaml":
    uv run python -m churn_model.train --config {{config}}
```

В курсе используем Makefile. Какой бы инструмент вы ни выбрали, правило одно: всё, что делается в проекте
регулярно, запускается одной короткой командой, и эта же команда работает в CI.

## Типичные ошибки

| Симптом | Причина | Решение |
|---|---|---|
| `ModuleNotFoundError` при импорте своего кода из ноутбука или теста | код не оформлен как пакет, корень проекта не входит в пути поиска | перенесите код в `src/<пакет>/`, добавьте `[build-system]`, выполните `uv sync` |
| В ноутбуках строка `sys.path.append("..")` | та же причина, «вылеченная» заплаткой | установите проект как пакет и удалите заплатки |
| `Makefile:2: *** missing separator.  Stop.` | команда под целью начинается с пробелов | замените отступ на табуляцию; в VS Code проверьте режим отступов для Makefile |
| `make: 'test' is up to date.`, команда не запускается | в проекте есть файл или папка с именем цели | добавьте цель в `.PHONY` |
| Пустые папки `data/raw`, `models` пропали после `git clone` | Git не хранит пустые папки | положите в них `.gitkeep` и добавьте исключение в `.gitignore` |
| В репозитории оказались CSV на сотни мегабайт | `data/` не внесена в `.gitignore` до первого коммита | добавьте правило и уберите файлы из индекса: `git rm -r --cached data/raw` |
| Результат «не сходится» с прошлым запуском | файл в `data/raw` поправили руками | сырые данные не меняем; правки оформляем кодом обработки |
| После правок в шаблоне проекты остались старыми | Cookiecutter не умеет обновлять созданные проекты | переносите правки вручную или используйте Copier |
