## 1. Как устроено виртуальное окружение

Виртуальное окружение — обычная папка. Никакой виртуализации в ней нет:

| Что лежит в `.venv` | Назначение |
|---|---|
| `bin/python` | символическая ссылка на настоящий интерпретатор; своей копии Python в окружении нет |
| `bin/` | ещё скрипты активации и консольные команды установленных пакетов (`pytest`, `ruff`, `jupyter`) |
| `lib/python3.12/site-packages/` | установленные пакеты — ради этой папки окружение и существует |
| `pyvenv.cfg` | маркер окружения: где лежит базовый Python и видны ли его пакеты |

```bash
cat .venv/pyvenv.cfg
```

```text
home = /home/user/.local/share/uv/python/cpython-3.12-linux-x86_64-gnu/bin
implementation = CPython
uv = 0.11.32
version_info = 3.12
include-system-site-packages = false
prompt = churn-model
```

При запуске `.venv/bin/python` интерпретатор находит рядом `pyvenv.cfg`, понимает, что запущен из окружения,
и подставляет в пути поиска модулей `site-packages` окружения вместо системного:

```bash
uv run python -c "import sys; print(sys.prefix); print(sys.base_prefix); print(*sys.path, sep='\n')"
```

```text
/home/user/projects/churn-model/.venv
/home/user/.local/share/uv/python/cpython-3.12.13-linux-x86_64-gnu

/home/user/.local/share/uv/python/cpython-3.12.13-linux-x86_64-gnu/lib/python312.zip
/home/user/.local/share/uv/python/cpython-3.12.13-linux-x86_64-gnu/lib/python3.12
/home/user/.local/share/uv/python/cpython-3.12-linux-x86_64-gnu/lib/python3.12/lib-dynload
/home/user/projects/churn-model/.venv/lib/python3.12/site-packages
/home/user/projects/churn-model/src
```

`sys.prefix` указывает на окружение, `sys.base_prefix` — на базовый Python. Если они различаются, код
выполняется в виртуальном окружении. Список `sys.path` — это места, где `import` ищет модули, по порядку:
текущая папка (пустая строка), стандартная библиотека базового Python, `site-packages` окружения и папка
`src` проекта, добавленная editable-установкой из урока 1.3.1.

**Активация** не делает ничего магического. `source .venv/bin/activate` ставит `.venv/bin` в начало
переменной `PATH` и задаёт переменную `VIRTUAL_ENV`:

```bash
source .venv/bin/activate
which python                         # /home/user/projects/churn-model/.venv/bin/python
echo $VIRTUAL_ENV                    # /home/user/projects/churn-model/.venv
echo $PATH | tr ':' '\n' | head -1   # /home/user/projects/churn-model/.venv/bin
deactivate
```

Отсюда три практических вывода:

1. Активация не обязательна: `.venv/bin/python script.py` работает так же. `uv run` делает именно это,
   предварительно проверив, что окружение соответствует lock-файлу.
2. Окружение нельзя переносить и копировать: внутри записаны абсолютные пути. Его не чинят, а удаляют
   и создают заново — `uv sync` делает это за секунды.
3. Окружение дёшево: `uv` не копирует пакеты, а связывает файлы из общего кеша, поэтому десять проектов
   с NumPy не занимают на диске в десять раз больше места.

## 2. pyproject.toml подробно

Добавим в проект зависимости разных видов (`uv add --optional viz matplotlib`,
`uv add --group notebooks jupyterlab`) и посмотрим на результат. Служебные поля и настройки инструментов
опущены:

```toml
[project]
name = "churn-model"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = [
    "pandas>=3.1.1",
    "scikit-learn>=1.9.1",
]

[project.optional-dependencies]
viz = [
    "matplotlib>=3.11.2",
]

[dependency-groups]
dev = [
    "pytest>=9.2.0",
    "ruff>=0.17.4",
]
notebooks = [
    "jupyterlab>=4.6.6",
]
```

| Секция | Что в ней | Как добавить | Когда устанавливается |
|---|---|---|---|
| `dependencies` | без чего код не работает | `uv add pandas` | всегда |
| `optional-dependencies` | дополнительные возможности пакета («extras»), видны его пользователям | `uv add --optional viz matplotlib` | `uv sync --extra viz`; у пользователей — `pip install "churn-model[viz]"` |
| `dependency-groups` | инструменты разработчика, в собранный пакет не попадают | `uv add --dev pytest`, `uv add --group notebooks jupyterlab` | группа `dev` — по умолчанию; остальные — `uv sync --group notebooks` |
| `requires-python` | с какими версиями Python проект обязан работать | вручную | учитывается при подборе версий пакетов |

В списке `dependencies` указывают только **прямые** зависимости — то, что импортирует ваш код. NumPy нужен
pandas и scikit-learn, но пока вы сами не пишете `import numpy`, в `dependencies` ему не место: его версию
подберёт и зафиксирует lock-файл.

`uv sync` приводит окружение в точное соответствие выбранному набору — лишнее удаляет:

```bash
uv sync                                 # основные зависимости + группа dev
uv sync --group notebooks --extra viz   # плюс JupyterLab и matplotlib
uv sync --no-dev                        # только основные: так собирают образ для продакшена
uv tree --depth 1                       # прямые зависимости с пометками групп и extras
```

`requires-python` и `.python-version` решают разные задачи. Первое — обещание: «проект работает на любом
Python из диапазона», и `uv` подбирает версии пакетов для всего диапазона. Второе — какой именно интерпретатор
использовать в этом окружении. Чем шире диапазон, тем сложнее подбор: для старых версий Python приходится
брать старые версии пакетов. Поэтому для прикладного ML-проекта диапазон держат узким.

## 3. Ограничения версий

| Запись | Смысл | Подходит | Не подходит |
|---|---|---|---|
| `numpy==2.3.5` | ровно эта версия | 2.3.5 | 2.3.6 |
| `numpy>=2.0` | не ниже | 2.0.0, 3.0.0 | 1.26.4 |
| `numpy>=2.0,<3` | диапазон | 2.5.4 | 3.0.0 |
| `numpy~=2.3` | совместимый релиз: `>=2.3,<3` | 2.3.0, 2.9.0 | 3.0.0 |
| `numpy~=2.3.1` | совместимый релиз: `>=2.3.1,<2.4` | 2.3.9 | 2.4.0 |
| `numpy!=2.4.0` | исключить сломанный релиз | 2.4.1 | 2.4.0 |

По умолчанию `uv add` записывает нижнюю границу по установленной версии (`pandas>=3.1.1`). Задать ограничение
явно: `uv add "numpy>=2.0,<3"`. Как выбирать:

- **Нижняя граница — всегда.** Она сообщает, начиная с какой версии есть нужные вам возможности. Граница
  должна быть честной: `pyyaml>=6.0` выглядит безобидно, но у версии 6.0 нет готовых сборок под Python 3.12,
  и установка падает при компиляции.
- **Точные версии (`==`) в `pyproject.toml` не нужны.** Точность обеспечивает lock-файл. Закрепляя всё через
  `==`, вы теряете возможность обновлять пакеты согласованно.
- **Верхняя граница — когда есть причина.** Причины: известная несовместимость («код не работает с pandas 3»),
  библиотека с частыми ломающими изменениями, зависимость, собранная под конкретную мажорную версию NumPy.
  Ставить потолок на всё подряд «на всякий случай» не нужно: приложение от неожиданных обновлений защищает
  lock-файл, а лишние потолки приводят к конфликтам, когда двум пакетам нужны непересекающиеся диапазоны.

## 4. Lock-файл

`pyproject.toml` описывает намерение: «нужен pandas не старше 3.1.1». `uv.lock` описывает факт: какие именно
версии всех пакетов, включая зависимости зависимостей, были подобраны. В проекте `churn-model` прямых
зависимостей шесть, а записей в lock-файле — 113. Фрагмент (длинные строки сокращены):

```toml
[[package]]
name = "pandas"
version = "3.1.1"
source = { registry = "https://pypi.org/simple" }
dependencies = [
    { name = "numpy" },
    { name = "python-dateutil" },
    { name = "tzdata", marker = "sys_platform == 'emscripten' or sys_platform == 'win32'" },
]
wheels = [
    { url = ".../pandas-3.1.1-cp312-cp312-macosx_11_0_arm64.whl", hash = "sha256:3b10ae67...", ... },
    { url = ".../pandas-3.1.1-cp312-cp312-manylinux_2_24_aarch64.manylinux_2_28_aarch64.whl", ... },
]
```

Что здесь важно для воспроизводимости:

- **точные версии** каждого пакета — без lock-файла `uv sync` через полгода поставил бы другие;
- **хеши файлов** — установится ровно тот файл, который был у вас, а не подменённый или пересобранный;
- **все платформы сразу** — в одном файле записаны сборки для Linux, macOS и Windows, поэтому один и тот же
  `uv.lock` работает на ноутбуке с macOS и на сервере с Linux.

Lock-файл не редактируют руками и всегда коммитят вместе с `pyproject.toml`.

| Команда | Что делает | Где применять |
|---|---|---|
| `uv sync` | при необходимости обновляет lock по `pyproject.toml` и приводит окружение к нему | ежедневная работа |
| `uv lock` | только обновляет lock-файл, окружение не трогает | после ручной правки `pyproject.toml` |
| `uv lock --check` | проверяет, что lock соответствует `pyproject.toml`, ничего не меняя | CI |
| `uv sync --locked` | то же, что `uv sync`, но падает с ошибкой, если lock устарел | CI |
| `uv sync --frozen` | ставит строго по lock-файлу, не сверяя его с `pyproject.toml` | Docker, продакшен |
| `uv lock --upgrade-package numpy` | обновляет в lock один пакет | плановое обновление |
| `uv lock --upgrade` | обновляет всё до последних допустимых версий | редко и осознанно |

Lock «липкий»: если версия пакета уже записана и не противоречит `pyproject.toml`, `uv lock` и `uv sync`
её не меняют, даже когда вышла новая. Пусть в проекте было `numpy<2.4`, в lock записана версия 2.3.5,
а затем ограничение в `pyproject.toml` ослабили до `numpy>=2.0`:

```bash
uv lock --check                   # error: The lockfile at `uv.lock` needs to be updated...
uv lock                           # lock приведён в соответствие, но numpy остался 2.3.5
uv lock --upgrade-package numpy   # Updated numpy v2.3.5 -> v2.5.4
uv sync                           # - numpy==2.3.5  + numpy==2.5.4
```

Рабочий порядок обновления: один пакет за раз, прогон тестов и контрольного обучения, отдельный коммит
с изменением `uv.lock`. Если метрики после обновления поехали, `git log -- uv.lock` покажет, какой коммит
и какой пакет в этом виноват.

## 5. Экспорт в requirements.txt

Часть инструментов (облачные сервисы, старые Docker-образы, чужие пайплайны) понимает только
`requirements.txt`. Его не ведут руками, а генерируют из lock-файла:

```bash
uv export --format requirements.txt --no-dev --no-hashes --no-emit-project -o requirements.txt
head -6 requirements.txt
```

```text
# This file was autogenerated by uv via the following command:
#    uv export --format requirements.txt --no-dev --no-hashes --no-emit-project -o requirements.txt
cloudpickle==3.1.2
    # via joblib
joblib==1.6.0
    # via scikit-learn
```

`--no-dev` исключает группу `dev`, `--no-emit-project` — сам проект (строку `-e .`). Без `--no-hashes` файл
длиннее, зато pip проверит целостность каждого пакета. Источник правды — по-прежнему `uv.lock`: после каждого
изменения зависимостей файл генерируют заново, лучше всего отдельной целью в Makefile.

## 6. Сравнение инструментов

В чужих проектах вы встретите всё перечисленное, поэтому важно понимать, что есть что.

| Инструмент | Файлы | Lock-файл | Когда использовать |
|---|---|---|---|
| venv + pip | `requirements.txt` | нет: `pip freeze` даёт снимок одного окружения на одной платформе, без разделения на прямые и транзитивные зависимости | разовый скрипт, учебный пример, среда, где нет ничего кроме Python |
| pip-tools | `requirements.in` → `requirements.txt` | да, под одну платформу и версию Python | существующий проект на pip, которому нужна фиксация версий без смены инструмента |
| Poetry | `pyproject.toml`, `poetry.lock` | да, кроссплатформенный | проекты и команды, где он уже принят; публикация библиотек |
| conda | `environment.yml` | отдельным инструментом (conda-lock) | нужны не-Python зависимости: системные библиотеки, компиляторы, конкретные сборки под GPU; научные кластеры |
| uv | `pyproject.toml`, `uv.lock` | да, кроссплатформенный | новые проекты; инструмент курса |

Чем `uv` отличается на практике: сам устанавливает нужную версию Python, работает заметно быстрее pip,
описывает зависимости стандартными секциями `pyproject.toml` и умеет работать в режиме совместимости с pip.
Последнее пригодится, когда вам достанется проект с одним `requirements.txt`:

```bash
uv venv --python 3.12
uv pip install -r requirements.txt
```

Главное ограничение pip-подобных инструментов, включая `uv`: они ставят только пакеты Python. Драйвер
видеокарты, системные библиотеки и компиляторы — зона ответственности conda или Docker.

## 7. Особенности ML: сборки под CPU и GPU

Большинство пакетов существует в одном варианте на платформу. У PyTorch и подобных библиотек вариантов
несколько: сборка только под CPU (компактная) и сборки под разные версии CUDA (в разы больше, с библиотеками
для GPU внутри). Варианты лежат в отдельных индексах пакетов. Какой вариант поставится, зависит от того,
какой индекс указан при установке, — и это частая причина ситуации «на сервере GPU есть, а `torch` его
не видит».

В `uv` индекс описывают в `pyproject.toml` и привязывают к нему конкретный пакет:

```toml
[[tool.uv.index]]
name = "pytorch-cpu"
url = "<адрес индекса со сборками PyTorch под CPU>"
explicit = true

[tool.uv.sources]
torch = { index = "pytorch-cpu" }
```

`explicit = true` означает, что из этого индекса берутся только явно привязанные к нему пакеты, остальные
по-прежнему приходят из PyPI. Точный адрес индекса для нужной версии CUDA берите из инструкции по установке
на сайте PyTorch. Источник попадает в `uv.lock`, поэтому у всей команды и на сервере будет одна и та же
сборка. Что стоит помнить:

- версия CUDA в сборке должна поддерживаться драйвером видеокарты на машине; драйвер — часть системы,
  `uv` им не управляет;
- для CI и ноутбуков без GPU обычно достаточно CPU-сборки — она ставится быстрее и занимает меньше места;
- если нужны и системные библиотеки под GPU, окружение целиком фиксируют Docker-образом (урок 1.1.3)
  или conda.

К установке PyTorch вернёмся в модуле 5; сейчас важна идея: «какая сборка» — такая же часть окружения,
как «какая версия», и она тоже должна быть записана в файлах проекта.

## 8. Seed: воспроизводимость случайности

Одинаковое окружение не гарантирует одинаковый результат: разбиение на train и test, инициализация весов,
перемешивание данных используют генераторы случайных чисел. Пример: случайный лес из 20 деревьев на датасете
`breast_cancer`, три запуска подряд. Без фиксации seed accuracy получилась 0.9649, 0.9825 и 0.9474,
с `random_state=42` в разбиении и в модели — трижды 0.9649. Разброс в три с половиной процентных пункта возник
только из-за случайности: не зафиксировав seed, нельзя понять, улучшила ли метрику ваша правка или просто
повезло с разбиением.

```python
import random

import numpy as np


def set_seed(seed: int) -> None:
    random.seed(seed)
    np.random.seed(seed)
```

Правила:

- у каждого источника случайности свой генератор: `random`, NumPy, у фреймворков глубокого обучения —
  собственные. Функция `set_seed` должна покрывать все, что используются в проекте;
- в scikit-learn передавайте seed явно через `random_state` — это надёжнее глобального состояния;
- в новом коде на NumPy используйте локальный генератор `rng = np.random.default_rng(seed)`;
- seed — параметр эксперимента: он хранится в конфиге и сохраняется вместе с результатами (урок 1.3.3);
- фиксированный seed нужен для воспроизводимости, а не для выбора «удачного» значения. Выводы о качестве
  модели делают по нескольким seed.

## Типичные ошибки

| Симптом | Причина | Решение |
|---|---|---|
| `pip install` ставит пакет «не туда» или падает с `externally-managed-environment` | в окружении, созданном `uv`, нет pip; команда нашла pip другого Python | добавляйте пакеты через `uv add`; для разовых задач — `uv pip install` |
| После переноса или переименования папки проекта команды из `.venv/bin` не запускаются | внутри окружения записаны абсолютные пути | удалите `.venv` и выполните `uv sync` |
| `error: The lockfile at uv.lock needs to be updated` в CI | `pyproject.toml` изменили, а `uv.lock` не обновили или не закоммитили | выполните `uv lock` локально и закоммитьте оба файла |
| После `uv sync` пропали JupyterLab или matplotlib | они в необязательной группе или в extras, а `uv sync` удаляет всё, что не запрошено | `uv sync --group notebooks --extra viz` |
| У коллеги другие версии пакетов | `uv.lock` не закоммичен или коллега ставил пакеты через pip | коммитьте `uv.lock`; окружение создавайте только через `uv sync` |
| Обновили «один пакет», а метрики изменились | вместе с ним обновились транзитивные зависимости | смотрите `git diff uv.lock`; обновляйте по одному пакету с прогоном тестов |
| `torch.cuda.is_available()` возвращает `False` на машине с GPU | установлена CPU-сборка или сборка под версию CUDA, которую не поддерживает драйвер | привяжите пакет к нужному индексу в `pyproject.toml`, проверьте версию драйвера |
| Метрики не совпадают между запусками | не зафиксирован один из источников случайности | вызывайте `set_seed` в начале запуска и передавайте `random_state` |
