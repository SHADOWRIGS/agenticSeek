# Урок 1.3.4: ПРАКТИКА: Создание шаблона для ML проекта

> **Модуль 1:** Foundations & Mindset Engineer · **Тема 1.3:** Инструменты репроизводимости
> **Тип:** практика · **Время:** 3–4 часа

## Цели урока

После практики у вас будет:

- собственный шаблон ML-проекта в отдельном Git-репозитории, из которого новый проект создаётся одной
  командой;
- сгенерированный проект, в котором сразу работают установка окружения, обучение по конфигу, тесты и линтер;
- автоматическая проверка самого шаблона;
- опыт, который объединяет три урока темы: структура проекта, управление зависимостями, конфигурации.

## Зачем это нужно

Первые два-три часа любого нового проекта уходят на одно и то же: папки, `pyproject.toml`, настройка линтера,
Makefile, `.gitignore`, загрузка конфига, первый тест. Каждый раз это делается чуть по-разному, и через год
у вас десять проектов с десятью вариантами структуры.

Шаблон превращает ваши договорённости в код. Все следующие проекты курса — от анализа данных в модуле 2
до финального проекта — вы будете начинать с него и дорабатывать шаблон по мере того, как узнаёте новое.
Хороший личный шаблон — ещё и аргумент на собеседовании: он показывает, как вы организуете работу.

## 1. Постановка задачи

Создайте шаблон Cookiecutter, из которого генерируется проект для задачи классификации на табличных данных.
Сгенерированный проект должен быть готов к работе без единой ручной правки:

```bash
uvx cookiecutter <ваш шаблон> -o ~/projects
cd ~/projects/<новый проект>
make install && make lint && make test && make train
```

Все четыре команды завершаются успешно, а `make train` оставляет папку запуска, по которой эксперимент можно
повторить.

## 2. Стартовая точка

В папке [practice](practice/) лежит минимальный рабочий шаблон; его устройство описано
в [practice/README.md](practice/README.md). Что в нём уже есть:

| Часть | Состояние в заготовке |
|---|---|
| Переменные | `project_name`, `project_slug`, `package_name`, `author`, `python_version`, `description` |
| Структура | `configs`, `data/{raw,interim,processed}`, `models`, `notebooks`, `src/<пакет>`, `tests` |
| Окружение | `pyproject.toml` с зависимостями, dev-группой, сборкой пакета и настройками Ruff |
| Конфиг | `configs/base.yaml`, схема pydantic с запретом неизвестных ключей |
| Обучение | `train.py`: читает конфиг, фиксирует seed, обучает логистическую регрессию на встроенном датасете, сохраняет модель, метрики и итоговый конфиг в `models/<запуск>/` |
| Тесты | проверка конфига, проверка запуска и воспроизводимости по seed |
| Команды | `Makefile`: `install`, `train`, `test`, `lint`, `format`, `clean` |

Чего в заготовке нет — перечислено в требованиях ниже. Это и есть ваша работа.

## 3. Требования к шаблону

**Генерация**

1. Проект генерируется и в интерактивном режиме, и с `--no-input`.
2. Работают нестандартные значения: название с пробелами, имя пакета, не совпадающее с именем проекта.
3. Недопустимое имя пакета (начинается с цифры, содержит дефис) отклоняется до создания файлов с понятным
   сообщением.
4. После генерации проект уже является Git-репозиторием.

**Структура и документация**

5. Раскладка из урока 1.3.1, включая `reports/figures/`; пустые папки сохраняются в Git.
6. `.gitignore` не пропускает в Git данные, модели, графики, окружение, кеши и `.env`.
7. Есть `.env.example`.
8. README сгенерированного проекта описывает назначение папок, команды и порядок запуска эксперимента.
9. README репозитория шаблона описывает переменные и способ генерации.

**Окружение**

10. Зависимости разделены на основные и группу `dev`; нижние границы версий указаны, `==` не используется.
11. Код проекта — устанавливаемый пакет в `src/`; тесты импортируют его по имени пакета.

**Конфигурация и воспроизводимость**

12. Параметры эксперимента приходят из конфига со схемой; опечатка в ключе приводит к ошибке до обучения.
13. Есть базовый конфиг и минимум один конфиг эксперимента; параметры можно переопределить из командной
    строки (свой разбор, как в уроке 1.3.3, или Hydra).
14. Seed задаётся в конфиге; два запуска с одним конфигом дают одинаковые метрики.
15. Папка запуска содержит модель, метрики, итоговый конфиг и хеш коммита Git, на котором выполнен запуск.

**Качество**

16. Код обучения разделён на модули: загрузка данных, построение модели, оценка, точка входа.
17. Не меньше пяти тестов; `make lint` и `make test` проходят в свежесгенерированном проекте.
18. В репозитории шаблона есть команда `make check`, которая генерирует проект во временную папку
    и выполняет в нём установку, линтер, тесты и обучение.

## 4. Пошаговый план

### Шаг 1. Репозиторий шаблона

Скопируйте заготовку в отдельную папку (точка в конце пути нужна, чтобы скопировались и скрытые файлы)
и создайте репозиторий:

```bash
mkdir -p ~/projects/ml-project-template
cp -r <репозиторий курса>/ml_bootcamp/module_01/topic_1_3/practice/. ~/projects/ml-project-template/
cd ~/projects/ml-project-template
git init
git add -A
git commit -m "Стартовая заготовка шаблона"
```

### Шаг 2. Проверка шаблона одной командой

Шаблон нельзя проверить, не сгенерировав проект: файлы внутри `{{cookiecutter.project_slug}}/` — ещё
не Python и не TOML, а заготовки с выражениями Jinja. Поэтому первым делом автоматизируйте цикл
«сгенерировал — проверил». `Makefile` в корне репозитория шаблона:

```makefile
.PHONY: check

check:  ## Сгенерировать проект во временную папку и прогнать в нём все проверки
	rm -rf .build
	uvx cookiecutter --no-input . -o .build
	$(MAKE) -C .build/ml-project install lint test train
```

Добавьте `.build/` в `.gitignore` репозитория шаблона и выполните `make check`. Запускайте эту команду после
каждой правки — так ошибка обнаружится сразу, а не через десять изменений.

### Шаг 3. Хуки

Хуки — скрипты в папке `hooks/` рядом с `cookiecutter.json`. Cookiecutter выполняет их до и после генерации;
в них тоже работают выражения Jinja. Проверка имени пакета, `hooks/pre_gen_project.py`:

```python
import re
import sys

package_name = "{{ cookiecutter.package_name }}"

if not re.fullmatch(r"[a-z][a-z0-9_]*", package_name):
    print(f"Недопустимое имя пакета: {package_name!r}. Допустимы строчные буквы, цифры и подчёркивания.")
    sys.exit(1)
```

Инициализация репозитория, `hooks/post_gen_project.py` (выполняется в папке созданного проекта):

```python
import subprocess

subprocess.run(["git", "init", "--quiet"], check=True)
print("Проект создан. Дальше: make install && make train")
```

Проверьте оба: обычная генерация создаёт папку `.git`, а запуск с `package_name="2bad-name"` завершается
сообщением об ошибке и не оставляет папку проекта.

### Шаг 4. Структура и документация

Добавьте `reports/figures/` с `.gitkeep`, правила для неё в `.gitignore`, файл `.env.example`. Обновите
README проекта. Проверьте в сгенерированном проекте: положите файлы в `data/raw`, `models`, `reports/figures`
и создайте `.env` — `git status` не должен показать ни один из них.

### Шаг 5. Конфигурация

Перенесите в шаблон то, что сделали в уроке 1.3.3: слияние базового конфига с конфигом эксперимента
и переопределениями из командной строки. Добавьте второй конфиг в `configs/` и параметр в `Makefile`,
чтобы работало `make train CONFIG=configs/<эксперимент>.yaml`. Если выбираете Hydra, замените `configs/`
на структуру с группами и обновите README.

### Шаг 6. Воспроизводимость запуска

Допишите сохранение хеша коммита (его возвращает команда `git rev-parse HEAD`) в папку запуска. Продумайте
два случая: проект ещё не является Git-репозиторием и в рабочей папке есть незакоммиченные изменения.
Во втором случае хеш не описывает код, которым получен результат, — запуск стоит пометить.

### Шаг 7. Модули и тесты

Разделите `train.py`: загрузка данных, построение модели, расчёт метрик, точка входа. На каждый новый модуль
добавьте тест. Тесты должны быть быстрыми — используйте встроенные датасеты и маленькие модели.

### Шаг 8. Финальная проверка

Сгенерируйте проект с нестандартными значениями в чистую папку и пройдите путь нового пользователя,
следуя только README:

```bash
uvx cookiecutter --no-input ~/projects/ml-project-template -o /tmp/template-check \
    project_name="Credit Scoring v2" package_name=scoring author="Ваше Имя"
cd /tmp/template-check/credit-scoring-v2
make install && make lint && make test && make train
```

Если где-то пришлось догадываться или править файл руками — исправьте шаблон или README и повторите.
Поставьте на итоговый коммит тег, например `v0.1.0`: проекты можно будет создавать с конкретной версии шаблона
(`--checkout v0.1.0`).

## Типичные ошибки

| Симптом | Причина | Решение |
|---|---|---|
| `Unable to create file '...'`, `Error message: 'config' is undefined` | в файле шаблона есть `{{ ... }}`, не относящееся к Cookiecutter (justfile, GitHub Actions, шаблоны Helm) | оберните фрагмент в `{% raw %}...{% endraw %}` |
| Ноутбук в шаблоне ломает генерацию или портится | содержимое `.ipynb` обрабатывается как шаблон Jinja | добавьте в `cookiecutter.json` ключ `"_copy_without_render": ["notebooks/*.ipynb"]` |
| Редактор и линтер подсвечивают ошибки в файлах шаблона | файлы внутри `{{cookiecutter.project_slug}}/` — не валидный Python до генерации | проверяйте сгенерированный проект (`make check`), а не шаблон |
| Генерация проходит, но `make install` падает на `pyproject.toml` | значение переменной сломало синтаксис TOML (например, кавычка в описании) | проверяйте значения в `pre_gen_project.py` или экранируйте их в шаблоне |
| `ModuleNotFoundError` в тестах сгенерированного проекта | имя папки в `src/` и имя в импортах подставляются из разных переменных | везде используйте `cookiecutter.package_name`; проверьте генерацию с `package_name`, отличным от имени проекта |
| Пустые папки исчезают после `git clone` шаблона | Git не хранит пустые папки | `.gitkeep` в каждой пустой папке шаблона |
| `.gitkeep` или другие файлы шаблона не попадают в коммит | их игнорирует `.gitignore` шаблона или вложенный `.gitignore` будущего проекта | `git status --short --untracked-files=all` и `git check-ignore -v <путь>` |
| `make check` проходит, а у коллеги проект не собирается | шаблон проверялся только со значениями по умолчанию | добавьте в `check` генерацию с нестандартными значениями |
| Запуск падает с `FileExistsError` | два запуска в одну секунду получили одно имя папки | сделайте имя запуска уникальным; не перезаписывайте старые результаты |

## Критерии приёмки

Сдаётся ссылка на репозиторий шаблона.

- [ ] `make check` в репозитории шаблона завершается без ошибок;
- [ ] генерация с `--no-input` и нестандартными `project_name` и `package_name` даёт проект, в котором
      проходят `make install`, `make lint`, `make test`, `make train`;
- [ ] генерация с недопустимым `package_name` завершается понятной ошибкой и не оставляет папку проекта;
- [ ] сгенерированный проект — Git-репозиторий; после `make train` и создания `.env` команда `git status`
      не показывает данные, модели, графики и секреты;
- [ ] папка запуска содержит модель, `metrics.json`, итоговый `config.yaml` и хеш коммита;
- [ ] повторный запуск по сохранённому `config.yaml` даёт те же метрики;
- [ ] `make train CONFIG=<другой конфиг>` и переопределение параметра из командной строки работают;
- [ ] опечатка в имени параметра конфига останавливает запуск до обучения;
- [ ] в сгенерированном проекте не меньше пяти тестов, код обучения разделён на модули;
- [ ] оба README — шаблона и сгенерированного проекта — позволяют пройти весь путь без подсказок;
- [ ] в репозитории шаблона нет `.venv`, `uv.lock`, кешей и сгенерированных проектов.

## Идеи для усложнения

- **Выбор вариантов.** Переменная-список в `cookiecutter.json` (например, `"license": ["MIT", "Apache-2.0",
  "Proprietary"]`) превращается в вопрос с выбором; в файлах шаблона по ней строятся условия
  `{% if cookiecutter.license == "MIT" %}...{% endif %}`. Сделайте так выбор между конфигами на pydantic
  и на Hydra.
- **Понятные вопросы.** Ключ `__prompts__` в `cookiecutter.json` задаёт человекочитаемый текст вопроса для
  каждой переменной.
- **Проверки перед коммитом.** Добавьте в шаблон конфигурацию pre-commit с Ruff.
- **CI.** Добавьте в сгенерированный проект конфигурацию CI, которая выполняет `uv sync --locked`,
  `make lint`, `make test`, а в репозиторий шаблона — CI с `make check`.
- **Docker.** Добавьте `Dockerfile` на основе урока 1.1.3 с установкой зависимостей через `uv sync --frozen`.
- **Перенос на Copier.** Перепишите шаблон под Copier и убедитесь, что `copier update` доставляет правку
  из шаблона в уже созданный проект.
- **Сводка экспериментов.** Добавьте команду `make report`, которая обходит папки запусков и собирает
  таблицу «запуск — параметры — метрики» в `reports/`.
