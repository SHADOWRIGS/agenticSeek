# Урок 1.2.4: ПРАКТИКА: Написание эффективного ETL пайплайна

> **Модуль 1:** Foundations & Mindset Engineer · **Тема 1.2:** Python для ML инженера
> **Тип:** практика · **Время:** 5–6 часов

## Цели урока

После практики вы сможете:

- провести оптимизацию по циклу «измерить — найти узкое место — исправить — проверить результат»;
- применить в одной задаче декораторы, генераторы, context managers, конкурентные запросы и профилирование;
- превратить скрипт, который «работает на примере», в пайплайн, время которого растёт линейно с объёмом
  данных, а память почти не растёт;
- оформить результат отчётом с замерами, по которому работу можно проверить.

## Зачем это нужно

ETL (extract, transform, load) — первый шаг любого ML-проекта: забрать сырые данные, очистить и положить
в удобное для обучения хранилище. Такой код обычно пишут быстро и проверяют на небольшом примере.
На настоящих данных он либо работает часами, либо падает по памяти.

В этой практике вы получаете именно такой код: корректный, покрытый тестами, но наивный. Писать пайплайн
с нуля не нужно — нужно сделать то, чем инженер занимается гораздо чаще: разобраться в чужом работающем коде
и сделать его пригодным для реальных объёмов, не сломав результат.

## 1. Задача

Интернет-магазин ежедневно выгружает события (просмотры, добавления в корзину, покупки) в CSV-файлы.
Данные грязные: встречаются оборванные строки, пропуски, разный регистр, повторные выгрузки одних
и тех же событий. Цены указаны в разных валютах, курс на нужный день отдаёт внешний сервис.

Пайплайн должен подготовить две таблицы в формате Parquet:

- `events_clean.parquet` — очищенные события с категорией товара и суммой в долларах;
- `daily_revenue.parquet` — выручка по дням, странам и категориям.

## 3. Данные и правила преобразования

**Вход.** В папке с сырыми данными лежат `products.csv` (колонки `product_id`, `category`,
`list_price_usd`) и файлы `events_NNN.csv`. Поля событий разделены запятой, кавычек и запятых внутри
значений нет. Первая строка каждого файла — заголовок:

```text
event_id,user_id,event_time,event_type,product_id,price,currency,quantity,country
```

**Строка корректна**, если выполнены все условия:

1. в строке ровно девять полей;
2. `event_id`, `user_id`, `product_id`, `quantity` — целые числа, `quantity` не меньше 1;
3. `event_time` — существующие дата и время в формате `ГГГГ-ММ-ДД ЧЧ:ММ:СС`;
4. `event_type` после удаления пробелов по краям и приведения к нижнему регистру — `view`, `cart`
   или `purchase`;
5. `product_id` есть в `products.csv`;
6. `price` — пустая строка либо число больше нуля;
7. `currency` после удаления пробелов и приведения к верхнему регистру — `USD`, `EUR`, `GBP` или `JPY`.

Некорректные строки отбрасываются. **Корректные строки очищаются:**

- `event_type` приводится к нижнему регистру без пробелов, `currency` и `country` — к верхнему;
- пустая страна заменяется на `UNKNOWN`;
- если цена пустая, берётся `list_price_usd` товара, а валютой события становится `USD`;
- добавляется `category` товара из справочника;
- добавляется `amount_usd = price * quantity * курс`, где курс — ответ сервиса для валюты события и дня
  события.

**Дубликаты.** Строки с одинаковым `event_id` — повторная выгрузка одного события; они могут находиться
в разных файлах. Гарантируется, что такие строки совпадают полностью. В результате остаётся одна.

**Выход.** Порядок строк в обоих файлах не важен.

| Файл | Колонки |
|---|---|
| `events_clean.parquet` | `event_id`, `user_id`, `event_time` (дата и время), `event_type`, `product_id`, `category`, `price`, `currency`, `quantity`, `country`, `amount_usd` |
| `daily_revenue.parquet` | `day` (дата), `country`, `category`, `orders` (число покупок), `units` (сумма `quantity`), `revenue_usd` (сумма `amount_usd`) — только по событиям `purchase` |

Функция пайплайна возвращает словарь со статистикой: `rows_read` (строк с данными во всех файлах),
`rows_invalid`, `rows_duplicate` (дубликаты среди корректных строк), `rows_clean`.

## 4. Что нужно сделать

Создайте рядом с `etl_baseline.py` модуль `etl_fast.py` с функцией того же вида:

```python
def run_pipeline(raw_dir: Path, out_dir: Path) -> dict[str, int]: ...
```

Требования:

- результат совпадает с результатом `etl_baseline` — это проверяют тесты:
  `ETL_MODULE=etl_fast uv run pytest`;
- запуск из командной строки принимает те же аргументы `--raw` и `--out` и печатает статистику, время
  и пик памяти;
- курсы валют запрашиваются только через `rates_service.get_rate` или `rates_service.get_rate_async`;
- пайплайн не знает данные заранее: никаких заготовленных ответов и чтения внутренностей сервиса;
- в решении осмысленно использованы приёмы темы: декораторы (как минимум повтор при сбое с ограничением
  числа попыток), потоковая обработка генераторами или батчами, context managers для всех ресурсов,
  конкурентные запросы к сервису курсов.

## 5. Пошаговый план

**Шаг 0. Точка отсчёта.** Сгенерируйте данные на 50, 100 и 200 тысяч строк и запишите время и память
`etl_baseline`. Замеры авторов:

| Строк | Время | Пик памяти |
|---|---|---|
| 50 000 | 14.1 с | 224 МБ |
| 100 000 | 37.5 с | 279 МБ |
| 200 000 | 135.3 с | 406 МБ |

Данных становится вдвое больше, а время растёт в 2.7 и 3.6 раза. Запомните это наблюдение: оно подсказывает,
какого рода проблему искать. Миллион строк такой пайплайн, по нашей оценке, обрабатывал бы около часа.

**Шаг 1. Профиль.** Не читайте код в поисках «подозрительных мест» — сначала измерьте:

```bash
uv run python -m cProfile -o baseline.prof etl_baseline.py --raw data/raw --out data/out
uv run python -c "import pstats; pstats.Stats('baseline.prof').strip_dirs().sort_stats('tottime').print_stats(15)"
```

Выпишите функции, которые дают основную часть времени, и для каждой сформулируйте причину.

**Шаг 2. Алгоритмы и структуры данных.** Исправьте самое дорогое место, запустите тесты, снимите профиль
заново. Повторяйте, пока в верхних строках отчёта не останется только неизбежная работа.

**Шаг 3. Ожидание сервиса.** Запросы к сервису курсов — I/O-bound часть. Три вопроса, на которые нужно
ответить кодом:

- сколько разных пар (валюта, день) есть в данных и сколько запросов делает `etl_baseline`;
- что произойдёт с пайплайном, если сервис ответит ошибкой, и сколько раз допустимо повторять запрос;
- можно ли ждать ответы одновременно. Подсказка: сначала соберите пары, которых ещё нет в кэше, затем
  запросите их все сразу через `asyncio` с семафором или через пул потоков.

**Шаг 4. Память.** `etl_baseline` хранит все строки в нескольких списках одновременно. Перестройте поток
данных: генератор строк из файлов → проверка и очистка → батчи (`itertools.batched`) → запись батча
на диск. Parquet-файл можно писать по частям (фрагмент, а не готовая программа):

```python
import pyarrow as pa
import pyarrow.parquet as pq

schema = pa.schema([("event_id", pa.int64()), ("country", pa.string()), ("amount_usd", pa.float64())])
with pq.ParquetWriter(out_dir / "events_clean.parquet", schema) as writer:
    for batch in batches:  # batch — кортеж или список словарей
        writer.write_table(pa.Table.from_pylist(list(batch), schema=schema))
```

Подумайте, что всё же придётся держать в памяти целиком (подсказка: дубликаты и агрегаты) и сколько это
занимает на миллионе строк.

**Шаг 5. Оставшиеся горячие точки.** Снова снимите профиль. Теперь наверху окажется разбор строк: даты,
числа, поиск товара. Часть этой работы можно удешевить, часть — распараллелить по файлам процессами
(это CPU-bound). Перед тем как подключать процессы, решите, где будет выполняться поиск дубликатов между
файлами.

**Шаг 6. Итоговые замеры и отчёт.** Проверьте пайплайн на миллионе строк
(`generate_data.py --rows 1000000 --out data/raw_1m`) и заполните таблицу в `REPORT.md`:

| Версия | 50 000 строк: время / память | 1 000 000 строк: время / память | Что изменено |
|---|---|---|---|
| baseline | | не запускать | |
| после шага 2 | | | |
| ... | | | |

## 6. Критерии приёмки

- [ ] `ETL_MODULE=etl_fast uv run pytest` — все тесты проходят;
- [ ] `uv run ruff check .` завершается без ошибок;
- [ ] на 50 000 строк `etl_fast` работает минимум в 20 раз быстрее `etl_baseline` на той же машине;
- [ ] 1 000 000 строк `etl_fast` обрабатывает быстрее, чем `etl_baseline` обрабатывает 50 000;
- [ ] пик памяти на 1 000 000 строк превышает пик на 50 000 строк не более чем в два раза;
- [ ] ошибка сервиса курсов не роняет пайплайн, а число повторов ограничено;
- [ ] файлы `rates_service.py`, `generate_data.py`, `etl_baseline.py` и тесты не изменены;
- [ ] в `REPORT.md` есть таблица замеров, фрагменты профилей до и после, описание каждой оптимизации
      с её эффектом и хотя бы одна идея, которая не дала выигрыша, с объяснением почему.

Все пороги достижимы на чистом Python с `pyarrow` для записи: проверочное решение авторов обрабатывает
миллион строк за 4.5 секунды с пиком памяти 234 МБ.

## 7. Идеи для усложнения

- **Процессы.** Распараллельте разбор файлов через `ProcessPoolExecutor` и измерьте выигрыш на 1, 2, 4
  процессах. Учтите, что у каждого процесса своё состояние сервиса курсов и свой кэш.
- **Инкрементальный режим.** Пайплайн запоминает обработанные файлы и при следующем запуске обрабатывает
  только новые, не теряя поиск дубликатов.
- **Отчёт о качестве данных.** Отброшенные строки сохраняются в `rejected.csv` с причиной отказа,
  в статистику добавляется число строк по каждой причине.
- **Загрузка в SQLite.** Добавьте второй приёмник данных: таблицу SQLite с пакетной вставкой
  (`executemany`) и транзакцией в context manager. Сравните скорость с Parquet.
- **pandas.** Напишите вариант на `pandas.read_csv(chunksize=...)` и сравните время, память и объём кода
  с вариантом на чистом Python. К этому сравнению вернёмся в модуле 2.

## Типичные ошибки

| Симптом | Причина | Решение |
|---|---|---|
| `rows_duplicate` меньше, чем у baseline | дубликаты ищутся внутри файла или батча, а не по всем данным | одно множество `event_id` на весь запуск |
| Пайплайн падает с `ConnectionError` | сервис курсов иногда отвечает временной ошибкой, а запрос не повторяется | декоратор `retry` из урока 1.2.1 |
| Запросы к сервису по-прежнему занимают секунды | корутины ожидаются по одной в цикле | `asyncio.gather` или `TaskGroup` с семафором |
| Память растёт вместе с данными | очищенные строки копятся в списке до записи | пишите батчами через `ParquetWriter` |
| Тест сравнения с baseline падает на `amount_usd` | сумма округлена или курс взят не для дня события | не округляйте; день берите из `event_time` события |
| Пайплайн стал быстрым, но тесты падают | оптимизация изменила результат | запускайте тесты после каждой правки, а не в конце |
| С процессами стало медленнее | между процессами передаются большие списки строк | передавайте путь к файлу, возвращайте компактный результат |
