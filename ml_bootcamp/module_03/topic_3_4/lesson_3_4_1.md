## Зачем это нужно

Рекомендации — одна из немногих ML-задач, где эффект измеряется прямо в деньгах: блоки «с этим товаром
покупают» и «вам может понравиться» дают интернет-магазинам и стримингам заметную долю оборота. При этом
это задача, в которой проще всего обмануть себя:

- перемешали журнал событий перед разбиением — модель «предсказывает» прошлое, зная будущее;
- не сравнили с «самым популярным» — и не узнали, что сложная модель ему проигрывает;
- смотрели только на точность — и выкатили систему, которая всем показывает одни и те же 20 товаров.

Поэтому порядок урока необычный: сначала данные и оценка, потом базовые линии и только потом алгоритмы.

## 1. Задача и данные

## 2. Явный и неявный отклик

| | Явный (explicit) | Неявный (implicit) |
|---|---|---|
| Что это | оценка, лайк, отзыв | просмотр, покупка, время на странице |
| Сколько данных | мало: оценку ставит малая часть | много: логируется всё |
| Отрицательные примеры | есть: оценка 1–2 | нет |
| Шум | низкий | высокий: случайный клик, подарок другу |

Главное отличие — в трактовке пустых ячеек. В матрице неявного отклика пустая ячейка **не означает
«не нравится»**: пользователь мог просто не увидеть товар. Отрицательных примеров в таких данных нет вообще.
В уроках 3.4.1 и 3.4.3 работаем с неявным откликом, к оценкам вернёмся в уроке 3.4.2.

## 3. Матрица «пользователь × товар»

Из 6 миллионов ячеек заполнено около 1 %, поэтому матрицу храним в разреженном формате CSR (урок 2.1.2).
Идентификаторы в журнале — произвольные числа, а матрице нужны индексы строк и столбцов от нуля: заводим
два отображения и храним их рядом с матрицей.

```python
import numpy as np
import pandas as pd
import scipy.sparse as sp


def build_matrix(events, user_index, item_index, weights=None):
    weights = weights or {"view": 1.0, "purchase": 2.0}
    known = events["user_id"].isin(user_index.index) & events["item_id"].isin(item_index.index)
    ev = events[known]
    rows = user_index.loc[ev["user_id"]].to_numpy()
    cols = item_index.loc[ev["item_id"]].to_numpy()
    vals = ev["event"].map(weights).to_numpy(dtype=float)
    keep = vals > 0
    m = sp.csr_matrix((vals[keep], (rows[keep], cols[keep])), shape=(len(user_index), len(item_index)))
    m.sum_duplicates()  # повторные события пары складываются
    return m
```

Просмотр даёт в ячейке 1, просмотр с покупкой — 3; бинарная матрица — это `(m > 0).astype(float)`.

## 4. Как оценивать: сначала разбиение

Модель будет работать в будущем, значит и проверять её нужно на будущем: обучаемся на событиях до даты
разбиения, проверяем на событиях после. **Цель — покупки тестового периода.**

```python
def time_split(events, split, end=None):
    if end is not None:
        events = events[events["timestamp"] < end]
    return events[events["timestamp"] < split], events[events["timestamp"] >= split]


class Split:

    def __init__(self, shop, train_events, test_events, weights=None):
        self.shop, self.train_events, self.test_events = shop, train_events, test_events
        self.items = shop.items
        self.user_index = pd.Series(np.arange(len(shop.users)), index=shop.users["user_id"])
        self.item_index = pd.Series(np.arange(len(shop.items)), index=shop.items["item_id"])
        self.train = build_matrix(train_events, self.user_index, self.item_index, weights)
        # цель — покупки тестового периода
        self.test = build_matrix(test_events, self.user_index, self.item_index, {"view": 0.0, "purchase": 1.0})
        has_train = self.train.getnnz(axis=1) > 0
        has_test = self.test.getnnz(axis=1) > 0
        self.test_users = np.flatnonzero(has_train & has_test)  # «тёплые» пользователи с покупками в тесте
        self.cold_users = np.flatnonzero(~has_train & has_test)
        self.item_pop = self.train.getnnz(axis=0)  # число пользователей, взаимодействовавших с товаром

    def evaluate(self, scores, k=10, users=None):
        users = self.test_users if users is None else users
        recs = top_k(scores, self.train[users], k)
        return ranking_metrics(recs, self.test[users], self.item_pop)


data = Split(shop, *time_split(shop.events, pd.Timestamp("2025-06-01")))
```

Функции `top_k` и `ranking_metrics` — в следующем разделе. Что получилось после разбиения по 1 июня:

| | Обучение (январь–май) | Тест (июнь) |
|---|---|---|
| События | 78 681 | 23 281, из них 5 883 покупки |
| Пары «пользователь–товар» | 59 070 (заполненность 0.98 %) | — |
| Пользователи без истории в обучении | — | 299; на них приходится 4.5 % тестовых покупок |
| Товары без единого взаимодействия в обучении | — | 156; на них приходится 8.9 % тестовых покупок |

Качество считаем по 1 902 пользователям, у которых есть и история, и покупки в июне. Почти 9 % покупок
приходится на товары, о которых коллаборативная модель ничего не знает, — этот потолок алгоритмами урока
не пробить.

**Почему не случайное разбиение.** Если отложить в тест случайные 23 % пар, модель при обучении увидит
события из будущего: какие новинки появились, что стало популярным в июне, что этот же пользователь
покупал позже. Сравним три схемы на одних и тех же моделях (они описаны ниже):

| Схема разбиения | Тестовых пользователей | Recall@10: популярное | Recall@10: item-kNN | NDCG@10: item-kNN |
|---|---|---|---|---|
| По времени (правильная) | 1 902 | 0.070 | 0.158 | 0.118 |
| Случайные 23 % пар | 1 918 | 0.078 | 0.186 | 0.142 |
| Leave-last-out: последняя покупка каждого | 2 693 | 0.079 | 0.170 | 0.098 |

Случайное разбиение завышает recall item-kNN на 17 %, NDCG — на 20 %, причём для разных моделей
по-разному: по нему можно выбрать не ту модель. **Leave-last-out** (в тест уходит последнее взаимодействие
каждого пользователя) популярно в статьях и даёт больше тестовых пользователей, но утечка остаётся:
чья-то последняя покупка случилась в феврале, а модель обучена на июньских событиях остальных. Решения
о запуске принимайте по разбиению по единой дате.

## 5. Метрики ранжирования

Для пользователя $u$ модель выдаёт упорядоченный список из $k$ товаров; $rel_j = 1$, если товар на позиции
$j$ куплен в тесте; $R_u$ — множество всех купленных в тесте товаров.

| Метрика | Формула для одного пользователя | Смысл |
|---|---|---|
| Precision@k | $\frac{1}{k}\sum_{j=1}^{k} rel_j$ | доля удачных рекомендаций |
| Recall@k | $\frac{1}{\lvert R_u \rvert}\sum_{j=1}^{k} rel_j$ | доля покупок, которую угадали |
| Hit rate@k | $[\sum_j rel_j > 0]$ | есть ли хоть одно попадание |
| AP@k | $\frac{1}{\min(k, \lvert R_u \rvert)}\sum_{j=1}^{k} rel_j \cdot \text{Precision@}j$ | попадания вверху списка ценнее |
| NDCG@k | $\frac{DCG}{IDCG}$, где $DCG = \sum_{j=1}^{k} \frac{rel_j}{\log_2(j+1)}$ | то же, с плавным убыванием веса позиции |

Итоговое значение — среднее по пользователям (для AP оно называется MAP). Precision@k и recall@k знакомы
по уроку 3.2.1, но там был один общий список, а здесь — свой у каждого пользователя. Первые три метрики
не замечают порядка внутри списка, MAP и NDCG — замечают. IDCG — DCG списка, где все покупки стоят первыми.

**Ручной пример.** Рекомендации: A, B, C, D, E. Куплены: B, E, F. Попадания на позициях 2 и 5.

- Precision@5 = 2/5 = 0.4; Recall@5 = 2/3 = 0.667; Hit rate = 1;
- AP@5 = (1/2 + 2/5) / 3 = 0.3 — на позиции 2 точность 1/2, на позиции 5 — 2/5;
- DCG = 1/log₂3 + 1/log₂6 = 0.631 + 0.387 = 1.018; IDCG = 1 + 0.631 + 0.5 = 2.131; NDCG@5 = 0.478.

**Метрики помимо точности.** Модель, показывающая всем десять бестселлеров, может иметь приличную
точность и быть бесполезной: эти товары пользователь найдёт сам. Поэтому рядом с точностью смотрим:
**покрытие каталога** (coverage) — долю товаров, попавших в рекомендации хотя бы одному пользователю;
**новизну** (novelty) — среднее по рекомендациям $-\log_2$ доли товара во взаимодействиях обучения
(товар с 1 % взаимодействий даёт 6.6 бита, с 0.01 % — 13.3); **разнообразие** внутри списка (урок 3.4.3).

```python
def top_k(scores, seen, k):
    """Индексы k лучших товаров для каждой строки; уже виденные товары исключаются."""
    scores = np.array(scores, dtype=float)
    if seen is not None:
        scores[seen.nonzero()] = -np.inf
    part = np.argpartition(-scores, k - 1, axis=1)[:, :k]  # k лучших без полной сортировки
    order = np.argsort(-np.take_along_axis(scores, part, axis=1), axis=1, kind="stable")
    return np.take_along_axis(part, order, axis=1)


def ranking_metrics(recs, test, item_pop=None):
    k = recs.shape[1]
    rows = np.repeat(np.arange(recs.shape[0]), k)
    hits = np.asarray(test[rows, recs.ravel()]).reshape(recs.shape) > 0  # куплен ли товар на позиции j
    n_rel = test.getnnz(axis=1)
    discounts = 1 / np.log2(np.arange(2, k + 2))
    dcg = (hits * discounts).sum(axis=1)
    idcg = np.cumsum(discounts)[np.minimum(n_rel, k) - 1]
    prec_at_j = np.cumsum(hits, axis=1) / np.arange(1, k + 1)
    ap = (prec_at_j * hits).sum(axis=1) / np.minimum(n_rel, k)
    out = {
        "precision": hits.mean(),
        "recall": (hits.sum(axis=1) / n_rel).mean(),
        "hit_rate": hits.any(axis=1).mean(),
        "map": ap.mean(),
        "ndcg": (dcg / idcg).mean(),
        "coverage": len(np.unique(recs)) / test.shape[1],
    }
    if item_pop is not None:
        share = np.maximum(item_pop, 1) / item_pop.sum()
        out["novelty"] = (-np.log2(share[recs])).mean()
    return out
```

На ручном примере функция возвращает те же 0.4, 0.667, 1, 0.3 и 0.478. Во всех моделях ниже результат —
матрица оценок `scores` размера «тестовые пользователи × товары»; чем больше оценка, тем выше товар.

## 7. User-based kNN

Идея коллаборативной фильтрации: признаки товаров не нужны, достаточно поведения. **User-based:** найти
пользователей с похожей историей и рекомендовать то, с чем взаимодействовали они.

**Меры сходства** двух пользователей $u$ и $v$ ($r_u$ — строка матрицы, $I_u$ — множество товаров $u$):

| Мера | Формула | Когда применять |
|---|---|---|
| Косинус | $\frac{r_u \cdot r_v}{\lVert r_u \rVert \lVert r_v \rVert}$ | неявный отклик, веса |
| Жаккар | $\frac{\lvert I_u \cap I_v \rvert}{\lvert I_u \cup I_v \rvert}$ | бинарный неявный отклик |
| Пирсон (центрированный косинус) | косинус векторов $r_u - \bar r_u$ и $r_v - \bar r_v$ по общим товарам | явные оценки |

Для бинарных данных косинус равен $\lvert I_u \cap I_v \rvert / \sqrt{\lvert I_u \rvert \lvert I_v \rvert}$
— от Жаккара отличается только знаменателем. Центрирование нужно оценкам, потому что люди пользуются
шкалой по-разному. Пусть три пользователя оценили четыре фильма: `[5, 4, 5, 3]`, `[3, 2, 3, 1]`
и `[2, 4, 1, 5]`. Второй — строгая копия первого (всё на два балла ниже), вкус третьего противоположен.
Косинус первого со вторым — 0.987, с третьим — 0.783: «все довольно похожи». Пирсон даёт 1.0 и −0.953 —
то, что есть на самом деле.

**Предсказание.** Для неявного отклика оценка товара — сумма сходств тех соседей, кто с ним
взаимодействовал; для явных оценок — взвешенное среднее отклонений соседей от их собственных средних:

$$score(u, i) = \sum_{v \in N_k(u)} sim(u, v)\, r_{vi} \qquad\qquad
\hat r_{ui} = \bar r_u + \frac{\sum_{v \in N_k(u)} sim(u, v)\,(r_{vi} - \bar r_v)}{\sum_{v \in N_k(u)} \lvert sim(u, v) \rvert}$$

где $N_k(u)$ — $k$ самых похожих на $u$ пользователей.

**Реализация без циклов.** Если нормировать строки матрицы на их длину, все попарные косинусы — это одно
произведение разреженных матриц. Оценки всех товаров — второе произведение.

```python
def keep_top(sim, k):
    if k < sim.shape[1]:
        drop = np.argpartition(-sim, k, axis=1)[:, k:]
        np.put_along_axis(sim, drop, 0.0, axis=1)
    return sp.csr_matrix(sim)


def user_knn_scores(matrix, users, k_neighbors=50):
    x = (matrix > 0).astype(float)
    norm = np.sqrt(x.getnnz(axis=1))
    xn = sp.diags(1 / np.maximum(norm, 1)) @ x
    sim = (xn[users] @ xn.T).toarray()  # косинус между тестовыми и всеми пользователями
    sim[np.arange(len(users)), users] = 0  # сам себе не сосед
    return keep_top(sim, k_neighbors) @ x


user_scores = user_knn_scores(data.train, users, k_neighbors=50).toarray()
data.evaluate(user_scores)["recall"]  # 0.1691
```

Расчёт для 1 902 пользователей занимает 0.2 секунды; цикл Python по 5.7 миллиона пар шёл бы минуты.

## 8. Item-based kNN

**Item-based:** считаем сходство не пользователей, а товаров — два товара похожи, если с ними
взаимодействовали одни и те же люди. Пользователю рекомендуем товары, похожие на те, что есть в его
истории:

$$score(u, j) = \sum_{i \in I_u} r_{ui}\, sim(i, j)$$

```python
def item_similarity(matrix, kind="cosine", k_neighbors=50, shrink=0.0, alpha=0.5):
    x = (matrix > 0).astype(float)
    co = (x.T @ x).toarray()  # co[i, j] — сколько пользователей взаимодействовали и с i, и с j
    n = co.diagonal().copy()  # n[i] — число пользователей товара i
    if kind == "jaccard":
        denom = n[:, None] + n[None, :] - co
    else:  # alpha = 0.5 — косинус; alpha = 1 — условная вероятность P(j | i)
        denom = n[:, None] ** alpha * n[None, :] ** (1 - alpha)
    sim = np.divide(co, denom, out=np.zeros_like(co), where=denom > 0)
    if shrink:
        sim *= co / (co + shrink)
    np.fill_diagonal(sim, 0)
    return keep_top(sim, k_neighbors)


S = item_similarity(data.train, k_neighbors=50)  # разреженная матрица товар × товар
item_scores = (X[users] @ S).toarray()
data.evaluate(item_scores)["recall"]  # 0.1583
```

**Число соседей.** Recall@10 в зависимости от $k$ (число соседей «все» — без отсечения):

| Соседей | 5 | 10 | 20 | 50 | 100 | 200 | все |
|---|---|---|---|---|---|---|---|
| User-kNN | 0.073 | 0.105 | 0.138 | 0.169 | **0.181** | 0.180 | 0.133 |
| Item-kNN | 0.123 | 0.143 | **0.165** | 0.158 | 0.154 | 0.147 | 0.157 |

Мало соседей — оценка шумная, много — в сумму попадают слабо похожие, и она сползает к популярности.
User-kNN нужно больше соседей: у каждого в истории около 14 товаров. Таблица посчитана на тесте только
для иллюстрации; выбирать $k$ по тесту нельзя — в уроке 3.4.2 заведём отдельный проверочный период.

**Какой сигнал использовать.** Цель — покупки, а в матрице ещё и просмотры. Три варианта (item-kNN,
косинус, 50 соседей):

| Сходство считаем по | Профиль пользователя | Recall@10 | NDCG@10 | Покрытие |
|---|---|---|---|---|
| всем взаимодействиям | все взаимодействия, вес 1 | 0.158 | 0.118 | 36 % |
| всем взаимодействиям | просмотр 1, покупка 3 | **0.165** | **0.126** | 42 % |
| только покупкам | только покупки | 0.100 | 0.074 | 67 % |

Выбросить просмотры — потерять треть качества: покупок втрое меньше, и сходство по ним слишком шумное.
Массовый слабый сигнал лучше редкого сильного, а силу сигнала полезно учесть весом в профиле.

**Нормализация на популярность.** Бестселлер встречается вместе с чем угодно. Параметр `alpha` управляет
штрафом: при $\alpha = 1$ сходство — это условная вероятность $P(j \mid i) = co_{ij} / n_i$ без штрафа
за популярность кандидата $j$; при $\alpha = 0.5$ — косинус; при меньших $\alpha$ популярные кандидаты
штрафуются сильнее.

| $\alpha$ | 0.3 | 0.4 | 0.5 | 0.6 | 0.7 | 1.0 |
|---|---|---|---|---|---|---|
| Recall@10 | 0.048 | 0.134 | **0.158** | 0.154 | 0.140 | 0.115 |
| Покрытие | 44 % | 47 % | 36 % | 23 % | 16 % | 8 % |

Без штрафа модель вырождается в «популярное» (покрытие 8 %), при слишком сильном — рекомендует редкие
товары, которые никто не покупает. Это ручка «точность ↔ длинный хвост», и положение 0.4 — пример
осознанного обмена: минус 16 % recall за плюс 10 пунктов покрытия.

**Сглаживание (shrinkage).** Два товара, которые видел один и тот же единственный пользователь, имеют
косинус 1.0 — максимум по одному совпадению. Поправка умножает сходство на $co_{ij} / (co_{ij} + \lambda)$
и прижимает к нулю сходства, посчитанные по малому числу общих пользователей. На наших данных она почти
не меняет точность (recall 0.158 без поправки; 0.161, 0.157 и 0.153 при $\lambda$ = 2, 5 и 20), а покрытие
снижает с 36 % до 20, 17 и 13 %: редкие товары перестают попадать в соседи. На матрицах явных оценок,
где сходство считают по нескольким общим оценкам, эффект обычно заметнее — проверяйте на своих данных.

**Почему item-based практичнее.** На наших данных user-kNN точнее (0.181 против 0.165 при лучших $k$) —
распространённое «item-based точнее» не подтвердилось. В промышленности item-based выбирают по инженерным
причинам: сходство товаров **стабильно** и пересчитывается раз в сутки, а профиль пользователя меняется
с каждым кликом; рекомендации — сумма нескольких строк **предрасчитанной** матрицы, поэтому новый
пользователь получает их после первого же просмотра; пользователей обычно на порядки больше, чем
товаров; результат **объясним** («с этим товаром покупают»), а матрица сходства — готовый блок «похожие
товары» для карточки товара.

## 10. Проблемы коллаборативной фильтрации

**Холодный старт.** У 156 товаров нет взаимодействий в обучении — их столбцы в матрице сходства нулевые,
и они никогда не будут рекомендованы, хотя на них приходится 8.9 % покупок теста. У 299 пользователей нет
истории — им можно показать только «популярное». Решения — признаки товаров (урок 3.4.3) и быстрый
пересчёт для новых пользователей (урок 3.4.2).

**Разреженность.** У пользователей с историей в 1–5 товаров recall@10 item-kNN — 0.138, у остальных —
0.160–0.162; «популярное», наоборот, лучше всего работает на новичках (0.108 против 0.060–0.069).
Выигрыш персонализации для коротких историй — 1.3–1.6 раза вместо 2.7–2.9 у активных пользователей.

**Смещение к популярному.** На 10 % самых популярных товаров приходится 42 % тестовых покупок, но 91 %
рекомендаций item-kNN и 94 % рекомендаций user-kNN. Модель усиливает перекос, который уже есть в данных;
в работающей системе её рекомендации попадают в журнал, на нём обучается следующая версия, и перекос
растёт с каждым кругом. Противодействие — нормализация на популярность, контроль покрытия и новизны,
доля случайных показов для сбора несмещённых данных.

**Масштабируемость.** Попарное сходство — это $O(n^2)$ памяти и времени: уже наша плотная матрица
совместных встреч 2 000 × 2 000 занимает 32 МБ. Для миллионов объектов считают разреженные произведения
с отсечением соседей, ищут соседей приближённо (тема 9.4) или переходят к скрытым факторам (урок 3.4.2).

## Типичные ошибки

| Симптом | Причина | Решение |
|---|---|---|
| Офлайн-метрики отличные, после запуска эффекта нет | случайное разбиение: утечка из будущего | разбиение по дате |
| Recall@10 выше 0.9 | в рекомендации попадают товары из истории или тест пересекается с обучением | исключать виденное; проверить разбиение |
| Модель «лучше случайной в 30 раз», а бизнес-эффекта нет | не было сравнения с «популярным» | базовые линии в каждой таблице результатов |
| Все пользователи получают почти одинаковые списки | нет нормализации на популярность, слишком много соседей | косинус вместо числа совпадений, меньше $k$, смотреть покрытие |
| `IndexError` или рекомендации «не тех» товаров | перепутаны идентификаторы и индексы матрицы | единые отображения id ↔ индекс, обратное преобразование на выходе |
