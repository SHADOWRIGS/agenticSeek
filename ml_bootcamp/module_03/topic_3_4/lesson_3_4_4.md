# Урок 3.4.4: ПРАКТИКА: Построение рекомендательной системы для e-commerce

> **Модуль 3:** Classical ML: Algorithms & Production Thinking · **Тема 3.4:** Рекомендательные системы
> **Тип:** практика · **Время:** 6–7 часов

## Задача

Интернет-магазин запускает на главной странице блок «Вам может понравиться»: десять товаров для каждого
посетителя. Руководитель продукта ставит три вопроса:

1. Что показывать пользователю с историей, чтобы он чаще находил то, что купит?
2. Что показывать человеку, который пришёл впервые или посмотрел один-два товара?
3. Как сделать, чтобы в блок попадали новинки, у которых ещё нет ни одного просмотра?

Первый вопрос — про качество модели, второй и третий — про холодный старт, и на практике именно они
отнимают больше всего времени. Блок, который отлично работает для постоянных покупателей и показывает
пустоту или случайные товары новичкам, запускать нельзя: новички — это и есть главная страница.

Результат работы — модуль с рекомендательными моделями (проверяется автотестами), ноутбук с выбором
модели и анализом холодного старта и записка для руководителя на одну страницу.

## Требования к системе

- **Цель** — покупки. Обучение — на событиях до 1 июня 2025 года, проверка — на покупках июня.
  Случайное разбиение журнала запрещено (урок 3.4.1, раздел 4).
- **Сигнал** — просмотры и покупки: в матрице 1 для просмотра и 3 для покупки.
- **Выдача** — ровно десять разных товаров, которых пользователь ещё не видел.
- **Новый пользователь** получает осмысленную выдачу, а не ошибку и не пустой список.
- **Идентификаторы**: модели работают с индексами строк и столбцов матрицы, сайт — с идентификаторами
  магазина. Перевод в обе стороны — часть системы, и это самое частое место ошибок.
- **Скорость**: обучение и расчёт выдачи для всех пользователей — секунды. Циклы Python по парам
  «пользователь–товар» и «товар–товар» недопустимы.

## Часть 1. Модуль рекомендаций

Реализуйте функции и классы в `recsys.py`. Точное поведение — в docstring.

| Что | Назначение | Материал |
|---|---|---|
| `time_split` | разбиение журнала по дате | урок 3.4.1, раздел 4 |
| `build_interaction_matrix` | разреженная матрица и отображения индекс → идентификатор | урок 3.4.1, раздел 3 |
| `precision_at_k`, `recall_at_k`, `ndcg_at_k` | метрики одного списка рекомендаций | урок 3.4.1, раздел 5 |
| `catalog_coverage` | покрытие каталога | урок 3.4.1, раздел 5 |
| `PopularRecommender` | базовая линия и запасной вариант для холодных пользователей | урок 3.4.1, раздел 6 |
| `ItemKNNRecommender` | item-based kNN с косинусным сходством | урок 3.4.1, раздел 8 |
| `ALSRecommender` | ALS для неявного отклика | урок 3.4.2, раздел 5 |
| `recommend_ids` | выдача в идентификаторах магазина, в том числе для нового пользователя | — |

Из двух персональных моделей обязательна **одна**, на ваш выбор; тесты второй будут пропущены. У всех
моделей общий интерфейс: `fit(matrix)` возвращает модель, `recommend(user_index, k, exclude_seen=True)` —
массив из `k` индексов товаров. Вызов с `user_index=None` означает неизвестного пользователя.

```bash
uv add pandas numpy scipy
uv add --dev pytest
cd projects/p_3_4_recsys/practice
uv run pytest -q                       # сначала падают все тесты
uv run pytest -q -k TestMetrics        # работайте над одной частью за раз
```

Пошаговый план:

1. **`time_split` и `build_interaction_matrix`.** Обратите внимание на отличия от кода урока: значение
   ячейки — наибольший вес среди событий пары, а не сумма; функция умеет строить матрицу в заданной
   индексации — так тестовая матрица получает те же строки и столбцы, что и обучающая.
2. **Метрики.** Здесь они считаются для одного пользователя и принимают обычные списки и множества.
   Проверьте граничные случаи из тестов: пустое множество релевантных товаров, список короче `k`.
3. **`PopularRecommender`.** Популярность — число пользователей, а не сумма весов. Продумайте порядок
   при равной популярности: он должен быть одинаковым при каждом запуске.
4. **Персональная модель.** Сходство или факторы считаются один раз в `fit`; `recommend` должен работать
   за доли миллисекунды. Запасной вариант для пустой истории — `PopularRecommender`, обученный внутри
   `fit` на той же матрице.
5. **`recommend_ids`.** Последний шаг перед сайтом: идентификатор пользователя → индекс → рекомендации →
   идентификаторы товаров.

Советы:

- в `ItemKNNRecommender` при равных оценках выше ставится более популярный товар. Это не мелочь: у товаров
  без общих пользователей с историей оценка нулевая, и без этого правила хвост списка заполнится
  товарами с наименьшими индексами;
- сортировку по двум ключам даёт `np.lexsort`; полная сортировка 2 000 оценок занимает десятки
  микросекунд, оптимизировать её не нужно;
- в `ALSRecommender` проверьте себя на маленькой матрице: значение функции потерь не должно расти
  ни на одном полушаге (урок 3.4.2, раздел 6);
- строку разреженной матрицы без копирования дают `matrix.indices[matrix.indptr[u]:matrix.indptr[u + 1]]`
  и такой же срез `matrix.data`.

## Часть 2. Выбор модели и холодный старт

В ноутбуке `analysis.ipynb` используйте свои функции из `recsys.py`, а не их копии.

**Выбор модели**

1. Постройте обучающую матрицу и матрицу покупок июня в общей индексации. Сколько пользователей
   участвует в оценке? Какая доля июньских покупок приходится на пользователей и на товары, которых нет
   в обучении?
2. Посчитайте precision@10, recall@10, NDCG@10 и покрытие для `PopularRecommender` и своей персональной
   модели. Добавьте базовую линию «популярное в любимых категориях пользователя».
3. Заведите проверочный период (май) и подберите на нём гиперпараметры персональной модели: число
   соседей либо число факторов, регуляризацию и уверенность. Июнь используйте один раз.
4. Сравните три варианта сигнала: только покупки, просмотры и покупки с весом 1, веса 1 и 3.
5. Постройте 95 % доверительные интервалы recall@10 бутстрепом по пользователям для лучшей модели
   и лучшей базовой линии. Значима ли разница?

**Новые пользователи**

6. Разбейте пользователей по длине истории (1–3, 4–10, 11–30, больше 30 взаимодействий) и сравните
   recall@10 персональной модели и «популярного» в каждой группе.
7. Смоделируйте новичка: для пользователей, зарегистрировавшихся в июне, возьмите первые $m$ событий
   как историю и предскажите остальные покупки при $m$ = 1, 3, 5. Для item-kNN достаточно сложить строки
   матрицы сходства, для ALS — сделать fold-in (урок 3.4.2, раздел 8). Начиная с какой длины истории
   персональная модель обгоняет «популярное»? Сформулируйте правило переключения.

**Новые товары**

8. Покажите, что ваша персональная модель не рекомендует ни одного товара без истории, и объясните
   почему.
9. Постройте content-based ранжирование новинок по тексту описания (урок 3.4.3, разделы 1–4) и оцените
   полку «Новинки для вас»: recall@10 по покупкам холодных товаров против случайного порядка.
10. Реализуйте квоту: одна из десяти позиций блока отдаётся лучшей новинке. Сколько общей точности
    это стоит и какая доля покупок новинок оказывается угаданной?

**Выдача**

11. Измерьте, сколько разных категорий в среднем в выдаче и в истории пользователя. Примените MMR
    или ограничение «не более трёх товаров одной категории» и покажите цену в recall.
12. Соберите итоговую функцию `recommend_for_site(user_id)`: правило для новичка, персональная модель,
    квота для новинки, разнообразие. Оцените её на июне целиком — включая пользователей без истории.

## Часть 3. Записка для руководителя

Файл `REPORT.md`, одна страница. Читатель не знает, что такое матричная факторизация.

1. **Что предлагается показывать** — тремя предложениями: постоянным покупателям, новичкам, как
   в блок попадают новинки.
2. **Чего ожидать.** В понятных единицах: «в блоке из десяти товаров у N % пользователей есть хотя бы
   один товар, который они купят в течение месяца; у блока с бестселлерами — у M %».
3. **Чего это стоит.** Как часто пересчитывать модель, что происходит с новым товаром в первый день.
4. **Чего мы не знаем.** Офлайн-оценка показывает, угадываем ли мы покупки, но не показывает, вызываем
   ли новые. Предложите A/B-тест: группы, целевая метрика, защитные метрики (урок 3.4.3, раздел 9).

| Уровень | Признаки |
|---|---|
| Базовый | тесты проходят с одной персональной моделью, ответы на вопросы 1–8 |
| Уверенный | ответы на все 12 вопросов, итоговая функция с правилами для новичков и новинок, записка понятна без пояснений |
| Продвинутый | реализованы обе модели и выполнено одно из заданий раздела «Идеи для усложнения» |

Для самопроверки — результаты эталонного решения. Протокол: обучающая матрица 2 701 × 1 844 с 59 070
заполненными ячейками; оценка по 1 846 пользователям, у которых есть покупки июня среди товаров
обучающей матрицы (5 117 покупок); $k = 10$.

| Модель | Precision | Recall | NDCG | Покрытие | Обучение, с |
|---|---|---|---|---|---|
| `PopularRecommender` | 0.019 | 0.075 | 0.049 | 1.3 % | — |
| `ItemKNNRecommender()` — 50 соседей | 0.052 | 0.180 | 0.135 | 45 % | 0.2 |
| `ItemKNNRecommender(100)` | 0.052 | 0.183 | 0.137 | 40 % | 0.2 |
| `ALSRecommender()` — 8 факторов, λ = 100, α = 10 | 0.064 | 0.223 | 0.177 | 15 % | 1.0 |
| `ALSRecommender(16, 30.0)` | 0.060 | 0.214 | 0.161 | 27 % | 1.2 |

Расчёт выдачи для всех 1 846 пользователей занимает 0.1–0.5 секунды. Числа немного выше, чем в уроках
3.4.1–3.4.3: там в знаменателе recall стояли и покупки товаров без истории (8.9 % покупок), которые
коллаборативная модель угадать не может, а здесь таких товаров в матрице нет. Это хороший пример того,
как протокол оценки меняет метрику при той же модели: в ноутбуке (вопросы 1 и 12) посчитайте оба варианта.

Ориентиры по части 2 из уроков темы: «популярное в категории» — recall около 0.12; полка новинок —
recall 0.46 у content-based ранжирования против 0.06 у случайного порядка; квота в одну позицию стоит
около 3 % общего recall; для новичка с одним просмотром «популярное» лучше персональной модели.

## Идеи для усложнения

1. **Вторая модель и смесь.** Реализуйте обе персональные модели и смешайте их оценки (урок 3.4.3,

   и content-based?
2. **Переранжирование.** Постройте каскад: кандидаты от ваших моделей, признаки пары, логистическая

3. **Свежесть.** Модель обучена 1 июня, а оценивается весь июнь. Разбейте июнь на недели и постройте
   recall@10 по неделям. Затем переобучайте модель каждую неделю на всех доступных к этому моменту
   событиях. Сколько качества даёт регулярное переобучение?
4. **Масштаб.** Сгенерируйте магазин `make_shop(n_users=30000, n_items=10000)`. Какие части вашего кода
   перестали помещаться в память или стали слишком медленными? Перепишите сходство товаров без плотной
   матрицы «товар × товар».
5. **Похожие товары.** Сделайте второй блок — «с этим товаром покупают» на карточке товара: по матрице
   сходства или по факторам. Как его оценить офлайн?
