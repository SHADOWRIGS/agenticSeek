# Урок 3.1.4: ПРАКТИКА: Предсказание оттока клиентов с интерпретацией

> **Модуль 3:** Classical ML: Algorithms & Production Thinking · **Тема 3.1:** Линейные модели в глубину
> **Тип:** практика · **Время:** 5–6 часов

## Задача

Интернет-провайдер теряет клиентов. Руководитель отдела удержания просит вас ответить на три вопроса:

1. Какие клиенты уходят чаще и насколько?
2. Кого из нынешних клиентов нужно удерживать в первую очередь?
3. Что компании стоит изменить, чтобы отток снизился?

Первые два вопроса — про связи в данных и предсказание; на них модель отвечает хорошо. Третий — про
причины и вмешательства, и здесь главный навык практики — честно обозначить границу между тем, что данные
показывают, и тем, чего они показать не могут.

Результат работы — модуль с функциями анализа (проверяется автотестами) и отчёт для руководителя на одной-двух
страницах (проверяется по критериям). Отчёт важнее кода: модель, результаты которой никто не понял или
понял неправильно, бесполезна.

## Часть 1. Модуль анализа

Реализуйте функции в `churn_report.py`. Точное поведение — в docstring каждой функции.

| Функция | Что делает | Материал |
|---|---|---|
| `prepare_features` | превращает исходную таблицу в числовые признаки | урок 3.1.3, раздел 1 |
| `fit_logit` | обучает логистическую регрессию без регуляризации | урок 3.1.3, раздел 3 |
| `odds_ratio_table` | коэффициенты, отношения шансов с интервалами, p-value | урок 3.1.3, раздел 4 |
| `average_marginal_effects` | средний эффект признака в единицах вероятности | урок 3.1.3, раздел 4 |
| `predict_scenarios` | вероятность ухода для описанных клиентов | урок 3.1.3, раздел 4 |
| `bootstrap_coef_intervals` | интервалы коэффициентов бутстрепом | урок 3.1.2, раздел 7 |
| `evaluate` | качество на отложенных данных кросс-валидацией | урок 3.1.1, раздел 8 |

```bash
uv add statsmodels scikit-learn
uv add --dev pytest
cd projects/p_3_1_churn/practice
uv run pytest -q                         # сначала падают все тесты
uv run pytest -q -k TestOddsRatioTable   # работайте над одной функцией за раз
```

Советы:

- в `odds_ratio_table` интервал нужен для отношения шансов, а не для коэффициента: сначала интервал
  коэффициента, затем экспонента от его границ;
- в `average_marginal_effects` бинарные признаки и непрерывные считаются по-разному — прочитайте docstring
  и тест `test_binary_feature_is_difference_of_probabilities`;
- в `bootstrap_coef_intervals` модель обучается сотни раз. Метод Ньютона в statsmodels справляется
  с каждым обучением за миллисекунды; оптимизатор scikit-learn на немасштабированных признаках будет
  работать минуты;
- метрики ROC-AUC и log loss подробно разбираются в теме 3.2. Здесь достаточно знать: ROC-AUC 0.5 —
  случайное угадывание, 1.0 — идеальное упорядочивание клиентов по риску; log loss — чем меньше, тем лучше,
  и он должен быть меньше, чем у предсказания одной и той же вероятности для всех.

**Вопросы руководителя**

9. Проверьте, не упускает ли модель нелинейность: добавьте логарифм стажа и взаимодействие контракта

**Проверка на прочность**

Пункт 10 — главный. В реальной работе скрытый признак останется скрытым, и ошибку вы не увидите.

## Часть 3. Отчёт для руководителя

Файл `REPORT.md`, одна-две страницы. Читатель не знает, что такое логарифм шансов.

Структура:

1. **Главное в трёх предложениях.**
2. **Кто уходит чаще.** Три-пять факторов с размером эффекта в понятных единицах («на 26 процентных пунктов
   реже», а не «коэффициент −1.45») и с указанием неопределённости.
3. **Кого удерживать.** Что даёт ранжирование по риску: сколько ушедших покрывают 10 % и 20 % клиентов
   с наибольшим риском.
4. **Что можно рекомендовать, а что нужно проверить.** Отдельно — выводы, которые следуют из данных,
   и гипотезы о причинах, требующие эксперимента. Для каждой гипотезы — как её проверить.
5. **Ограничения.** Чего модель не знает и где может ошибаться.

Правила формулировок:

| Нельзя | Можно |
|---|---|
| «Автоплатёж снижает отток вдвое» | «Клиенты с автоплатежом уходят реже; является ли автоплатёж причиной, покажет только эксперимент» |
| «Шансы ухода ниже в 4.3 раза» | «Среди клиентов с годовым контрактом уходит 17 %, с помесячным — 48 %; при прочих равных разница — около 26 процентных пунктов» |
| «Признак незначим, он не влияет» | «На наших данных связь не обнаружена; возможно, для этого недостаточно данных» |
| «Модель предсказывает уход с точностью 77 %» | «В 20 % клиентов с наибольшим риском оказывается такая-то доля всех ушедших» |

## Критерии приёмки

- [ ] `uv run pytest -q` — все 24 теста проходят, прогон занимает меньше минуты;
- [ ] `uv run ruff check .` проходит без ошибок;
- [ ] ноутбук выполняется целиком и использует функции из `churn_report.py`, а не их копии;
- [ ] на каждый из 10 вопросов есть таблица или график и письменный вывод;
- [ ] ROC-AUC на отложенных данных лежит в диапазоне 0.75–0.80;
- [ ] в отчёте нет ни одного термина из списка: логит, шансы, коэффициент, p-value, регрессия;
- [ ] в отчёте эффекты выражены в процентных пунктах или долях клиентов и для каждого указана
      неопределённость;
- [ ] в отчёте выводы о связях отделены от гипотез о причинах, и для каждой гипотезы предложена проверка;
- [ ] в ноутбуке есть раздел по вопросу 10 с ответом, какие рекомендации изменились бы.

| Уровень | Признаки |

| Продвинутый | в пункте 10 количественно показано, насколько ошиблась бы оценка эффекта кампании по подключению автоплатежа; выполнено задание из раздела ниже |

Для самопроверки:

- ROC-AUC на отложенных данных — около 0.77; в 20 % клиентов с наибольшим риском попадает около 40 % всех
  ушедших — вдвое больше, чем при случайном выборе;
- коэффициент при автоплатеже на наблюдаемых данных — около −0.7, со скрытым признаком — около −0.2.
  Ожидаемый эффект кампании, рассчитанный по первой цифре, завышен более чем втрое;
- число услуг на наблюдаемых данных значимо (p около 0.03), хотя в генераторе на отток оно не влияет:
  со скрытым признаком его коэффициент равен нулю. Значимость создана пропущенной переменной.

## Идеи для усложнения

1. **Эксперимент.** Опишите A/B-тест, который проверил бы гипотезу об автоплатеже: кого включать, что
   измерять, как долго. Оцените нужный размер групп, чтобы обнаружить эффект из генератора с мощностью 80 %
   (симуляцией: генерируйте данные с включённым и выключенным эффектом).
2. **Регуляризованная модель.** Добавьте one-hot признаки тарифа и все парные взаимодействия. Сравните
   модель без регуляризации, Ridge и Lasso по качеству на отложенных данных. Какие взаимодействия оставил
   Lasso?
3. **Обращения в поддержку.** Постройте пуассоновскую модель числа обращений (урок 3.1.3). Какие клиенты
   создают наибольшую нагрузку на поддержку? Связана ли она с оттоком?
4. **Экономика удержания.** Пусть удержание клиента стоит 500 рублей, срабатывает в 30 % случаев, а клиент
   приносит 12 абонентских плат в год. Скольким клиентам выгодно делать предложение? Это мостик
   к практике 3.2.4.
