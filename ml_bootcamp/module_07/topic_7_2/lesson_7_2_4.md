# Урок 7.2.4: ПРАКТИКА: Настройка системы трекинга экспериментов

> **Модуль 7:** ML Engineering & MLOps · **Тема 7.2:** Версионирование и эксперименты
> **Тип:** практика · **Время:** 6–8 часов

## Задача

Пайплайн из практики 7.1.4 умеет обучить модель за дату и положить рядом `metadata.json`. Этого хватает,
пока запуск один. Теперь запусков будут десятки — с разными параметрами, окнами, версиями кода, — и к ним
предъявляется одно требование:

> **Любое число в отчёте восстанавливается по идентификатору запуска:** каким кодом, на каких данных,
> с какими параметрами и в каком окружении оно получено — и какой командой получить его снова.

Вы пишете тонкий слой поверх MLflow — модуль `tracking.py` из восьми функций — и подключаете его
к своему пайплайну:

```bash
uv run python run_tracked.py --date 2024-06-30 --alpha 1.0
```

Команда выполняет пайплайн, записывает запуск со всеми обязательными сведениями, регистрирует модель
и переносит псевдоним `champion`, только если новая модель достаточно лучше текущей. Отдельной командой
строится таблица сравнения запусков, а для любого запуска — текст команд, которые его воспроизводят.

Зачем свой слой, если есть `mlflow.log_param`? Затем, что правила из уроков 7.2.2 и 7.2.3 —
обязательные теги, запрет на регистрацию «грязных» запусков, секреты вне журнала, порог продвижения —
работают, только когда их нельзя забыть. Функция, которая не создаст запуск без хеша данных, надёжнее
договорённости «всегда записывать хеш данных».

## Пошаговый план

Точные требования — в docstring заготовки. Порядок выбран так, чтобы каждый шаг проверялся отдельно;
начиная с шага 4 тесты создают запуски **вашими** функциями из шагов 2 и 3.

### Шаг 1. `collect_run_metadata`

Словарь строк: коммит, признак «грязного» дерева, хеш данных, версия Python, seed, команда запуска, версии
библиотек. Команды Git — через `subprocess.run(["git", "-C", каталог, ...])`: `rev-parse HEAD`
и `status --porcelain` (урок 7.2.2).

Подводные камни:

- вне репозитория `git` завершается с ненулевым кодом — это не ошибка функции, а результат:
  `"git_commit": "unknown"`, `"git_dirty": "true"`. Не используйте `check=True`;
- `status --porcelain` сам учитывает `.gitignore` и показывает неотслеживаемые файлы — дополнительных
  флагов не нужно;
- хеш данных: каталог раскрывается рекурсивно, файлы сортируются по строке пути **все вместе**,
  а не внутри каждого элемента `data_paths` — иначе результат зависит от порядка аргументов;
- все значения — строки: теги MLflow другими не бывают, и `"false"` удобнее сравнивать, чем `False`.

```bash
uv run pytest -q -k test_metadata
```

### Шаг 2. `start_run`

Контекстный менеджер поверх `mlflow.start_run`. Проверка обязательных ключей — **до** создания запуска:
тест убеждается, что после отказа в эксперименте нет ни одного запуска. Исключения не перехватывайте:
`with mlflow.start_run()` сам пометит запуск как `FAILED`.

Здесь же впервые понадобится маскирование секретов (правило — в описании модуля). Удобно сразу написать
вспомогательную функцию «словарь → словарь без секретов»: она нужна и тегам, и параметрам.

### Шаг 3. `log_training_result`

Самая объёмная функция: параметры, метрики, модель, окружение.

- Вложенный конфиг разворачивается в плоские ключи через точку — рекурсией. Маскирование применяется
  **после** разворачивания: ключ `db.password` секретный, хотя ключ `db` — нет.
- Тот же плоский словарь сохраняется артефактом `config/params.json`. Параметры MLflow — строки,
  а в артефакте типы сохраняются; через полгода это единственный способ отличить `"1"` от `1`.
- Метрика по фолдам — одно имя, шаг равен номеру фолда; итоговые `_mean` и `_std` — отдельные метрики.
  По ним ищут лучший запуск и принимают решение о продвижении.
- Модель: `mlflow.sklearn.log_model(..., name=MODEL_NAME, signature=..., input_example=...,
  pip_requirements=[...])`. Явный список зависимостей — не формальность: без него MLflow определяет
  зависимости сам, и запись модели занимает секунды вместо долей секунды.
- Секретные значения берутся из `os.environ` **в момент вызова**: тест задаёт переменную окружения
  через `monkeypatch`. Значение короче четырёх символов секретом не считается — иначе переменная
  `DEBUG_TOKEN=1` замаскировала бы половину параметров.

```bash
uv run pytest -q -k "test_log or test_secrets"
```

### Шаг 4. `find_best_run`

`mlflow.search_runs(..., output_format="list")` возвращает объекты запусков — с ними проще, чем
с таблицей. Условие статуса и фильтры — в строке запроса; выбор лучшего — в Python.

- Имена тегов с точкой (`version.numpy`) в запросе берутся в обратные кавычки:
  ``tags.`version.numpy` = '2.0.0'``.
- MLflow не знает направления метрики: `"min"` и `"max"` — ваша ответственность. Запусков без этой
  метрики в кандидатах быть не должно.
- Несуществующий эксперимент — `None`, а не исключение: `mlflow.get_experiment_by_name` возвращает `None`.

### Шаг 5. `register_and_promote`

Правило публикации из практики 7.1.4, перенесённое в реестр. Порядок действий:

1. проверки аргументов и запуска — до любого изменения реестра;
2. версия: если запуск уже зарегистрирован (`run_id` версии совпадает) — взять её, иначе
   `mlflow.register_model("runs:/<run_id>/model", name)` и теги версии;
3. псевдоним: текущий обладатель — `client.get_model_version_by_alias`; если его нет, MLflow бросает
   `MlflowException` — это случай «первая версия».

Метрика «чемпиона» читается из тега его версии. Равная метрика — не улучшение: псевдоним остаётся.
Версии не удаляются никогда: откат — это перенос псевдонима назад, а переносить его можно только на то,
что существует.

```bash
uv run pytest -q -k "version or champion or alias or improvement or registration or promotion or register"
```

### Шаг 6. `load_champion`, `reproduce_command`, `compare_runs`

Три короткие функции. `load_champion` превращает исключение MLflow в `LookupError`: вызывающему коду
незачем знать, какой трекер под капотом. `reproduce_command` отказывается строить команду для запуска
с `git_dirty == "true"` — лучше честный отказ, чем команда, дающая другой результат. `compare_runs` —
таблица для отчёта; столбцы и порядок строк заданы в docstring.

```bash
uv run python -W error -m pytest -q
```

### Шаг 7. Подключение к пайплайну практики 7.1.4

Напишите `run_tracked.py`: он вызывает `run(...)` из вашего `ml_pipeline.py`, затем записывает результат.

```python
result = run(args.date, args.workdir, sales_source, config)

train_days, valid_days = window_days(args.date, config)
partitions = [partition_path(args.workdir / "data", day) for day in train_days + valid_days]
metadata = collect_run_metadata(".", partitions, seed=0, command=command)

model = joblib.load(result["run_dir"] / "model.joblib")
example = pd.read_csv(partitions[-1])[FEATURES].astype({"price": float})
with start_run("sales-pipeline", name, metadata, {"stage": "candidate", "run_date": str(args.date)}) as active:
    log_training_result(
        model,
        example,
        {"run_date": str(args.date), **config},
        {"valid_mae": [metrics["mae"]], "valid_mae_ratio": [metrics["mae_ratio"]]},
        environment_files=["uv.lock"],
        serialization_format="cloudpickle",
    )
outcome = register_and_promote(active.info.run_id, "sales-forecast", "valid_mae_ratio_mean", min_improvement=0.01)
```

На что обратить внимание:

- в хеш данных входят партиции **окон этого запуска**, а не весь каталог `data/`: иначе хеш зависел бы
  от того, какие даты считались раньше;
- `command` — строка, которой запуск можно повторить, со всеми аргументами;
- в пайплайне собственные трансформеры (`DateFeatures`, `RareCategoryGrouper`), и формат skops отказывается
  их записывать — отсюда `serialization_format="cloudpickle"` (урок 7.2.2). Модуль `ml_pipeline` должен
  импортироваться там, где модель загружают;
- проверочное окно одно, поэтому «фолдов» — один. Задание на усложнение — заменить его настоящей
  кросс-валидацией по времени;
- `work/`, `mlruns/`, `mlflow.db` — в `.gitignore`, скрипт — в коммите: иначе `git_dirty` будет `true`
  и модель не зарегистрируется.

## Ориентиры

Эталонное решение проходит 49 тестов за 14 секунд, с `-W error` — тоже.

Пайплайн практики 7.1.4 (эталон, данные темы 2.1) с подключённым трекингом, дата 30 июня 2024,
метрика продвижения — `valid_mae_ratio_mean`, `min_improvement=0.01`. Пять запусков подряд:

| Запуск | `mae` | `mae_ratio` | Версия | Псевдоним `champion` |
|---|---|---|---|---|
| `alpha=100`, окно 56 дней | 1.3783 | 0.6063 | 1 | назначен: первая версия |
| `alpha=1`, окно 56 дней | 1.3344 | 0.5870 | 2 | перенесён: улучшение 0.019 |
| `alpha=0.1`, окно 56 дней | 1.3344 | 0.5870 | 3 | остался на версии 2: улучшение меньше порога |
| `alpha=1`, окно 112 дней | 1.3310 | 0.5575 | 4 | перенесён: улучшение 0.030 |
| `alpha=0.5`, окно 112 дней, в скрипте незакоммиченная правка | — | — | — | `ValueError`: запуск записан, но не зарегистрирован |

Хеш данных у запусков с окном 56 дней — `020f5827…`, тот же, что в ориентирах практики 7.1.4; у запусков
с окном 112 дней — `4de82a96…`. Вывод `reproduce_command` для лучшего «чистого» запуска:

```text
git checkout 4dcb89e1ee09ab98b21e017a3dc567291936f52f
uv sync --locked
uv run python run_tracked.py --date 2024-06-30 --alpha 1.0 --train-days 112
# data_hash: 4de82a96efefa4def6d00e42ab5fe7ad7b513f630bf521d22c9410f8357f69d3
```

(Хеш коммита у вас будет своим.) «Грязный» запуск в таблице `compare_runs` стоит первым — его метрика
лучшая, — но `find_best_run` с фильтром `{"tags.git_dirty": "false"}` его пропускает, а реестр не принимает.
Это и есть работающее правило из урока 7.2.2: результат, полученный кодом, которого нет в Git, виден,
но ни на что не влияет.

## Идеи для усложнения

1. **Стадии DVC.** Опишите пайплайн в `dvc.yaml` (урок 7.2.1), а в `collect_run_metadata` берите версию
   данных из `.dvc`-файла или `dvc.lock`. `reproduce_command` тогда дополняется строкой `uv run dvc pull`.
2. **Сервер трекинга в Compose.** Опишите в `compose.yaml` сервер MLflow с базой и каталогом артефактов
   в томах (уроки 1.1.3 и 7.2.2); пайплайн получает адрес через `MLFLOW_TRACKING_URI`. Тесты при этом
   по-прежнему работают с локальным хранилищем.
3. **W&B как второй бэкенд.** Выделите интерфейс «записать параметры, метрики, артефакт» и реализуйте
   его дважды: для MLflow и для W&B в офлайн-режиме. Что из `register_and_promote` переносится, а что нет?
4. **Автоматический откат псевдонима.** Функция `rollback(name, alias)` возвращает псевдоним на версию,
   которая владела им до последнего продвижения. Где хранить историю переносов? (Подсказка: теги версий
   или теги самой зарегистрированной модели.)
5. **Честное сравнение с «чемпионом».** Сейчас метрика «чемпиона» берётся из тега, то есть посчитана
   на данных его запуска. Загрузите «чемпиона» и оцените его на проверочном окне претендента; продвигайте
   по этой паре чисел. Что делать, если `data_hash` у запусков разный?
6. **Кросс-валидация по времени.** Замените единственное проверочное окно несколькими (`TimeSeriesSplit`):
   в `fold_metrics` появятся настоящие фолды, а в решении о продвижении — разброс (`_std`).
7. **Воспроизведение как тест.** Напишите `reproduce.py` из урока 7.2.3 для своего проекта и запускайте
   его в CI для последнего зарегистрированного запуска: упавшая проверка означает, что кто-то сломал
   воспроизводимость.
8. **Образ и запуск.** Запишите в теги запуска идентификатор образа Docker (урок 7.2.3) и добавьте его
   в `reproduce_command`.

## Что дальше

Теперь у каждого результата есть происхождение: код, данные, параметры, окружение — и у рабочей модели есть
имя, по которому её получает любой потребитель. Не решённым остался вопрос о признаках: обучение и применение
