## Зачем это нужно

Запись о запуске из урока 7.2.2 говорит, **что** было сделано: коммит, версия данных, параметры. Этот
урок о том, чтобы по записи можно было получить тот же результат — на другой машине, через полгода,
после обновления библиотек. Невоспроизводимый результат нельзя ни проверить, ни улучшить: непонятно,
помогло ваше изменение или сдвинулось что-то под ногами.

Проект — тот же `sales-dvc`. К нему добавлен скрипт `train.py`: одно обучение по `params.yaml`, на выходе —
строка JSON с метрикой и **контрольной суммой прогнозов** (SHA-256 от байтов массива). Метрика совпадает
и у чуть разных моделей; контрольная сумма совпадает, только если прогнозы совпали бит в бит.

```bash
uv run python train.py --model ridge
# {"model": "ridge", "valid_mae": 1.3364638406013931, "predictions_sha256": "cc01994d76d3b805",
#  "n_jobs": 1, "cpus_available": 4}
```

Версии урока: Python 3.12.13, `uv 0.11.32`, Docker 29.9.2, `scikit-learn 1.9.1`, `numpy 2.5.4`,
`lightgbm 4.7.0`, `xgboost 3.4.1`, `mlflow 3.18.0`, `dvc 3.67.1`; машина — 4 ядра x86-64, Linux.

| 1. Код | алгоритм и признаки | коммит Git, чистое рабочее дерево | уроки 1.1.2, 7.2.2 |
| 2. Данные | выборка байт в байт | хеш данных, DVC | урок 7.2.1 |

| 5. Система | версия Python, системные библиотеки, ОС | образ Docker, закреплённый по digest | раздел 4 |

Чем выше уровень, тем дороже его удержать, и на шестом полная гарантия заканчивается. Реалистичная цель:

- **на той же машине и в том же образе** — совпадение бит в бит. Это проверяемо, и в конце урока проверено;
- **на другом железе** — совпадение метрики с заранее названным допуском (например, `1e-6`) и одинаковые
  выводы. Требовать битового совпадения между разными процессорами или между CPU и GPU — значит
  чинить то, что не сломано.

## 2. Источники невоспроизводимости

### Seed и генераторы

Основы — в уроке 1.3.2. Генераторов случайности в проекте несколько, и у каждого свой seed:

| Источник | Как зафиксировать |
|---|---|
| модуль `random` | `random.seed(seed)` |
| NumPy, старый интерфейс | `np.random.seed(seed)` — глобальное состояние; им пользуется sklearn при `random_state=None` |
| NumPy, новый интерфейс | `rng = np.random.default_rng(seed)` и передавать `rng` явно |
| scikit-learn | `random_state=seed` у каждой модели, разбиения и поиска |
| LightGBM, XGBoost | `random_state=seed` |
| Optuna | `TPESampler(seed=seed)` |
| порядок элементов `set` со строками | переменная окружения `PYTHONHASHSEED` |

Проверка на данных урока (прогнозы на проверочном окне, два запуска подряд):

| Модель | Совпали бит в бит | Наибольшее расхождение прогнозов |
|---|---|---|
| `RandomForestRegressor(50)` без `random_state` | нет | 2.2 единицы товара |
| `RandomForestRegressor(50, random_state=0)` | да | 0 |
| `LGBMRegressor(subsample=0.8, ...)` без seed | да | 0 |

LightGBM совпал и без seed: у него seed по умолчанию — фиксированное число, а не «случайный». Полагаться
на это не стоит: значение по умолчанию — ровно то, что меняется между версиями. Seed записывается явно
и попадает в параметры запуска.

Про `PYTHONHASHSEED` вспоминают последним. Три запуска одной команды:

```bash
python -c "print(list({'store_id', 'product', 'dow', 'price', 'promo'}))"
# ['store_id', 'product', 'price', 'dow', 'promo']
# ['promo', 'product', 'price', 'dow', 'store_id']
# ['price', 'store_id', 'dow', 'product', 'promo']
PYTHONHASHSEED=0 python -c "..."     # дважды: ['dow', 'store_id', 'promo', 'product', 'price']
```

Если список признаков получен из множества, порядок столбцов меняется от запуска к запуску — а с ним
и модель: случайный выбор признаков в деревьях привязан к номерам столбцов. Лечение — не полагаться
на порядок множества (`sorted(...)`), а `PYTHONHASHSEED` фиксировать в образе как страховку.

### Потоки и порядок операций с плавающей точкой

Сложение чисел с плавающей точкой не ассоциативно:

```python
0.1 + 0.2 + 0.3     # 0.6000000000000001
0.3 + 0.2 + 0.1     # 0.6
```

Параллельный алгоритм складывает части в том порядке, в каком потоки закончили работу или как поделены
данные, — и результат может отличаться в последних разрядах. «Может» проверено по факту: одно и то же
обучение при разном числе потоков, сравнение прогнозов бит в бит.

| Модель и данные | Потоки | Совпали бит в бит | Наибольшее расхождение |
|---|---|---|---|
| `LGBMRegressor`, 300 деревьев, продажи (5.3 тыс. строк) | 1 / 2 / 4 | да | 0 |
| `LGBMRegressor`, 100 деревьев, 200 тыс. × 40 | 1 / 2 / 4 | да | 0 |
| `XGBRegressor`, оба набора | 1 / 2 / 4 | да | 0 |
| `HistGradientBoostingRegressor`, оба набора | 1 / 4 | да | 0 |
| `RandomForestRegressor(100, random_state=0)`, продажи | `n_jobs` 1 / 4 | **нет** | 1.8e-15 |
| `LinearRegression`, 200 тыс. × 40 | BLAS 1 / 4 | **нет** | 3.7e-14 |
| `Ridge(alpha=1.0)`, 200 тыс. × 40 | BLAS 1 / 4 | **нет** | 6.5e-14 |

(Синтетический набор 200 тыс. × 40 — нормальный шум с линейной зависимостью; число потоков BLAS
ограничивалось через `threadpoolctl.threadpool_limits`.)

Результат расходится с расхожим ожиданием: бустинги в установленных версиях на этой машине дали битовое
совпадение при любом числе потоков, а расхождение показали линейные модели (умножение матриц в OpenBLAS
делится между потоками) и случайный лес (усреднение деревьев в другом порядке). Обобщать таблицу
на другие версии, процессоры и параметры нельзя — у LightGBM для этого есть отдельный параметр
`deterministic`, — но способ проверки переносится: посчитайте контрольную сумму прогнозов при 1 и N потоках.

Расхождение порядка `1e-14` на метрику не влияет. Оно ломает другое: сравнение «бит в бит» в тестах
и кэши, построенные на хеше результата. Поэтому число потоков — параметр запуска (`n_jobs` в записи),
а переменные `OMP_NUM_THREADS` и `OPENBLAS_NUM_THREADS` — часть окружения.

### Видеокарта

> Не проверялось запуском: в среде подготовки нет видеокарты. По документации PyTorch и NVIDIA.

На GPU недетерминизма больше: часть операций (некоторые свёртки, суммирование по индексам) реализована
алгоритмами, результат которых зависит от порядка выполнения параллельных потоков, а библиотека cuDNN
может выбирать разные алгоритмы от запуска к запуску. В PyTorch детерминированный режим включается
явно (`torch.use_deterministic_algorithms(True)`, отключение автоподбора алгоритмов cuDNN) и стоит
скорости. Между разными моделями видеокарт битовое совпадение не гарантируется вовсе.

### Порядок данных

Те же строки в другом порядке (перемешанная обучающая таблица):

| Модель | Совпали бит в бит | Расхождение прогнозов | Расхождение MAE |
|---|---|---|---|
| `Ridge` | нет | 8.9e-15 | 0 |
| `LGBMRegressor`, `n_jobs=1` | да | 0 | 0 |
| `RandomForestRegressor(100, random_state=0)` | нет | 1.08 единицы | 0.0056 |

У леса seed тот же, а модель другая: бутстрэп выбирает строки **по номерам**, и под теми же номерами
теперь другие строки. Источники изменения порядка — `SELECT` без `ORDER BY`, `glob` без сортировки,
параллельная выгрузка. Правило: порядок строк — часть данных; сортируйте по ключу до обучения. Хеш
данных (DVC, `data_hash`) такое изменение ловит.

### Версии библиотек

Один и тот же код в двух версиях NumPy — `uv run --no-project --with numpy==<версия> python demo.py`:

```python
total = np.float32(0.1) + 0.2
print(repr(total), total.dtype)
print(repr(np.uint8(200) + 100))
```

| | `numpy 1.26.4` | `numpy 2.5.4` |
|---|---|---|
| `np.float32(0.1) + 0.2` | `0.30000000149011613`, `float64` | `np.float32(0.3)`, `float32` |
| `np.uint8(200) + 100` | `300` | `np.uint8(44)` — переполнение |

Во второй версии изменились правила приведения типов: число Python больше не расширяет тип массива.
Признак, посчитанный в `float32` или `uint8`, после обновления получает другие значения — без единой
ошибки. Это не экзотика: между основными версиями меняются значения параметров по умолчанию, алгоритмы
решателей, формат сериализации. Отсюда правило: версии всех пакетов фиксируются, а обновление — отдельное
изменение с отдельным сравнением метрик.

## 3. Окружение: `uv.lock` как источник правды

`pyproject.toml` описывает намерение (`scikit-learn>=1.9.1`), `uv.lock` — факт: точные версии **всех**
173 пакетов проекта, включая транзитивные, и хеши их файлов (урок 1.3.2). Воспроизводимость окружения
держится на трёх проверках.

**Lock-файл соответствует `pyproject.toml`.** Зависимость добавлена в `pyproject.toml`, а `uv lock`
не выполнен:

```bash
uv lock --check
# error: The lockfile at `uv.lock` needs to be updated, but `--check` was provided.
uv sync --locked            # то же сообщение с `--locked`, код возврата 1
uv sync --frozen            # код возврата 0: поставлено по старому lock-файлу, новая зависимость молча пропущена
```

`--locked` — для CI и сборки образа: устаревший lock останавливает сборку. `--frozen` не сверяет ничего;
он уместен там, где `pyproject.toml` недоступен или заведомо не менялся.

**Окружение соответствует lock-файлу.** В `.venv` руками поставлен лишний пакет:

```bash
uv pip install tomli
uv sync --locked --check
# Would uninstall 1 package
#  - tomli==2.5.0
# The environment is outdated; run `uv sync` to update the environment          (код возврата 1)
uv sync --locked && uv sync --locked --check
# Would make no changes                                                         (код возврата 0)
```

`uv sync` приводит окружение к lock-файлу точно: лишнее удаляется. `uv pip install` в проекте — способ
получить результат, который никто не повторит; `--check` перед запуском эксперимента это ловит.

**Версия Python.** `requires-python = ">=3.12"` — обещание совместимости, а не фиксация. Файл
`.python-version` (создан командой `uv python pin 3.12`) закрепляет минорную версию для uv. Исправление
(3.12.13 или 3.12.16) не закрепляет ни то, ни другое — это делает образ Docker.

Для инструментов, не знающих про uv, lock-файл экспортируется в `requirements.txt` с хешами:

```bash
uv export --frozen --no-dev --no-emit-project -o requirements.txt      # 13 пакетов, 273 хеша
```

```text
numpy==2.5.4 \
    --hash=sha256:067374eb538c34c745436365cf7b0112595c1d326f21ce4ff340f61230239fbb \
    --hash=sha256:0b4724a19de67bea8cfc4970798efa78bcbbe2ac2613cfac16721a42d44de2a5 \
```

Хеш защищает от подмены: пакет с тем же номером версии, но другим содержимым, установлен не будет.
Тринадцать пакетов — потому что в проекте наведён порядок: в основных зависимостях только то, что нужно
для обучения (`scikit-learn`, `pandas`, `pyyaml`, `lightgbm`), а инструменты исследования (`dvc`,
`mlflow`, `optuna`, `wandb`, `xgboost`) перенесены в группу `dev`.

**Окружение — в артефакты запуска.** Запись о запуске должна содержать само окружение, а не ссылку
на «то, что было тогда на машине»:

```python
mlflow.log_artifact("uv.lock", "environment")
mlflow.log_dict(environment(), "environment/environment.json")
```

```json
{"python": "3.12.13", "platform": "Linux-6.18.44-fc-v445-x86_64-with-glibc2.39", "machine": "x86_64",
 "cpus_available": 4, "threads_env": {"OMP_NUM_THREADS": null, "OPENBLAS_NUM_THREADS": null},
 "packages": {"numpy": "2.5.4", "pandas": "3.1.1", "scikit-learn": "1.9.1", "lightgbm": "4.7.0",
              "scipy": "1.18.1", "joblib": "1.6.0"}}
```

`environment()` собирает сведения через `platform`, `os.sched_getaffinity` и `importlib.metadata.version`.
`uv.lock` отвечает на вопрос «что должно было стоять», `environment.json` — «что стояло и на чём
считалось». При записи модели MLflow 3.18 делает похожее сам: `requirements.txt` модели получен через
`uv export` (урок 7.2.2).

## 4. Docker: образ, который соберётся таким же

Урок 1.1.3 дал основу: слои, кэш сборки, многоэтапный Dockerfile, `.dockerignore`. Тот Dockerfile
воспроизводим «сегодня». Ниже — что нужно, чтобы он был воспроизводим через полгода.

```dockerfile
FROM python:3.12-slim@sha256:5e2bdb1b0d542d5039cffb8181c65930093949194a65c365dfb1b0fe13a4fa5b AS base
ENV PYTHONUNBUFFERED=1 PYTHONDONTWRITEBYTECODE=1 PYTHONHASHSEED=0


FROM base AS deps
COPY --from=ghcr.io/astral-sh/uv:0.11.32 /uv /bin/uv
ENV UV_LINK_MODE=copy UV_PYTHON_DOWNLOADS=never
WORKDIR /app
COPY pyproject.toml uv.lock .python-version ./
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --locked --no-dev --no-install-project


FROM base AS runtime
RUN useradd --create-home --uid 1000 app
WORKDIR /app
COPY --from=deps /app/.venv /app/.venv
ENV PATH="/app/.venv/bin:$PATH"
COPY params.yaml train.py ./
ARG GIT_COMMIT=unknown
ARG DATA_VERSION=unknown
LABEL org.opencontainers.image.revision=$GIT_COMMIT \
      ml.data-version=$DATA_VERSION
USER app
ENTRYPOINT ["python", "train.py"]
```

```bash
docker build -t sales-train:$(git rev-parse --short HEAD) \
  --build-arg GIT_COMMIT=$(git rev-parse HEAD) \
  --build-arg DATA_VERSION=$(awk '/md5/ {print $3}' data/raw.dvc) .
```

Сборка заняла 24 секунды, образ — 529 МБ.

### Базовый образ по digest

Тег `python:3.12-slim` — указатель, который издатель передвигает: сегодня под ним Python 3.12.16
на Debian 13.7, через месяц — следующее исправление и обновлённые системные пакеты. Digest — хеш
содержимого образа, он не меняется:

```bash
docker image inspect python:3.12-slim --format '{{index .RepoDigests 0}}'
# python@sha256:5e2bdb1b0d542d5039cffb8181c65930093949194a65c365dfb1b0fe13a4fa5b
```

Запись `FROM python:3.12-slim@sha256:…` закрепляет ровно этот образ; тег в ней остаётся для читателя.
Обновление базового образа становится осознанным изменением: новая строка в Dockerfile, коммит, сравнение
метрик. Версия `uv` закреплена тегом `0.11.32` по той же причине; `UV_PYTHON_DOWNLOADS=never` запрещает
uv скачивать собственный Python — используется тот, что в образе.

### Системные пакеты

Lock-файл фиксирует пакеты Python, но не системные библиотеки. Пример из этого же проекта: `lightgbm`
установлен, а модель не обучается —

```bash
docker run --rm -v "$PWD/data/prepared:/app/data/prepared:ro" sales-train:e1ee574 --model lgbm
# OSError: libgomp.so.1: cannot open shared object file: No such file or directory
```

LightGBM нужна системная библиотека OpenMP, которой в `slim`-образе нет. На машине разработчика она
есть — поэтому ошибка видна только в контейнере. Исправление — установка пакета в этапе `base`:

```dockerfile
RUN apt-get update \
    && apt-get install -y --no-install-recommends libgomp1=<версия> \
    && rm -rf /var/lib/apt/lists/*
```

> Установка системных пакетов не проверялась запуском: репозитории Debian из среды подготовки недоступны.
> Поэтому в проверенном образе работает только модель `ridge`.

Версию показывает `apt-cache policy libgomp1`. Закрепление версии — защита с оговоркой: старые версии
из репозиториев дистрибутива со временем удаляются, и сборка с точной версией однажды перестанет
проходить. Надёжнее всего собрать собственный базовый образ с системными пакетами, положить его в реестр
и ссылаться на него по digest: тогда `apt-get` при сборке проекта не выполняется вообще.

### Отдельный этап зависимостей

В уроке 1.1.3 зависимости ставились в общем этапе, и `uv` оставался в образе. Здесь этап `deps` создаёт
окружение, а `runtime` получает только готовый каталог `.venv` — без `uv`, без его кэша, без инструментов
сборки. Работает это потому, что оба этапа растут из одного `base`: путь `/app/.venv` и интерпретатор
`/usr/local/bin/python` в них совпадают. Порядок слоёв прежний: редко меняющееся — выше; правка `train.py`
пересобирает один слой в 20 КБ.

(Строки нулевого размера и служебные слои сокращены.) Для сравнения — «наивный» Dockerfile: один этап,
`COPY . .`, `uv sync --locked`, без `.dockerignore`:

| | Наивный | Из урока |
|---|---|---|
| Контекст сборки | 1.06 ГБ | 990 КБ |
| Время сборки | 91 секунда | 24 секунды |
| Размер образа | 3.54 ГБ | 529 МБ |
| Самые тяжёлые слои | `uv sync --locked` — 1.16 ГБ; `COPY . .` — 1.11 ГБ; `uv` — 66 МБ | `.venv` — 274 МБ |
| Пользователь | `root` | `app` (uid 1000) |
| Лишнее внутри | `.git`, `.venv` с машины разработчика, `mlruns/`, `mlflow.db`, `wandb/`, данные, группа `dev` | — |

`docker history` — первый инструмент поиска лишнего: слой в сотни мегабайт у инструкции `COPY` означает,
что в образ попало что-то из рабочего каталога. В наивном образе оказалась вся история экспериментов
и локальная база MLflow — образ, который нельзя никому отдавать.

`.dockerignore` проекта перечисляет `.git`, `.venv`, `.dvc/cache`, `.dvc/tmp`, `data`, `models`, `plots`, `mlruns`,
`mlflow.db`, `wandb`, `__pycache__` и `.env`.

Данных в образе нет намеренно: образ — это код и окружение, данные приходят томом или из хранилища.
Образ с данными внутри нельзя переиспользовать для другой версии данных, и он весит столько же, сколько
данные.

### Не от root

```bash
docker run --rm --entrypoint sh sales-train:e1ee574 -c 'id; touch /app/x; which uv || echo "uv: нет"'
# uid=1000(app) gid=1000(app) groups=1000(app)
# touch: cannot touch '/app/x': Permission denied
# uv: нет
```

Процесс не может изменить код и окружение внутри контейнера; писать он может только в подключённые тома.
Явный `--uid 1000` нужен, чтобы владелец файлов в томе был предсказуем (типичная ошибка из урока 1.1.3).

### Секреты при сборке

Закрытому индексу пакетов нужен токен. Очевидный способ — аргумент сборки:

```dockerfile
ARG INDEX_TOKEN
ENV PIP_INDEX_URL=https://ci:${INDEX_TOKEN}@pypi.example.com/simple
RUN test -n "$INDEX_TOKEN" && echo "зависимости установлены"
```

```bash
docker build --build-arg INDEX_TOKEN=s3cr3t-token-123 -t secret-demo:arg .
docker history --no-trunc --format '{{.CreatedBy}}' secret-demo:arg
```

```text
RUN |1 INDEX_TOKEN=s3cr3t-token-123 /bin/sh -c test -n "$INDEX_TOKEN" && echo "зависимости установлены"
ENV PIP_INDEX_URL=https://ci:s3cr3t-token-123@pypi.example.com/simple
ARG INDEX_TOKEN=s3cr3t-token-123
```

Токен записан в историю образа трижды, а через `ENV` — ещё и в окружение каждого контейнера
(`echo $PIP_INDEX_URL` внутри контейнера печатает адрес с токеном). История — часть образа: её видит
каждый, кто может его скачать, и удалить секрет можно только пересборкой. Правильный способ — секрет,
подключаемый на время одной инструкции:

```dockerfile
RUN --mount=type=secret,id=index_token \
    test -s /run/secrets/index_token && echo "зависимости установлены"
```

```bash
docker build --secret id=index_token,src=token.txt -t secret-demo:mount .
docker history --no-trunc secret-demo:mount | grep -c s3cr3t        # 0
docker run --rm secret-demo:mount ls /run/secrets                   # No such file or directory
```

Файл `/run/secrets/index_token` существует только во время выполнения этой инструкции: его нет
ни в слоях, ни в истории, ни в контейнере. Оба варианта собраны и проверены; сама установка из закрытого
индекса не выполнялась — индекса `pypi.example.com` не существует. То же правило для всего, что попадает
в образ: `.env` — в `.dockerignore`, ключи хранилища — через окружение контейнера при запуске.

### Метки: образ знает, из чего собран

```bash
docker inspect --format '{{json .Config.Labels}}' sales-train:e1ee574
# {"ml.data-version":"0ed16eacc2a51a921f06bde7709ef8c1.dir",
#  "org.opencontainers.image.revision":"e1ee57439747610c30060693561bfed2dcffa059"}
```

Метка с коммитом и тег образа по короткому хешу связывают образ с кодом; идентификатор самого образа
(`docker inspect --format '{{.Id}}'`) записывается в теги запуска MLflow — так цепочка «запуск → образ →
коммит → данные» замыкается. Тег `latest` для этого не годится по той же причине, что и тег базового
образа: он переезжает.

### Один образ или два

| | Образ обучения | Образ применения |
|---|---|---|
| Что внутри | код обучения, библиотеки моделей; клиент трекера и DVC — если запись идёт из контейнера | код прогноза и сервис; модель — из реестра при старте или внутри образа |
| Размер и запуск | размер терпим, запускается редко | важны размер, время старта, поверхность атаки |
| Данные и доступы | чтение обучающих данных, запись в трекер | никаких обучающих данных и ключей к ним |

Разумная схема — один Dockerfile, общий этап `deps` и две цели (`--target`). Жёсткое требование одно:
версии библиотек, участвующих в сериализации модели (scikit-learn, LightGBM, NumPy), в обоих образах
совпадают — то есть берутся из одного `uv.lock`. Пока проект мал, один образ для обоих назначений —
нормальное решение; разделяют его, когда появляется отдельный сервис применения модели.

## 5. Тот же образ — другие числа

Контейнер и машина разработчика, модель `ridge`:

```bash
docker run --rm -v "$PWD/data/prepared:/app/data/prepared:ro" sales-train:e1ee574 --model ridge
# {"model": "ridge", "valid_mae": 1.3364638406013931, "predictions_sha256": "cc01994d76d3b805", ...}
```

Метрика и контрольная сумма прогнозов те же, что вне контейнера, — при том, что Python в образе 3.12.16,
а на машине 3.12.13. Образ изолирует окружение, но не процессор. Скрипт, обучающий `LinearRegression`
на 200 тыс. × 40 и печатающий контрольную сумму коэффициентов, в одном и том же образе:

| Запуск | Контрольная сумма | Первый коэффициент |
|---|---|---|
| `--cpuset-cpus 0` (доступно 1 ядро) | `477278a8468c2bea` | 0.9487401081985845 |
| `--cpuset-cpus 0-3` (4 ядра) | `35cb6ffa72ae7ea2` | 0.9487401081985861 |
| 4 ядра и `-e OPENBLAS_NUM_THREADS=1` | `477278a8468c2bea` | 0.9487401081985845 |
| `--cpus 1` (квота времени, видны 4 ядра) | `35cb6ffa72ae7ea2` | 0.9487401081985861 |

Один образ — два результата: OpenBLAS создаёт столько потоков, сколько ядер видит, и порядок сложений
меняется. Третья строка показывает лечение: число потоков задаётся явно — и результат на четырёх ядрах
совпадает с одноядерным. Четвёртая — ловушка: `--cpus` ограничивает время процессора, а не число видимых
ядер; библиотека по-прежнему видит четыре.

Что ещё может отличаться при том же образе (не проверялось запуском: в среде подготовки одна машина):
другая модель процессора — BLAS выбирает реализацию под набор инструкций (AVX2, AVX-512); другая
архитектура (x86-64 и ARM) — это вообще разные образы под одним тегом; видеокарта и версия драйвера.
Отсюда `cpus_available` и `threads_env` в `environment.json`: при расхождении в пятнадцатом знаке
первым делом сравнивают их.

## 6. Чек-лист воспроизводимого эксперимента

- [ ] рабочее дерево чистое; коммит и признак `git_dirty` записаны в запуск;
- [ ] данные — под контролем версий; хеш данных записан; порядок строк определён сортировкой;
- [ ] итоговый конфиг целиком — в параметрах запуска, включая seed и число потоков;
- [ ] seed передан всем генераторам; порядок признаков не зависит от `set`;
- [ ] `uv lock --check` и `uv sync --locked --check` проходят перед запуском;
- [ ] `uv.lock` и сведения об окружении лежат в артефактах запуска;
- [ ] образ собран от базового по digest, с `uv sync --locked`; в запуск записан идентификатор образа;
- [ ] в образе нет данных, секретов, истории экспериментов; процесс работает не от root;
- [ ] число потоков задано явно, если требуется битовое совпадение;
- [ ] есть команда, которая по идентификатору запуска повторяет его и сравнивает результат, — и она
      выполняется в CI хотя бы для одного запуска.

## 7. Итог: воспроизведение запуска по идентификатору

Проверка всего урока — одна команда. `train.py --track` записал запуск: параметры (включая `seed`
и `n_jobs`), теги `git_commit`, `git_dirty`, `data_version`, `predictions_sha256`, метрику и окружение.
`reproduce.py` получает только идентификатор:

```python
run = mlflow.MlflowClient().get_run(run_id)
tags, params = run.data.tags, run.data.params
if tags["git_dirty"] == "True":
    sys.exit("Запуск сделан с незакоммиченными правками: воспроизвести его нельзя")

workdir = Path.cwd().parent / f"repro-{run_id[:8]}"
sh("git", "worktree", "add", "--detach", str(workdir), tags["git_commit"], cwd=Path.cwd())   # код
sh("uv", "sync", "--locked")                                                              # окружение
sh("uv", "run", "dvc", "pull")                                                            # данные
data_version = yaml.safe_load((workdir / "data/raw.dvc").read_text())["outs"][0]["md5"]
assert data_version == tags["data_version"]

output = sh("uv", "run", "python", "train.py", "--model", params["model"], "--seed", params["seed"],
            "--n-jobs", params["n_jobs"])
result = json.loads(output.strip().splitlines()[-1])
```

(`sh` — обёртка над `subprocess.run` с рабочим каталогом `workdir`; дальше скрипт сравнивает метрику
и контрольную сумму прогнозов с записанными.) `git worktree` создаёт отдельный рабочий каталог на нужном
коммите — текущий каталог с незаконченной работой не затрагивается.

```bash
uv run python reproduce.py 918af84d1dd04b48bf021477148f0e60
```

```text
$ git worktree add --detach ../repro-918af84d 0ac448036d5cbc0a0af378750ca808243218e96c
$ uv sync --locked
$ uv run dvc pull
$ uv run python train.py --model ridge --seed 0 --n-jobs 1
valid_mae:  записано 1.3364638406013931, получено 1.3364638406013931
прогнозы:   записано cc01994d76d3b805, получено cc01994d76d3b805
ВОСПРОИЗВЕДЕНО
```

(Путь к рабочему каталогу сокращён.) 11 секунд — и результат подтверждён с нуля: чистый каталог, новое
окружение по lock-файлу, данные из хранилища DVC. Так же воспроизведён запуск LightGBM с `n_jobs=4`
(`valid_mae` 1.434419083516825, сумма `821c8a7b8d9e20cf`). Проверка сделана на той же машине — это
четвёртый уровень из шести; пятый добавляет образ: та же команда внутри контейнера с образом, идентификатор
которого записан в запуске.

Запуск, который нельзя воспроизвести такой командой, — не результат, а наблюдение. В практике 7.2.4
функция `reproduce_command` строит эту команду для любого запуска.

## Типичные ошибки

| Симптом | Причина | Решение |
|---|---|---|
| Два запуска с одним seed дают разные модели | seed передан не всем генераторам; порядок признаков из `set`; другой порядок строк | `random_state` везде; `sorted`; сортировка данных по ключу |
| Результаты сходятся до 14-го знака, тест «бит в бит» падает | другое число потоков BLAS или `n_jobs` | задать потоки явно либо сравнивать с допуском |
| После обновления библиотек метрика сдвинулась | изменились правила или значения по умолчанию | обновление — отдельный коммит с новым `uv.lock` и сравнением метрик |
| У коллеги в окружении другие версии при том же `uv.lock` | пакеты ставились через `uv pip install` или `uv sync --frozen` при устаревшем lock | `uv sync --locked`; `uv sync --locked --check` перед запуском |
| Образ, собранный через месяц, ведёт себя иначе | базовый образ указан тегом, тег переехал | `FROM образ:тег@sha256:…` |
| В контейнере `libgomp.so.1: cannot open shared object file` | системной библиотеки нет в `slim`-образе | установить системный пакет в базовом этапе |
| Образ весит гигабайты | `COPY . .` без `.dockerignore`; кэш и группа `dev` в образе | `docker history`; этап зависимостей; `--no-dev` |
| Токен виден в `docker history` | секрет передан через `ARG` или `ENV` | `RUN --mount=type=secret`; заменить скомпрометированный токен |
| В контейнере с `--cpus 1` результат как на четырёх ядрах | `--cpus` — квота, а не число видимых ядер | `OMP_NUM_THREADS`, `OPENBLAS_NUM_THREADS` или `--cpuset-cpus` |
| Запуск записан, но воспроизвести его нельзя | `git_dirty = True`; данные не отправлены в хранилище; окружение не записано | чек-лист из раздела 6; проверка воспроизведения в CI |

   прогнозов. Составьте таблицу: совпадает ли сумма при 1 и N потоках и при перемешанных данных —
   минимум для трёх моделей.
2. Покажите три состояния окружения: lock устарел (`uv lock --check`), в окружении лишний пакет
   (`uv sync --locked --check`), всё в порядке. Запишите `uv.lock` и `environment.json` в артефакты запуска.
3. Соберите образ по схеме урока: базовый образ по digest, этап зависимостей, пользователь не root, метки
   с коммитом и версией данных. Приведите `docker history` и объясните каждый слой больше 1 МБ.
4. Соберите два учебных образа с «секретом» — через `ARG` и через `--mount=type=secret` — и покажите

   число доступных ядер, и устраните его переменной окружения.
6. Напишите `reproduce.py`: по идентификатору запуска MLflow он восстанавливает код, окружение и данные
   в отдельном каталоге, повторяет обучение и сравнивает результат с записанным.

**Критерии приёмки:**

- [ ] таблица потоков и порядка данных составлена по реальным запускам, расхождения объяснены;
- [ ] `uv sync --locked --check` проходит; в артефактах запуска есть `uv.lock` и сведения об окружении;
- [ ] в Dockerfile базовый образ закреплён по digest; зависимости ставятся с `--locked` и без группы `dev`;
- [ ] `docker run ... id` показывает не root; в образе нет `.git`, данных, `mlruns/`, `.env`;
- [ ] в `docker history --no-trunc` итогового образа нет секретов;
- [ ] метки образа содержат коммит и версию данных;
- [ ] `reproduce.py <run_id>` завершается с кодом 0 для запуска с чистым деревом и отказывается

- [ ] созданные контейнеры удалены, учебные образы с «секретом» удалены.
