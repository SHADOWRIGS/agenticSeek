# Урок 7.2.1: DVC для версионирования данных и моделей

> **Модуль 7:** ML Engineering & MLOps · **Тема 7.2:** Версионирование и эксперименты
> **Тип:** теория · **Время:** 120 минут + 90 минут на домашнее задание

## Цели урока

После урока вы сможете:

- объяснить, что такое «версия данных» и почему её нельзя хранить в Git напрямую;
- поставить каталог с данными под контроль DVC, отправить его в удалённое хранилище и вернуться
  к любой прошлой версии вместе с кодом;
- описать пайплайн в `dvc.yaml` и объяснить, почему `dvc repro` пересчитал именно эти стадии;
- сравнивать параметры и метрики между коммитами и запускать эксперименты через `dvc exp`;
- выбрать тип связи рабочего каталога с кэшем и безопасно чистить кэш;
- разделить обязанности между DVC, оркестратором и трекером экспериментов.

## Зачем это нужно

В уроке 1.1.2 было обещано: «данные и модели версионируют отдельными инструментами». Причина в устройстве
Git: он хранит каждую версию каждого файла в истории навсегда и рассчитан на небольшие текстовые файлы.
Таблица на гигабайт, изменённая десять раз, — это десять гигабайт в каждом клоне; двоичные файлы
не сравниваются построчно; хостинги ограничивают размер файла. Поэтому в `.gitignore` курса с первого
модуля стоят `data/` и `models/` — и вместе с ними из истории исчезает ответ на вопрос «на чём обучена
эта модель».

Пайплайн практики 7.1.4 сделал полшага: записал в `metadata.json` хеш данных. По нему видно, **что**
данные изменились, но вернуть прежние нельзя. **Версия данных** — это не дата и не имя файла, а пара:
точное содержимое (его хеш) и способ это содержимое получить. DVC (Data Version Control) хранит первое
в Git, а второе — рядом с Git.

## 1. Как устроен DVC

```text
   Git-репозиторий                          кэш DVC (.dvc/cache)             удалённое хранилище
┌──────────────────────┐                ┌───────────────────────────┐      ┌─────────────────────┐
│ src/, params.yaml    │                │ files/md5/2f/aa63…  .dir  │ push │ files/md5/2f/aa63…  │
│ dvc.yaml, dvc.lock   │   хеш (md5)    │ files/md5/75/d1ed…        │ ───► │ files/md5/75/d1ed…  │
│ data/raw.dvc  ───────┼──────────────► │ files/md5/…               │ ◄─── │ …                   │
│ data/.gitignore      │                └─────────────┬─────────────┘ pull └─────────────────────┘
└──────────────────────┘                              │ checkout: копия или ссылка
                                           data/raw/ — рабочий каталог, в Git не попадает
```

- В Git лежит **маленький текстовый файл** `.dvc` с хешем содержимого. Он версионируется как код:
  коммиты, ветки, теги, ревью.
- Само содержимое лежит в **кэше** — хранилище, адресуемом по содержимому: имя файла в кэше равно его
  хешу. Одинаковые файлы хранятся один раз, сколько бы версий на них ни ссылалось.
- **Удалённое хранилище** (remote) — такой же набор файлов по хешам, только в общем месте: бакет S3,
  сервер по SSH, сетевой диск. В уроке его роль играет каталог на диске.

Версия данных, таким образом, — это коммит Git: в нём записано, какой хеш должен лежать в `data/raw`.

Окружение — отдельный проект uv; DVC ставится как обычная зависимость:

```bash
uv init --python 3.12 sales-dvc && cd sales-dvc
uv add dvc scikit-learn pandas pyyaml
```

Версии урока: `dvc 3.67.1` (`dvc-data 3.18.3`, `dvc-objects 5.3.1`, `scmrepo 3.6.2`), Python 3.12.13,
`scikit-learn 1.9.1`, `pandas 3.1.1`, `numpy 2.5.4`, Git 2.43.0. С основными библиотеками курса DVC
не конфликтует — отдельный проект нужен только для порядка. Все команды урока выполнены; вывод сокращён
там, где это отмечено.

## 2. Первая версия данных

Данные — дневные партиции продаж, как в теме 7.1: `data/raw/date=YYYY-MM-DD/sales.csv`. Роль внешнего
источника играет скрипт `make_partitions.py`: он берёт продажи из генератора темы 2.1 (`sales_data.py`
скопирован в проект) и записывает партиции за указанный период.

```bash
git init -b main
uv run dvc init                          # создаёт .dvc/ и .dvcignore и сам добавляет их в индекс Git
uv run dvc config core.analytics false   # не отправлять анонимную статистику использования
git add -A && git commit -m "Проект и инициализация DVC"

uv run python make_partitions.py --start 2024-04-22 --end 2024-06-23   # 63 партиции, 760 КБ
uv run dvc add data/raw
```

```text
To track the changes with git, run:

	git add data/.gitignore data/raw.dvc
```

`dvc add` сделал три вещи: посчитал хеши файлов и положил их копии в кэш, записал `data/raw.dvc`
и добавил `/raw` в `data/.gitignore`, чтобы сами данные в Git не попали.

```yaml
# data/raw.dvc
outs:
- md5: 2faa63a09e88faf7e83571842041e2ea.dir
  size: 274470
  nfiles: 63
  hash: md5
  path: raw
```

```bash
git add data/raw.dvc data/.gitignore
git commit -m "Данные: партиции 22.04–23.06" && git tag data-v1
```

Хеш с суффиксом `.dir` — это хеш **списка**: в кэше под этим именем лежит JSON из 63 записей вида
`{"md5": "2f5c3934…", "relpath": "date=2024-04-22/sales.csv"}`. Каталог — это список «путь → хеш файла»,
поэтому добавление одной партиции меняет один маленький список и добавляет один файл.

## 3. Удалённое хранилище

```bash
uv run dvc remote add -d storage /srv/dvc-storage      # -d: хранилище по умолчанию
git add .dvc/config && git commit -m "Удалённое хранилище DVC"
uv run dvc push
# 64 files pushed
```

Адрес записан в `.dvc/config` и попадает в Git — коллеге не нужно ничего настраивать:

```ini
[core]
    analytics = false
    remote = storage
['remote "storage"']
    url = /srv/dvc-storage
```

(Здесь и далее путь к каталогу хранилища сокращён: при подготовке урока это был временный каталог.)

Отправлено 64 файла: 63 партиции и список каталога. В хранилище они лежат так же, как в кэше:
`files/md5/75/d1edfd5af6918793811fcde308f1a4`. Человеку такая раскладка ничего не говорит — в хранилище
DVC не ходят руками, как не редактируют руками каталог `.git/objects`.

## 4. Новая версия и возврат к старой

Прошла неделя: источник отдал семь новых дней и задним числом исправил продажи за 20 июня.

```bash
uv run python make_partitions.py --start 2024-06-24 --end 2024-06-30
# ...и правка одной строки в data/raw/date=2024-06-20/sales.csv
uv run dvc status
```

```text
data/raw.dvc:
	changed outs:
		modified:           data/raw
```

```bash
uv run dvc diff          # что именно изменилось относительно HEAD
```

```text
Added:
    data/raw/date=2024-06-24/sales.csv
    ...
    data/raw/date=2024-06-30/sales.csv

Modified:
    data/raw/
    data/raw/date=2024-06-20/sales.csv

files summary: 7 added, 1 modified
```

Жизненный цикл изменения данных — четыре команды, и порядок важен:

```bash
uv run dvc add data/raw                       # 1. новый хеш в data/raw.dvc, содержимое — в кэш
git add data/raw.dvc                          # 2. в Git меняются три строки:
git commit -m "Данные: +неделя, исправлена партиция 20.06" && git tag data-v2
uv run dvc push                               # 3. 9 files pushed: 7 новых, 1 изменённый, новый список
```

```diff
-- md5: 2faa63a09e88faf7e83571842041e2ea.dir
-  size: 274470
-  nfiles: 63
+- md5: ec133116cb6c582a7ee06f38e10cb8ce.dir
+  size: 304964
+  nfiles: 70
```

Отправлено 9 файлов, а не 70: шестьдесят две неизменившиеся партиции уже есть в хранилище под своими
хешами.

Возврат к прошлой версии — две команды: Git возвращает файл `.dvc`, DVC приводит данные в соответствие.

```bash
md5sum data/raw/date=2024-06-20/sales.csv      # c5775f371b983e917b4d035ede2edacd
git checkout data-v1
uv run dvc checkout                            # M       data/raw/
ls data/raw | wc -l                            # 63
md5sum data/raw/date=2024-06-20/sales.csv      # 61a47256a35cb770272cb63bdd35af89 — до исправления
git checkout main && uv run dvc checkout       # снова 70 партиций
```

Семь партиций исчезли, восьмая вернулась к прежнему содержимому. Данные брались из кэша, без сети.
Две полезные разновидности:

```bash
git checkout data-v1 -- data/raw.dvc && uv run dvc checkout data/raw.dvc   # старые данные, текущий код
uv run dvc get . data/raw --rev data-v2 -o raw_v2    # копия версии в стороне, рабочий каталог не тронут
uv run dvc diff data-v1 data-v2                      # сравнение двух версий: 7 added, 1 modified
```

Модели версионируются точно так же: `dvc add models/model.joblib`. Но удобнее, когда модель — выход
стадии пайплайна (раздел 6): тогда вместе с хешем модели записано, из чего она получена.

## 5. Совместная работа и забытый `dvc push`

Коллега клонирует репозиторий и получает код и файлы `.dvc`, но не данные:

```bash
git clone <адрес> sales-dvc && cd sales-dvc
uv sync && uv run dvc pull
# A       data/raw/
# 71 files fetched and 70 files added
```

Самая частая ошибка при работе с DVC — `git push` без `dvc push`. Она воспроизведена намеренно: версия
`data-v2` закоммичена, но в хранилище ещё не отправлена. У коллеги:

```text
WARNING: Some of the cache files do not exist neither locally nor on remote. Missing cache files:
md5: ec133116cb6c582a7ee06f38e10cb8ce.dir
ERROR: failed to pull data from the cloud - Checkout failed for following targets:
data/raw
```

В Git записано, какими данные должны быть, а взять их негде. Пока данные есть в кэше автора, это
исправляется одной командой `dvc push`; если автор успел почистить кэш или сменить машину — версия
потеряна. Проверка перед `git push`:

```bash
uv run dvc status -c       # -c: сравнить кэш с удалённым хранилищем
# new:                data/raw/date=2024-06-24/sales.csv   ... (9 строк)
# после dvc push:  Cache and remote 'storage' are in sync.
```

Чтобы не полагаться на память, `dvc install` ставит хуки Git: `dvc checkout` после `git checkout`
и `dvc push` перед `git push` (команда в уроке не запускалась, чтобы не менять поведение Git
в демонстрациях).

## 6. Пайплайн как код: `dvc.yaml`

DVC умеет больше, чем хранить файлы: он знает, **какой командой из чего получен каждый файл**. Описание —
в `dvc.yaml`:

```yaml
stages:
  prepare:
    cmd: python src/prepare.py
    deps:
      - data/raw
      - src/prepare.py
    params:
      - prepare
    outs:
      - data/prepared
  train:
    cmd: python src/train.py
    deps:
      - data/prepared/train.csv
      - src/train.py
    params:
      - train
    outs:
      - models/model.joblib
  evaluate:
    cmd: python src/evaluate.py
    deps:
      - data/prepared
      - models/model.joblib
      - src/evaluate.py
    metrics:
      - metrics.json:
          cache: false
    plots:
      - plots/predictions.csv:
          cache: false
          template: scatter
          x: actual
          y: predicted
```

| Раздел | Смысл |
|---|---|
| `cmd` | команда оболочки; выполняется из каталога, где лежит `dvc.yaml` |
| `deps` | файлы и каталоги, от которых зависит результат: данные **и код стадии** |
| `params` | ключи из `params.yaml`; `prepare` — весь раздел, `train.alpha` — одно значение |
| `outs` | результаты; попадают в кэш и в `.gitignore` |
| `metrics`, `plots` | тоже выходы, но DVC умеет их показывать и сравнивать. `cache: false` — файл маленький, пусть хранится в Git |

Параметры — в `params.yaml` (это конфиг из урока 1.3.3, только с именем, которое DVC ищет по умолчанию):

```yaml
prepare:
  run_date: "2024-06-23"
  train_days: 56
  valid_days: 7
train:
  alpha: 1.0
  min_frequency: 20
```

Скрипты стадий — обычные программы без единого импорта DVC. `prepare.py` собирает партиции обучающего
и проверочного окон в `train.csv` и `valid.csv`; `evaluate.py` считает MAE модели и MAE прогноза средним.
`train.py` целиком:

```python
params = yaml.safe_load(Path("params.yaml").read_text())["train"]
train = pd.read_csv("data/prepared/train.csv")

encoder = OneHotEncoder(min_frequency=params["min_frequency"], handle_unknown="infrequent_if_exist")
features = ColumnTransformer(
    [("cat", encoder, ["store_id", "product", "dow"]), ("num", StandardScaler(), ["price", "promo"])]
)
regressor = TransformedTargetRegressor(Ridge(alpha=params["alpha"]), func=np.log1p, inverse_func=np.expm1)
model = Pipeline([("features", features), ("model", regressor)]).fit(train, train["units"])

Path("models").mkdir(exist_ok=True)
joblib.dump(model, "models/model.joblib")
```

```bash
uv run dvc dag            # граф: data/raw.dvc -> prepare -> train -> evaluate (prepare -> evaluate)
uv run dvc repro          # 10 секунд на три стадии
```

```text
'data/raw.dvc' didn't change, skipping
Running stage 'prepare':
> python src/prepare.py
Generating lock file 'dvc.lock'
Running stage 'train':
> python src/train.py
Running stage 'evaluate':
> python src/evaluate.py
```

Граф выводится из совпадения путей: выход `data/prepared` стадии `prepare` указан в `deps` стадии
`train` — значит, `train` идёт после. Порядок стадий в файле роли не играет.

Результат запуска — `dvc.lock`: для каждой стадии хеши всех зависимостей, значения параметров и хеши
выходов. Фрагмент:

```yaml
  train:
    cmd: python src/train.py
    deps:
    - path: data/prepared/train.csv
      hash: md5
      md5: fb7e110467b7a827c29c60b00965a728
      size: 251526
    - path: src/train.py
      hash: md5
      md5: 1d58b8f07770190b2abcd7f1e4cfafda
      size: 1069
    params:
      params.yaml:
        train:
          alpha: 1.0
          min_frequency: 20
    outs:
    - path: models/model.joblib
      hash: md5
      md5: 4a6e79f799871bf878940325ba1a4662
      size: 4296
```

Это тот же `metadata.json` из практики 7.1.4, только полный и составленный автоматически: какие данные,
какой код, какие параметры дали какую модель. В Git коммитятся `dvc.yaml`, `dvc.lock`, `params.yaml`,
`metrics.json`, `plots/predictions.csv` и обновлённые `.gitignore`; модель и таблицы — в кэше.

## 7. «Умный» пересчёт

`dvc repro` сравнивает текущие хеши зависимостей и параметров с записанными в `dvc.lock` и выполняет
только те стадии, у которых что-то изменилось, — и всё, что от них зависит. Пять проверенных случаев:

| Что изменили | `prepare` | `train` | `evaluate` | Почему |
|---|---|---|---|---|
| ничего | — | — | — | `Data and pipelines are up to date.` |
| `train.alpha: 1.0 → 10.0` | — | выполнена | выполнена | параметр — зависимость только `train`; модель изменилась — изменился вход `evaluate` |
| `prepare.run_date → 2024-06-30` | выполнена | выполнена | выполнена | другие окна — другие таблицы |
| добавили партицию за 1 июля (`dvc add data/raw`) | выполнена | — | — | каталог `data/raw` изменился, но окна до 30 июня те же: `train.csv` и `valid.csv` получились байт в байт прежними |
| дописали комментарий в `src/evaluate.py` | — | — | выполнена | код стадии — её зависимость |

Вывод для второй строки:

```text
'data/raw.dvc' didn't change, skipping
Stage 'prepare' didn't change, skipping
Running stage 'train':
> python src/train.py
Running stage 'evaluate':
> python src/evaluate.py
```

Четвёртая строка показывает, что сравниваются **хеши содержимого, а не время изменения**: стадия
выполнилась, но выдала те же файлы — и цепочка остановилась. `make` в такой ситуации пересобрал бы всё.

Шестой случай: комментарий из `evaluate.py` убрали. DVC не стал выполнять стадию второй раз:

```text
Stage 'evaluate' is cached - skipping run, checking out outputs
```

Это **кэш запусков** (run cache): сочетание «эти зависимости + эти параметры + эта команда» уже
встречалось, и выходы достаются из кэша. Отсюда требование к стадиям: результат должен зависеть только
от объявленных зависимостей. Стадия, которая читает файл, не указанный в `deps`, текущую дату или сеть,
получит из кэша устаревший результат.

## 8. Параметры и метрики

```bash
uv run dvc metrics show
# Path          baseline_mae    mae      mae_ratio    n_valid
# metrics.json  2.3674          1.38964  0.58699      668

uv run dvc metrics diff          # рабочий каталог против HEAD; можно указать два коммита или тега
# Path          Metric     HEAD    workspace    Change
# metrics.json  mae        1.3873  1.38964      0.00235
# metrics.json  mae_ratio  0.586   0.58699      0.00099

uv run dvc params diff
# Path         Param        HEAD    workspace
# params.yaml  train.alpha  1.0     10.0
```

Вместе эти две таблицы — готовое описание изменения: «`alpha` с 1 до 10, MAE вырос на 0.002». Флаг `--md`
выводит таблицу в Markdown — её удобно вставлять в описание pull request. Команда `dvc plots show`
строит по `plots/predictions.csv` HTML-страницу `dvc_plots/index.html` (в уроке — диаграмма рассеяния
«факт — прогноз»); `dvc plots diff` накладывает графики двух версий.

## 9. Эксперименты: `dvc exp`

Проверять гипотезу коммитом на каждое значение параметра неудобно. `dvc exp run` — это `dvc repro`
с подстановкой параметров и записью результата вне веток:

```bash
uv run dvc exp run -n alpha-0.1 -S train.alpha=0.1
uv run dvc exp run -n alpha-100 -S train.alpha=100 -S train.min_frequency=50
uv run dvc exp show --no-pager --md --drop 'baseline_mae|n_valid|prepare|data|src|models'
```

| Experiment              | Created   | mae    | mae_ratio   | train.alpha   | train.min_frequency   |
|-------------------------|-----------|--------|-------------|---------------|-----------------------|
| workspace               | -         | 1.3583 | 0.5974      | 100           | 50                    |
| main                    | 11:57 AM  | 1.3365 | 0.58781     | 10            | 20                    |
| ├── a353c7d [alpha-100] | 11:57 AM  | 1.3583 | 0.5974      | 100           | 50                    |
| └── fd4f40c [alpha-0.1] | 11:57 AM  | 1.3357 | 0.58745     | 0.1           | 20                    |

В обоих запусках стадия `prepare` была пропущена — кэш работает и здесь. Что важно знать:

- эксперимент — это скрытый коммит Git (ссылки `refs/exps/...`): он не виден в `git log` и не уходит
  при `git push`. Для обмена есть `dvc exp push <git-remote>` (не проверялось запуском: в среде
  подготовки нет удалённого Git-сервера);
- `-S` **переписывает `params.yaml`**, и результат последнего эксперимента остаётся в рабочем каталоге:
  после двух запусков `git status` показывает изменённые `params.yaml`, `dvc.lock`, `metrics.json`;
- `dvc exp apply alpha-0.1` переносит выбранный эксперимент в рабочий каталог — дальше обычный
  `git commit`; `dvc exp remove alpha-100` удаляет ненужный; `dvc exp diff` сравнивает два эксперимента;
- после отказа от экспериментов: `git checkout params.yaml dvc.lock metrics.json && dvc checkout`.

`dvc exp` — лёгкий учёт для одного человека и одного репозитория. Общий журнал экспериментов команды
с интерфейсом, артефактами и реестром моделей — задача трекера (урок 7.2.2).

## 10. Кэш, ссылки и очистка

```bash
uv run dvc doctor          # сокращено
# Supports: http, https
# Cache types: hardlink, symlink
# Cache directory: ext4 on /dev/vda
```

Строка `Cache types` — способы связать рабочий каталог с кэшем, доступные на этой файловой системе:

| `cache.type` | Что лежит в рабочем каталоге | Место на диске | Правка файла на месте |
|---|---|---|---|
| `reflink` | копия с общими блоками (copy-on-write: Btrfs, XFS, APFS) | один раз | безопасна |
| `copy` | обычная копия | дважды | безопасна |
| `hardlink` | жёсткая ссылка на файл кэша | один раз | **портит кэш** — файл сделан доступным только для чтения |
| `symlink` | символическая ссылка на файл кэша | один раз | то же |

По умолчанию DVC пробует `reflink`, затем `copy`. На ext4 из примера `reflink` недоступен, поэтому
данные лежат дважды: в `data/raw` и в `.dvc/cache`. Для больших данных это дорого:

```bash
uv run dvc config cache.type hardlink && uv run dvc checkout --relink
stat -c '%h %A %n' data/raw/date=2024-06-30/sales.csv
# 2 -r--r--r-- data/raw/date=2024-06-30/sales.csv        (было: 1 -rw-r--r--)
echo x >> data/raw/date=2024-06-30/sales.csv
# sh: 1: cannot create data/raw/date=2024-06-30/sales.csv: Permission denied
uv run dvc unprotect data/raw/date=2024-06-30/sales.csv    # заменить ссылку копией — теперь можно править
```

Файл в рабочем каталоге и файл в кэше — один и тот же: дописав в него строку, вы изменили бы содержимое,
лежащее под именем старого хеша, то есть испортили прошлые версии. Защита «только чтение» — единственное,
что этому мешает (запись проверялась от имени обычного пользователя; `root` такая защита не остановит).
Правило: при `hardlink` и `symlink` отслеживаемые файлы не правят на месте — их заменяют целиком
или сначала вызывают `dvc unprotect`. Стадии пайплайна это не касается: DVC удаляет выходы перед запуском.

Кэш растёт с каждой версией. Очистка:

```bash
uv run dvc gc --workspace --dry      # что будет удалено: всё, чего нет в текущем рабочем каталоге
uv run dvc gc --workspace --force    # Removed 20 objects from repo cache.   (1.8 МБ -> 1.4 МБ)
```

После этого старые версии остались только в хранилище. Проверка, что это не потеря:

```bash
git checkout data-v1 -- data/raw.dvc
uv run dvc checkout data/raw.dvc     # ERROR: Checkout failed ... Is your cache up to date?
uv run dvc pull data/raw.dvc         # 1 file fetched and 63 files added
```

Два наблюдения из этой проверки. Первое: `git checkout data-v1 && dvc pull` завершился ошибкой
`No remote provided and no default remote set` — хранилище было настроено коммитом позже тега,
а `.dvc/config` версионируется вместе со всем остальным. Настраивайте remote первым коммитом. Второе:
выходы стадий из ранних коммитов (`data/prepared` до смены `run_date`) в хранилище не отправлялись,
и после очистки `dvc gc --all-commits --cloud --dry` честно предупредил: `Some of the cache files do not
exist neither locally nor on remote`. Выходы стадий можно пересчитать, сырые данные — нет.

Флаги области: `--workspace` (оставить только текущее), `--all-branches`, `--all-tags`, `--all-commits`,
`--all-experiments`; `--cloud` чистит ещё и удалённое хранилище — всегда сначала с `--dry`.

## 11. DVC, пайплайн из практики 7.1.4 и оркестратор

| Этап практики 7.1.4 | В проекте с DVC |
|---|---|
| `extract` — выгрузка партиций | вне `dvc.yaml`: результат зависит от внешнего мира. Выгруженное фиксируется `dvc add data/raw` |
| `validate` | часть стадии `prepare` или отдельная стадия: упала — следующие не выполняются |
| `train`, `evaluate` | стадии с `deps`, `params`, `outs`, `metrics` |
| `publish` — реестр моделей | вне DVC: реестр и псевдонимы — урок 7.2.2 |
| `metadata.json`: хеш данных, параметры | `dvc.lock` |
| идемпотентность повторного запуска | `dvc repro` ничего не выполняет, если ничего не изменилось |

DVC и оркестратор отвечают на разные вопросы:

| | DVC | Оркестратор (Airflow, урок 7.1.2) |
|---|---|---|
| Главный вопрос | из чего получен этот файл и нужно ли его пересчитывать | когда и где запускать, что делать при сбое |
| Единица | стадия: команда + зависимости + выходы | задача с расписанием, повторами, уведомлениями |
| Расписание, backfill, повторы | нет | есть |
| Кэш результатов, версии данных | есть | нет |
| Где живёт | в репозитории исследователя, рядом с кодом | на сервере, один на команду |

Они сочетаются: задача оркестратора выполняет `dvc pull && dvc repro && dvc push`, а исследователь
получает те же данные и ту же модель командой `dvc pull`. В ежедневных производственных пайплайнах
версию данных чаще задают партицией по дате в объектном хранилище, а DVC оставляют исследовательским
репозиториям, где версий мало, а вопросов «на чём это обучено» много.

**CI.** Проверка pull request в проекте с DVC — те же команды, что выполнялись в уроке по отдельности:

```bash
uv sync --locked
uv run dvc pull                  # данные и выходы стадий из хранилища
uv run dvc repro                 # пересчитает только то, что изменил автор
git diff --exit-code dvc.lock    # автор забыл закоммитить результаты — проверка не пройдёт
uv run dvc metrics diff main --md
```

Сам конвейер CI в уроке не запускался: в среде подготовки нет сервера CI. Учётные данные хранилища
конвейер получает из секретов CI — как в уроке 1.1.2.

## 12. Хранилища и права

> Раздел не проверялся запуском: в среде подготовки нет облачного хранилища. Имена команд и параметров —
> по документации DVC.

Для облака меняются только адрес и способ аутентификации; `add`, `push`, `pull`, `checkout` остаются
прежними. Поддержка протокола ставится дополнением пакета — в установке из урока, судя по `dvc doctor`,
есть только `http` и `https`:

```bash
uv add "dvc[s3]"                                        # также gs, azure, ssh
uv run dvc remote add -d storage s3://my-bucket/dvc-storage
uv run dvc remote modify --local storage access_key_id <ключ>      # пишется в .dvc/config.local
uv run dvc remote modify --local storage secret_access_key <секрет>
```

- `.dvc/config` — в Git, в нём только адрес. `.dvc/config.local` — в `.gitignore`, в нём секреты. Ещё
  лучше не хранить ключи в файлах вовсе: DVC использует стандартные способы аутентификации облака
  (переменные окружения, профиль, роль машины).
- Права на данные — это права на бакет: читать версии может тот, у кого есть доступ на чтение. Доступ
  к репозиторию Git данных не открывает — и это свойство, а не недостаток.
- Удобная схема: исследователи — чтение и запись, CI — чтение, удаление (`gc --cloud`) — только
  у владельца хранилища.

## 13. Альтернативы

Без запуска — для ориентира при выборе:

| Подход | Идея | Сильная сторона | Ограничение |
|---|---|---|---|
| DVC | хеши в Git, содержимое в кэше и хранилище; стадии и кэш запусков | версия данных привязана к коммиту кода; работает с любым хранилищем | две команды вместо одной; мелких файлов много — медленно |
| Git LFS | большие файлы заменяются указателями, содержимое — на LFS-сервере | прозрачно: обычные `git add` и `git push` | нужен LFS-сервер и квота; нет пайплайнов и кэша запусков |
| lakeFS | ветки и коммиты поверх объектного хранилища | версионируется озеро данных целиком, без копирования | отдельный сервис, который нужно сопровождать |
| Версии в путях бакета | `s3://bucket/sales/date=2024-06-30/`, партиции не изменяются | просто, понятно оркестратору | «исправление задним числом» ломает схему; связь с кодом — только по соглашению |
| Хранилище признаков | признаки с метками времени, выборка «на момент» | согласованность обучения и применения (тема 7.3) | версионирует признаки, а не произвольные файлы и модели |

## Типичные ошибки

| Симптом | Причина | Решение |
|---|---|---|
| Репозиторий весит гигабайты, `git clone` идёт минуты | данные закоммичены в Git до `dvc add` | `git rm -r --cached data/raw`, затем `dvc add`; из истории файл уберёт только её переписывание (урок 1.1.2) |
| `dvc add` отказывается: файл уже отслеживается Git | то же | сначала `git rm --cached`, затем `dvc add` |
| У коллеги `dvc pull`: `Missing cache files`, `Checkout failed` | сделан `git push` без `dvc push` | `dvc status -c` перед отправкой; `dvc install`; проверка в CI |
| `Permission denied` при записи в файл данных | `cache.type` — `hardlink` или `symlink`, файл защищён | `dvc unprotect <файл>` или заменить файл целиком |
| После смены ветки код новый, а данные старые | `git checkout` без `dvc checkout` | выполнять обе команды; `dvc install` |
| `dvc repro` не пересчитывает стадию после изменения кода | изменённый модуль не указан в `deps` | перечислить в `deps` весь код, от которого зависит стадия |
| Стадия выдаёт устаревший результат «из кэша» | стадия читает то, чего нет в `deps`: дату, сеть, другой файл | сделать вход явным: параметр или зависимость; для внешних шагов — `dvc add` результата |
| `dvc add` и `dvc push` идут часами | сотни тысяч мелких файлов: хеш и запрос к хранилищу на каждый | укрупнить: партиции по дням, а не по строкам; архив или Parquet вместо россыпи файлов |
| `dvc pull` на старом коммите: `No default remote set` | remote настроен позже этого коммита | `git checkout <коммит> -- <файл>.dvc` и `dvc pull <файл>.dvc`; настраивать remote первым коммитом |
| После `dvc gc` старая версия не восстанавливается | она не была отправлена в хранилище | перед `gc`: `dvc push` и `dvc status -c`; `--dry` перед настоящим запуском |
