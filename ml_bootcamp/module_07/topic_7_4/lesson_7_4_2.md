# Урок 7.4.2: Docker контейнеризация, Kubernetes deployment

> **Модуль 7:** ML Engineering & MLOps · **Тема 7.4:** Деплой и мониторинг
> **Тип:** теория · **Время:** 120 минут + 90 минут на домашнее задание

## Цели урока

После урока вы сможете:

- собрать образ сервиса предсказаний: с проверкой здоровья, без root и с корректной остановкой;
- объяснить, почему форма записи `CMD` решает, сколько длится остановка контейнера;
- подобрать ограничения процессора и памяти по замерам и предсказать, что будет при их нарушении;
- описать сервис в Kubernetes: Deployment, Service, ConfigMap, Secret;
- настроить три проверки (startup, readiness, liveness) и рассказать, что делает кластер при отказе каждой;
- обновить сервис без потери запросов, увидеть остановившуюся выкладку и откатить её;
- включить автоматическое масштабирование по загрузке процессора;
- проверить манифесты без кластера.

## Зачем это нужно

Сервис из урока 7.4.1 работает, пока открыт терминал, в котором его запустили. Чтобы он работал всегда,
кто-то должен запускать его на сервере, перезапускать после сбоя, держать несколько экземпляров,
заменять их при выходе новой версии — и не терять при этом запросы. Образ Docker отвечает на вопрос
«что запускать», Kubernetes — на вопросы «где, сколько и что делать, когда что-то пошло не так».

Основы Docker — в уроке 1.1.3 (слои, кэш, Compose), воспроизводимый образ — в уроке 7.2.3 (digest,
этап зависимостей, `USER`, секреты, метки). Здесь они не повторяются: урок начинается с того, чем образ
**сервиса** отличается от образа обучения.

Версии урока: Docker 29.9.2, образ `python:3.12-slim` (Python 3.12.13), `uv 0.11.32`; Kubernetes —
`k3s v1.34.1+k3s1`; пакеты сервиса — как в уроке 7.4.1; машина — 4 ядра x86-64, 16 ГБ памяти.

## 1. Образ сервиса

Проект сервиса: `app.py`, `pyproject.toml`, `uv.lock`, `.python-version` и каталог `model/` из урока 7.4.1.
В зависимостях — только то, что нужно для ответа на запрос: `fastapi`, `uvicorn[standard]`, `pandas`,
`scikit-learn`, `joblib`; `pytest` и `httpx2` — в группе `dev`.

```dockerfile
FROM python:3.12-slim@sha256:5e2bdb1b0d542d5039cffb8181c65930093949194a65c365dfb1b0fe13a4fa5b AS base
ENV PYTHONUNBUFFERED=1 PYTHONDONTWRITEBYTECODE=1


FROM base AS deps
COPY --from=ghcr.io/astral-sh/uv:0.11.32 /uv /bin/uv
ENV UV_LINK_MODE=copy UV_PYTHON_DOWNLOADS=never
WORKDIR /app
COPY pyproject.toml uv.lock .python-version ./
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --locked --no-dev --no-install-project


FROM base AS runtime
RUN useradd --create-home --uid 1000 app
WORKDIR /app
COPY --from=deps /app/.venv /app/.venv
ENV PATH="/app/.venv/bin:$PATH" MODEL_DIR=/app/model OMP_NUM_THREADS=1
COPY app.py ./
COPY model/ ./model/
ARG GIT_COMMIT=unknown
ARG MODEL_VERSION=unknown
LABEL org.opencontainers.image.revision=$GIT_COMMIT \
      ml.model-version=$MODEL_VERSION
USER app
EXPOSE 8000
HEALTHCHECK --interval=10s --timeout=2s --start-period=15s --retries=3 \
    CMD ["python", "-c", "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/health', timeout=1)"]
CMD ["uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8000"]
```

```bash
docker build -t sales-service:1.0.0 --build-arg GIT_COMMIT=$(git rev-parse --short HEAD) \
  --build-arg MODEL_VERSION=3 .
```

Сборка заняла 16 секунд, образ — 562 МБ на диске (127 МБ в сжатом виде, столько уйдёт в реестр).
В среде подготовки образ собирался через прокси: в копию Dockerfile были добавлены сертификат
и `--network host`; показанный Dockerfile отличается от проверенного только этим.

Первые два этапа — из урока 7.2.3. Что добавлено для сервиса:

| Строка | Зачем |
|---|---|
| `--host 0.0.0.0` | по умолчанию uvicorn слушает `127.0.0.1` — внутри контейнера это адрес, недоступный снаружи |
| `CMD [...]` в форме списка | процесс сервера получает сигналы остановки напрямую — раздел 3 |
| `HEALTHCHECK` на Python | в `python:3.12-slim` нет `curl`; ставить пакет ради проверки — лишний слой и лишняя уязвимость |
| `OMP_NUM_THREADS=1` | по замерам урока 7.4.1: потоки OpenMP на маленьких запросах только мешают — раздел 4 |
| `COPY model/` | модель — часть образа: версия образа однозначно задаёт и код, и модель |
| `ml.model-version` | по метке видно, какая модель внутри, без запуска контейнера |
| `EXPOSE 8000` | документация: порт не публикуется, пока нет `-p` |

`docker history` показывает, из чего состоит образ: слой окружения — 300 МБ, модель — 319 КБ, код —
16 КБ. При смене модели или кода пересобираются и передаются только два последних слоя.

**Модель в образе или отдельно?** Модель в образе — простой и надёжный вариант: откат образа откатывает
и модель. Он перестаёт подходить, когда модель весит гигабайты или обновляется чаще кода; тогда образ
содержит только код, а модель скачивается при старте из реестра моделей (урок 7.2.2) либо подключается
томом. Платой становится зависимость старта от внешнего хранилища — и тем важнее различать «жив» и «готов».

## 2. Запуск и проверка здоровья

```bash
docker run -d --name sales -p 127.0.0.1:8000:8000 sales-service:1.0.0
docker inspect --format '{{.State.Health.Status}}' sales
```

Опрос раз в секунду после запуска — статус контейнера и код ответа `/ready`:

```text
19:43:22 starting 000        (4 секунды: процесс стартует, порт ещё не слушается)
19:43:26 starting 200        (2 секунды: сервис отвечает, проверка здоровья ещё не выполнялась)
19:43:28 healthy 200
```

Сервис готов через 4 секунды: столько занимают импорт `pandas` и `scikit-learn` и чтение модели.
У `HEALTHCHECK` три состояния: `starting`, `healthy`, `unhealthy`. В течение `--start-period` неудачные
проверки не считаются — это время на загрузку модели; для модели, которая грузится минуту, его нужно
увеличить, иначе контейнер будет признан больным раньше, чем успеет подняться.

```bash
docker exec sales sh -c 'id; touch /app/x; which uv curl || echo "uv, curl: нет"'
docker stats --no-stream --format '{{.MemUsage}}' sales
docker inspect --format '{{json .Config.Labels}}' sales
```

```text
uid=1000(app) gid=1000(app) groups=1000(app)
touch: cannot touch '/app/x': Permission denied
uv, curl: нет
149.1MiB / 15.71GiB
{"ml.model-version":"3","org.opencontainers.image.revision":"e1ee574"}
```

Сервис работает не от root, в свой каталог писать не может, инструментов сборки в образе нет. Ему и
не нужно писать: с `docker run --read-only` контейнер стартовал и ответил `200` на `/ready`. Простаивающий
сервис занимает 149 МБ памяти — это отправная точка для ограничений в разделе 4.

**`HEALTHCHECK` знает один вопрос.** Контейнер, запущенный с `-e MODEL_DIR=/nonexistent`:

```text
docker inspect …  -> healthy
GET /ready        -> 503 {"detail":"модель не загружена"}
```

Docker считает контейнер здоровым, а сервис не может ответить ни на один запрос. Проверка в Dockerfile
обращается к `/health` — «процесс жив». Если направить её на `/ready`, получится другая ошибка: Docker
(в режиме Swarm) и многие облачные сервисы перезапускают «больной» контейнер, а перезапуск не вернёт
отсутствующую модель. Два вопроса требуют двух проверок; в Docker проверка одна, в Kubernetes их три —
раздел 7.

## 3. Остановка: кто получает сигнал

`docker stop` посылает главному процессу контейнера (PID 1) сигнал `SIGTERM`, ждёт 10 секунд и посылает
`SIGKILL`. Uvicorn по `SIGTERM` перестаёт принимать соединения, дожидается текущих запросов и выходит.
Но только если сигнал дошёл до него.

| Запуск | PID 1 | `docker stop` | Код выхода |
|---|---|---|---|
| `CMD ["uvicorn", "app:app", …]` | `uvicorn` | 0.6 с | 0 |
| `CMD uvicorn app:app …` (строкой) | `sh -c uvicorn app:app …` | 10.1 с | 137 |

Команда, записанная строкой, выполняется через `/bin/sh -c`. PID 1 — оболочка; `SIGTERM` она дочернему
процессу не передаёт. Десять секунд ничего не происходит, затем всё убивается (137 = 128 + 9, `SIGKILL`):
запросы, которые в этот момент обрабатывались, обрываются. В журнале первого варианта есть строки
`Shutting down`, `Waiting for application shutdown`, `Application shutdown complete`. У второго варианта этих строк нет. При каждой выкладке новой версии старые контейнеры останавливаются —
и от этой детали зависит, потеряет ли потребитель запросы (раздел 8).

## 4. Ресурсы под нагрузкой

Контейнер без ограничений может занять все ядра и всю память машины. Ограничения задаются при запуске:
`--cpus 1 --memory 512m`. Замер — клиент из урока 7.4.1, `/predict`, 4 000 запросов от 16 клиентов:

| Запуск | p50, мс | p99, мс | Запросов/с | Память |
|---|---|---|---|---|
| без ограничений, 1 воркер | 105.5 | 189.4 | 148 | 136 МБ |
| `--cpus 1`, 1 воркер | 116.2 | 224.6 | 133 | 135 МБ |
| `--cpus 1`, `-e OMP_NUM_THREADS=4` | 276.9 | 407.3 | 59 | 138 МБ |
| `--cpus 1`, 4 воркера (`--workers 4`) | 98.6 | 292.9 | 148 | 557 МБ |
| без ограничений, 4 воркера | 23.2 | 114.3 | 471 | 557 МБ |

Что видно:

- **один воркер использует одно ядро.** Ограничение в одно ядро почти ничего не изменило: 133 запроса
  в секунду против 148. Давать такому контейнеру четыре ядра бессмысленно;
- **ограничение процессора — это квота времени, а не число видимых ядер.** Библиотека внутри контейнера
  по-прежнему видит четыре ядра и создаёт четыре потока OpenMP. Вчетвером они расходуют квоту вчетверо
  быстрее, и до конца периода контейнер стоит: 59 запросов в секунду, а от одного клиента p95 вырос
  с 8.6 до 71 мс. Поэтому `OMP_NUM_THREADS=1` записан в образе;
- **четыре воркера на одном ядре** дают ту же пропускную способность, что один, и вчетверо больше памяти.
  Число воркеров должно соответствовать ограничению процессора;
- **четыре воркера на четырёх ядрах** — 471 запрос в секунду и 557 МБ.

Отсюда два способа масштабирования: больше воркеров в одном контейнере или больше контейнеров по одному
воркеру. Второй принят в Kubernetes: каждый экземпляр мал и одинаков, число экземпляров меняется
снаружи, а отказ одного забирает четверть мощности, а не всю.

**Память.** Процессорное ограничение замедляет, ограничение памяти убивает:

```bash
docker run -d --name tiny --memory 64m sales-service:1.0.0
docker inspect --format 'status={{.State.Status}} oom={{.State.OOMKilled}} exit={{.State.ExitCode}}' tiny
# status=exited oom=true exit=137
```

Сервису нужно 135–150 МБ; с 64 МБ ядро системы убило процесс при загрузке библиотек. В журнале контейнера
при этом пусто: процесс не успел ничего сообщить. Признак — `OOMKilled=true` и код 137. Ограничение памяти
выбирают по замеру под нагрузкой с запасом, а не по среднему.

## 5. Kubernetes: что добавляется к образу

Kubernetes принимает описание желаемого состояния («два экземпляра этого образа, доступные по такому-то
имени») и непрерывно приводит к нему действительное. Объекты, которые нужны сервису:

| Объект | За что отвечает | Аналог в Docker |
|---|---|---|
| Pod | один экземпляр: контейнер и его окружение | контейнер |
| Deployment | сколько подов, из какого образа, как их заменять | `docker run` в цикле и скрипт выкладки |
| Service | постоянное имя и адрес для набора подов, распределение запросов | `-p` и балансировщик |
| ConfigMap | несекретные настройки | `-e`, файл `.env` |
| Secret | секретные настройки | `-e` из защищённого хранилища |
| HorizontalPodAutoscaler | число подов по нагрузке | — |

> **Как это проверено.** Облачного кластера в среде подготовки нет. Все команды и выводы разделов 6–10
> получены на одноузловом `k3s v1.34.1`, запущенном в контейнере Docker на той же машине. Образы сервиса
> переданы в кластер импортом (`docker save` и `ctr images import`), а не через реестр.
> **Не проверялось запуском:** загрузка образа из реестра и `imagePullSecrets`, Ingress и внешний
> балансировщик, поведение на нескольких узлах, управляемые кластеры облачных провайдеров. Замеры
> пропускной способности сделаны на машине, где работают и кластер, и клиент нагрузки.

## 6. Deployment, Service, ConfigMap, Secret

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: sales-service
  labels:
    app: sales-service
spec:
  replicas: 2
  selector:
    matchLabels:
      app: sales-service
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  template:
    metadata:
      labels:
        app: sales-service
    spec:
      terminationGracePeriodSeconds: 30
      securityContext:
        runAsNonRoot: true
        runAsUser: 1000
      containers:
        - name: service
          image: sales-service:1.0.0
          imagePullPolicy: IfNotPresent
          ports:
            - name: http
              containerPort: 8000
          envFrom:
            - configMapRef:
                name: sales-service-config
          env:
            - name: FEATURE_STORE_TOKEN
              valueFrom:
                secretKeyRef:
                  name: sales-service-secret
                  key: feature-store-token
          resources:
            requests:
              cpu: 250m
              memory: 256Mi
            limits:
              cpu: "1"
              memory: 512Mi
          startupProbe:
            httpGet:
              path: /health
              port: http
            periodSeconds: 2
            failureThreshold: 30
          readinessProbe:
            httpGet:
              path: /ready
              port: http
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 2
          livenessProbe:
            httpGet:
              path: /health
              port: http
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
          lifecycle:
            preStop:
              sleep:
                seconds: 5
```

Остальные три объекта (в файлах `service.yaml`, `configmap.yaml`, `secret.yaml`; служебные строки
`apiVersion: v1` и `metadata.name` опущены):

```yaml
kind: Service                        # имя sales-service
spec:
  type: NodePort                     # доступ снаружи через порт узла; внутри кластера хватит ClusterIP
  selector:
    app: sales-service               # запросы идут подам с этой меткой — и только готовым
  ports:
    - name: http
      port: 80
      targetPort: http
      nodePort: 30080
---
kind: ConfigMap                      # имя sales-service-config
data:
  MODEL_DIR: /app/model
  OMP_NUM_THREADS: "1"               # значения ConfigMap — всегда строки
---
kind: Secret                         # имя sales-service-secret
type: Opaque
stringData:
  feature-store-token: replace-me    # настоящее значение в Git не хранится
```

```bash
kubectl apply -f k8s/
kubectl rollout status deployment/sales-service
kubectl get pods -o wide
```

```text
deployment "sales-service" successfully rolled out                      (через 7 секунд после apply)
NAME                             READY   STATUS    RESTARTS   AGE   IP          NODE
sales-service-58858dd4bf-2txjl   1/1     Running   0          6s    10.42.0.4   f903dcda869b
sales-service-58858dd4bf-d459j   1/1     Running   0          6s    10.42.0.5   f903dcda869b

$ curl -s -X POST http://127.0.0.1:30080/predict -H 'Content-Type: application/json' -d '{…}'
{"units":16.524,"model_version":"3","warnings":[]}
```

**Ресурсы.** `requests` — сколько под гарантированно получит; по ним планировщик выбирает узел, от них
считает проценты автомасштабирование. `limits` — потолок: превышение по процессору замедляет, по памяти —
убивает (раздел 4). Числа взяты из замеров: 135 МБ в работе — запрос 256 МБ, предел 512 МБ; один воркер —
предел в одно ядро. `kubectl top pods` показал 133 МБ на под в покое.

**ConfigMap и Secret.** Настройки попадают в контейнер переменными окружения — так же, как в `docker run -e`.
Secret — не шифрование:

```bash
kubectl get secret sales-service-secret -o jsonpath='{.data.feature-store-token}'             # cmVwbGFjZS1tZQ==
kubectl get secret sales-service-secret -o jsonpath='{.data.feature-store-token}' | base64 -d # replace-me
```

Это base64: прочитать значение может любой, у кого есть право читать объект. От ConfigMap секрет
отличается правилами доступа и тем, что не печатается в `kubectl describe`. Манифест с настоящим
значением в Git не кладут; в кластер его доставляет отдельный инструмент (не рассматривается в уроке).

**Безопасность.** `runAsNonRoot` запрещает запуск образа, который работает от root; `readOnlyRootFilesystem`
делает файловую систему контейнера неизменяемой. Проверено: в поде недоступен для записи и `/tmp`.
Сервису из урока запись не нужна; если библиотеке понадобится временный каталог, его подключают
отдельным томом `emptyDir`.

## 7. Три проверки

| Проверка | Вопрос | При отказе | В манифесте |
|---|---|---|---|
| `startupProbe` | контейнер уже запустился? | ждать; после исчерпания попыток — перезапуск | `/health`, до 60 с |
| `readinessProbe` | можно направлять запросы? | убрать под из Service, не трогая контейнер | `/ready`, 2 отказа по 5 с |
| `livenessProbe` | процесс не завис? | перезапустить контейнер | `/health`, 3 отказа по 10 с |

Пока `startupProbe` не прошла, две другие не выполняются: медленный старт не будет принят за зависание.

Опыт: процесс сервиса в одном из двух подов заморожен сигналом `SIGSTOP` — он есть, но не отвечает.

```text
20:04:27  процесс заморожен
20:04:33  READY 1/1   под в Service
20:04:43  READY 0/1   под убран из Service: две проверки готовности не прошли
20:04:52  Liveness probe failed (x3) … Container service failed liveness probe, will be restarted
20:05:25  RESTARTS 1  контейнер перезапущен
20:05:31  READY 1/1   под снова в Service
```

Запросы перестали попадать на зависший под через 11–16 секунд (опрос шёл раз в 5 секунд), контейнер
перезапущен через 58 секунд после заморозки. Из них полминуты — `terminationGracePeriodSeconds`:
замороженный процесс не ответил на `SIGTERM`, и кластер ждал положенный срок, прежде чем убить его. Всё
это время запросы обслуживал второй под: при `replicas: 1` сервис был бы недоступен минуту.

Что проверки говорят о сервисе из урока 7.4.1: обработчик `async def` с моделью внутри отвечал
на `/health` за 0.5–1.4 секунды под нагрузкой. При `timeoutSeconds: 2` это ещё проходит; при таймауте
в секунду (значение по умолчанию) кластер перезапускал бы здоровые поды под нагрузкой — в тот момент,
когда они нужнее всего.

## 8. Обновление без простоя и откат

Новая версия — образ `sales-service:1.1.0` с моделью версии 4. Во время выкладки четыре клиента
непрерывно отправляют запросы и записывают версию модели из ответа либо ошибку.

```bash
kubectl set image deployment/sales-service service=sales-service:1.1.0
kubectl rollout status deployment/sales-service
```

```text
  0-5   с: {'v3': 682}
  5-10  с: {'v3': 726}              <- на 8-й секунде: kubectl set image
 10-15  с: {'v3': 677}
 20-25  с: {'v3': 506}              <- на 21-й секунде: rollout status сообщил об успехе
 25-30  с: {'v3': 87, 'v4': 563}
 30-35  с: {'v4': 713}
всего: {'v3': 3340, 'v4': 2005} самый долгий запрос 101 мс
```

Ни одной ошибки на 5 345 запросов. Что для этого сделано в манифесте:

- `maxUnavailable: 0`, `maxSurge: 1` — сначала поднимается новый под, и только когда он готов,
  останавливается старый: готовых подов никогда не меньше двух;
- `readinessProbe` — «готов» означает «модель загружена», а не «контейнер запущен»;
- `CMD` в форме списка — uvicorn получает `SIGTERM` и завершает начатые запросы (раздел 3);
- `preStop: sleep 5` — пауза перед `SIGTERM`: за это время сведения о том, что под выводится из работы,
  доходят до всех, кто направляет на него запросы.

Последний пункт проверен отдельно: четыре выкладки с `preStop` и четыре без него.

| Манифест | Выкладок | Запросов | Ошибок |
|---|---|---|---|
| с `preStop: sleep 5` | 4 | 18 590 | 0 |
| без `preStop` | 4 | 18 018 | 7 (по выкладкам: 2, 0, 4, 1) |

Ошибки — `ReadError` и `RemoteProtocolError`: соединение закрыто, пока клиент отправлял запрос. Семь
запросов из восемнадцати тысяч — это 0.04 %; заметит ли их потребитель, зависит от того, повторяет ли он
запросы. Клиенты продолжали получать ответы старой версии ещё несколько секунд после сообщения об успехе:
постоянные соединения живут, пока старый под не остановлен.

**Откат.** Каждое изменение шаблона пода создаёт ревизию; список показывает
`kubectl rollout history deployment/sales-service`, возврат к предыдущей —
`kubectl rollout undo deployment/sales-service` (к указанной — с `--to-revision=N`; этот вариант
в уроке не выполнялся).

Откат — та же постепенная замена подов, только на прежний шаблон. Образ 1.0.0 никуда не делся, поэтому
откат занимает секунды; пересборки не требуется (сравните с псевдонимом `champion` в уроке 7.2.2).

**Остановившаяся выкладка.** В ConfigMap внесена ошибка — путь к несуществующему каталогу модели:

```bash
kubectl patch configmap sales-service-config -p '{"data":{"MODEL_DIR":"/nonexistent"}}'
```

Через 20 секунд в работающем поде `MODEL_DIR` по-прежнему `/app/model`, а `/ready` отвечает `200`.
Изменение ConfigMap не перезапускает поды: переменные окружения читаются при старте контейнера. Новое
значение применяет перезапуск:

```bash
kubectl rollout restart deployment/sales-service
kubectl rollout status deployment/sales-service --timeout=40s
```

```text
Waiting for deployment "sales-service" rollout to finish: 1 out of 2 new replicas have been updated...
error: timed out waiting for the condition
NAME                             READY   STATUS    RESTARTS   AGE
sales-service-58858dd4bf-bj854   1/1     Running   0          68s
sales-service-58858dd4bf-cflhx   1/1     Running   0          75s
sales-service-66b8f6766-ptdvx    0/1     Running   0          41s

$ kubectl logs sales-service-66b8f6766-ptdvx
модель не загружена: FileNotFoundError(2, 'No such file or directory')
```

Новый под запущен, но не готов; оба старых работают, `/ready` через Service отвечает `200`. Выкладка
остановилась на первом же поде и не тронула остальные — это работа `readinessProbe` и `maxUnavailable: 0`.
Потребители ничего не заметили. Если бы `/ready` отвечал `200` без модели (урок 7.4.1), кластер заменил бы
оба пода на неработающие.

`kubectl rollout undo` убрал неготовый под. Но ConfigMap остался испорченным: откат возвращает шаблон
пода, а не объекты, на которые он ссылается. Любой следующий перезапуск снова получил бы неверный путь.
ConfigMap исправляют отдельно; надёжнее — давать ему новое имя при каждом изменении (`…-config-v2`)
и менять ссылку в Deployment: тогда настройки откатываются вместе с шаблоном.

Команда `kubectl rollout status` с таймаутом завершается с ненулевым кодом — её и ставят в скрипт
выкладки, чтобы тот не сообщил об успехе при остановившейся замене.

## 9. Автомасштабирование

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: sales-service
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: sales-service
  minReplicas: 2
  maxReplicas: 5
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 60
```

Цель — средняя загрузка процессора 60 % **от `requests`** (250m), то есть 150m на под. Без `requests`
в Deployment автомасштабирование не работает: проценты считать не от чего. Данные о потреблении
поставляет `metrics-server`; в k3s он установлен сразу.

Нагрузка — 16 клиентов, 60 000 запросов; состояние каждые 15 секунд:

```text
t=15   cpu: 0%/60%    replicas=2     (метрики запаздывают)
t=31   cpu: 135%/60%  replicas=2     готовых подов уже 5
t=46   cpu: 330%/60%  replicas=5
t=185  cpu: 153%/60%  replicas=5
t=200  нагрузка закончилась
t=277  cpu: 0%/60%    replicas=5     готовых подов 2
t=292  cpu: 0%/60%    replicas=2
Normal  SuccessfulRescale  New size: 5; reason: cpu resource utilization (percentage of request) above target
Normal  SuccessfulRescale  New size: 2; reason: All metrics below target
```

Число подов выросло с 2 до 5 примерно за 30 секунд и вернулось к 2 через 75 секунд после конца нагрузки
(`stabilizationWindowSeconds: 60` не даёт сокращать число подов при каждом кратком спаде). Загрузка так
и осталась выше цели — 153 %: достигнут `maxReplicas`. Это сигнал, а не норма: либо мал потолок, либо
мал запрос ресурсов.

Сколько дают реплики на этой машине (16 клиентов, 6 000 запросов, автомасштабирование выключено):

| Реплик | p50, мс | p99, мс | Запросов/с |
|---|---|---|---|
| 2 | 47.6 | 106.6 | 312 |
| 4 | 25.5 | 80.2 | 557 |

Автомасштабирование отвечает на рост нагрузки за десятки секунд, а не мгновенно: метрики собираются
с задержкой, поду нужно время на старт (здесь 4 секунды; для большой модели — минуты). Всплеск короче
этого времени оно не сгладит: для него нужен запас в `minReplicas`.

## 10. Проверка манифестов без кластера

Ошибку в YAML лучше найти до `kubectl apply`. Два способа, оба выполнены:

```bash
uvx kubernetes-validate@1.37.0 -k 1.34.0 --strict k8s/*.yaml       # по схеме, кластер не нужен
kubectl apply --dry-run=server -f k8s/                             # сервер кластера, без изменений
```

Оба способа приняли все пять файлов (`deployment.yaml passed for resource deployment/sales-service against
version 1.34`, `deployment.apps/sales-service created (server dry run)`). Манифест с двумя намеренными
ошибками — `replicas: two` и `containerPorts` вместо `containerPort`:

```text
ERROR bad_deployment.yaml did not validate for resource deployment/sales-service against version 1.34:
spec.replicas: 'two' is not of type 'integer', 'null'
```

Проверка по схеме сообщила о первой ошибке и остановилась: после исправления её запускают снова. Схема
ловит опечатки и неверные типы, но не смысл: ссылку на несуществующий ConfigMap, порт, который никто
не слушает, образ, которого нет в реестре, покажет только запуск.

## Типичные ошибки

| Симптом | Причина | Решение |
|---|---|---|
| Контейнер запущен, `curl` снаружи: `Connection reset` | uvicorn слушает `127.0.0.1` | `--host 0.0.0.0` |
| `docker stop` длится 10 секунд, код выхода 137, запросы обрываются | `CMD` записан строкой: PID 1 — оболочка | `CMD ["uvicorn", …]` |
| Контейнер `healthy`, а сервис отвечает 503 | проверка здоровья обращается к `/health` и не знает о модели | в Docker — принять; в Kubernetes — `readinessProbe` на `/ready` |
| `HEALTHCHECK` всегда `unhealthy` | в образе нет `curl` | проверка средствами Python |
| Под перезапускается при старте, в журнале ничего | модель не успевает загрузиться до проверки живости | `startupProbe` с запасом по времени |
| `OOMKilled`, код 137, журнал пуст | предел памяти меньше потребления | замерить под нагрузкой; увеличить `limits.memory` |
| Задержка скачет при малой загрузке процессора | потоков больше, чем ядер в квоте | `OMP_NUM_THREADS` и число воркеров — по `limits.cpu` |
| Четыре воркера в поде с пределом в одно ядро | число воркеров не согласовано с пределом | один воркер на под, масштабировать репликами |
| При выкладке потребители получают ошибки соединения | под получает `SIGTERM`, пока на него ещё идут запросы | `preStop` с паузой; `maxUnavailable: 0` |
| Выкладка «успешна», а сервис не работает | `/ready` отвечает 200 без модели или проверки готовности нет | `readinessProbe` на настоящую готовность |
| ConfigMap изменён, поведение прежнее | переменные окружения читаются при старте пода | `kubectl rollout restart` или новое имя ConfigMap |
| После `rollout undo` ошибка возвращается | откат не затрагивает ConfigMap и Secret | исправить объект; версионировать настройки именем |
| `HPA`: `cpu: <unknown>/60%` | нет `requests.cpu` или нет `metrics-server` | задать `requests`; проверить `kubectl top pods` |
| Секрет виден в репозитории | манифест Secret с настоящим значением закоммичен | значение — вне Git; заменить скомпрометированный секрет |
