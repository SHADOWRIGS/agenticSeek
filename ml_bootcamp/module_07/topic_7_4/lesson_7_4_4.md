# Урок 7.4.4: ПРАКТИКА: Деплой ML сервиса в облако

> **Модуль 7:** ML Engineering & MLOps · **Тема 7.4:** Деплой и мониторинг
> **Тип:** практика · **Время:** 7–9 часов

## Задача

У проекта прогноза продаж есть пайплайн (практика 7.1.4), запись о каждом обучении и реестр моделей
(практика 7.2.4), хранилище признаков (практика 7.3.4). Прогноз при этом получает только тот, у кого
открыт ноутбук. Модель нужно выпустить как сервис, к которому предъявляется одно требование:

> **Потребитель получает прогноз по адресу в сети; на неверный запрос сервис отвечает отказом, а не
> числом; по ответу видно, какая модель его дала; а владелец сервиса узнаёт о сбое, о незнакомых данных
> и о сдвиге входа раньше потребителя.**

Работа состоит из двух частей.

**Код — проверяется автотестами.** Модуль `sales_service.py` из четырёх функций: каталог модели →
таблица признаков → прогнозы и предупреждения → приложение FastAPI с проверкой входа, готовностью, версией
модели и метриками. Модуль `sales_drift.py` из восьми функций: PSI, критерий Колмогорова — Смирнова,
пропуски, новые категории и отчёт по столбцам.

**Развёртывание — проверяется вами по критериям приёмки.** Образ, локальный стенд с мониторингом
и, наконец, сервис контейнеров облачного провайдера по вашему выбору.

Зачем свои функции, если FastAPI и `prometheus_client` всё умеют? Уроки темы показали места, где
поведение по умолчанию не защищает: строка `"yes"` принимается как `true`, незнакомый магазин получает
правдоподобный прогноз (7.4.1), контейнер без модели считается здоровым (7.4.2), метка с адресом запроса
плодит ряды, а p-значение на большой выборке срабатывает всегда (7.4.3). Каждое из них закрывается
функцией, поведение которой задано тестами.

## Требования

| Требование | Что это значит здесь | Как проверяется |
|---|---|---|
| Модель читается один раз | `load_model` вызывается при старте, не при создании приложения и не в запросах | `test_app_loads_model_once_at_startup` |
| «Жив» и «готов» — разные ответы | `/health` — 200 всегда; `/ready`, `/predict` — 503 без модели; испорченный каталог модели не роняет процесс | `test_app_is_alive_without_model`, `test_app_without_model_is_not_ready`, `test_load_model_*` |
| Неверный запрос не доходит до модели | границы, типы без приведения, лишние поля, размер пакета; ответ 422 называет поле | `test_app_predict_rejects_invalid_input` (21 случай), `test_app_batch_size_limits`, `test_app_batch_rejects_invalid_item_and_names_it` |
| Ответ объясняет себя | версия модели в каждом ответе; незнакомый магазин или товар — в `warnings` | `test_app_predict_returns_units_version_and_warnings`, `test_app_predict_warns_about_unknown_categories` |
| Пакет — один вызов модели | результат пакета равен одиночным запросам, порядок сохранён | `test_app_batch_matches_single_requests`, `test_app_batch_calls_model_once` |
| Сбой модели не раскрывает внутренностей | 500 с постоянным текстом; сервис продолжает работать | `test_app_model_failure_is_reported_without_details` |
| Метрики считают всё, включая отказы | 404, 422, 500, 503 учтены; `/metrics` — нет; адрес запроса не попадает в метки | `test_metrics_count_requests_by_endpoint_and_status`, `test_metrics_unknown_paths_share_one_label` |
| Метрики модели | число строк, распределение прогнозов, доля акций, незнакомые категории, версия | `test_metrics_prediction_histogram`, `test_metrics_count_unknown_categories`, `test_metrics_model_info` |
| У приложения свой реестр метрик | два приложения в одном процессе не мешают друг другу | `test_metrics_each_app_has_its_own_registry` |
| PSI задан точно | корзины по квантилям эталона, значение на границе — в левую корзину, пустые доли — `EPS` | `test_numeric_psi_matches_definition_on_random_data`, `test_numeric_psi_value_equal_to_edge_goes_to_left_bin` |
| Статус не зависит от p-значения | сдвиг в 0.05 стандартного отклонения на 50 000 строк: p < 0.001, статус `ok` | `test_report_pvalue_does_not_affect_status` |
| Малой выборке не верят | при ожидаемом шуме PSI от 0.1 статус `low_sample`; пропуски и новые категории видны всё равно | `test_report_small_sample_is_marked`, `test_report_small_sample_still_reports_missing_and_new_categories` |

## Пошаговый план

Точные требования — в docstring заготовок. Шаги 1–5 проверяются тестами, шаги 6–9 — критериями приёмки.

### Шаг 1. `load_model`, `build_frame`, `predict_rows`

Три функции без FastAPI. На что обратить внимание:

- `load_model` превращает любую причину отказа в `ModelLoadError`: нет каталога, нет файла, описание —
  не JSON или не объект, нет ключа. Наружу не должен выйти ни `FileNotFoundError`, ни `KeyError`;
- в `build_frame` типы задайте явно: `float64` для цены, `int64` для остального. Тип столбца, собранного
  из списка, зависит от содержимого списка — у строки с целой ценой и у строки с дробной он разный;
- `predict_rows` вызывает модель один раз на все строки и не трогает метрики: это чистая функция,
  её удобно проверять подделкой модели.

```bash
uv run pytest -q tests/test_sales_service.py -k "test_load_model or test_frame or test_predict_rows"
```

### Шаг 2. `create_app`: эндпоинты и проверка входа

Схемы Pydantic и обработчики — из урока 7.4.1, но приложение собирается функцией, а не на уровне
модуля: так у каждого теста своё приложение. Подводные камни:

- строгость задаётся по полям (`Field(strict=True)`, `StrictBool`): со `ConfigDict(strict=True)`
  перестают приниматься даты;
- `extra="forbid"` нужен и строке запроса, и телу пакета;
- поле называется `date` — импортируйте `datetime as dt` и пишите `date: dt.date`;
- модель берите из `request.app.state.model` в каждом запросе: тесты подменяют её на ходу;
- в `lifespan` перехватывайте только `ModelLoadError`.

```bash
uv run pytest -q tests/test_sales_service.py -k test_app
```

### Шаг 3. `create_app`: метрики

Метрики создаются внутри `create_app` с параметром `registry=...` — не на уровне модуля. Запросы
считает промежуточный обработчик (урок 7.4.3): он видит и те запросы, которые отклонила схема. Метрики
прогнозов обновляйте после успешного вызова модели, а не до него: запрос, закончившийся ошибкой 500,
не должен увеличить число выданных прогнозов.

```bash
uv run pytest -q tests/test_sales_service.py -k test_metrics
```

### Шаг 4. Метрики дрейфа

`psi_from_shares`, `numeric_psi`, `categorical_psi`, `psi_noise`, `ks_test`, `missing_share`,
`new_category_share`. Формулы — из урока 7.4.3; тесты сверяют числовой PSI с медленной реализацией
«по определению», поэтому важны детали: границы только по эталону, повторяющиеся границы объединяются,
`searchsorted` с `side="left"`, доли после замены на `EPS` заново не нормируются. Все функции возвращают
`float`, а не `numpy.float64`.

### Шаг 5. `drift_report`

Отчёт собирает метрики по столбцам и выносит статус по пяти правилам в заданном порядке. Порядок
существен: рост доли пропусков и новые категории — «сдвиг» при любом размере выборки, а PSI на малой
выборке не оценивается вовсе.

```bash
uv run python -W error -m pytest -q
```

### Шаг 6. Модель и локальный запуск

```bash

uv run python train_model.py --out model --version 3

curl -s -X POST http://127.0.0.1:8000/predict -H 'Content-Type: application/json' \

```

`champion`, её номер — в `metadata.json`. Сохраните `openapi.json` сервиса в репозиторий.

### Шаг 7. Образ и стенд в Docker

```bash
docker build -t sales-service:1.0.0 --build-arg GIT_COMMIT=$(git rev-parse --short HEAD) \
  --build-arg MODEL_VERSION=3 .
docker compose up -d
```

Проверьте по списку урока 7.4.2: контейнер работает не от root; `docker compose stop service` занимает
около секунды и завершается с кодом 0; состояние здоровья переходит в `healthy`. Затем по списку урока
7.4.3: обе цели Prometheus в состоянии `up`; под потоком запросов из данных продаж получите через HTTP API
число запросов в секунду, p95, средний прогноз и долю акций; добавьте в поток незнакомый магазин
и дождитесь `SalesUnknownCategories`. Закончив, выполните `docker compose down -v`.

### Шаг 8. Отчёт о дрейфе

Напишите `drift_job.py`: эталон — обучающая выборка с прогнозами модели, текущее окно — запросы
за период (для практики — данные `make_sales` после даты обучения или собственный генератор сдвига),
`drift_report` по столбцам `price`, `prediction`, `promo`, `store_id`, `product`, отправка PSI и времени
отчёта в Pushgateway (урок 7.4.3). Покажите срабатывание `SalesFeatureDrift` и объясните каждое.

### Шаг 9. Облако

> **Не проверялось запуском:** в среде подготовки курса нет облачных учётных записей. Шаг описан
> в терминах, общих для сервисов запуска контейнеров; точные команды — в документации выбранного
> провайдера. Всё, что шаг требует от образа и сервиса, проверено локально на шагах 6–7.

Выберите сервис, который запускает контейнер из образа и выдаёт ему адрес: управляемый сервис
контейнеров, управляемый Kubernetes или виртуальную машину с Docker. Последовательность везде одна:

1. **Реестр образов.** Создайте реестр у провайдера, пометьте образ его адресом
   (`docker tag sales-service:1.0.0 <реестр>/sales-service:1.0.0`) и отправьте (`docker push`). Тег —
   версия, а не `latest`: иначе откатываться будет не к чему.
2. **Сервис.** Образ из реестра; порт 8000; один воркер на экземпляр; ограничения по замерам урока
   7.4.2 — от 256 МБ памяти и одно ядро; не меньше двух экземпляров, если сервис это позволяет.
3. **Окружение.** `MODEL_DIR`, `OMP_NUM_THREADS=1` — переменными окружения сервиса; секреты — через
   хранилище секретов провайдера, а не в образе и не в репозитории.
4. **Проверки.** Проверка живости — `/health`, проверка готовности (если сервис их различает) — `/ready`;
   время на старт — с запасом: холодный запуск дольше тёплого (см. ориентиры).
5. **Доступ.** Адрес по HTTPS. Решите, кто может вызывать сервис: открытый адрес без проверки
   подлинности — это ещё и чужие запросы за ваш счёт.
6. **Журнал и метрики.** Найдите журнал контейнера в консоли провайдера и убедитесь, что в нём видны
   запросы и сообщение о загрузке модели. `/metrics` не должен быть доступен снаружи без ограничений.
7. **Проверка.** Запрос с вашей машины: верный, неверный (422), с незнакомым магазином. Сравните
   прогноз с локальным — он должен совпасть до последнего знака. Измерьте p50 и p95 по 200 запросам.
8. **Выкладка и откат.** Выпустите образ `1.1.0` с другой версией модели, убедитесь по `model_version`
   в ответе, что версия сменилась, и верните прежнюю.
9. **Стоимость и удаление.** До запуска найдите в тарифах, за что берётся плата: время работы
   экземпляров, хранение образов, исходящий трафик, балансировщик. После проверки удалите сервис,
   образы в реестре, сам реестр, балансировщик и выделенные адреса; через сутки проверьте в разделе
   расходов, что начисления прекратились.

Если облако недоступно, замените шаг локальным кластером Kubernetes (k3d, kind, minikube) с манифестами
из `k8s/` и критериями урока 7.4.2 — и укажите это в отчёте.

## Как оценить свою работу

| Уровень | Признаки |
|---|---|
| Базовый | все тесты проходят; сервис отвечает в контейнере; стенд собирает метрики |
| Уверенный | сервис развёрнут вне вашей машины (облако или кластер), выкладка и откат показаны; вы можете объяснить, какой тест ловит каждое из нарушений: модель читается в запросе; `"yes"` принят как `true`; метрики объявлены на уровне модуля; в метке — адрес запроса; прогноз учтён до вызова модели; значение на границе корзины отнесено вправо; статус зависит от p-значения; малая выборка получила `drift` по PSI — и к чему каждое приводит в работе |
| Продвинутый | выполнено хотя бы два задания из раздела ниже |

## Идеи для усложнения

1. **Признаки из хранилища.** Добавьте в запрос только ключи и цену, а средние продаж берите
   из онлайн-хранилища практики 7.3.4; статус свежести — в `warnings` и в метрики.
2. **Замена модели без перезапуска.** Эндпоинт или фоновая задача, которая читает новую версию
   из реестра и подменяет `app.state.model`; `sales_model_info` должен показывать одну версию.
3. **Журнал запросов.** Записывайте строки запросов и прогнозы (без блокировки обработчика) и стройте
   `drift_job.py` по настоящему журналу, а не по генератору.
4. **Мониторинг качества.** Задание, которое сопоставляет вчерашние прогнозы с фактом продаж и публикует
   смещение и MAE по срезам; оповещение на смещение, которое держится три дня.
5. **Теневая модель.** Вторая версия считает прогноз для тех же запросов, но в ответ не попадает;
   расхождение версий — в метрики. Что это стоит по времени ответа?
6. **Нагрузочный профиль.** Найдите число запросов в секунду, при котором p95 превышает 250 мс,
   для одного экземпляра и для HPA с пределом в пять; сработало ли `SalesSlowPredict`?
7. **Выкладка из CI.** Сборка образа, тесты, проверка манифестов по схеме и `kubectl rollout status`
   с таймаутом — одним сценарием; неуспешная выкладка откатывается автоматически.
8. **Эталон по сезону.** Сравнивайте окно с тем же месяцем прошлого года и покажите, как изменился
   статус столбца `prediction` в таблице ориентиров.
