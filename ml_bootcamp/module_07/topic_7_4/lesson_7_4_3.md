## Зачем это нужно

Сервис из уроков 7.4.1 и 7.4.2 развёрнут, проверки готовности проходят, запросы обслуживаются. По этим
признакам он «работает» — и будет «работать», когда начнёт отвечать втрое медленнее, когда в запросах
появится магазин, которого модель не видела, и когда спрос вырастет на пятую часть, а прогноз останется
прежним. Обычный сервис ломается с ошибкой. Модель ломается молча: код ответа 200, число правдоподобное.

Мониторинг ML-сервиса отвечает на четыре вопроса, от дешёвых к дорогим:

| Уровень | Вопрос | Откуда данные | Когда известно |
|---|---|---|---|
| Сервис | отвечает ли, как быстро, с какими ошибками | метрики процесса | через секунды |
| Вход | похожи ли запросы на то, на чём модель обучена | поля запросов | через минуты и часы |
| Выход | изменилось ли распределение прогнозов | ответы модели | через минуты и часы |
| Качество | насколько прогноз расходится с фактом | факт продаж | когда появится факт: здесь — через сутки |

## 1. Метрики в сервисе

Prometheus сам приходит к сервису за метриками: раз в несколько секунд запрашивает адрес `/metrics`
и сохраняет то, что получил. От сервиса требуется вести числа в памяти и отдавать их текстом.

```python
from prometheus_client import CONTENT_TYPE_LATEST, Counter, Gauge, Histogram, generate_latest

REQUESTS = Counter("sales_requests_total", "Запросы к сервису", ["endpoint", "status"])
DURATION = Histogram(
    "sales_request_duration_seconds",
    "Время обработки запроса",
    ["endpoint"],
    buckets=(0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5),
)
PREDICTIONS = Counter("sales_predictions_total", "Выданные прогнозы (строки)")
PREDICTED_UNITS = Histogram("sales_prediction_units", "Значения прогнозов", buckets=(1, 2, 5, 10, 20, 50, 100))
PROMO_ROWS = Counter("sales_promo_rows_total", "Строки запросов с акцией")
UNKNOWN = Counter("sales_unknown_category_total", "Строки с незнакомой категорией", ["field"])
MODEL_INFO = Gauge("sales_model_info", "Загруженная модель: значение всегда 1", ["version"])
```

Три вида метрик:

- **счётчик** (`Counter`) только растёт; из него получают скорость: запросов в секунду, долю ошибок;
- **гистограмма** (`Histogram`) раскладывает наблюдения по заранее заданным корзинам; из неё получают
  перцентили и среднее;
- **датчик** (`Gauge`) хранит текущее значение. `sales_model_info{version="3"} 1` — приём для строковых
  сведений: значение всегда 1, а версия — в метке.

Запросы считает промежуточный обработчик, который видит каждый запрос, включая отклонённые схемой:

```python
@app.middleware("http")
async def observe(request: Request, call_next):
    start = time.perf_counter()
    status = 500
    try:
        response = await call_next(request)
        status = response.status_code
        return response
    finally:
        route = request.scope.get("route")
        endpoint = route.path if route is not None else "other"  # шаблон маршрута, а не адрес запроса
        if endpoint != "/metrics":
            REQUESTS.labels(endpoint, str(status)).inc()
            DURATION.labels(endpoint).observe(time.perf_counter() - start)


@app.get("/metrics", include_in_schema=False)
def metrics() -> Response:
    return Response(generate_latest(), media_type=CONTENT_TYPE_LATEST)
```

Метрики модели обновляются там, где считается прогноз, — в `LoadedModel.predict` из урока 7.4.1:

```python
        for item, value in zip(items, units, strict=True):
            unseen = [field for field, known in self.known.items() if getattr(item, field) not in known]
            ...
            PREDICTED_UNITS.observe(float(value))
            for field in unseen:
                UNKNOWN.labels(field).inc()
        PREDICTIONS.inc(len(items))
        PROMO_ROWS.inc(sum(item.promo for item in items))
```

из пяти строк, двух запросов по несуществующим адресам и одного сбоя модели `/metrics` отдаёт (фрагмент):

```text
sales_requests_total{endpoint="/predict",status="200"} 4.0
sales_requests_total{endpoint="/predict",status="422"} 1.0
sales_requests_total{endpoint="/predict/batch",status="200"} 1.0
sales_requests_total{endpoint="other",status="404"} 2.0
sales_requests_total{endpoint="/predict",status="500"} 1.0
sales_request_duration_seconds_bucket{endpoint="/predict",le="0.005"} 2.0
sales_request_duration_seconds_bucket{endpoint="/predict",le="0.01"} 3.0
sales_request_duration_seconds_bucket{endpoint="/predict",le="+Inf"} 6.0
```

Корзины гистограммы — накопительные: `le="0.01"` считает все запросы не дольше 10 мс. Границы выбираются
под ожидаемое время ответа сервиса; что бывает при неудачном выборе — в разделе 3.

**Что из входа и выхода модели уже здесь.** Доля акций, доля незнакомых категорий и распределение
прогнозов считаются прямо в сервисе и стоят одну операцию сложения на запрос. Это самый дешёвый
мониторинг данных: он не требует хранить запросы и работает с задержкой в секунды.

## 2. Три ловушки

**Метка с неограниченным числом значений.** Каждое сочетание значений меток — отдельный временной ряд
в Prometheus. В коде выше метка `endpoint` — шаблон маршрута, а запросы мимо маршрутов получают значение
`other`: два запроса к `/nope/1` и `/nope/2` дали один ряд. Если положить в метку `request.url.path`,
число рядов будет расти с каждым новым адресом; то же случится с меткой `store_id` или `product`,
когда магазинов станут тысячи. После двух серий запросов рядов с именами `sales_*` в Prometheus — 48.

**Несколько воркеров.** Счётчики живут в памяти процесса. Сервис запущен с `--workers 2`, отправлено
200 запросов, затем `/metrics` прочитан десять раз подряд:

```text
sales_requests_total{/predict,200}: ['117.0', '83.0', '83.0', '117.0', '117.0', '117.0', '117.0', …]
```

Каждый сбор попадает в случайный воркер и видит только его счётчик: 117 или 83, но не 200. Для Prometheus
это выглядит как счётчик, который то падает, то растёт, — скорость по нему считается неверно. Выхода два:
один воркер на контейнер и масштабирование репликами (урок 7.4.2) — тогда каждый под собирается отдельно;
либо многопроцессный режим `prometheus_client` (переменная `PROMETHEUS_MULTIPROC_DIR`; в уроке
не проверялся запуском).

**Перезапуск.** После перезапуска сервиса счётчики начинаются с нуля. Функция `rate()` это учитывает:
падение счётчика она считает сбросом. Сравнивать «сырые» значения счётчика между собой нельзя.

Нагрузку создаёт скрипт: четыре клиента берут строки из данных продаж за октябрь — декабрь 2024 года
и отправляют их в `/predict`, около 33 запросов в секунду. Сначала 90 секунд обычного потока, затем
100 секунд потока со сдвигом: в 11 % строк магазин заменён на `S09`, доля акций доведена до 30 %.

Запросы PromQL выполнены через HTTP API (`/api/v1/query?query=…`) после каждой серии:

| Что | Запрос | Обычный поток | Со сдвигом |
|---|---|---|---|
| запросов в секунду | `sum by (endpoint, status) (rate(sales_requests_total[1m]))` | `/predict`, 200: 32.7 | 32.5 |
| p95 времени ответа, с | `histogram_quantile(0.95, sum by (le) (rate(sales_request_duration_seconds_bucket{endpoint="/predict"}[1m])))` | 0.0425 | 0.0429 |
| среднее время ответа, с | `sum(rate(…_sum[1m])) / sum(rate(…_count[1m]))` | 0.0176 | — |
| доля ошибок сервиса | `sum(rate(sales_requests_total{status=~"5.."}[1m])) / sum(rate(sales_requests_total[1m]))` | пусто | пусто |
| средний прогноз | `rate(sales_prediction_units_sum[1m]) / rate(sales_prediction_units_count[1m])` | 5.23 | 6.01 |
| доля акций | `rate(sales_promo_rows_total[1m]) / rate(sales_predictions_total[1m])` | 0.080 | 0.302 |
| доля незнакомых категорий | `sum by (field) (rate(sales_unknown_category_total[1m])) / scalar(rate(sales_predictions_total[1m]))` | пусто | `store_id`: 0.107 |

Что стоит заметить:

- `rate(x[1m])` — средняя скорость роста счётчика за последнюю минуту. Почти все запросы к счётчикам
  начинаются с неё;
- **сдвиг виден без единой строки кода анализа**: доля акций 0.08 → 0.30, незнакомый магазин в 10.7 % строк,
  средний прогноз 5.2 → 6.0. Время ответа и коды ответов при этом не изменились: мониторинг уровня
  «сервис» сдвига не видит;
- **«пусто» — не ноль.** Ошибок 5xx не было, ряда с таким значением метки не существует, и запрос
  возвращает пустой результат. На графике это «нет данных», а не линия на нуле; оповещение по такому
  выражению не сработает, пока не появится первая ошибка, — здесь это и требуется;
- **перцентиль из гистограммы — оценка.** Клиент измерил p50 20.9, p95 35.9 и p99 43.6 мс; из гистограммы
  получилось 17.3, 42.5 и 48.9 мс. Почти все запросы попали в корзину 25–50 мс, и внутри неё
  `histogram_quantile` считает распределение равномерным. Точность перцентиля не выше ширины корзины —
  границы стоит ставить около значений, по которым вы даёте обещания.

## 4. Оповещения

Правила — файл в репозитории рядом с кодом сервиса:

```yaml
# monitoring/alerts.yml (четыре правила из шести)
groups:
  - name: sales-service
    rules:
      - alert: SalesServiceDown
        expr: up{job="sales-service"} == 0
        for: 15s
        labels:
          severity: page
        annotations:
          summary: "Сервис прогноза не отвечает на сбор метрик"
      - alert: SalesSlowPredict
        expr: >
          histogram_quantile(0.95, sum by (le) (
            rate(sales_request_duration_seconds_bucket{endpoint="/predict"}[1m])
          )) > 0.25
        for: 30s
        labels:
          severity: ticket
      - alert: SalesUnknownCategories
        expr: >
          sum(rate(sales_unknown_category_total[1m]))
          / sum(rate(sales_predictions_total[1m])) > 0.01
        for: 30s
        labels:
          severity: ticket
      - alert: SalesFeatureDrift
        expr: sales_feature_psi > 0.25
        labels:
          severity: ticket
        annotations:
          summary: "PSI признака {{ $labels.feature }} равен {{ $value }}"
```

Ещё два — `SalesHighErrorRate` (доля 5xx выше 1 %) и `SalesDriftReportStale` (раздел 9). Файл проверяется
до запуска:

```bash
docker run --rm --entrypoint promtool -v "$PWD/monitoring:/cfg:ro" prom/prometheus:v3.16.0 \
  check config /cfg/prometheus.yml
#  SUCCESS: 1 rule files found … SUCCESS: 6 rules found
```

`for` — сколько условие должно держаться, прежде чем оповещение сработает: между «выполнилось»
и «сработало» оно находится в состоянии `pending`. Остановка сервиса (`docker compose stop service`
в 20:23:57), состояние из `/api/v1/alerts`:

```text
20:24:03  up = 0  SalesServiceDown  pending
20:24:15  up = 0  SalesServiceDown  pending
20:24:21  up = 0  SalesServiceDown  firing
```

Во время потока со сдвигом сработало `SalesUnknownCategories` со значением 0.107; после окончания потока
оно снялось само. Порог в 1 % выбран по смыслу: в обучающих данных незнакомых категорий нет вовсе.

Два уровня важности — не украшение. `page` будит дежурного: сервис недоступен, потребители получают
ошибки. `ticket` создаёт задачу на рабочий день: дрейф признака не чинится в три часа ночи. Оповещение,
на которое нельзя отреагировать действием, приучает не реагировать ни на какие.

Prometheus только вычисляет состояние оповещений. Доставку (почта, мессенджер, дежурная система),
группировку и подавление повторов выполняет Alertmanager; в уроке он не запускался.

| Панель | Запросы |
|---|---|
| Запросы в секунду по кодам ответа | `sum by (status) (rate(sales_requests_total[1m]))` |

смотрят, жив ли сервис, затем — что изменилось во входе.

> запрос `sales_feature_psi` через `/api/ds/query` вернул пять рядов с теми же значениями, что Prometheus.

## 6. Метрики дрейфа

Счётчики из раздела 1 ловят простое: новую категорию, изменившуюся долю. Сравнить распределение признака
с обучающим целиком — отдельная задача над сохранёнными запросами. Четыре числа, реализация на NumPy
и SciPy:

```python
EPS = 1e-4


def psi_from_shares(reference: np.ndarray, current: np.ndarray, eps: float = EPS) -> float:
    reference = np.clip(reference, eps, None)           # нулевая доля дала бы бесконечность
    current = np.clip(current, eps, None)
    return float(np.sum((current - reference) * np.log(current / reference)))


def numeric_psi(reference, current, bins: int = 10) -> float:
    reference = pd.Series(reference, dtype="float64").dropna().to_numpy()
    current = pd.Series(current, dtype="float64").dropna().to_numpy()
    edges = np.unique(np.quantile(reference, np.arange(1, bins) / bins))  # границы — по эталону
    ref_share = np.bincount(np.searchsorted(edges, reference, side="left"), minlength=len(edges) + 1) / len(reference)
    cur_share = np.bincount(np.searchsorted(edges, current, side="left"), minlength=len(edges) + 1) / len(current)
    return psi_from_shares(ref_share, cur_share)


def categorical_psi(reference, current) -> float:
    reference = pd.Series(reference).dropna().astype(str)
    current = pd.Series(current).dropna().astype(str)
    categories = sorted(set(reference) | set(current))
    ref_share = reference.value_counts(normalize=True).reindex(categories, fill_value=0.0).to_numpy()
    cur_share = current.value_counts(normalize=True).reindex(categories, fill_value=0.0).to_numpy()
    return psi_from_shares(ref_share, cur_share)


def ks_test(reference, current) -> tuple[float, float]:
    reference = pd.Series(reference, dtype="float64").dropna().to_numpy()
    current = pd.Series(current, dtype="float64").dropna().to_numpy()
    result = stats.ks_2samp(reference, current)
    return float(result.statistic), float(result.pvalue)


def new_category_share(reference, current) -> float:
    known = set(pd.Series(reference).dropna().astype(str))
    current = pd.Series(current).dropna().astype(str)
    return float((~current.isin(known)).mean())
```

| Метрика | Что измеряет | Как читать |
|---|---|---|
| PSI (индекс стабильности) | насколько разошлись доли по корзинам: Σ (pᵢ − qᵢ) · ln(pᵢ / qᵢ) | принятые пороги: до 0.1 — стабильно, 0.1–0.25 — присмотреться, выше 0.25 — сдвиг |
| Колмогоров — Смирнов | наибольшее расхождение двух функций распределения (D) и p-значение | малое p — «выборки из разных распределений» |
| доля пропусков | долю пустых значений | сравнивать с долей в эталоне |
| доля новых категорий | долю строк со значением, которого нет в эталоне | в норме 0 |

Пороги PSI — соглашение из кредитного скоринга, а не закон; следующие разделы показывают, где они
не работают. Эталон (`reference`) здесь — обучающая выборка модели версии 3: 52 263 строки с 1 января
2023 по 30 июня 2024 года. Готовые библиотеки отчётов о дрейфе (например, Evidently) считают те же
величины; в уроке они не запускались.

## 7. Когда метрикам нельзя верить

**Малые выборки: PSI шумит.** Две случайные выборки из одного и того же набора прогнозов модели — сдвига
нет по построению. 500 повторов для каждого размера:

| Размер каждой выборки | PSI в среднем | PSI, 95-й перцентиль | Доля PSI > 0.1 | Доля PSI > 0.25 | Доля p < 0.05 (KS) |
|---|---|---|---|---|---|
| 100 | 0.190 | 0.365 | 84 % | 20 % | 2.0 % |
| 300 | 0.062 | 0.117 | 10 % | 0 % | 4.2 % |
| 1 000 | 0.019 | 0.035 | 0 % | 0 % | 6.6 % |
| 3 000 | 0.006 | 0.011 | 0 % | 0 % | 2.6 % |
| 10 000 | 0.001 | 0.003 | 0 % | 0 % | 1.4 % |

На ста строках PSI без всякого сдвига в среднем равен 0.19, и каждое пятое сравнение показывает «сдвиг».
Шум убывает как (число корзин − 1) · (1/n₁ + 1/n₂): для 100 строк — 0.18, для 1 000 — 0.018, что совпадает
с измеренным. Порог 0.1 осмыслен начиная примерно с тысячи строк в окне; на меньших окнах нужно меньше
корзин или более длинное окно. Критерий Колмогорова — Смирнова ведёт себя как положено: ложных
срабатываний около 5 % или меньше при любом размере.

**Большие выборки: p-значение срабатывает на всё.** Теперь сдвиг есть, но малый: спрос вырос на 3 %.

| Размер каждой выборки | Среднее | KS: D | KS: p | PSI |
|---|---|---|---|---|
| 1 000 | 4.08 → 4.43 | 0.043 | 0.31 | 0.027 |
| 5 000 | 4.07 → 4.27 | 0.026 | 0.076 | 0.005 |
| 20 000 | 4.15 → 4.23 | 0.014 | 0.049 | 0.001 |
| 52 263 | 4.11 → 4.24 | 0.012 | 0.0007 | 0.001 |

Тот же опыт на прогнозах модели, умноженных на 1.03: p-значение падает с 0.29 при тысяче строк
до 6·10⁻¹¹ на полной выборке, PSI остаётся около 0.002.

p-значение отвечает на вопрос «различаются ли распределения», и при достаточном объёме данных ответ
всегда «да»: одинаковых распределений в жизни не бывает. Оповещение по `p < 0.05` на суточном окне
в десятки тысяч строк будет срабатывать каждый день. PSI и статистика D измеряют **величину** расхождения
и от объёма не зависят. Для оповещений берут их, а p-значение оставляют в отчёте для справки.

## 8. Сдвиги на данных продаж

Текущее окно — октябрь — декабрь 2024 года. Его создаёт функция `make_shifted`: тот же процесс, что
в `make_sales` (базовый спрос, размер магазина, тренд, неделя, сезон, акции), с параметрами для сдвигов.

| Сценарий | PSI цены | KS цены: D | PSI акций | PSI магазинов | Новые магазины | PSI прогнозов | MAE |
|---|---|---|---|---|---|---|---|
| без изменений | 0.0003 | 0.003 | 0.000 | 0.000 | 0 | 0.134 | 2.07 |
| акций 30 % вместо 8 % | 0.007 | 0.039 | **0.363** | 0.000 | 0 | **0.275** | 2.34 |
| эффект акции 1.2 вместо 1.8 | 0.0003 | 0.003 | 0.000 | 0.000 | 0 | 0.134 | 2.06 |
| новый магазин `S09` | 0.0003 | 0.003 | 0.000 | **0.792** | **11.1 %** | 0.148 | 2.25 |
| цена магазина `S03` в копейках | 0.114 | 0.125 | 0.000 | 0.000 | 0 | 0.105 | 2.26 |

По строкам:

- **без изменений.** Признаки стабильны, а PSI прогнозов — 0.13: осенние прогнозы сравниваются с эталоном
  за полтора года. Это сезон, а не сдвиг (раздел 10);
- **больше акций.** PSI акций 0.36 — сдвиг найден. PSI цены при этом 0.007: скидка 15 % почти не меняет
  децили цены. MAE вырос с 2.07 до 2.34, но и продажи выросли: ошибка относительно среднего факта —
  31.4 % против 32.7 %. Модель знает, что делает акция; качество не упало. **Дрейф признаков есть,
  дрейфа качества нет**;
- **акции стали работать хуже.** Ни одна метрика дрейфа не изменилась — входные данные те же. Ожидалось,
  что вырастет MAE; он не вырос: 2.06 против 2.07. В строках с акцией прогноз остался 8.81 при факте 7.24
  (было 10.94): модель, которая занижала, стала завышать примерно на столько же. Изменение видно только
  в срезе и только по знаку смещения. **Дрейф качества есть, дрейфа признаков нет, и общая метрика
  его тоже не показала**;
- **новый магазин.** PSI магазинов 0.79, доля новых категорий 11.1 % — её же в реальном времени показал
  счётчик из раздела 3. MAE по строкам `S09` — 3.78 (факт 8.69, прогноз 5.17) против 2.06 по остальным;
- **цена в копейках.** Цены одного магазина из восьми выросли в 100 раз, а PSI цены — 0.11, «присмотреться».
  Все испорченные значения попали в верхнюю корзину, и PSI видит только то, что в ней стало на 12.5 %
  строк больше; на сколько именно значения вышли за границу, он не знает. PSI прогнозов даже уменьшился.
  Между тем MAE по `S03` — 3.48 против 1.96, прогноз 2.76 вместо 4.83. Такую ошибку ловит проверка
  диапазона (урок 7.3.3) и граница `le=1_000_000` в схеме запроса — если поставить её по смыслу.

Вывод: метрики дрейфа отвечают на вопрос «изменился ли вход», а не «стало ли хуже». Четыре сценария —
четыре разных сочетания ответов на эти два вопроса.

## 9. От отчёта к оповещению

PSI считается не в сервисе, а отдельным заданием по расписанию: оно читает запросы за окно, сравнивает
с эталоном и публикует результат. Задание завершается за секунды, и Prometheus не успеет прийти к нему
за метриками, поэтому результат отправляется в Pushgateway, откуда Prometheus его забирает.

```python
from prometheus_client import CollectorRegistry, Gauge, push_to_gateway

registry = CollectorRegistry()
psi = Gauge("sales_feature_psi", "PSI признака: окно запросов против обучающей выборки", ["feature"], registry=registry)
stamp = Gauge("sales_drift_report_timestamp_seconds", "Время построения отчёта", registry=registry)

for feature in ["price", "prediction"]:
    psi.labels(feature).set(numeric_psi(reference[feature], current[feature]))
for feature in ["promo", "store_id", "product"]:
    psi.labels(feature).set(categorical_psi(reference[feature], current[feature]))
stamp.set_to_current_time()
push_to_gateway("127.0.0.1:9091", job="sales-drift", registry=registry)
```

В настоящей системе `current` — журнал запросов сервиса за окно; на стенде его заменяет `make_shifted`
с теми же сдвигами, что в потоке запросов из раздела 3 (30 % акций и магазин `S09`). Через 12 секунд
после запуска задания:

```text
sales_feature_psi: prediction 0.298, price 0.007, product 0.000, promo 0.361, store_id 0.792
SalesFeatureDrift firing prediction | PSI признака prediction равен 0.2979243297495736
SalesFeatureDrift firing promo      | PSI признака promo равен 0.3610235381602378
SalesFeatureDrift firing store_id   | PSI признака store_id равен 0.7916212091930074
```

Pushgateway хранит последнее присланное значение бессрочно. Если задание перестанет запускаться,
оповещение о дрейфе будет гореть или молчать вечно — по вчерашним данным. Поэтому вместе с PSI
публикуется время отчёта, а шестое правило следит за ним:

```yaml
      - alert: SalesDriftReportStale
        expr: time() - sales_drift_report_timestamp_seconds > 2 * 86400
```

Это та же мысль, что возраст значения в хранилище признаков (урок 7.3.2): отсутствие новостей — тоже
новость, и за ней нужно следить явно.

## 10. Дрейф качества: когда вход не изменился

Модель версии 3 обучена по 30 июня 2024 года. Что было дальше — на данных `make_sales` без каких-либо
вмешательств:

| Месяц | PSI цены | PSI акций | PSI прогнозов | Средний прогноз | Средний факт | Смещение | MAE |
|---|---|---|---|---|---|---|---|
| 2024-07 | 0.0003 | 0.0006 | 0.193 | 2.98 | 3.53 | −0.55 (−15.6 %) | 1.47 |
| 2024-08 | 0.0000 | 0.0000 | 0.069 | 3.36 | 4.07 | −0.71 (−17.4 %) | 1.56 |
| 2024-09 | 0.0000 | 0.0002 | 0.023 | 3.98 | 4.85 | −0.87 (−17.9 %) | 1.78 |
| 2024-10 | 0.0001 | 0.0000 | 0.051 | 4.63 | 5.69 | −1.06 (−18.7 %) | 2.00 |
| 2024-11 | 0.0000 | 0.0013 | 0.155 | 5.35 | 6.40 | −1.05 (−16.4 %) | 2.04 |
| 2024-12 | 0.0000 | 0.0010 | 0.259 | 5.67 | 6.82 | −1.14 (−16.8 %) | 2.13 |

PSI магазинов и товаров во все месяцы — ноль. Входные данные не изменились вовсе, а модель каждый месяц
занижает прогноз на 16–19 %. Причина — в данных есть рост спроса на 25 % в год, а у модели нет признака,
который его передаёт: она воспроизводит уровень обучающего периода. Это дрейф зависимости между
признаками и ответом; по входу его не найти.

Три наблюдения:

- **надёжный сигнал — смещение**, то есть средняя разность прогноза и факта. Оно требует факта, а факт
  приходит с опозданием: о продажах дня — на следующий день. Задание, которое сопоставляет вчерашние
  прогнозы с пришедшим фактом и публикует смещение и MAE, устроено так же, как отчёт о дрейфе;
- **MAE сам по себе читать трудно.** Он вырос с 1.47 до 2.13, но в декабре и продажи вдвое больше, чем
  в июле; относительная ошибка даже снизилась. Сравнивать нужно с прогнозом-ориентиром на том же окне
  (как `mae_ratio` в практике 7.1.4);
- **PSI прогнозов следует за сезоном, а не за ошибкой.** 0.19 в июле, 0.02 в сентябре, 0.26 в декабре —
  при том, что смещение почти постоянно. Порог 0.25 сработал бы в декабре на обычный предновогодний спрос.
  Эталон для величин с сезонностью — тот же сезон прошлого года либо предыдущая неделя, а не вся
  обучающая выборка.

## 11. Что делать после срабатывания

| Сигнал | Первая проверка | Действие |
|---|---|---|
| сервис недоступен, растёт доля 5xx | журнал подов, последняя выкладка | откат (урок 7.4.2); причину искать после |
| выросло время ответа | нагрузка, число реплик, загрузка процессора | масштабирование; проверить размер пакетов |
| появились незнакомые категории | какие именно значения и от какого потребителя | новый магазин — в план переобучения; опечатка — потребителю |
| PSI признака выше порога | размер окна; один ли признак; есть ли причина (акция, сезон) | причина известна и качество в норме — зафиксировать и поднять порог или сменить эталон |
| PSI резко вырос у одного потребителя или магазина | диапазон значений, единицы измерения | ошибка данных: чинить источник, а не модель |
| смещение прогноза держится несколько дней | срезы: по магазинам, товарам, акциям | переобучение на свежих данных (пайплайн 7.1); сравнение с действующей моделью и продвижение (7.2.2) |
| отчёт о дрейфе устарел | задание расписания | починить задание; до тех пор панели дрейфа не доверять |

Переобучение — не универсальный ответ. Оно помогает, когда изменился мир (спрос вырос, появились
магазины), и вредит, когда изменились данные из-за ошибки: модель, обученная на ценах в копейках,
закрепит ошибку. Сначала выясняют, что именно изменилось, и только потом решают, что с этим делать.

## Типичные ошибки

| Симптом | Причина | Решение |
|---|---|---|
| `ValueError: Duplicated timeseries in CollectorRegistry` | метрика объявлена дважды: модуль импортирован повторно, приложение создаётся в каждом тесте | свой `CollectorRegistry` на приложение (практика 7.4.4) |
| Число рядов в Prometheus растёт без остановки | в метке — адрес запроса, идентификатор или другое неограниченное значение | шаблон маршрута; значения мимо списка — в `other` |
| Счётчик на графике скачет вверх и вниз | несколько воркеров, каждый со своим счётчиком | один воркер на контейнер или многопроцессный режим |
| Запросы с кодом 422 не попадают в метрики | счётчик увеличивается внутри обработчика | считать в промежуточном обработчике |
| График «нет данных» вместо нуля | ряда с таким значением метки ещё не было | ожидаемо; для графика — `or vector(0)` |
| p95 на панели не совпадает с замером клиента | перцентиль интерполируется внутри корзины | границы корзин около пороговых значений |
| Оповещение о дрейфе срабатывает каждый день | условие по p-значению на большой выборке | порог по PSI или статистике D |
| PSI выше 0.1 на спокойных данных | в окне сотни строк | окно от тысячи строк или меньше корзин |
| PSI цены в норме, а прогнозы бессмысленны | значения ушли далеко за границу, но в ту же крайнюю корзину | проверка диапазона на входе |
| PSI прогнозов «плывёт» в течение года | эталон — вся обучающая выборка, а величина сезонная | эталон того же сезона |
| Оповещение о дрейфе горит, хотя задание давно не запускалось | Pushgateway хранит последнее значение | метрика времени отчёта и правило на её возраст |
| Дежурные перестали реагировать на оповещения | оповещения без действия; всё с важностью `page` | два уровня важности; у каждого правила — описанное действие |
