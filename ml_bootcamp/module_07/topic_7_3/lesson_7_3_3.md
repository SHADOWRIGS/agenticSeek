## Зачем это нужно

Хранилище признаков из уроков 7.3.1 и 7.3.2 делает ровно то, что обещает: хранит то, что ему дали,
и выдаёт это быстро и на нужный момент. Вопроса «а правильные ли это числа» в нём нет. Ночная загрузка,
в которой один магазин прислал продажи в штуках вместо упаковок, пройдёт через `materialize` без единого
предупреждения — и первым же запросом окажется в ответе сервиса:

```text
без шлюза:  units_mean_7d магазина S03, товар «Мышь» = 12714.285714      (настоящее значение — 12.71)
```

Это число получено в этом уроке, а не придумано. Модель, получившая на вход 12 714 вместо 12.7, ответит
прогнозом — уверенно и неверно; ошибок в журнале не будет.

Проверка данных — последний рубеж перед тем, как данные начнут влиять на прогнозы. В пайплайне практики
7.1.4 она была функцией `validate` на десять строк. Здесь — тот же принцип с инструментом, который
превращает проверки в документ, отчёт и историю.

Версии урока: Python 3.12.13, `great-expectations 1.25.0`, `pandera 0.36.0`, `pandas 2.3.3`,
`numpy 2.5.4`, `feast 0.68.0`. Проект uv — тот же, что в уроках 7.3.1 и 7.3.2:

```bash
uv add great_expectations pandera
```

Сам Great Expectations верхней границы на pandas не задаёт (в отдельном проекте решатель выбрал для него
`pandas 3.1.1`), но в этой теме он работает рядом с Feast, то есть на `pandas 2.3.3`; под pandas 3 примеры
урока не запускались.

## 1. Проверка данных — не тест кода

| | Тест кода | Проверка данных |
|---|---|---|
| Что проверяет | функцию на подготовленном входе | настоящие данные сегодняшней загрузки |
| Когда выполняется | при изменении кода: в CI | при каждом поступлении данных: в пайплайне |
| Вход | фиксирован, придуман автором теста | неизвестен заранее |
| Провал означает | в коде ошибка | данные не такие, как ожидалось: сломался источник, изменился мир или устарело ожидание |
| Что делать при провале | исправить код | остановить пайплайн, оставить прошлые данные, разобраться |
| Пороги | точные: `assert result == 7` | с допуском: «не больше 1 % пропусков» |

Тест `test_features_rolling_means` из практики этой темы доказывает, что функция верно считает среднее
по семи числам. Он ничего не говорит о том, что в сегодняшней выгрузке не окажется продаж за прошлый
месяц или столбца с другим именем. И наоборот: проверка данных не найдёт ошибку в окне скользящего
среднего — числа будут правдоподобными.

Отсюда и разница в поведении при провале. Упавший тест блокирует слияние ветки. Проваленная проверка
данных блокирует **публикацию**: сервис продолжает работать на вчерашних признаках, а человек получает
отчёт о том, что именно не так.

## 2. Устройство Great Expectations

| Объект | Что это | В уроке |
|---|---|---|
| Контекст (data context) | точка входа: хранит все остальные объекты; бывает в памяти и в файлах | каталог `gx/` в проекте |
| Источник данных (data source) | откуда берутся данные | pandas |
| Актив (data asset) и определение партии (batch definition) | какая именно таблица и как из неё берётся порция | таблица целиком, передаётся при запуске |
| Ожидание (expectation) | одно проверяемое утверждение о данных | «`promo_share_28d` лежит в [0, 1]» |
| Набор ожиданий (expectation suite) | все утверждения об одной таблице | `pair_stats_daily`, 10 ожиданий |
| Определение проверки (validation definition) | пара «данные — набор ожиданий» | `pair_stats_daily_check` |
| Checkpoint | что запускать и что делать с результатом | `before_materialize` |
| Отчёт (validation result, Data Docs) | итог запуска: объект Python, JSON и HTML-страницы | каталог `gx/uncommitted/data_docs` |

Объектов много, и для таблицы из семи столбцов это выглядит избыточно. Разделение оправдывается, когда
один набор ожиданий применяется к разным источникам (файл в тесте, таблица хранилища в работе), а один
checkpoint запускают и пайплайн, и человек из командной строки.

## 3. Одно ожидание

Самый короткий путь — контекст в памяти и проверка одной таблицы одним утверждением:

```python
import great_expectations as gx
import great_expectations.expectations as gxe
import pandas as pd

context = gx.get_context(mode="ephemeral")
batch = context.data_sources.pandas_default.read_dataframe(pd.DataFrame({"x": [1, 2, None]}))
result = batch.validate(gxe.ExpectColumnValuesToNotBeNull(column="x"))
result.success, dict(result.result)
```

```text
(False, {'element_count': 3, 'unexpected_count': 1, 'unexpected_percent': 33.33333333333333,
         'partial_unexpected_list': [nan], 'partial_unexpected_counts': [{'value': nan, 'count': 1}],
         'partial_unexpected_index_list': [2]})
```

Весь скрипт выполнился за 2.1 секунды, и почти всё это время — `import great_expectations`. Ожидание — объект
с именем, которое читается как предложение, и с результатом, в котором есть не только «нет», но и сколько
строк нарушают утверждение и какие именно. На этом строится всё остальное.

## 4. Набор ожиданий для таблицы признаков

Проверяется суточная партия таблицы `pair_stats`: 96 строк, по одной на пару, с отметкой времени
`2025-01-01 00:00` — то, что ночная загрузка собирается добавить в офлайн-таблицу и материализовать.

```python
context = gx.get_context(mode="file", project_root_dir=".")          # 0.03 секунды; создаёт каталог gx/
source = context.data_sources.add_pandas(name="features")
asset = source.add_dataframe_asset(name="pair_stats")
batch_definition = asset.add_batch_definition_whole_dataframe("daily_batch")

COLUMNS = ["store_id", "product", "event_timestamp", "created", "units_mean_7d", "units_mean_28d", "promo_share_28d"]
suite = context.suites.add(gx.ExpectationSuite(name="pair_stats_daily"))
# схема
suite.add_expectation(gxe.ExpectTableColumnsToMatchSet(column_set=COLUMNS, exact_match=True))
suite.add_expectation(gxe.ExpectColumnValuesToBeOfType(column="units_mean_7d", type_="float64"))
# объём и ключи
suite.add_expectation(gxe.ExpectTableRowCountToEqual(value=96))
suite.add_expectation(gxe.ExpectCompoundColumnsToBeUnique(column_list=["store_id", "product", "event_timestamp"]))
suite.add_expectation(gxe.ExpectColumnValuesToBeInSet(column="store_id", value_set=[f"S{i:02d}" for i in range(1, 9)]))
# пропуски и диапазоны
suite.add_expectation(gxe.ExpectColumnValuesToNotBeNull(column="units_mean_7d", mostly=0.99))
suite.add_expectation(gxe.ExpectColumnValuesToBeBetween(column="units_mean_7d", min_value=0, max_value=100))
suite.add_expectation(gxe.ExpectColumnValuesToBeBetween(column="promo_share_28d", min_value=0, max_value=1))
# распределение
suite.add_expectation(gxe.ExpectColumnMeanToBeBetween(column="units_mean_7d", min_value=3, max_value=9))
# свежесть: порог задаётся при запуске
suite.add_expectation(
    gxe.ExpectColumnMaxToBeBetween(column="event_timestamp", min_value={"$PARAMETER": "freshness_floor"})
)
```

Восемь видов проверок и то, от чего каждая защищает:

| Вид | Ожидание | Какую поломку ловит |
|---|---|---|
| Схема | набор столбцов, тип столбца | источник переименовал или убрал столбец; число пришло строкой |
| Объём | число строк | загрузка оборвалась на середине; партия пришла дважды |
| Уникальность ключей | составной ключ уникален | повторная загрузка; размножение строк после неудачного соединения |
| Допустимые значения | множество значений | новый или испорченный идентификатор |
| Пропуски | доля непустых (`mostly`) | источник перестал заполнять поле |
| Диапазоны | границы значений | смена единиц измерения, знак, проценты вместо долей |
| Распределение | среднее в интервале | сдвиг, при котором каждое значение само по себе допустимо |
| Свежесть | наибольшая отметка времени не раньше порога | загрузка принесла вчерашние данные под видом сегодняшних |

Три замечания о порогах.

- `mostly=0.99` — допуск. Требование «ни одного пропуска» на настоящих данных означает ложную тревогу
  раз в неделю; после третьей проверку отключат. В таблице признаков пропуск `units_mean_7d` возможен
  (у пары нет продаж за окно), поэтому порог — доля.
- Границы диапазона берутся из знания о предмете, а не из сегодняшних данных: продажи не отрицательны,
  доля лежит в [0, 1]. Верхняя граница 100 — «на порядок больше наблюдаемого максимума»: её задача —
  поймать смену единиц, а не выброс.
- Интервал среднего (3–9 при фактическом около 7) придётся пересматривать: у продаж есть тренд
  и сезонность. Проверки распределения — самые полезные и самые хрупкие; у каждой должен быть владелец.

Свежесть — единственная проверка, зависящая от текущего времени. Порог не зашит в набор, а передаётся
параметром при запуске: так набор остаётся одним и тем же документом, а проверку можно повторить
для любого момента.

## 5. Checkpoint и то, что остаётся на диске

```python
definition = context.validation_definitions.add(
    gx.ValidationDefinition(name="pair_stats_daily_check", data=batch_definition, suite=suite)
)
checkpoint = context.checkpoints.add(
    gx.Checkpoint(
        name="before_materialize",
        validation_definitions=[definition],
        actions=[gx.checkpoint.UpdateDataDocsAction(name="docs")],
        result_format={"result_format": "COMPLETE"},
    )
)

AS_OF = datetime(2025, 1, 1, 6, 0, tzinfo=timezone.utc)                # момент проверки — параметр
result = checkpoint.run(
    batch_parameters={"dataframe": batch},
    expectation_parameters={"freshness_floor": AS_OF - timedelta(days=1)},
)
result.success        # True: 10 ожиданий из 10, 0.22 секунды
```

`result_format="COMPLETE"` просит вернуть все строки-нарушители с их индексами; по умолчанию
возвращается сокращённая сводка. Действие `UpdateDataDocsAction` после каждого запуска обновляет
HTML-отчёт.

Контекст в режиме `file` сохранил всё описанное в каталог проекта:

```text
├── checkpoints/before_materialize.json

    └── data_docs/local_site/index.html             HTML-отчёты и результаты запусков
```


Набор ожиданий — файл JSON. Он хранится в Git рядом с определениями признаков, и изменение порога
проходит обзор кода, как любое другое изменение. Каталог `uncommitted/` в Git не попадает: после восьми
запусков этого урока в нём 30 файлов на 4.4 МБ. В следующем запуске пайплайна ничего создавать не нужно:

```python
context = gx.get_context(mode="file", project_root_dir=".")
checkpoint = context.checkpoints.get("before_materialize")             # 10 ожиданий прочитаны из файлов
```

Две настройки для запуска без человека. Индикаторы выполнения, которыми библиотека по умолчанию
заполняет журнал, отключаются так:

```python
from great_expectations.data_context.types.base import ProgressBarsConfig

context.variables.progress_bars = ProgressBarsConfig(globally=False)
```

Отправку анонимной статистики использования отключает переменная окружения `GX_ANALYTICS_ENABLED=false`;
в CI и закрытых контурах её задают явно.

Фрагмент отчёта для второй строки (`result.describe_dict()`, списки сокращены до двух элементов):

```json
{
 "expectation_type": "expect_compound_columns_to_be_unique",
 "success": false,
 "kwargs": {"column_list": ["store_id", "product", "event_timestamp"]},
 "result": {
  "element_count": 108,
  "unexpected_count": 24,
  "unexpected_percent": 22.22222222222222,
  "partial_unexpected_list": [
   {"store_id": "S05", "product": "Блендер", "event_timestamp": "2025-01-01T00:00:00+00:00"},
   {"store_id": "S05", "product": "Зонт", "event_timestamp": "2025-01-01T00:00:00+00:00"}
  ],
  "unexpected_index_list": [48, 49]
 }

```

Отчёт отвечает на три вопроса дежурного: что нарушено (уникальность ключа), насколько (24 строки из 108),
где именно (магазин `S05`, индексы строк). С этим можно идти к владельцу источника, не открывая данные.

Что видно при сравнении строк таблицы:

- **Одна поломка — несколько срабатываний.** Умножение на 1000 поймано и диапазоном, и средним.
  Это не избыточность: если бы магазин ошибся в 3 раза, а не в 1000, диапазон [0, 100] промолчал бы,
  а среднее могло бы сработать.
- **Переименование столбца поймано только проверкой схемы.** Ни одного ожидания на `units_mean_28d`
  в наборе нет, поэтому без `ExpectTableColumnsToMatchSet` переименование прошло бы незамеченным.
  Схема проверяется первой.
- **Неверный тип не обрушил запуск.** Ожидания, которые не смогли вычислиться на строках, отмечены
  как проваленные с записью об исключении; остальные семь выполнены. Checkpoint всегда возвращает отчёт.
- **Проверка среднего на трети пропусков промолчала:** среднее по оставшимся значениям прежнее. Пропуски
  ловит своя проверка — виды ожиданий не заменяют друг друга.
- **Свежесть не поймал бы никто другой:** партия трёхдневной давности безупречна по всем остальным
  девяти ожиданиям.

## 7. Шлюз перед материализацией

Проверка полезна, только если её результат что-то решает. Шлюз — функция, которая либо пропускает
данные дальше, либо останавливает пайплайн исключением:

```python
class DataValidationError(ValueError):
    pass


def validate_or_raise(df: pd.DataFrame, as_of: datetime) -> None:
    result = checkpoint.run(
        batch_parameters={"dataframe": df},
        expectation_parameters={"freshness_floor": as_of - timedelta(days=1)},
    )
    if not result.success:
        failed = [r.expectation_config.type for vr in result.run_results.values() for r in vr.results if not r.success]
        raise DataValidationError(f"партия отклонена: {', '.join(failed)}")


def publish(df: pd.DataFrame, as_of: datetime) -> None:
    validate_or_raise(df, as_of)                                   # шлюз: до любой записи
    current = pd.read_parquet("data/pair_stats.parquet")
    pd.concat([current, df], ignore_index=True).to_parquet("data/pair_stats.parquet", index=False)
    store.materialize_incremental(end_date=as_of)
```

Порядок действий — главное в этой функции: проверка стоит **до записи в офлайн-таблицу**, а не между
записью и материализацией. Плохая партия, попавшая в офлайн-таблицу, испортит следующую обучающую
выборку, даже если до сервиса не дойдёт.

Проверка на проекте: офлайн-таблица — по 31 декабря, онлайн-хранилище материализовано по тот же день.
Сначала приходит партия с испорченным магазином `S03`, затем исправленная. Значение `units_mean_7d`
пары `S03` / «Мышь» в онлайн-хранилище:

| Шаг | Онлайн-значение | Отметка времени | Строк в офлайн-таблице |
|---|---|---|---|
| до публикации | 11.428571 | 2024-12-31 00:00 | 70 080 |
| плохая партия: `DataValidationError: партия отклонена: expect_column_values_to_be_between, expect_column_mean_to_be_between` | 11.428571 | 2024-12-31 00:00 | 70 080 |
| хорошая партия | 12.714286 | 2025-01-01 00:00 | 70 176 |
| та же плохая партия без шлюза | **12714.285714** | 2025-01-01 00:00 | 70 176 |

После отказа сервис продолжает получать вчерашнее значение — устаревшее на сутки, но верное.
Это осознанный выбор: вчерашние признаки лучше сегодняшних неправильных, а возраст значения сервис
видит сам (урок 7.3.2). Последняя строка — то, что происходит без шлюза: число из начала урока.

Где ставить шлюз в пайплайне (DAG из урока 7.1.2): отдельной задачей между расчётом признаков
и публикацией. Провал задачи останавливает ветку публикации и отправляет оповещение; повторный запуск
после исправления источника проходит тот же шлюз.

## 8. Шлюз перед обучением

Обучающая выборка — тоже данные, и у неё свои способы сломаться: дыра в истории превращается в пропуски
после соединения по времени, а ошибка соединения — в утечку. Второй набор ожиданий проверяет выборку,
собранную в уроке 7.3.1 (в ней оставлен столбец `feature_ts` — отметка времени присоединённой строки
признаков):

```python
suite = context.suites.add(gx.ExpectationSuite(name="training_frame"))
suite.add_expectation(gxe.ExpectTableRowCountToBeBetween(min_value=50_000))
suite.add_expectation(gxe.ExpectCompoundColumnsToBeUnique(column_list=["store_id", "product", "event_timestamp"]))
suite.add_expectation(gxe.ExpectColumnValuesToNotBeNull(column="units"))
suite.add_expectation(gxe.ExpectColumnValuesToBeBetween(column="units", min_value=0, max_value=100))
for column in ("units_mean_7d", "units_mean_28d", "promo_share_28d"):
    suite.add_expectation(gxe.ExpectColumnValuesToNotBeNull(column=column, mostly=0.99))
suite.add_expectation(
    gxe.ExpectColumnPairValuesAToBeGreaterThanB(
        column_A="event_timestamp", column_B="feature_ts", or_equal=True, ignore_row_if="either_value_is_missing"
    )
)
```

Последнее ожидание — правило соединения по времени, записанное как проверка данных: момент запроса
не раньше отметки времени признака. Результаты на 69 841 строке:

| Выборка | Итог | Что провалено |
|---|---|---|
| честная: соединение по времени | 8 из 8, 0.11 с | — (пропусков в `units_mean_7d` 0.14 %) |
| в офлайн-таблице нет июня 2024 | 5 из 8 | три проверки пропусков: 2 770 строк (3.97 %) при пороге 1 % |
| `merge` по дате вместо соединения по времени | 7 из 8 | отметка признака позже момента запроса в 69 841 строке из 69 841 |

Вторая строка — случай, который без проверки обнаруживается через месяц: модель обучилась, метрика чуть
хуже, причина неизвестна. Третья — утечка из урока 7.3.1, пойманная в данных: достаточно не выбрасывать
отметку времени признака после соединения. Тест кода ловит ту же ошибку раньше и дешевле, но только
в функции, для которой он написан; проверка данных срабатывает на любом способе сборки выборки.

## 9. Лёгкие альтернативы: pandas и pandera

Те же проверки без Great Expectations. Функция на pandas:

```python
def check_pandas(df: pd.DataFrame, as_of: datetime) -> list[str]:
    problems = []
    if set(df.columns) != set(COLUMNS):
        extra, missing = sorted(set(df.columns) - set(COLUMNS)), sorted(set(COLUMNS) - set(df.columns))
        return [f"столбцы: лишние {extra}, нет {missing}"]
    if len(df) != 96:
        problems.append(f"строк {len(df)}, ожидалось 96")
    duplicates = int(df.duplicated(["store_id", "product", "event_timestamp"], keep=False).sum())
    if duplicates:
        problems.append(f"повторяющихся ключей: {duplicates}")
    if df["units_mean_7d"].isna().mean() > 0.01:
        problems.append(f"пропусков units_mean_7d: {df['units_mean_7d'].isna().mean():.1%}")
    outside = int((~df["units_mean_7d"].dropna().between(0, 100)).sum())
    if outside:
        problems.append(f"units_mean_7d вне [0, 100]: {outside}")
    outside = int((~df["promo_share_28d"].dropna().between(0, 1)).sum())
    if outside:
        problems.append(f"promo_share_28d вне [0, 1]: {outside}")
    if df["event_timestamp"].max() < as_of - timedelta(days=1):
        problems.append(f"данные устарели: {df['event_timestamp'].max()}")
    return problems
```

Схема pandera — декларативное описание таблицы:

```python
import pandera.pandas as pa

schema = pa.DataFrameSchema(
    {
        "store_id": pa.Column(str, pa.Check.isin([f"S{i:02d}" for i in range(1, 9)])),
        "product": pa.Column(str),
        "event_timestamp": pa.Column("datetime64[us, UTC]"),
        "created": pa.Column("datetime64[us, UTC]"),
        "units_mean_7d": pa.Column(float, pa.Check.in_range(0, 100), nullable=True),
        "units_mean_28d": pa.Column(float, pa.Check.ge(0), nullable=True),
        "promo_share_28d": pa.Column(float, pa.Check.in_range(0, 1)),
    },
    checks=[pa.Check(lambda df: len(df) == 96, error="строк должно быть 96")],
    unique=["store_id", "product", "event_timestamp"],
    strict=True,
)

try:
    schema.validate(df, lazy=True)                       # lazy=True: собрать все нарушения, а не первое
except pa.errors.SchemaErrors as error:
    failures = error.failure_cases                       # таблица: проверка, столбец, значение, индекс
```

Результаты на тех же партиях:

| Партия | pandas | pandera |
|---|---|---|
| хорошая | `[]` | проходит |
| `S03` × 1000 | `units_mean_7d вне [0, 100]: 12` | 12 нарушений `in_range(0, 100)`, первое — 4571.43, индекс 24 |
| `S05` дважды | `строк 108, ожидалось 96`; `повторяющихся ключей: 24` | уникальность ключа и число строк |
| трёхдневной давности | `данные устарели: 2024-12-29 00:00:00+00:00` | **проходит** |
| переименован столбец | `столбцы: лишние ['units_mean_4w'], нет ['units_mean_28d']` | нет `units_mean_28d`, лишний `units_mean_4w`, `promo_share_28d` вне [0, 1] |

Pandera пропустила устаревшую партию не из-за ошибки: в схеме нет проверки свежести, а статическая схема
не знает текущего времени. Её добавляют отдельной функцией — и это общее правило: какой бы инструмент
ни использовался, проверки, зависящие от времени запуска, приходится писать самому.

Время одной проверки, миллисекунды (медиана по 5–20 запускам, без импорта):

| | 96 строк | 70 176 строк |
|---|---|---|
| Great Expectations, checkpoint из 10 ожиданий с обновлением HTML-отчёта | 219 | 301 |
| pandera, схема | 3.4 | 32 |
| pandas, функция | 0.46 | 6.5 |

На партии из 96 строк Great Expectations в 60 раз медленнее pandera и почти в 500 раз медленнее функции:
200 мс — постоянные накладные расходы
на построение плана вычислений и запись отчёта. Для ночной загрузки это неважно; для проверки каждого
запроса к сервису — неприемлемо.

| Критерий | Great Expectations | pandera | Функция на pandas |
|---|---|---|---|
| Отчёт для людей | HTML с историей запусков | таблица нарушений | список строк |
| Ожидания как документ в Git | JSON | код схемы | код функции |
| Время проверки | сотни мс | единицы мс | доли мс |
| Зависимости и время импорта | тяжёлые; импорт 2 с | лёгкие | нет |
| Другие источники (SQL, Spark) | есть | частично | нет |
| Проверка внутри сервиса, на каждый запрос | нет | да | да |

Практический выбор. Для границ функций и входа сервиса — pandera или функция: быстро и рядом с кодом.
Для пакетных данных, которыми пользуются несколько команд и у которых есть владелец, — Great
Expectations: ценность в отчёте и в том, что ожидания становятся общим документом. В практике 7.3.4
реализация проверки свободная: тесты проверяют только результат.

## 10. Чего проверка данных не ловит

- **Правдоподобную ошибку.** Продажи магазина занижены на 10 % — все значения в диапазоне, среднее
  в интервале. Для этого нужны сверки с независимым источником и наблюдение за качеством прогноза
  (тема 7.4).
- **Ошибку в логике признака.** Окно в восемь дней вместо семи даёт допустимые числа. Это ловят тесты кода.
- **То, чего нет в наборе.** Переименование столбца поймано только потому, что в наборе была проверка
  схемы. Каждый инцидент с данными должен заканчиваться новым ожиданием.
- **Устаревшие ожидания.** Сеть открыла девятый магазин — проверка множества значений начнёт отклонять
  верные данные. Проверка, которая часто срабатывает ложно, хуже отсутствующей: её научатся обходить.

## Типичные ошибки

| Симптом | Причина | Решение |
|---|---|---|
| Проверка есть, а плохие данные в сервисе | результат проверки записывается в журнал, но ничего не останавливает | шлюз: исключение до записи в офлайн-таблицу и до материализации |
| Плохая партия не дошла до сервиса, но попала в обучающую выборку | проверка стоит после записи в офлайн-таблицу | проверять до любой записи |
| Проверка падает каждую неделю, её отключили | порог «ни одного пропуска», «ровно такое среднее» | `mostly`, интервалы с запасом; пересмотр порогов — через обзор кода |
| Партия трёхдневной давности прошла все проверки | нет проверки свежести | наибольшая отметка времени против порога, порог — параметр запуска |
| Переименованный столбец прошёл проверку | ожидания заданы только для отдельных столбцов | проверка набора столбцов с `exact_match=True` первой в наборе |
| Проверка проходит на любом входе | ожидания подобраны по сегодняшним данным с огромным запасом | проверять набор на заведомо испорченных партиях, как в разделе 6 |
| Тест с проверкой свежести проходит сегодня и падает завтра | текущее время читается внутри проверки | момент проверки — параметр функции |
| Журнал пайплайна забит строками `Calculating Metrics` | индикаторы выполнения включены | `ProgressBarsConfig(globally=False)` |
| В Git попали мегабайты HTML | закоммичен `gx/uncommitted/` | оставить `.gitignore`, созданный библиотекой |
| Проверка на каждый запрос добавляет 200 мс | Great Expectations внутри сервиса | pandera или функция; Great Expectations — для пакетных данных |
