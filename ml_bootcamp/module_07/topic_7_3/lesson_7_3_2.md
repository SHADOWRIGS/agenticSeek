## Зачем это нужно

Урок 7.3.1 закончился обучающей выборкой: `get_historical_features` собрал её по истории за 0.4 секунды.
Сервису прогноза нужно другое — признаки одной пары «магазин — товар» прямо сейчас и за миллисекунды.
Историческим запросом это не делается: он читает parquet-файл целиком.

Поэтому хранилищ два, и между ними есть перенос данных. У переноса есть расписание, а значит, и задержка;
у значений есть возраст; запись в одно хранилище не означает запись в другое. Каждое из этих «значит» —
источник расхождения между тем, на чём модель обучена, и тем, что она получает в работе. Урок проходит
по ним по очереди, с числами.

Проект и окружение — из урока 7.3.1: репозиторий `sales_repo`, проект uv с `feast 0.68.0`,
`pandas 2.3.3`, `numpy 2.5.4`, `duckdb 2.0.0`, Python 3.12.13; онлайн-хранилище — SQLite из стандартной
библиотеки. Выводы получены 13 ноября 2026 года около 18:37 UTC — для этого урока дата запуска важна.

## 1. Два хранилища — два вопроса

| | Офлайн-хранилище | Онлайн-хранилище |
|---|---|---|
| Вопрос | что было известно в момент T? | что известно сейчас? |
| Что хранит | всю историю значений | одно, последнее значение на ключ |
| В проекте | parquet + DuckDB: 70 176 строк `pair_stats` | SQLite: 96 ключей × 3 признака = 288 строк |
| Кто читает | обучение, пакетный прогноз, анализ | сервис прогноза |
| Запрос | тысячи и миллионы строк, секунды и минуты | один или несколько ключей, миллисекунды |
| Операция | соединение по времени | чтение по ключу |

Связывает их **материализация** — перенос последних значений из офлайн-хранилища в онлайн. Определение
признаков одно (`features.py`), а путей к значению два, и согласованность между ними не возникает сама.

## 2. Материализация

```bash
cd sales_repo
uv run feast materialize 2024-12-25T00:00:00 2025-01-02T00:00:00
```

Первая попытка закончилась ошибкой:

```text
_duckdb.ConversionException: Conversion Error: Unimplemented type for cast (TIMESTAMPTZ_NS -> TIMESTAMP)
when casting from source column event_timestamp
```

Таблицы признаков были записаны из pandas 2 с отметками времени в наносекундах. Исторические запросы
с такими файлами работали, а материализация — нет. После приведения столбцов времени к
`datetime64[us, UTC]` перед записью (так и сделано в уроке 7.3.1):

```text

pair_stats:
store_stats:
```

Команда взяла из офлайн-таблицы строки с отметкой времени в заданном интервале, оставила последнюю
на каждый ключ и записала в SQLite. Что получилось в базе:

```python

con.execute("select sql from sqlite_master where name = 'sales_pair_stats'").fetchone()[0]

con.execute("select count(*), count(distinct entity_key) from sales_pair_stats").fetchone()     # (288, 96)
con.execute("select count(*) from sales_store_stats").fetchone()                                # (8,)
```

Первичный ключ — (ключ сущности, имя признака): место есть ровно для одного значения. Истории здесь нет
и быть не может; файл базы занимает 127 КБ против 70 тысяч строк в офлайн-таблице.

**Инкрементальная материализация.** Интервалы выполненных материализаций Feast записывает в реестр:

```python

# [(datetime(2024, 12, 25, 0, 0, tzinfo=utc), datetime(2025, 1, 2, 0, 0, tzinfo=utc))]
```

Для представления, которое ни разу не материализовалось, началом служит «сейчас минус `ttl`». Эту команду
и ставят в расписание (DAG Airflow из урока 7.1.2):

```bash
uv run feast materialize-incremental $(date -u +"%Y-%m-%dT%H:%M:%S")
```

## 3. Чтение из онлайн-хранилища

```python
from feast import FeatureStore

store = FeatureStore(repo_path=".")
response = store.get_online_features(
    features=["pair_stats:units_mean_7d", "pair_stats:units_mean_28d", "store_stats:store_units_7d"],
    entity_rows=[{"store_id": "S01", "product": "Мышь"}],
)
response.to_dict()
# {'store_id': ['S01'], 'product': ['Мышь'], 'units_mean_28d': [27.464285714285715],
#  'units_mean_7d': [27.428571428571427], 'store_units_7d': [896.0]}
```

Запрос — список ключей; ответ — столбцы. Вместо списка признаков можно передать сервис признаков:
`features=store.get_feature_service("sales_forecast_v1")` — тот же объект, что при сборе обучающей выборки.
`response.to_df()` возвращает таблицу. Порядок столбцов в ответе не совпадает с порядком в запросе —
обращайтесь к признакам по имени.

В словаре нет двух вещей, без которых ответом нельзя пользоваться: статуса и отметки времени.

```python
from datetime import datetime, timezone

from feast.protos.feast.serving.ServingService_pb2 import FieldStatus

data = response.to_dict(include_event_timestamps=True)
names = response.proto.metadata.feature_names.val
for name, result in zip(names, response.proto.results):
    stamp = datetime.fromtimestamp(data[f"{name}__ts"][0], timezone.utc) if data[f"{name}__ts"][0] else None
    print(name, data[name][0], FieldStatus.Name(result.statuses[0]), stamp)
```

Ответ для известной пары и для магазина `S99`, которого в данных нет (значения здесь — из опыта 2
раздела 4, поэтому отличаются от словаря выше):

```text

   0  units_mean_7d  31.142857   PRESENT 2026-11-10 00:00:00+00:00
   1  units_mean_7d       None NOT_FOUND                       NaT
   0 units_mean_28d      27.75   PRESENT 2026-11-10 00:00:00+00:00
   1 units_mean_28d       None NOT_FOUND                       NaT
   0 store_units_7d      949.0   PRESENT 2026-11-10 00:00:00+00:00
   1 store_units_7d       None NOT_FOUND                       NaT
```

Статусов в протоколе пять: `INVALID`, `PRESENT`, `NULL_VALUE`, `NOT_FOUND`, `OUTSIDE_MAX_AGE`. Неизвестный
ключ — не исключение, а `None` со статусом `NOT_FOUND`. Что делать с `None`, решает сервис: модель
из темы 7.1 пропуски заполняет, но новый магазин без истории и сбой материализации выглядят для неё
одинаково. Долю ответов `NOT_FOUND` стоит считать и выводить на график (тема 7.4).

## 4. TTL и устаревшие признаки

У обоих представлений `ttl=timedelta(days=2)`. По документации значение старше TTL при чтении должно
считаться отсутствующим; в протоколе для этого есть статус `OUTSIDE_MAX_AGE`. Проверка на деле.

**Опыт 1.** После материализации из раздела 2 в онлайн-хранилище лежат значения с отметкой времени
`2025-01-01 00:00`. Чтение 13 ноября 2026 года — возраст значения 681 день при сроке годности 2 дня:

```text
units_mean_28d  27.464285714285715  PRESENT  2025-01-01 00:00:00+00:00
units_mean_7d   27.428571428571427  PRESENT  2025-01-01 00:00:00+00:00
store_units_7d  896.0               PRESENT  2025-01-01 00:00:00+00:00
```

Значение почти двухлетней давности возвращено как действующее.

**Опыт 2**, ближе к жизни: задача материализации не запускалась три дня. Учебные данные сдвинуты так,
чтобы последний день продаж был вчера:

```python
yesterday = pd.Timestamp.now(tz="UTC").tz_localize(None).normalize() - timedelta(days=1)
sales["date"] = sales["date"] + (yesterday - sales["date"].max())      # 2024-11-12 … 2026-11-12
```

Таблицы признаков пересчитаны, затем выполнена материализация до момента «три дня назад»:

```python
now = datetime.now(timezone.utc)                                 # 2026-11-13 18:36:47
store.materialize_incremental(end_date=now - timedelta(days=3))
# pair_stats from 2025-01-02 00:00:00+00:00 to 2026-11-10 18:36:47+00:00:
```

Ответ — таблица из раздела 3: `units_mean_7d = 31.14`, статус `PRESENT`, отметка `2026-11-10 00:00`.
Возраст значения — 3 дня 18 часов. Настоящее значение на этот момент — 27.43: сервис получает число
на 14 % больше, и ничто в ответе на это не указывает.

**Что это значит.** В `feast 0.68.0` с онлайн-хранилищем SQLite обычный путь чтения возраст значения
не проверяет: всё найденное получает статус `PRESENT`. В исходном коде этой версии статус
`OUTSIDE_MAX_AGE` выставляется только на пути чтения заранее собранных векторов (сервис признаков
с параметром `precompute_online=True`); этот путь запуском не проверялся. `ttl` в этой версии действует
в двух местах: в исторических запросах и при выборе начала первой инкрементальной материализации.

Отсюда расхождение между обучением и работой. В офлайн-запросе TTL работает точно — запросы к значению
с отметкой `2026-11-13 00:00`:

| Момент запроса | Возраст значения | Офлайн (`get_historical_features`) | Онлайн при таком возрасте |
|---|---|---|---|
| 2026-11-14 00:00 | 1 день | 27.428571 | значение |
| 2026-11-15 00:00 | 2 дня | 27.428571 | значение |
| 2026-11-16 00:00 | 3 дня | NaN | значение, статус `PRESENT` (опыты 1 и 2) |

Модель обучена на выборке, где признак старше двух суток — пропуск. В работе она получит на его месте
число. Это не утечка, а сдвиг входных данных, который включается ровно тогда, когда что-то уже сломалось.

**Что делать.** Проверять свежесть самим: отметка времени в ответе есть.

```python
def is_fresh(data: dict, name: str, row: int, ttl: timedelta, now: datetime) -> bool:
    seconds = data[f"{name}__ts"][row]                 # 0 — значения нет
    return bool(seconds) and now - datetime.fromtimestamp(seconds, timezone.utc) <= ttl
```

Устаревшее значение заменяется пропуском — тогда сервис видит то же, что видела бы обучающая выборка, —
а сам факт попадает в журнал и метрики. В практике 7.3.4 это функция `online_features` с тремя
статусами: `fresh`, `stale`, `missing`. Второй рубеж — наблюдение за материализацией: возраст самого
свежего значения в онлайн-хранилище — число, по которому ставят оповещение.

Обобщать результат опыта на другие версии и другие онлайн-хранилища нельзя; переносится способ проверки:
запишите значение со старой отметкой времени и прочитайте его.

## 5. Согласованность онлайн и офлайн

После материализации до текущего момента обе стороны должны отдавать одно и то же. Проверка для всех
96 пар: онлайн-значения сейчас против исторического запроса с моментом «сейчас».

```python
store.materialize_incremental(end_date=now)
pairs = feat[["store_id", "product"]].drop_duplicates()
service = store.get_feature_service("sales_forecast_v1")

online = store.get_online_features(features=service, entity_rows=pairs.to_dict("records")).to_df()
offline = store.get_historical_features(
    entity_df=pairs.assign(event_timestamp=pd.Timestamp(now)), features=service
).to_df()
both = online.merge(offline, on=["store_id", "product"], suffixes=("_online", "_offline"))
```

| Признак | Пар | Совпало бит в бит | Наибольшее расхождение |
|---|---|---|---|
| `units_mean_7d` | 96 | 96 | 0 |
| `units_mean_28d` | 96 | 96 | 0 |
| `promo_share_28d` | 96 | 96 | 0 |
| `store_units_7d` | 96 | 96 | 0 |

(Онлайн-запрос на 96 ключей — 10 мс, исторический — 70 мс.) Соединять результаты нужно по ключу:
порядок строк у двух ответов разный.

Совпадение — свойство момента сразу после материализации. Расходятся значения по четырём причинам,
и три из них воспроизведены в этом уроке:

| Причина | Что происходит | Где показано |
|---|---|---|
| Материализация отстаёт | онлайн отдаёт старое значение, офлайн — новое или пропуск по TTL | раздел 4 |
| Запись только в онлайн | push без записи в офлайн-таблицу | раздел 8 |
| Запоздавшее событие | старое значение записано поверх нового | раздел 8 |
| Пересчёт истории | офлайн-таблица исправлена, онлайн-хранилище не обновлено | практика 7.3.4 |

Проверка согласованности — не разовое действие, а регулярная задача: раз в сутки сверить онлайн-значения
выборки ключей с офлайн-запросом и записать число расхождений.

## 6. Признаки в момент запроса: on-demand feature views

Часть признаков нельзя посчитать заранее: они зависят от данных запроса. Цена на завтра известна
сервису, но не хранилищу. Такие признаки описываются функцией над готовыми признаками и полями запроса:

```python
import pandas as pd
from feast import Field, RequestSource
from feast.on_demand_feature_view import on_demand_feature_view
from feast.types import Float64

forecast_request = RequestSource(name="forecast_request", schema=[Field(name="price", dtype=Float64)])


@on_demand_feature_view(
    sources=[pair_stats, forecast_request],
    schema=[Field(name="units_trend", dtype=Float64), Field(name="revenue_at_price", dtype=Float64)],
    mode="pandas",
)
def demand_signals(inputs: pd.DataFrame) -> pd.DataFrame:
    out = pd.DataFrame()
    out["units_trend"] = inputs["units_mean_7d"] / inputs["units_mean_28d"]
    out["revenue_at_price"] = inputs["units_mean_7d"] * inputs["price"]
    return out
```

После `feast apply` (`Created on demand feature view demand_signals`, `No changes to infrastructure` —
таблиц для таких признаков не создаётся) поле запроса передаётся вместе с ключом:

```python
refs = ["pair_stats:units_mean_7d", "pair_stats:units_mean_28d",
        "demand_signals:units_trend", "demand_signals:revenue_at_price"]
store.get_online_features(
    features=refs, entity_rows=[{"store_id": "S01", "product": "Мышь", "price": 1490.0}]
).to_dict()
# {'store_id': ['S01'], 'product': ['Мышь'], 'units_mean_7d': [27.428571428571427],
#  'units_mean_28d': [27.464285714285715], 'units_trend': [0.9986996098829648],
#  'revenue_at_price': [40868.57142857143]}
```

В историческом запросе `price` — столбец таблицы запросов, и та же функция применяется к каждой строке.
Для одной пары и одного момента онлайн- и офлайн-значения обоих признаков совпали бит в бит. В этом
и смысл: преобразование написано один раз и выполняется одним кодом в обучении и в работе — то самое
расхождение из урока 7.3.1 устранено устройством, а не дисциплиной.

Запрос без `price` — ошибка, а не пропуск:

```text
RequestDataNotFoundInEntityRowsException: Required request data source features ['price'] not found
in the entity rows, but required by feature views
```

Цена удобства — время: раздел 7.

## 7. Задержка чтения

Замер на локальном SQLite, один процесс, 2 000 вызовов после прогрева (для запросов тяжелее — 500 и 30),
миллисекунды:

| Запрос | p50 | p95 | p99 |
|---|---|---|---|
| прямой `SELECT` из SQLite по ключу, без Feast | 0.005 | 0.005 | 0.008 |
| 1 ключ, 3 признака одного представления | 0.084 | 0.115 | 0.131 |
| 1 ключ, сервис признаков (4 признака, два представления) | 0.122 | 0.156 | 0.173 |
| то же и `to_dict()` | 0.135 | 0.169 | 0.185 |
| 1 ключ с on-demand view (`mode="pandas"`) | 1.963 | 2.758 | 2.944 |
| 96 ключей одним запросом, сервис признаков | 2.448 | 3.550 | 3.689 |
| 96 ключей по одному, сервис признаков | 12.310 | 12.596 | 12.659 |
| HTTP-сервер признаков на той же машине, 1 ключ | 2.02 | 2.29 | 2.75 |

Что из этого следует:

- само чтение по ключу — 5 микросекунд; остальные 80–120 — работа Feast: реестр, сериализация ключа,
  сборка ответа. Второе представление признаков — второй запрос к базе: +0.04 мс;
- on-demand view в режиме `pandas` стоит 1.8 мс на запрос — в 15 раз дороже всего остального: на одну
  строку создаётся `DataFrame`. Арифметику из двух действий дешевле выполнить в коде сервиса или внутри
  `Pipeline` модели; on-demand view оправдан, когда преобразование нетривиально и должно быть общим;
- 96 ключей одним запросом — 2.4 мс, по одному — 12.3 мс: запросы нужно объединять;
- HTTP добавляет около 2 мс даже без сети (новое соединение на каждый запрос).

Это нижняя граница: локальный файл, без сети и без конкурирующих запросов. Удалённое хранилище
добавляет время сетевого обмена — обычно оно и определяет результат.

## 8. Push-источники

Материализация по расписанию даёт признаки с задержкой в период расписания. Если значение нужно сразу —
его записывают напрямую через push-источник:

```python
from feast import PushSource

pair_stats_push = PushSource(name="pair_stats_push", batch_source=pair_stats_source)
pair_stats = FeatureView(name="pair_stats", ..., source=pair_stats_push)      # остальное без изменений
```

`feast plan` показывает `Updated feature view pair_stats` и смену типа источника с `BATCH_FILE`
на `PUSH_SOURCE`. Пакетный источник остаётся внутри: исторические запросы и материализация работают
как прежде.

```python
from feast.data_source import PushMode

event = pd.DataFrame({
    "store_id": ["S01"], "product": ["Мышь"],
    "event_timestamp": [pd.Timestamp(now).floor("s")], "created": [pd.Timestamp(now).floor("s")],
    "units_mean_7d": [30.0], "units_mean_28d": [28.0], "promo_share_28d": [0.1],
})
store.push("pair_stats_push", event, to=PushMode.ONLINE)                       # 7 мс
```

| Шаг | Онлайн `units_mean_7d` | Отметка времени онлайн | Офлайн `units_mean_7d` |
|---|---|---|---|
| до записи | 27.428571 | 2026-11-13 00:00:00 | 27.428571 |
| `push(..., to=PushMode.ONLINE)` | 30.0 | 2026-11-13 18:37:52 | 27.428571 |
| запоздавшее событие: отметка на 5 дней старше, значение 1.0 | **1.0** | **2026-11-08 18:37:52** | 27.428571 |
| `push(..., to=PushMode.ONLINE_AND_OFFLINE)`, значение 31.0 | 31.0 | 2026-11-13 18:37:53 | 31.0 |

Три наблюдения.

1. **Запись только в онлайн — расхождение по построению.** Сервис уже отвечает 30.0, а обучающая выборка
   на тот же момент содержит 27.43. Модель обучается не на тех значениях, которые видела в работе.
2. **Запоздавшее событие перезаписало свежее значение.** SQLite-хранилище в этой версии отметки времени
   не сравнивает: кто записал последним, тот и прав. Событие, пришедшее с опозданием (повтор доставки,
   перезапуск обработчика), вернуло признак на пять дней назад. Защита — на стороне пишущего: сравнить
   отметку времени с уже записанной.
3. **`ONLINE_AND_OFFLINE` пишет в оба хранилища:** в parquet-файле стало 70 177 строк вместо 70 176,
   и исторический запрос вернул 31.0. Для файла это дозапись при каждом событии; в промышленной установке
   офлайн-запись идёт в таблицу хранилища данных.

После `push` следующая инкрементальная материализация значение не тронула: в её интервале не было новых
строк пакетного источника. Записанное значение остаётся в онлайн-хранилище, пока материализация
не запишет поверх него новое значение из пакетного источника.

Сервис, написанный не на Python, получает признаки по HTTP:


```json
{"results": [{"values": ["S01"], "statuses": ["PRESENT"], "event_timestamps": ["1970-01-01T00:00:00Z"]},
             {"values": ["Мышь"], "statuses": ["PRESENT"], "event_timestamps": ["1970-01-01T00:00:00Z"]},
```

машине, замер — в таблице раздела 7; после проверки процесс остановлен.

## 10. Что меняется в промышленной установке

> Не проверялось запуском: в среде подготовки нет ни Redis, ни облачных учётных записей. Раздел
> написан по документации Feast.

| Часть | Локально (этот урок) | Промышленная установка |
|---|---|---|
| Онлайн-хранилище | файл SQLite, один процесс | Redis, DynamoDB, Bigtable, PostgreSQL — общий для всех экземпляров сервиса |
| Офлайн-хранилище | parquet + DuckDB | хранилище данных: BigQuery, Snowflake, Redshift, Spark |
| Реестр | файл `registry.db` | база данных (SQL-реестр) или файл в объектном хранилище |
| Материализация | команда вручную | задача оркестратора по расписанию; для больших объёмов — отдельный движок |
| Чтение | вызов библиотеки в процессе | сервер признаков или библиотека в сервисе прогноза |
| Свежие события | `store.push` из скрипта | потоковый обработчик (Kafka, Kinesis), пишущий через push-источник |

Замена хранилища — правка `feature_store.yaml` (например, `online_store: {type: redis,
connection_string: "хост:6379"}`); определения признаков не меняются. Меняется поведение: в Redis срок
жизни ключа может обеспечивать сама база, задержка чтения определяется сетью, а запись и чтение идут
из разных процессов одновременно. Всё, что в этом уроке проверено на SQLite, — возраст значений,
запоздавшие события, согласованность — на новом хранилище проверяется заново теми же опытами.

## Типичные ошибки

| Симптом | Причина | Решение |
|---|---|---|
| `Conversion Error: Unimplemented type for cast (TIMESTAMPTZ_NS -> TIMESTAMP)` при `materialize` | отметки времени в parquet записаны в наносекундах (pandas 2) | `astype("datetime64[us, UTC]")` перед записью |
| `get_online_features` возвращает `None` для всех ключей | материализация не выполнялась или её интервал не покрыл данные | `materialize-incremental`; проверить `materialization_intervals` |
| Сервис получает значения недельной давности, ошибок нет | материализация остановилась; Feast 0.68 с SQLite возраст при чтении не проверяет | своя проверка по отметке времени; оповещение на возраст данных |
| Признак в работе есть, а в обучающей выборке за тот же момент — пропуск | офлайн TTL применяется, онлайн — нет | устаревшие онлайн-значения заменять пропуском |
| Онлайн- и офлайн-значения разошлись после срочного исправления | `push` с `PushMode.ONLINE` | `ONLINE_AND_OFFLINE`; регулярная сверка |
| Признак «откатился» на старое значение | запоздавшее событие записано поверх свежего | сравнивать отметку времени перед записью |
| `RequestDataNotFoundInEntityRowsException` | в запросе нет поля, нужного on-demand view | передавать поля `RequestSource` вместе с ключом |
| p50 чтения вырос с 0.1 до 2 мс | добавлен on-demand view в режиме `pandas` | простую арифметику — в код сервиса или в `Pipeline` |
| Сервис отвечает медленно при прогнозе по всем товарам | ключи запрашиваются по одному | один запрос со списком ключей |
| Признаки перепутаны местами | порядок столбцов ответа принят равным порядку запроса | обращаться по имени |
