# Урок 7.3.4: ПРАКТИКА: Создание Feature Store для проекта

> **Модуль 7:** ML Engineering & MLOps · **Тема 7.3:** Feature Store и данные
> **Тип:** практика · **Время:** 6–8 часов

## Задача

У проекта прогноза продаж есть пайплайн (практика 7.1.4) и трекинг экспериментов (практика 7.2.4).
Признаки при этом считаются внутри обучения и нигде больше: сервису прогноза взять их неоткуда,
а проверить, что обучающая выборка собрана без взгляда в будущее, нечем. К признакам предъявляется одно
требование:

> **Значение признака, на котором модель обучалась, и значение, которое она получает в работе, — одно
> и то же число, известное в момент прогноза, проверенное и не старше срока годности.**

Вы пишете модуль `sales_features.py` из восьми функций. Они проводят признак по всему пути: таблица
продаж → таблица признаков с отметками времени → проверка → публикация в Feast → обучающая выборка
без утечки → признаки для прогноза с контролем свежести → сверка двух хранилищ.

```bash
uv run python run_store.py --now 2025-01-01T06:00:00+00:00
```

Команда строит признаки, публикует их, собирает обучающую выборку, обучает модель, получает признаки
для прогноза и печатает число расхождений между онлайн- и офлайн-значениями.

Зачем свои функции поверх Feast? Уроки темы показали три места, где библиотека не защищает: отметку
времени задаёт ваш код (7.3.1), возраст значения при чтении не проверяется (7.3.2), содержимое данных
не проверяется вовсе (7.3.3). Каждое из них закрывается функцией, поведение которой задано тестами.

## Требования

| Требование | Что это значит здесь | Как проверяется |
|---|---|---|
| Отметка времени — момент, когда значение стало известно | статистика за день D получает отметку 00:00 UTC дня D+1; значение не зависит от более поздних дней | `test_features_timestamp_is_start_of_next_day`, `test_features_do_not_depend_on_later_days` |
| Окна — календарные | среднее за 7 дней считается по дням D-6 … D, даже если части дней в данных нет; пропуски не учитываются | `test_features_rolling_means`, `test_features_window_is_calendar_days`, `test_features_missing_units_are_skipped` |
| Соединение по времени | берётся последнее значение не позже момента запроса и не старше `ttl`; обе границы включены | `test_join_takes_latest_value_known_at_request_time`, `test_join_ttl_bounds_are_inclusive`, `test_join_never_looks_into_the_future` |
| Нет утечки целевой переменной | продажи дня, для которого строится прогноз, в его признаки не попадают | `test_join_does_not_leak_the_label_day`, `test_training_frame_does_not_leak_the_label_day` |
| Проверка перед публикацией | восемь проверок; отчёт перечисляет непройденные в заданном порядке | `test_validate_reports_failed_checks` (16 случаев), `test_validate_freshness_depends_on_now_and_max_age` |
| Шлюз | отклонённая таблица не меняет ни офлайн-таблицу, ни онлайн-хранилище | `test_publish_rejects_bad_table_and_changes_nothing`, `test_publish_rejected_first_table_leaves_store_empty` |

## Пошаговый план

Точные требования — в docstring заготовки. Шаги 1–3 — чистый pandas, Feast для них не нужен. Тесты
шагов 4–7 готовят данные сами (пишут parquet и онлайн-значения в обход ваших функций), поэтому каждый шаг
проверяется отдельно; от предыдущих шагов зависят только публикация и сверка.

### Шаг 1. `build_pair_features`

Таблица признаков пары: два скользящих средних продаж и доля дней с акцией. Три решения, на которых
держится остальное:

- `event_timestamp = date + 1 день`, тип `datetime64[us, UTC]`. Используйте `datetime.timedelta`:
  `pd.Timedelta(days=1)` в этом окружении выдаёт предупреждение (урок 7.3.1);
- окна — по календарным дням: `rolling("7D")` по индексу-дате, а не `rolling(7)` по строкам. При пропущенных
  днях `rolling(7)` захватит продажи двухнедельной давности;
- результат `groupby(...).rolling(...)` выравнивайте по индексу (пара, дата), а не по порядку строк.
  Порядок групп в результате не обязан совпадать с порядком строк таблицы: на данных с двумя магазинами
  и тремя товарами значения молча уезжают в чужие пары. Тест
  `test_features_pairs_are_independent_and_row_order_is_irrelevant` написан после того, как это случилось
  с эталонным решением.

```bash
uv run pytest -q -k test_features
```

### Шаг 2. `point_in_time_join`

Соединение по времени на pandas — `pd.merge_asof` с параметрами `by` и `tolerance`. Подводные камни:

- обе таблицы должны быть отсортированы по времени, а результат — возвращён в исходном порядке и с исходным
  индексом: пронесите через соединение номер строки;
- типы столбцов времени слева и справа должны совпадать — приведите оба к `TIMESTAMP_DTYPE`;
- `tolerance` принимает `pd.Timedelta`; из `timedelta` он создаётся без предупреждения:
  `pd.Timedelta(ttl)`;
- две строки признаков с одной отметкой времени: берётся та, у которой больше `created`. Уберите лишние
  до соединения.

```bash
uv run pytest -q -k test_join
```

### Шаг 3. `validate_features`

Восемь проверок из `CHECKS`. Реализация свободная: функция на pandas, схема pandera, набор ожиданий
Great Expectations (урок 7.3.3) — тесты смотрят только на словарь-отчёт. Два правила порядка: провал
`schema` или `not_empty` прекращает проверку (остальные на такой таблице бессмысленны или упадут),
а `failed` всегда перечисляет имена в порядке `CHECKS`. Момент `now` приходит параметром — системные
часы функция не читает.

```bash
uv run pytest -q -k test_validate
```

### Шаг 4. `create_store`

Репозиторий Feast без `feature_store.yaml`: объект `RepoConfig` и `store.apply([...])` вместо команды
`feast apply`. Офлайн-хранилище — DuckDB, пути — абсолютные (урок 7.3.1).

Подводный камень — пустая офлайн-таблица, которую функция создаёт при первом вызове. Пустой столбец
pandas типа `object` записывается в parquet с типом `null`, и первый же исторический запрос падает:

```text
IbisTypeError: Arguments store_id:unknown(...) and store_id:string are not comparable
```

Задайте типы явно — схемой Arrow (`pa.schema([...]).empty_table()` и `pyarrow.parquet.write_table`).

```bash
uv run pytest -q -k test_store
```

### Шаг 5. `get_training_frame`

Обёртка над `get_historical_features` с сервисом признаков. Вся работа — вернуть результат в том виде,
в каком пришёл запрос: Feast меняет порядок строк (на запросе из 600 строк — при каждом запуске
по-разному) и точность отметок времени. Тест сравнивает результат с вашим же `point_in_time_join`
через `assert_frame_equal`: два независимых расчёта должны сойтись до бита.

### Шаг 6. `publish_features`

Шлюз из урока 7.3.3: проверка → запись офлайн-таблицы → материализация. Порядок строгий: до успешной
проверки не меняется ничего. Путь к файлу берите из реестра (`view.batch_source.path`), интервал
материализации — `[now - ttl, now]` через `store.materialize(...)`: у `materialize_incremental`
начало первого интервала отсчитывается от системных часов, а не от `now`.

```bash
uv run pytest -q -k "test_training_frame or test_publish"
```

### Шаг 7. `online_features` и `check_consistency`

`online_features` — чтение с тремя статусами. Отметку времени значения отдаёт
`response.to_dict(include_event_timestamps=True)` в ключах `<признак>__ts` (секунды; 0 — значения нет).
Отличайте «пары нет» от «пара есть, а значение признака пустое»: во втором случае статус `fresh`.

`check_consistency` — две ваши функции и сравнение. Пропуск с обеих сторон — согласие: устаревшее значение
и для обучения (`ttl`), и для прогноза (`stale`) выглядит одинаково, и это именно то свойство, ради
которого `online_features` прячет устаревшее.

```bash
uv run python -W error -m pytest -q
```

### Шаг 8. Подключение к проекту

Напишите `run_store.py`, который выполняет весь путь на данных `make_sales()`:

```python
sales = make_sales()
features = build_pair_features(sales)
store = create_store(args.repo)
publish_features(store, features, args.now)

entity = sales.dropna(subset=["units"])[["date", "store_id", "product", "price", "promo", "units"]].copy()
entity["event_timestamp"] = entity["date"].dt.tz_localize("UTC")        # прогноз делается в начале дня
frame = get_training_frame(store, entity)
frame["dow"] = frame["date"].dt.day_of_week
columns = ["price", "promo", "dow", *FEATURE_NAMES]
train = frame[frame["date"] < "2024-07-01"]
model = HistGradientBoostingRegressor(random_state=0).fit(train[columns], train["units"])

rows = features[KEYS].drop_duplicates().to_dict("records")
online = online_features(store, rows, args.now)                         # признаки для прогноза на сегодня
mismatches = check_consistency(store, rows, args.now)
```

На что обратить внимание:

- `now` — аргумент командной строки, а не `datetime.now()`: запуск можно повторить для любого момента;
- в запись о запуске (практика 7.2.4) добавьте имя сервиса признаков `FEATURE_SERVICE`, хеш файла
  офлайн-таблицы и границу времени обучающей выборки;
- каталог хранилища (`registry.db`, `online_store.db`, parquet) — в `.gitignore`;
- модель обучается на пропусках там, где признак устарел или отсутствует, — и в работе получает пропуски
  в тех же случаях. `HistGradientBoostingRegressor` принимает их как есть; для линейной модели
  заполнение пропусков — шаг `Pipeline` (урок 7.1.1).

## Что дальше

Теперь у модели есть не только происхождение, но и снабжение: признаки вычисляются одним кодом,
проверяются перед публикацией, выдаются обучению «на момент», а сервису — с отметкой о свежести.
Не хватает самого сервиса: модель из реестра и признаки из онлайн-хранилища пока встречаются только
