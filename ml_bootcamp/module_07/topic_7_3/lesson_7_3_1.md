## Зачем это нужно

К концу темы 7.2 у каждой модели есть происхождение: код, данные, параметры, окружение. Признаки остались
без присмотра. Обучение считает их в одном скрипте, по всей истории сразу; сервис прогноза — в другом,
по тому, что известно сейчас. Пока оба делают одно и то же, всё хорошо. Расходятся они молча: метрика
на проверочной выборке отличная, а прогнозы в работе хуже — и ни один тест не падает.

Хранилище признаков (feature store) — это одно определение признака, из которого получаются и обучающая
выборка, и значения для прогноза, причём обучающая выборка собирается **на тот момент времени, когда
делался бы прогноз**. Последнее — самое важное и наименее очевидное, поэтому бо́льшая часть урока о нём.

Сквозная задача модуля прежняя: прогноз дневных продаж сети магазинов, данные — генератор `sales_data.py`
из темы 2.1 (8 магазинов, 12 товаров, два года, 70 176 строк).

Версии урока: Python 3.12.13, `feast 0.68.0`, `pandas 2.3.3`, `numpy 2.5.4`, `pyarrow 26.0.1`,
`duckdb 2.0.0`, `ibis-framework 12.0.0`, `scikit-learn 1.9.1`; машина — 4 ядра, 16 ГБ памяти, Linux.
Все числа в уроке получены на этих версиях.

## 1. Три проблемы

**Расхождение обучения и применения (training-serving skew).** Признак «средние продажи пары за 7 дней»
в обучении считается через `groupby().rolling()` по всей таблице, а в сервисе — запросом к базе за последние
семь дней. Два кода — два результата: один включает сегодняшний день, другой нет; один пропускает
пустые значения, другой считает их нулями. Модель обучена на одних числах, а получает другие.

**Утечка во времени.** Обучающая строка за 30 июня должна содержать только то, что было известно утром
30 июня. Таблица признаков, посчитанная сегодня, знает и про 30 июня, и про всё, что было после. Обычный
`merge` присоединит эти знания к обучающей строке, и модель научится пользоваться тем, чего в работе
у неё не будет. Раздел 3 показывает размер эффекта на числах.

**Повторное использование.** Статистики продаж нужны модели прогноза, модели оттока, отчёту о промоакциях.
Без общего места каждая команда считает их заново — со своими ошибками и своими определениями «недели».

Хранилище признаков отвечает на все три одним устройством:

| Часть | Что делает | Какую проблему закрывает |
|---|---|---|
| Определения признаков в коде | одно описание: ключ, источник, типы, срок годности | повторное использование; расхождение |
| Офлайн-хранилище | вся история значений с отметками времени; из неё собирается обучающая выборка | утечка во времени |
| Онлайн-хранилище | последнее значение на каждый ключ; из него читает сервис прогноза | расхождение; скорость ответа |
| Реестр | список всех объектов: что есть, кто владелец, откуда берётся | повторное использование |

Важно, чего в этом списке нет: хранилище признаков **не вычисляет** признаки. Feast, о котором пойдёт
речь, получает готовую таблицу и отвечает за хранение, выдачу «на момент» и перенос в онлайн-хранилище.
Расчёт остаётся вашим кодом — и требования к нему разбираются в следующем разделе.

Два следствия для кода этой темы — оба проверены и оба стоят ошибок, если о них не знать:

- отметки времени в pandas 2 по умолчанию хранятся с точностью до наносекунд, а связка Feast — DuckDB
  наносекунды из parquet читает не везде (урок 7.3.2). Таблицы признаков записываются с типом
  `datetime64[us, UTC]`;
- в сочетании `pandas 2.3.3` и `numpy 2.5.4` выражения `pd.Timedelta(days=1)` и `pd.Timedelta("1D")` выдают
  `DeprecationWarning: The 'generic' unit for NumPy timedelta is deprecated`. Со строгим режимом
  предупреждений (`-W error`) это падение. `datetime.timedelta(days=1)` и `pd.Timedelta(1, "D")`
  предупреждения не вызывают — в уроках используется `timedelta`.

## 3. Отметка времени признака

Признаки урока — скользящие статистики пары «магазин — товар» и магазина целиком:

```python
import sys
from datetime import timedelta

import pandas as pd

sys.path.insert(0, "../../module_02/topic_2_1")
from sales_data import make_sales

KEYS = ["store_id", "product"]


def pair_stats(sales: pd.DataFrame) -> pd.DataFrame:
    """Скользящие статистики пары «магазин — товар» на конец каждого дня."""
    sales = sales.sort_values(KEYS + ["date"], ignore_index=True)
    grouped = sales.groupby(KEYS, sort=False)
    out = sales[KEYS].copy()
    out["event_timestamp"] = (sales["date"] + timedelta(days=1)).dt.tz_localize("UTC")
    out["units_mean_7d"] = grouped["units"].transform(lambda s: s.rolling(7, min_periods=1).mean())
    out["units_mean_28d"] = grouped["units"].transform(lambda s: s.rolling(28, min_periods=1).mean())
    out["promo_share_28d"] = grouped["promo"].transform(lambda s: s.astype(float).rolling(28, min_periods=1).mean())
    out["created"] = out["event_timestamp"] + timedelta(hours=3)
    return out
```

`store_stats` устроена так же: ключ — `store_id`, признак `store_units_7d` — сумма продаж магазина за 7 дней.
Перед записью оба столбца времени приводятся к `datetime64[us, UTC]`.

```python
sales = make_sales()
pair_stats(sales).to_parquet("sales_repo/data/pair_stats.parquet", index=False)      # 70 176 строк
store_stats(sales).to_parquet("sales_repo/data/store_stats.parquet", index=False)    # 5 848 строк
```

Главная строка функции — `event_timestamp = date + 1 день`. Статистика «за семь дней по 30 июня
включительно» становится известна, когда 30 июня закончилось: в 00:00 1 июля. **Отметка времени признака —
это момент, начиная с которого значение можно использовать, а не дата, которую оно описывает.** Назвать
столбец `date` и записать в него 30 июня — самая частая ошибка при заведении хранилища признаков: формально
всё верно, а по существу значение объявлено известным на сутки раньше, чем оно появилось.

Столбец `created` — время, когда строка попала в таблицу (здесь — через три часа, после ночной загрузки).
Он нужен, когда значение за тот же момент приходит повторно: из двух строк с одной отметкой времени
берётся записанная позже. На вопрос «когда значение стало известно» он не отвечает; что из этого следует,
если загрузка опаздывает, — в «Типичных ошибках».

Продажи одной пары (магазин `S01`, товар «Мышь») и её строки в таблице признаков:

```text
      date  promo  units          event_timestamp  units_mean_7d
2024-06-28  False    3.0      2024-06-29 00:00+00      11.571429
2024-06-29  False   12.0      2024-06-30 00:00+00      11.428571
2024-06-30   True   24.0      2024-07-01 00:00+00      12.428571
2024-07-01  False    8.0      2024-07-02 00:00+00      12.000000
2024-07-02  False   13.0      2024-07-03 00:00+00      11.857143
```

Строка с отметкой `2024-07-01 00:00` — среднее за 24–30 июня: (11 + 14 + 12 + 11 + 3 + 12 + 24) / 7 = 12.43.
День акции 30 июня с 24 продажами в неё входит.

## 4. Соединение по времени — и чем оно отличается от merge

Обучающая строка — «30 июня, S01, Мышь, продано 24». Прогноз на 30 июня делается утром 30 июня, значит
**момент запроса** — `2024-06-30 00:00`. Правило соединения по времени:

> для каждой обучающей строки взять строку признаков того же ключа с наибольшей отметкой времени,
> не превышающей момент запроса, — и не старше срока годности (TTL).

Три способа собрать обучающую выборку:

```python
base = sales.dropna(subset=["units"])[["date", "store_id", "product", "price", "promo", "units"]].copy()
base["dow"] = base["date"].dt.day_of_week
base["event_timestamp"] = base["date"].dt.tz_localize("UTC")          # момент запроса

# A. merge по дате: строка признаков «за день D» присоединяется к продажам дня D
by_date = feat.assign(date=(feat["event_timestamp"] - timedelta(days=1)).dt.tz_localize(None))
A = base.merge(by_date.drop(columns="event_timestamp"), on=["date", "store_id", "product"], how="left")

# B. последний снимок: текущие значения признаков присоединяются ко всей истории
snapshot = feat.sort_values("event_timestamp").groupby(KEYS, as_index=False).last()
B = base.merge(snapshot.drop(columns="event_timestamp"), on=KEYS, how="left")

# C. соединение по времени
C = pd.merge_asof(
    base.sort_values("event_timestamp"),
    feat.sort_values("event_timestamp").rename(columns={"event_timestamp": "feature_ts"}),
    left_on="event_timestamp", right_on="feature_ts", by=KEYS, tolerance=pd.Timedelta(timedelta(days=2)),
)
```

(`feat` — таблица `pair_stats` без столбца `created`; признак магазина присоединяется так же.) Что получает
одна и та же пара:

| Обучающая строка | `units` | A: merge по дате | B: последний снимок | C: по времени |
|---|---|---|---|---|
| 29 июня | 12 | 11.43 | 27.43 | 11.57 |
| 30 июня | 24 | **12.43** | 27.43 | 11.43 |
| 1 июля | 8 | 12.00 | 27.43 | 12.43 |
| 2 июля | 13 | 11.86 | 27.43 | 12.00 |

Вариант A выглядит естественно — «признаки за день к продажам за день» — и содержит ответ: среднее 12.43
в строке за 30 июня уже включает 24 продажи этого дня. Вариант B присоединяет ко всей истории значение
конца декабря 2024 года (27.43 — предновогодний пик): модель, обучаемая на июне, видит будущее на полгода
вперёд. Вариант C даёт 11.43 — среднее за 23–29 июня, то, что действительно было известно утром 30-го.

Насколько это важно для модели. Обучение — до 1 июля 2024 (52 263 строки), проверка — последние полгода
(17 578 строк, средние продажи 5.22). Признаки модели: `price`, `promo`, `dow` и четыре признака
из хранилища. Для каждого варианта считаются две ошибки:

- **MAE офлайн** — на проверочной выборке, собранной тем же способом, что и обучающая. Это число,
  которое увидит автор модели;
- **MAE в работе** — та же модель на проверочной выборке с честными признаками (вариант C): в работе
  сервис получит именно их, других значений в момент прогноза не существует.

`HistGradientBoostingRegressor(random_state=0)`:

| Вариант | MAE офлайн | MAE в работе |
|---|---|---|
| без признаков хранилища | 2.3790 | 2.3790 |
| C: соединение по времени | 1.7408 | 1.7408 |
| A: merge по дате | 1.5987 | 1.8237 |
| B: последний снимок | 2.1203 | 2.5214 |

Вариант A на бумаге лучше честного на 8 % (1.5987 против 1.7408), а в работе хуже на 5 % (1.8237).
Разрыв между «офлайн» и «в работе» — 0.225 единицы товара — и есть цена утечки: модель привыкла, что
в среднем за неделю уже учтён сегодняшний день, и в работе получает признак, сдвинутый на сутки.
Корреляция `units_mean_7d` с целевой переменной: 0.768 у честного варианта и 0.826 у варианта A.

Вариант B плох даже офлайн (2.12) и ещё хуже в работе (2.52 — хуже модели вообще без этих признаков):
снимок конца декабря описывает уровень продаж пары, но не её динамику, а в работе модель получает
динамику. С линейной моделью (`Ridge` после заполнения пропусков и масштабирования) картина та же:
честный вариант — 1.8394; A — 1.7001 офлайн и 1.9275 в работе; B — 2.1972 и 2.5765.

Утечка этого вида опасна тем, что **делает метрику лучше**. Её не ловит ни проверочная выборка, ни
кросс-валидация по времени: проверочные строки собраны тем же ошибочным способом. Ловит её только
сравнение с работой — или устройство, в котором неправильно соединить нельзя.

## 5. Feast: объекты и реестр

Feast — библиотека и набор соглашений, а не сервер: определения признаков лежат в Python-файле,
состояние — в реестре, данные — в хранилищах, которые вы укажете. Локальный вариант не требует ничего,
кроме файлов.

```text
sales_repo/
├── feature_store.yaml        настройки: проект, реестр, хранилища
├── features.py               определения признаков
└── data/
    ├── pair_stats.parquet    офлайн-данные: история значений
    └── store_stats.parquet
```

```yaml
# feature_store.yaml
project: sales
provider: local
registry: data/registry.db
offline_store:
  type: duckdb
online_store:
  type: sqlite
  path: data/online_store.db
entity_key_serialization_version: 3
```

```python
# features.py
from datetime import timedelta

from feast import Entity, FeatureService, FeatureView, Field, FileSource, ValueType
from feast.types import Float64

store = Entity(name="store", join_keys=["store_id"], value_type=ValueType.STRING, description="Магазин сети")
product = Entity(name="product", join_keys=["product"], value_type=ValueType.STRING, description="Товар")

pair_stats_source = FileSource(
    name="pair_stats_source",
    path="data/pair_stats.parquet",
    timestamp_field="event_timestamp",
    created_timestamp_column="created",
)

pair_stats = FeatureView(
    name="pair_stats",
    entities=[store, product],
    ttl=timedelta(days=2),
    schema=[
        Field(name="units_mean_7d", dtype=Float64, description="Средние продажи пары за 7 дней"),
        Field(name="units_mean_28d", dtype=Float64),
        Field(name="promo_share_28d", dtype=Float64),
    ],
    source=pair_stats_source,
    online=True,
    tags={"owner": "forecast-team"},
)

sales_forecast_v1 = FeatureService(
    name="sales_forecast_v1",
    features=[pair_stats, store_stats],
    description="Признаки модели прогноза дневных продаж, версия 1",
)
```

(`store_stats_source` и `store_stats` описаны так же: одна сущность `store`, один признак `store_units_7d`.)

| Объект | Что это | В проекте |
|---|---|---|
| Сущность (entity) | то, к чему относится признак; задаёт ключ соединения | `store` → `store_id`, `product` → `product` |
| Источник данных (data source) | где лежит история и какой столбец — отметка времени | два parquet-файла |
| Представление признаков (feature view) | группа признаков с общим ключом, источником и сроком годности | `pair_stats` (ключ из двух сущностей), `store_stats` |
| Сервис признаков (feature service) | именованный набор признаков для одной модели | `sales_forecast_v1` |
| Реестр (registry) | сериализованное описание всех объектов проекта | файл `data/registry.db` |

`ttl` — срок годности значения: признак старше двух суток считается отсутствующим. В исторических
запросах это правило работает точно (раздел 6); как оно ведёт себя при чтении из онлайн-хранилища —
отдельный и не самый приятный разговор в уроке 7.3.2.

Сервис признаков — это контракт модели. Модель записывает в параметры запуска `sales_forecast_v1`
и получает один и тот же набор признаков в обучении и в работе. Изменился набор — появляется
`sales_forecast_v2`, а первая версия продолжает обслуживать уже выкаченную модель.

Команда `feast apply` читает определения и приводит реестр и хранилища в соответствие с ними:

```bash
cd sales_repo && uv run feast apply          # 3.5 секунды, бо́льшая часть — импорт библиотек
```

```text

Created feature view store_stats
Created feature view pair_stats
```

В `data/` появились `registry.db` (3 КБ) и `online_store.db` с двумя пустыми таблицами. Реестр — это
документация, которая не устаревает, потому что из неё же работает код:

```bash

# NAME         ENTITIES              TYPE         ENABLED    STATE
# store_stats  {'store'}             FeatureView  Yes        STATE_UNSPECIFIED
# pair_stats   {'store', 'product'}  FeatureView  Yes        STATE_UNSPECIFIED
uv run feast feature-services list
# NAME               FEATURES
# sales_forecast_v1  pair_stats:units_mean_7d, pair_stats:units_mean_28d, pair_stats:promo_share_28d,
#                    store_stats:store_units_7d
```

```python
from feast import FeatureStore

store = FeatureStore(repo_path=".")
view = store.get_feature_view("pair_stats")
view.ttl, [f.name for f in view.features], view.tags
# (datetime.timedelta(days=2), ['units_mean_7d', 'units_mean_28d', 'promo_share_28d'], {'owner': 'forecast-team'})
```

Изменение определений — обычное изменение кода: правка `features.py`, `feast plan` (показывает разницу,
ничего не меняя), `feast apply`. `feast plan` печатает объекты целиком; существенные строки после
добавления нового представления — `Created on demand feature view demand_signals` и
`No changes to infrastructure` (пример — в уроке 7.3.2). Файл `features.py` хранится в Git, `registry.db`

## 6. Исторические признаки

`get_historical_features` принимает таблицу запросов (entity dataframe): ключи и момент запроса
в столбце `event_timestamp`. Остальные столбцы — целевая переменная, признаки, известные заранее, —
проходят насквозь.

```python
entity = pd.DataFrame({
    "store_id": "S01", "product": "Мышь",
    "event_timestamp": pd.to_datetime(
        ["2024-07-01 00:00", "2024-07-01 12:00", "2024-07-02 00:00", "2024-07-03 00:00"], utc=True),
})
store.get_historical_features(
    entity_df=entity,
    features=["pair_stats:units_mean_7d", "store_stats:store_units_7d"],
).to_df()
```

```text
store_id product           event_timestamp  units_mean_7d  store_units_7d
     S01    Мышь 2024-07-01 00:00:00+00:00      12.428571           465.0
     S01    Мышь 2024-07-01 12:00:00+00:00      12.428571           465.0
     S01    Мышь 2024-07-02 00:00:00+00:00      12.000000           458.0
     S01    Мышь 2024-07-03 00:00:00+00:00      11.857143           472.0
```

Запрос ровно в полночь 1 июля получает строку с отметкой `2024-07-01 00:00` — граница включена. Запрос
в полдень — её же: следующее значение появится только в полночь. Признаки двух представлений с разными
ключами (пара и магазин) собраны одним вызовом.

**Срок годности.** Из офлайн-таблицы убраны строки пары с 1 по 5 июля — как будто загрузка не работала
пять дней. `ttl` представления — двое суток:

| Момент запроса | `units_mean_7d` | Откуда |
|---|---|---|
| 2024-06-30 00:00:00 | 11.428571 | строка от 30 июня |
| 2024-07-01 00:00:00 | 11.428571 | строка от 30 июня, возраст 1 день |
| 2024-07-02 00:00:00 | 11.428571 | строка от 30 июня, возраст ровно 2 дня — ещё годна |
| 2024-07-02 00:00:01 | NaN | возраст 2 дня и 1 секунда |
| 2024-07-03 00:00:00 | NaN | |
| 2024-07-06 00:00:00 | 12.000000 | строка от 6 июля |

Значение годно, если `момент запроса − ttl <= отметка времени <= момент запроса`; обе границы включены.
Без TTL обучающая строка за 3 июля молча получила бы значение трёхдневной давности. С TTL она получает
пропуск — и это правильно: модель должна учиться на том, что увидит в работе, а в работе признак в такой
день будет отсутствовать.

**Вся выборка.** Сервис признаков передаётся вместо списка:

```python
entity = sales.dropna(subset=["units"])[["store_id", "product", "price", "promo", "units"]].copy()
entity["event_timestamp"] = sales["date"].dt.tz_localize("UTC")
training = store.get_historical_features(
    entity_df=entity, features=store.get_feature_service("sales_forecast_v1")
).to_df()                                              # 69 841 строка, 10 столбцов, 0.4 секунды
```

Пропусков в `units_mean_7d` — 96: 95 строк первого дня (истории ещё нет) и одна строка, где пуст сам
признак. Результат проверен независимым расчётом — `merge_asof` из раздела 4 с `tolerance` в двое суток
(0.04 секунды):

| Признак | Совпадение с `merge_asof` бит в бит | Пропусков в обоих |
|---|---|---|
| `units_mean_7d` | да | 96 |
| `units_mean_28d` | да | 96 |
| `promo_share_28d` | да | 95 |
| `store_units_7d` | да | 95 |

Проверка не лишняя по двум причинам. Первая: это единственный способ убедиться, что вы понимаете
правило соединения так же, как библиотека, — включая границы. Вторая: `get_historical_features`
**не сохраняет порядок строк** и меняет точность отметок времени (на входе наносекунды, на выходе
микросекунды). В проверке 400 запросов к таблице из 1 600 строк вернулись в другом порядке, причём
порядок менялся от запуска к запуску; 40 запросов порядок сохранили. Присваивать столбцы результата
исходной таблице по номеру строки нельзя: сортируйте обе таблицы по ключу и моменту запроса или
пронесите через запрос столбец с номером строки.

**Выбор офлайн-хранилища.** В `feature_store.yaml` стоит `type: duckdb`, хотя по умолчанию у локального
провайдера `type: file` (расчёт на Dask). Причина — в замерах на тех же данных и том же сервисе признаков:

| Офлайн-хранилище | Строк в запросе | Время | Пик памяти процесса |
|---|---|---|---|
| `file` (Dask) | 2 976 (месяц) | 5.2 с | 639 МБ |
| `file` (Dask) | 8 832 (три месяца) | 14.3 с | 1 327 МБ |
| `file` (Dask) | 69 841 (два года) | процесс остановлен системой: не хватило памяти | — |
| `duckdb` | 8 832 | 0.63 с | 304 МБ |
| `duckdb` | 70 176 | 0.84 с | 388 МБ |

(Время — с загрузкой реестра и чтением файлов; у Dask оно и память растут пропорционально числу
запросов.) Судя по этому росту, файловое хранилище сначала соединяет запросы с историей по ключу и лишь
затем отбирает строки по времени: для полной выборки это порядка 96 пар × 731 запрос × 731 строку
истории — 51 миллион промежуточных строк на каждое представление. Учебные примеры Feast на нескольких
сотнях строк этого не показывают. Вывод практический: локальное файловое хранилище — для знакомства;
уже для десятков тысяч строк нужен DuckDB, а в промышленной установке соединение выполняет хранилище
данных (BigQuery, Snowflake, Spark — не проверялось запуском: облачных учётных записей в среде
подготовки нет).

У DuckDB своя особенность: относительный путь источника (`data/pair_stats.parquet`) он отсчитывает
от **текущего каталога**, а не от каталога репозитория. Запуск скрипта из родительской папки
с `FeatureStore(repo_path="sales_repo")` закончился ошибкой:

```text
_duckdb.IOException: IO Error: No files found that match the pattern ".../data/pair_stats.parquet"
```

С файловым хранилищем тот же запуск работал. Запускайте код из каталога репозитория или указывайте
в `FileSource` абсолютный путь.

## 7. Чего Feast не делает

- **Не считает признаки.** Скользящие средние посчитаны вашим кодом. Если в нём ошибка — отметка времени
  равна дате или окно захватывает сегодняшний день, — Feast честно выдаст признаки с утечкой.
- **Не проверяет данные.** Отрицательные продажи и дубли ключей попадут в обучение и в сервис. Проверка
  данных — урок 7.3.3.
- **Не знает, когда значение стало известно на самом деле.** Он верит столбцу `event_timestamp`.
- **Не версионирует значения.** Пересчитали историю — прежних значений нет. Версия данных, на которой
  обучена модель, — задача DVC и записи о запуске (тема 7.2); в параметры запуска записываются имя сервиса
  признаков, хеш офлайн-таблицы и граница времени выборки.

## 8. Когда хранилище признаков не нужно

Feast добавляет в проект реестр, два хранилища, задачу материализации и новый вид ошибок. Это окупается
не всегда.

| Ситуация | Нужно ли | Что вместо |
|---|---|---|
| Пакетный прогноз раз в сутки, одна модель, одна команда | нет | одна функция расчёта признаков, которую вызывают и обучение, и прогноз (пайплайн из темы 7.1); соединение по времени — `merge_asof` |
| Все признаки известны в момент запроса (цена, день недели, текст обращения) | нет | трансформеры внутри `Pipeline` |
| Признаки — агрегаты по истории, прогноз нужен за миллисекунды | да | — |
| Одни и те же признаки нужны нескольким моделям или командам | да | — |
| В истории проекта уже была утечка во времени | да — или хотя бы тест на соединение по времени | функция соединения, покрытая тестами, как в практике 7.3.4 |

Главное, что стоит забрать из этой темы даже без Feast, — дисциплина: у каждой строки признаков есть
отметка времени, означающая «известно с этого момента», и обучающая выборка собирается только
соединением по времени. Функция из двадцати строк на `merge_asof` с тестом на границы даёт эту гарантию
для проекта, которому остальное пока не нужно.

## Типичные ошибки

| Симптом | Причина | Решение |
|---|---|---|
| Метрика на проверке заметно лучше, чем в работе; после «исправления» признаков она ухудшилась | отметка времени признака равна дате, которую он описывает; признаки присоединены через `merge` по дате | отметка = момент, когда значение стало известно; только соединение по времени |
| Прогнозы, сделанные сразу после полуночи, систематически хуже | загрузка приходит в 03:00, а отметка времени — 00:00: значение объявлено известным на три часа раньше | отметка времени не раньше фактического появления данных; сверять её с `created` |
| `uv add feast` прошёл, `import feast` падает с `No module named 'pkg_resources'` | решатель выбрал `feast 0.20.0`, совместимый с pandas 3 только формально | отдельный проект; `uv add "feast[duckdb]>=0.68"` |
| `DeprecationWarning: The 'generic' unit for NumPy timedelta is deprecated` | `pd.Timedelta(days=1)` в связке pandas 2.3 и numpy 2.5 | `datetime.timedelta(days=1)` |
| `get_historical_features` на десятках тысяч строк работает минутами или падает по памяти | офлайн-хранилище `file` (Dask) | `offline_store: type: duckdb` |
| `IO Error: No files found that match the pattern` | DuckDB отсчитывает относительный путь источника от текущего каталога | запуск из каталога репозитория или абсолютный путь |
| Признаки в обучающей выборке «съехали» относительно целевой переменной | результат `get_historical_features` присвоен по номеру строки, а порядок строк другой | сортировка по ключу и моменту запроса либо столбец с номером строки |
| В обучающей выборке неожиданно много пропусков | `ttl` короче, чем промежуток между обновлениями признака | `ttl` не меньше периода обновления с запасом; доля пропусков — в проверках данных |
| Модель обучена на признаках, которых в сервисе нет | признаки запрошены списком, а не сервисом признаков; списки в обучении и в сервисе разошлись | один `FeatureService` на версию модели, его имя — в параметрах запуска |
| После пересчёта истории метрика старого запуска не воспроизводится | значения в офлайн-таблице заменены, версия данных не записана | хеш офлайн-таблицы в записи о запуске; DVC |
